    1. Phoenix가 backbone/reranker head 두 층으로 서빙된다는 사실이 처음 코드에 드러났다 — X 4세대+14

    자료 xai-org/x-algorithm@85ac72a — 공개 소스코드, 2026-09-02 19:46 UTC, X.AI Corp.

    배경 X의 랭킹 모델(코드명 Phoenix)은 4세대 공개(2026-08-13)에서 문서당 24개 참여 확률을 뽑는 트랜스포머라는 사실이 알려졌고, 4세대+11(2026-08-28, bc8e5f0)에서 응답 스코어에 rerankerHeadTag(재순위 헤드 태그) 필드가 붙으면서 "여러 재순위 헤드가 존재한다"는 정황이 처음 드러났다. 다만 그 헤드들이 얹혀 있는 아래 층(backbone)이 무엇을 뱉는지는 canon에 없었다 — proto 응답에 backbone 층 출력이 노출되지 않았기 때문이다. 이번 4세대+14가 그 backbone 출력 필드를 응답에 노출하고 home-mixer가 5개 피드 전체에서 이를 강제로 요청하기 시작했다. backbone은 다중-태스크 랭커의 공용 인코더/타워를 가리키는 표준 용어로, 그 출력이 여러 태스크 헤드(재순위·다양성·slate 등)로 분기된다.

      request 필드 returnBackboneScores(#20)와 response 필드 backboneTopLogProbs(#10, repeated float)·backboneContinuousValues(#11, repeated float)가 짝을 이룬다. **Top**은 discrete-head의 상위 로그확률(예: action 어휘의 top-K 로짓), **Continuous**는 dense 회귀 출력을 가리키는 것으로 읽힌다 — 이름 규약이 그렇고, NextActionDistribution에 이미 존재하는 topLogProbs(reranker head가 뱉는 discrete)와 대응한다.     어디에 쓰는가 (해석) [추정] — 코드가 backbone_scores를 어떻게 소비하는지는 이 커밋에서 아직 보이지 않는다(scorer가 저장까지만 하고 downstream 소비처는 이번 diff 밖). 다만 backbone 출력을 candidate에 계속 들고 다닌다는 사실은 다음 중 하나 이상을 뜻한다: (a) 재순위·다양성 단계가 backbone 로짓을 부가 특성으로 소비, (b) 광고/피드 mixer가 backbone 출력을 debug/attribution용 payload로 기록, (c) 다른 스코어러(예: VMRanker의 slate 재정렬, MultiRiskAdsBlender)가 backbone 출력을 입력으로 사용, (d) 오프라인 분석·A/B 판정에서 "reranker head가 아닌 backbone이 얼마나 움직였는가"를 볼 수 있게 하기 위한 관측용 채널. 근거: backbone_scores가 PostCandidate의 필드로 들어가 있고 스캐폴딩 상 값을 dropped하는 경로가 없다. 새 소비처가 다음 커밋들에서 보일 가능성이 높다.

    의미

    • Phoenix 랭커의 층 구조가 코드로 확정됐다. 4세대 공개 이후 canon은 "Phoenix가 후보당 24개 확률을 뱉는 트랜스포머"라는 최상위 시맨틱만 알았고, 4세대+11의 rerankerHeadTag 필드로 "여러 재순위 헤드가 존재"까지 관찰했으며, 이번 4세대+14로 "그 헤드들 아래에 backbone 층이 있고 그 출력이 별도 응답 필드"라는 것을 확정한다. 다중-태스크 랭커의 표준 형태(shared bottom + task-specific heads)가 X 프로덕션에도 그대로 있다는 뜻이다.
    • return_backbone_scores가 파라미터 게이팅 없이 5개 피드에서 강제 on이라는 사실은, 이 응답 추가가 A/B 실험 단계가 아니라 이미 프로덕션 default로 서빙되고 있다는 강한 신호다. Phoenix 서빙 측이 이미 backbone 출력을 계산해서 응답에 실을 준비가 되어 있고 지연 예산도 여유가 있다는 뜻이다.
    • "backbone score를 candidate에 들고 다닌다" = 다음 층에서 소비할 수 있다는 예약. 이 커밋에서는 저장까지만 보이지만, downstream(MultiRiskAdsBlender, VMRanker, DPP re-rank 등)이 backbone 로짓을 부가 특성으로 쓰는 코드가 곧 붙을 가능성이 높다. 이는 4세대+11의 rerankerHeadTag와 짝을 이뤄 "hydra 헤드 사이의 스위칭·앙상블·attribution" 코드가 후속 커밋에서 열릴 관전 포인트를 만든다.
    • Phoenix retrieval의 dwell 기본이 long으로 옮겨간 사실은 4세대+6 이후 광고 conversion 헤드 확대 흐름과 정합적이다. 두 층 랭커에서 backbone이 학습하는 신호와 retrieval이 참조하는 유저 히스토리 집계가 같은 방향(long-dwell-heavy)으로 정렬되는 셈이다.

    2. Scarecrow(구 Botmaker)에 XReview 인테이크 gRPC 파이프라인이 신설됐다 — X 4세대+14, 신규 canon

    자료 xai-org/x-algorithm@85ac72a — 공개 소스코드, 2026-09-02, X.AI Corp. 관련 파일 3개 신규 + 1개 수정 (총 333줄).

    배경 scarecrow는 X 내부의 "규칙 기반 자동 탐지·조치" 시스템이다 — 옛 Twitter의 Botmaker(트래픽에 룰을 매기고 조치를 취하는 엔진, com.twitter.botmaker 패키지 유산이 이번 커밋의 Scala 파일에도 그대로 남아 있다)를 X.AI가 인수 후에도 유지·확장 중이다. 반면 XReview는 신고·모더레이션 큐 이름 — 유저가 UI에서 "신고"를 누르면 리포트가 XReview로 흘러가 리뷰 대상이 된다(2025~2026 X 내부 명칭). 이번 커밋 전까지 canon은 scarecrow와 XReview 사이의 프로그램적 연결을 갖고 있지 않았다. 이번 커밋이 새로 여는 것은 scarecrow의 자동 탐지 봇이 XReview에 리포트를 "유저가 신고한 것처럼" 프로그램적으로 넣는 gRPC 파이프라인이다.

      키 몇 개가 이 파이프라인의 성격을 그대로 보여준다:

      • report_surface = "x_app" — 유저 신고와 같은 표면에서 들어온다.
      • report_source = "proactive" — 유저 신고("user")가 아니라 자동 탐지("proactive")임을 XReview에게 알린다. 즉 XReview는 어떤 리포트가 사람이 눌러서 만들어졌고 어떤 리포트가 봇이 만들어 넣은 것인지를 이 필드로 구분한다.
      • subject = "Botmaker report" — 리포트의 최상단 문구가 고정된다.

    • content-hash + timestamp가 report id의 uniqueness를 결정한다 [확인]. 위 인용문의 "intake's content-hash report id is unique; evidence rollup then applies" 문구는 XReview 서버가 (내용 해시 + detection_timestamp_ms)로 report id를 만든다는 뜻이다. 같은 봇이 같은 콘텐츠를 두 번 감지해도 timestamp가 다르면 별개의 report가 되고 XReview가 사후에 evidence를 rollup(집계)한다. 즉 봇 리포트는 자연스럽게 여러 번 중복 감지가 발생하며 그 중복을 XReview가 처리하는 구조다.

    • impersonation 봇은 bystander_impersonation을 써야 한다 [확인]. "Impersonation bots should use bystander_impersonation (lane tags key on that type, not generic impersonation)." 여기서 lane tag는 XReview 큐 라우팅(어떤 인간 리뷰어 팀·SLA로 갈지)을 뜻하는 것으로 읽힌다. 즉 XReview에는 리포트를 리뷰어 팀으로 라우팅하는 "lane" 개념이 있고, report_type 값이 lane을 결정한다. 봇이 잘못된 report_type을 쓰면 잘못된 lane으로 라우팅돼서 검토가 지연되거나 무시된다.

    • staging 클라이언트가 별도로 있고 CreateXReviewReportStaging은 action level을 NO_ACTION으로 설정한다 [확인] — XReviewIntakeRegistry.scala. scarecrow의 action level은 이 함수가 실제 조치인지 dry-run인지를 표시하는 메타데이터인데, staging 버전은 NO_ACTION으로 표시돼 룰이 실전에 반영되지 않는 실험용임을 명시한다. 프로덕션 버전은 PROD_AGENT_WORKFLOW_ACTION — "agent workflow"라는 표현은 자동 조치 파이프라인의 일부라는 뜻이다.

    • localMode나 personalAccountMode에서는 noop으로 대체된다 [확인] — XReviewIntakeRegistry.scala.

    let mut action = VfAction::Allow;
    let mut decided_by = None;
    for rule in self.rules() {
        match rule.evaluate(context) {
            VfAction::Drop(reason) => {
                return Verdict {
                    action: VfAction::Drop(reason),
                    decided_by: Some(rule.name()),
                };
            }
            VfAction::Interstitial(reason) if matches!(action, VfAction::Allow) => {
                action = VfAction::Interstitial(reason);
                decided_by = Some(rule.name());
            }
            VfAction::Allow | VfAction::Interstitial(_) => {}
        }
    }

    4. 체크포인트 암호화 진화 — in-envelope 파생 마스터 키 지원 + context 강제 필드 + mint_nonce 자동 첨부 — X 4세대+14

            "not the xai-dek1 derived form"
        )
    _salt, master = field[len(_DERIVED_PREFIX) :].split(":", 1)

      두 키의 이름이 시사하는 것: domain은 이 checkpoint가 속하는 시스템 도메인(예: "recsys", "grox"), run은 학습 run id. 이 두 값이 KMS 호출의 encryption_context로 실려서 감사 로그가 "어떤 domain의 어떤 run이 어떤 checkpoint를 언제 unwrap했는가"를 남긴다. 즉 KMS 감사 흐름이 이 코드에서 강제된다.

    • mint_nonce가 자동으로 encryption_context에 추가된다 [확인].

      encryption_context = dict(self.checkpoint_config.encryption_context)
encryption_context["mint_nonce"] = hashlib.sha256(os.fsencode(path)).hexdigest()
kms_client = xai_kms.KmsClient.from_cluster_env(
    key_id=self.checkpoint_config.encryption_key_id,
    encryption_context=encryption_context,
)

      체크포인트 경로의 sha256 해시가 encryption_context의 mint_nonce 값으로 자동 삽입된다. 이는 KMS가 unwrap 시점에 context 매칭을 검사하는 표준 AWS-KMS 패턴을 이용해 같은 KMS 키로 다른 체크포인트를 unwrap하려는 시도를 실패시킨다. 예컨대 공격자가 체크포인트 파일을 다른 경로로 복사하고 unwrap을 시도하면 mint_nonce가 어긋나서 KMS가 거부한다.

    • _uses_tensorstore_save가 더 이상 encrypt를 강제하지 않는다 [확인] — phoenix/xrex/train/trainer.py.

      def _uses_tensorstore_save(self) -> bool:
    return self.checkpoint_config.save_method == "tensorstore"

      이전에는 encrypt=True가 tensorstore save 방식을 자동으로 켰지만, 이제 두 옵션이 분리됐다. checkpoint_write.save_checkpoint가 kms_client를 인자로 받아 자체적으로 orbax_encrypted.get_encrypted_checkpointer를 조립한다.

    • downgrade 방지 메시지가 구체화됐다 [확인]. "restored from an ENCRYPTED checkpoint but orbax writer cannot produce encrypted saves" → "restored from an ENCRYPTED checkpoint but checkpoint_config.encrypt is false — refusing to downgrade to plaintext saves; set checkpoint_config.encrypt=true with encryption_key_id/encryption_context". 오류 메시지가 "왜 실패했고 무엇을 하면 되는가"를 명시한다.

    • _AsyncCheckpointer가 orbax_encrypted 모듈의 wait_until_finished까지 대기하도록 확장됐다 [확인] — phoenix/xrex/utils/checkpointing.py. checkpoint save의 flush 완료 시점에 암호화 IO도 다 끝난 것을 보장한다.

    정본 반영 services/x.md 4세대+13 subsection의 "envelope-encrypted Orbax checkpoint writer" 블록 뒤에 4세대+14의 evolution 델타를 이어붙인다.

    의미

    • 아직 프로덕션 default에서 켜졌다는 증거는 없다. 이번 커밋은 write path의 검증(domain/run 강제, mint_nonce 자동 삽입)과 read path의 두 포맷 지원을 완성한다. 그러나 CheckpointConfig.encrypt = True가 실제 트레이닝 config에서 default로 켜졌는지는 이 diff에 없다. 이는 여전히 관전 포인트다.
    • 파일 포맷이 문서화됐다. 4096바이트 헤더, XAIENC01 magic, wrapped_len/context_len 오프셋이 코드에 남았기 때문에 미래의 외부 도구(체크포인트 뷰어, 감사 툴)가 이 포맷을 파싱할 수 있다.
    • xai-dek1: prefix가 signals a key derivation scheme. "derived master" 표현이 시사하는 것은 salt로부터 파생된 마스터 키를 헤더에 담고, 감쌈은 wrapped 필드에 담는 KDF-based 방식이다. legacy per-file wrapped key(각 파일마다 KMS-wrapped DEK를 별도 저장)와 대비된다. [추정] X.AI가 만든 자체 KDF 스펙("xai-dek1")의 세부는 코드에 없다 — 아마 xai_kms.nfs 모듈에 있다.
    • KMS-proxy KvStore 소거의 성능적 의미. 이전에는 매 IO(ocdbt operation 하나)가 KMS 호출을 필요로 했지만 이제는 DEK 한 번 unwrap 후 로컬 대칭 복호화. checkpoint restore 지연이 tokens/s 규모로 떨어진다. Phoenix가 3만 개 파일로 구성된 체크포인트를 로드할 때 KMS 호출 3만 번이 1번으로 준다.

    5. two-tower 학습 config: qk_norm=True, attn_logit_cap 해제 — X 4세대+14

    자료 xai-org/x-algorithm@85ac72a — 공개 소스코드, 2026-09-02.

    새로 알게 된 것 [확인] — phoenix/xrex/configs/xrecsys_two_tower.py.

    def _xrecsys_two_tower_combined_base() -> dict:
    return {
        ...
        "learning_rate": 2e-3,
        "emb_learning_rate": 0.1,
        "qk_norm": True,          # was False
        "attn_logit_cap": -1,     # was 80.0
        "primer_norm": True,
        ...
    }
    • qk_norm: False → True — attention의 query·key 벡터에 대해 정규화(L2)를 추가한다. QK-norm은 트랜스포머 학습 안정화의 표준 기법 중 하나다.
    • attn_logit_cap: 80.0 → -1 — attention softmax 이전에 로짓 값을 clip하던 상한(80)이 -1(=off)로 바뀌었다. QK-norm이 켜지면 QK 내적이 이미 bounded되므로 별도 로짓 상한이 불필요해진다.

    배경 4세대+5(2026-08-21, d0cef2f)에서 처음 qk_norm=True·attn_logit_cap=-1·right_anchored_rope=True 세 옵션이 xrecsys_two_tower에 도입됐다. 다만 그때는 옵션 정의만 추가됐고 실제 조합 base config에서는 qk_norm=False·attn_logit_cap=80.0이 default였다. 이번 4세대+14가 그 default를 뒤집는다 — QK-norm이 실제로 조합 두-타워 학습의 기본이 됐다.

    정본 반영 services/x.md 4세대+14 서브섹션에 이 hyperparameter flip을 짧게 기록.

    의미 two-tower retrieval의 학습 안정화 방식이 (a) logit clamp에서 (b) QK-norm으로 옮겨졌다. 두 기법은 등가는 아니지만 유사한 목적(soft attention의 dynamic range 제어)에 쓰인다. 4세대+5의 옵션 도입에서 4세대+14의 default flip까지 12일이 걸린 것은 아마 짧은 A/B에서 QK-norm 쪽이 학습 loss나 다운스트림 metric 상 우세를 보였기 때문일 것이다 [추정].
