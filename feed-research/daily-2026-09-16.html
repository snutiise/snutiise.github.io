배경 X For You 랭킹의 최종 슬레이트는 Phoenix 랭커가 매긴 점수를 그대로 쓰는 것이 아니라, VMRanker DPP(θ=0.65, K=150)로 코사인 유사도 기반 다양성을 강제하고, 작성자 반복 감쇠·OON(out-of-network) 배수·새 작성자 부스트 같은 heuristic을 얹은 뒤 남는다. 이 heuristic 층이 랭커 원점수 대비 슬레이트 구성을 얼마나 바꾸는지, 즉 "다양성 개선 vs 랭킹 손실"의 실제 폭이 얼마나 되는지는 지금까지 X 공개 코드에 계량 지표가 없었다. 이번 커밋이 그 관측성 층을 붙였다. 함께 광고 Phoenix ranker에 구매액 자체를 continuous head로 회귀 예측하는 배선이 새로 열렸고(기존은 클릭·컨버전 확률 헤드만), H100 학습·서빙 커널이 GB300과 동일한 CUTe DSL 계열로 옮겨졌으며, Kafka OTel export가 30→120초로 완화됐고, coordinated spam 필터의 팔로워 임계가 10k→30k로 처음 완화됐다.

A. Response diversity 3단 관측 side effect 신설 — sampled 5%(또는 experiment bucket 100%), stage마다 12~15개 지표를 histogram으로 방출 확인 — home-mixer/side_effects/response_diversity_stats_side_effect.rs (186줄 신규), home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs (+2), home-mixer/params/param.rs (+7).

새 side effect ResponseDiversityStatsSideEffect가 Phoenix candidate pipeline에 6번째 관측 side effect로 배선됐다(ScoredStatsSideEffect 다음, AuthorServedMetricsSideEffect 앞). 활성 조건은 두 갈래:

  • 기본: feature-switch param EnableResponseDiversityStatsExperimentBucket이 어떤 실험 버킷도 안 잡히면 DEFAULT_SAMPLING_RATE = 0.05(요청의 5%)에서만 실행.
  • 실험: 이 param에 실험 버킷이 잡히면 그 버킷 안에서는 100% 실행되면서 각 지표에 ddg(실험 id)와 bucket 스코프 태그를 붙여 발행 — 즉 실험군별 다양성 분포를 분리 관측할 수 있다.

세 stage를 각각 계량한다:

  • final — 최종 선택된 후보(input.selected_candidates)를 score 내림차순 정렬. 이것이 유저에게 실제 나가는 슬레이트다.
  • top10 — final의 상위 10개(TOP_POSITIONS = 10).
  • pre_heuristic — selected_candidates + non_selected_candidates를 합쳐 weighted_score(head-weight sum 원점수, DPP·author-decay·OON 배수 적용 전) 내림차순으로 상위 K개(K = 최종 슬레이트 크기). 즉 "만약 heuristic 층 없이 원점수 top-K만 그대로 냈다면 어떤 다양성을 갖는 슬레이트였을까"의 counterfactual.

Sampling 확률 5%와 stage 3개의 조합은 랭킹 지연에는 거의 영향이 없되(sort 두 번, entropy·HHI 계산은 벡터 순회 O(n)), 관측 정확도는 유지한다는 튜닝. 실험 버킷일 때만 100% 관측으로 tail 분포까지 검증할 수 있게 열어 뒀다.

즉 리포트·뮤트·블록·not_dwelled 같은 부정 신호와 dwell·quality view 같은 노출성 신호는 의도적으로 제외됐다. 이 세트는 X 공개 코드의 다른 어느 곳에서도 나온 적이 없는 새 상수 집합으로, "적극적 참여로 관계가 형성된 작성자"의 정의를 처음 코드로 잠근다. 이 세트가 어떤 랭킹 head에 대응하는지, 즉 phoenix/runners.py:233-253의 positive engagement head 정의와 정확히 일치하는지는 이번 커밋 밖.

C. TweetTypeMetrics bitset에 슬레이트 축 12개 bit 신설 (predicate slot 239-244 + 315-320) 확인 — home-mixer/candidate_hydrators/tweet_type_metrics_hydrator.rs (+100/−4), home-mixer/util/tweet_type_metrics.rs (+27), home-mixer/models/candidate.rs (+8).

TweetTypeMetricsHydrator가 지금까지는 후보 하나 하나에 대해 tweet 자체 속성(리트윗 여부, media 종류, tweet age 버킷, 작성자 팔로워 규모 6단 등)을 bitset으로 세팅했다. 이번 커밋이 여기에 슬레이트 전역 통계를 슬레이트 안 모든 후보에게 반영하는 6개 bit(239-244)와 각 후보가 슬레이트 안에서 갖는 문맥을 반영하는 6개 bit(315-320)를 추가했다.

슬레이트 전역(모든 후보에 동일하게 세팅):

  • UNIQUE_AUTHOR_RATIO_LTE_50_PCT = 239 — 슬레이트의 unique_ratio ≤ 0.5
  • UNIQUE_AUTHOR_LTE_5/10/15 = 240/241/242
  • SINGLE_AUTHOR_GTE_25_PCT/50_PCT = 243/244

슬레이트 문맥(후보마다 다르게 세팅):

  • AUTHOR_REPEAT_IN_SLATE = 315, AUTHOR_REPEAT_GTE_3_IN_SLATE = 316 — score 내림차순으로 순회하면서 같은 author_id를 두 번째·세 번째 이상 만나는 순간부터 켜진다(첫 만남은 안 켜짐, 즉 "슬레이트에서 이 tweet은 같은 작성자의 몇 번째 등장인가"를 표현)
  • AUTHOR_NOT_ENGAGED_BY_VIEWER = 317 — 후보의 author가 (a) 뷰어가 팔로우한 계정이 아니고 (b) B의 positive-engagement set에도 없을 때 켜짐. 뷰어와 관계 없는 새 작성자 표식이다
  • HAS_SEMANTIC_IDS = 318 — 후보에 semantic_ids가 배정돼 있을 때
  • SID_L1_REPEAT_IN_SLATE = 319, SID_L2_REPEAT_IN_SLATE = 320 — score 내림차순 순회에서 같은 SID L1(혹은 L2) prefix가 이미 슬레이트에 있는 두 번째 이상 후보에 켜짐

새 helper PostCandidate::semantic_id_prefix(levels: usize) -> Option<&[i32]>가 SID 배열에서 상위 levels 코드 슬라이스를 안전하게 잘라 낸다(levels가 배열 길이보다 크면 None).

이 bit들은 hydrate에서 후보별 base bitset에 slate-level bit set과 per-position bit set이 union으로 합쳐진 뒤 압축돼 tweet_type_metrics payload로 저장된다. TweetTypeMetrics는 지금까지 랭킹 학습·서빙 로그와 오프라인 분석에 쓰이는 축이므로, 이제 슬레이트 다양성이 후보별 feature로 로깅되고 학습·모델링에 접근 가능해진다. 다만 이번 커밋에는 이 bit들을 실제로 소비하는 학습 config 변경이 없어 배선만 열렸고, 실측 소비는 후속 커밋에서 관측 대상.

D. Phoenix proto — 광고 웹 클릭 후 실제 구매 금액 continuous head ADS_WEB_CT_PURCHASE_VALUE = 5 신설 + PurchaseValueBaseline 메시지 신설 확인 — phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto (+9), phoenix/crates/serving/xai-recsys-proto/src/purchase_value.rs (114줄 신규), phoenix/python/common/xai-proto/proto/recsys.proto (+9).

ContinuousActionName enum에 다섯 번째 continuous head가 붙었다. 기존 4개는 DWELL_TIME = 1, CLICK_DWELL_TIME = 2, ACTIVE_SECS_5M_RESIDUAL_NORM = 3(active seconds의 5분 이동평균 residual normalization — 이 세션의 다음 5분 활성 초를 이전 이동평균으로 정규화해 예측), BRIDGE_PROBABILITY = 4(부문 간 다리 확률)까지였다. 새 ADS_WEB_CT_PURCHASE_VALUE = 5는 웹 클릭-스루 컨버전 후 발생한 구매 금액의 회귀 target이다. CT는 Click-Through의 약어로, 광고 클릭 이후 랜딩 페이지에서 발생한 실제 구매다.

같은 커밋에서 PredictNextActionsRequest 요청 페이로드에 새 필드 23이 붙었다:

각 baseline은 (impression_id, advertiser_account_id, 광고주의 최근 28일 평균 구매 금액 USD) 튜플이다. Rust 헬퍼 purchase_value.rs가 is_valid_baseline(positive id + positive finite USD)와 find_baseline(request, impression_id, advertiser_account_id)를 제공하고, wire tag 안정성(field 23 = 0xBA 0x01, returnLogitsList field 22 = 0xB0 0x01 0x01와 독립)과 하위 호환성(구 요청은 baseline 리스트가 비어 있는 상태로 정상 디코딩)을 unit test 5개로 잠근다.

의미: 광고 랭킹이 지금까지 광고 클릭 확률(4세대+6에서 신설된 20개 conversion 액션 확률 헤드 포함)만 예측하고 그 확률에 광고주가 지불한 가격을 곱해 광고 랭킹 스코어로 썼다면, 이 continuous head는 광고 노출·클릭이 실제 발생시킬 구매 금액 자체를 예측한다. 광고주별 최근 28일 평균 구매액 baseline이 요청 페이로드로 함께 실려 오면 그 baseline 대비 이 impression이 얼마나 상회·하회할지의 residual을 학습·서빙할 수 있다(직접 학습 target인지 baseline offset인지는 이번 커밋에 명시 없음). 광고주별 평균 구매액에 비해 이 유저·이 광고 조합이 유독 큰(작은) 구매를 유도할 확률이 광고 랭킹 스코어에 들어가면서, X 광고 랭킹이 진일보한 value-optimizing 옥션 구조로 옮겨 갈 준비가 됐다 추정 — Meta·Google이 각각 VBB(Value-Based Bidding)·tCPA/tROAS로 부르는 것과 방향이 같다.

Baseline이 request마다 실려 온다는 것은 광고주 계정의 28일 평균값을 별도 오프라인 파이프라인이 매일 갱신해서 광고 서빙 요청에 병렬로 주입해야 한다는 뜻이다. 서빙 트래픽 오버헤드가 걱정되므로 광고주 계정 수를 절대치로 다 실지는 않을 가능성이 높고, 요청 시점에 어느 광고가 이 뷰어에게 진지하게 스코어링될지 사전 pruning 후 그 광고주들의 baseline만 붙여 넣는 형태로 읽힌다 추정.

E. H100 학습 attn 커널이 GB300과 동일한 CUTe DSL 계열로 통일 (pallas_ranker_varlen_attn → cutedsl_ranker_varlen_attn) 확인 — phoenix/xrex/configs/xrecsys_two_tower.py (+1/−1).

cutedsl_ranker_varlen_attn은 4세대+6(28e414f, 2026-08-21)에서 _GB300_OVERRIDES에 처음 등장한 NVIDIA CUTLASS/CUTe DSL 기반 variable-length attention 커널이었고, 4세대+15(9b0dc31, 2026-09-04)에서 SM80·SM90 forward·backward가 모두 오픈소스로 공개됐다(phoenix/xrex/cutedsl/ranker_fa4/). SM80은 H100(및 A100), SM90은 GB300에 각각 대응하므로, 이번 flip은 H100 배포도 같은 커널을 쓰도록 통일한 후속이다. GB300과 H100 두 GPU generation의 학습 code path가 이제 attn 층 시맨틱까지 동일해졌다.

부수적으로 4세대+11(bc8e5f0)에서 관측된 seqpack 학습 config가 H100에서만 pallas_ranker_varlen_attn을 강제하는 제약이 이번 커밋으로 해소되는지는 미확인 — seqpack 코드 경로에 명시된 NotImplementedError 검사가 여전히 남아 있으면 seqpack + FA4 조합은 여전히 막힌 상태다. 후속 커밋에서 관측 대상.

F. Phoenix 학습 Kafka OTel export 간격 30s → 120s (지표 export 부하 4배 완화) 확인 — phoenix/xrex/data/streaming/kafkaloader.py (+2/−2).

_init_otel_metrics의 default export_interval_ms와 PhoenixKafkaDataset.metrics_export_interval_ms 둘 다 30_000 → 120_000. 4세대+20(6bb4594, 2026-09-12)의 H. Kafka mTLS 배선과 짝으로 읽히지만 방향은 반대(mTLS는 인증 오버헤드 증가, export 완화는 지표 부하 감소). OTel(OpenTelemetry) 지표를 4배 덜 자주 배출한다는 것은 학습 잡의 관측 tail 분해능이 낮아지는 대신 collector 부담이 낮아진다는 트레이드오프다. 지표 host cost가 실측적으로 부담됐다는 방증 추정.

G. Grox coordinated_spam 필터 팔로워 임계 10k → 30k (첫 완화) 확인 — grox/flows/reply_spam/task_filter.py (+1/−1).

Grox reply-spam 파이프라인에는 두 개의 팔로워 임계가 별개로 존재한다:

  • TaskSpamFilter·TaskReplyRankingFilter: 4세대 공개 이후 15k → 30k(4세대+1) → 60k(4세대+3) → 80k(4세대+6) → 100k(4세대+7)로 다섯 단계 상향됐다. 이 임계는 팔로워 수가 임계 이하인 계정의 답글만 스팸 분류에 넣는다는 뜻이므로, 상향은 분류 범위 확대(더 큰 계정까지 검사)를 의미한다.
  • TaskCoordinatedSpamFilter: 지금까지 15k(원래) → 10k(어느 시점의 하향)에서 이번에 10k → 30k로 첫 완화. coordinated spam은 여러 계정이 짝지어 같은 스팸 패턴을 반복 게시하는 유형이다.

두 필터의 임계 곡선이 정반대 방향으로 움직이는 것이 특이하다: 일반 spam 분류는 큰 계정까지 확대(오탐 감수), coordinated spam 분류는 큰 계정을 제외(작은 계정에 집중, 오탐 감소). Coordinated spam은 조직화된 소규모 계정 클러스터가 전형이라 30k 이상 팔로워 계정은 이 파이프라인에서 판정 가치가 낮다는 판단으로 읽힌다 추정.

정본 반영 ../services/x.md 4세대 공개 표에 4세대+21 행 추가, 상세 절 ### 4세대+21 (2026-09-15, 2d4a03c) — … 신설. 광고 절과 피드백 신호 절, Phoenix 랭킹 절에도 새 continuous head와 슬레이트 관측 지표를 배선 있는 대로만 짧게 반영.

의미: 두 가지 축이 나란히 열렸다.

  1. 관측성이 슬레이트 다양성에 진입했다. 지금까지 X 공개 코드의 스코어링 관측은 후보별 점수와 head별 확률까지였고, 슬레이트 층의 heuristic(DPP, author-decay, OON multiplier)이 후보 집합을 얼마나 바꾸는지는 계량되지 않았다. 이번 커밋의 pre_heuristic/top10/final 세 stage 병렬 관측이 heuristic 층의 실제 영향폭을 실측할 수 있는 첫 배선이다 — 특히 pre_heuristic은 counterfactual("heuristic 없었다면")이므로 다양성 개선과 랭킹 손실의 트레이드오프를 실측 가능하게 만든다. 4세대+4의 slate context 파이프라인, 4세대+8의 VMRanker DPP 단순화, 4세대+20의 seed anchor pinning으로 이어진 슬레이트 층 재편 계열의 관측 counterpart로 읽힌다.
  2. 광고 랭킹이 확률 예측에서 금액 예측으로 확장됐다. 4세대+6의 conversion 액션 20개는 여전히 확률(클릭·컨버전 발생 여부)의 헤드였다. 새 continuous head는 금액 자체를 회귀 target으로 받고, 광고주별 28일 baseline까지 요청에 함께 실어 residual 학습을 가능하게 하는 배선을 준비했다. Value-optimizing 옥션은 광고주 ROI 최적화를 서빙 계층에서 직접 처리한다는 뜻이므로, 광고 랭킹 스코어 계산과 그 뒤의 옥션 로직 양쪽에 파급이 있을 것이다.

두 축 모두 이번 커밋에는 feature-switch 게이트 뒤에서 배선만 열렸고, 실측 소비(학습 config에 새 bit·head 승격, 프로덕션 experiment ramp)는 후속 커밋의 관측 대상이다.
