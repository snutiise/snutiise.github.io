    배경

    어제 daily/2026-08-15.md에서 다룬 4세대 공개(47c1bcd, 2026-08-13)는 파일 300개 이상, 추가된 줄 +363K 규모였고, 파라미터 미러링과 visibility-filtering, labeling 서브레포 15개를 통째로 열었다. 그 다음 날에 X는 커밋 하나를 더 추가했는데, 이 커밋은 4세대의 후속 정리이자 확장이다. 새 README가 스스로 평가하듯이 이번 릴리즈는 "로직의 형태를 보여주는 것"에서 "값과 규칙을 검증 가능한 형태로 붙이는 것"으로 넘어왔고, 오늘 커밋은 그 성격을 하루 만에 다섯 방향으로 확장한 셈이다.

    특히 세 방향이 canon에 직접 영향을 준다.

    첫째, 가중치 비율을 어떻게 읽어야 하는지가 코드 주석에 명시됐다. canon은 3세대까지 인용해 온 "reply 13.5 vs favorite 0.5 → 27배" 같은 서술을 여러 곳에서 사용했는데(예: multi-task-ranking.md), 이 서술이 원리적으로 잘못된 설명이라는 사실이 X 자신의 주석으로 확정됐다. 가중치는 예측 확률에 곱해지므로 raw count의 비율이 아니다. X는 4세대에서 파라미터 미러를 공개하면서, 판독 가이드가 없으면 이 값들이 오히려 오해를 낳는다는 점을 명시적으로 인정한 셈이다.

    둘째, 관할권 필터를 코드에서 그대로 관찰할 수 있는 첫 사례가 나왔다. DSA와 GDPR, NetzDG 같은 규제 대응은 지금까지 대부분 규제 제출 문서(EU 투명성 리포트)를 통해서만 확인할 수 있었다. Brazil2026ElectionFilter는 브라질 선거법원(TSE)이 조치한 계정 665개를 코드 상수 FxHashSet<u64>에 하드코딩하고, 각 ID 옆 주석에 @username을 남기며, 뷰어가 그 계정을 팔로우하고 있으면 예외로 처리한다(정치적 성향과 무관하게 대칭적으로 적용된다). 이 관행이 유지된다면 각국의 선거 주기마다 비슷한 필터를 코드에서 확인할 수 있게 된다는 뜻이며, X가 4세대 README에서 강조한 *"a benefit of open-source is that you can see that changes like this exist, and exactly how they work"*가 규제 대응에도 적용된다는 신호이다.

    셋째, Phoenix 랭커의 입력 피처가 처음으로 채워졌다. 4세대 초까지 코드에서 관찰된 bool_features: vec![false; ...]는 canon에서 "죽은 필드"로 분류돼 주의할 점 목록에 남아 있었다. 4세대+1에서는 그중 3개(stale post 14일 여부, author와 viewer 사이의 팔로우 방향 2개)가 처음으로 실제 값을 받는다. 특히 stale post 신호가 count zeroing과 짝을 이뤄 들어간다는 점이 흥미롭다. 랭커에게 "이 카운트가 낮은 이유는 인기가 없어서가 아니라 오래돼서 노출이 끊겼기 때문"이라고 명시적인 라벨을 붙여 주는 것이며, 3세대까지 canon이 관찰해 온 snowball 문제(오래된 포스트의 낮은 count가 낮은 랭킹을 낳고 그 랭킹이 다시 낮은 count를 낳는 자기강화 루프)를 랭커가 학습으로 우회하도록 만든 설계이다.

    새로 알게 된 것 — 가중치 해석 규칙 (canon 정정)

    파일 헤더 주석이 이 규칙을 가장 앞에 명시한다 [확인] — home-mixer/params/param.rs:281-306:

    "Each weight multiplies the predicted probability of that action (P(favorite), P(repost), …) or a continuous value e.g. watch time -- the weights do not multiply raw engagement counts. One common misinterpretation is that you can read these weight ratios as count equivalences, e.g. the incorrect statement that 'one report cancels 468 likes' -- this is incorrect because the weights apply to the predicted probabilities rather than raw counts." — home-mixer/params/param.rs:283-292

    그리고 왜 그 절댓값이 그렇게 커 보이는지를 이어서 설명한다:

    "And the baseline probability of a Report is more than 1000x lower than a Like, so it's weighted more to allow the prediction to affect the final ranking at all."

    즉 report −234라는 값의 크기는 가치 × 1/propensity의 곱이며, 리포트의 propensity가 like에 비해 1000분의 1 이하이기 때문에 절댓값이 크게 나타난다. 어제 정본에도 이미 같은 방향으로 주의 사항을 적어 두었는데, 이번에는 X가 코드 안에서 스스로 이렇게 서술했다.

    같은 주석은 mass reporting에 관한 오해도 두 가지 이유를 들어 부정한다:

    "It's predicting your likelihood of the action, not summing up raw weights on counts. Also, recommendations are personalized, so reports from bad actors will primarily affect recommendations for users who are similar to the bad actors, rather than having the same effect on the post's ranking to everyone."

    즉 봇 계정이 대량으로 리포트를 넣더라도 (1) 스코어는 당신의 예측 확률이므로 그 봇들과 비슷한 유저의 추천에만 우선적으로 영향을 주고, (2) Home Timeline에 서빙된 포스트에서 이뤄진 액션만 랭킹 신호로 반영되므로, 그룹 채팅으로 링크를 공유해서 발생한 반응은 랭킹에 영향을 주지 않는다.

    같은 주석 블록은 home-mixer/scorers/ranking_scorer.rs:415-446에도 똑같이 들어갔고, README #scoring-and-ranking 절에도 같은 내용의 문단이 삽입됐다. 세 곳에 같은 서술을 배치해서 코드와 문서 중 어디를 읽더라도 오해하지 않도록 했다.

    static BRAZIL_2026_ELECTION_USER_IDS: LazyLock<FxHashSet<u64>> = ...;  // 665개

impl Brazil2026ElectionFilter {
    fn is_excluded_author(user_id: u64, followed_user_ids: &FxHashSet<u64>) -> bool {
        BRAZIL_2026_ELECTION_USER_IDS.contains(&user_id) && !followed_user_ids.contains(&user_id)
    }
    fn should_remove(candidate: &PostCandidate, followed_user_ids: &FxHashSet<u64>) -> bool {
        let is_excluded = |user_id: u64| Self::is_excluded_author(user_id, followed_user_ids);
        if is_excluded(candidate.author_id) { return true; }
        if candidate.retweeted_user_id.is_some_and(is_excluded) { return true; }
        if candidate.quoted_user_id.is_some_and(is_excluded) { return true; }
        candidate.ancestor_users.iter().copied().any(is_excluded)
    }
}

    즉 (a) 후보의 작성자, (b) 리트윗 원저자, (c) 인용 원저자, (d) 답글 스레드의 조상 작성자 가운데 하나라도 리스트에 있고 뷰어가 그 계정을 팔로우하지 않았다면 후보에서 제거한다. 팔로우 예외는 유저 개인의 팔로우 그래프를 기준으로 삼기 때문에, 정치적 스펙트럼과 관계없이 대칭적으로 작동한다.

    의미 (관할권 필터 코드 공개의 관전 포인트)

    이 필터는 services/x.md 필터 21개 절에 4세대+1 신규 항목 1개로 반영했다. 앞으로는 다음 3가지를 계속 지켜봐야 한다.

    새로 알게 된 것 — 콜드스타트 Thompson sampling

    author_cold_start.rs가 갱신됐다 [확인] — home-mixer/scorers/author_cold_start.rs:151-190. 콜드스타트 대상 후보 집합에서 "슬롯을 어느 후보로 채울지" 고르는 방식이 greedy max-score와 Beta reward Thompson sampling 두 갈래로 나뉜다(Thompson sampling: 후보마다 Bayesian posterior에서 한 번씩 샘플을 뽑아 그 값으로 선택하며, exploration을 확률적으로 유도하는 표준 밴딧 기법이다).

    새로 추가된 파라미터는 6개다 [확인] — home-mixer/params/param.rs:687-724:

    • EnableColdStartThompsonSampling = false — 기본값은 off이다. 즉 실제 프로덕션은 여전히 greedy로 동작한다.
    • ColdStartBetaAlpha0 = 0.75 — Beta(α₀, β₀) 사전분포의 α이며, like의 사전 관측치에 해당한다.
    • ColdStartBetaBeta0 = 49.25 — β₀이며, non-like의 사전 관측치에 해당한다. α₀ + β₀ = 50이 사전 분포의 유효 표본 크기이므로, 대략 "50 impression 중 0.75 like"라는 사전 지식을 뜻한다.
    • ColdStartTsTopK = 5 — Beta 샘플링으로 상위 K개를 뽑은 다음, 실제 스코어로 동점을 가른다.
    • ColdStartImpressionScale = 1.0 — view_count에 곱하는 스케일이다.
    • ColdStartTrackedIds = "" — 쉼표로 구분한 계정 및 포스트 ID 리스트이며, 서빙 통계를 계측할 대상을 지정한다.

    샘플링 규칙은 같은 파일에 다음과 같이 적혀 있다 [확인]:

    fn sample_reward<R: Rng + ?Sized>(candidate: &PostCandidate, alpha0: f64, beta0: f64, scale: f64, rng: &mut R) -> f64 {
    let n = scale * candidate.view_count.unwrap_or(0) as f64;
    let x = (candidate.fav_count.unwrap_or(0).max(0) as f64).min(n);
    let alpha = alpha0 + x;
    let beta = beta0 + (n - x).max(0.0);
    Beta::new(alpha, beta).map(|d| d.sample(rng)).unwrap_or(0.5)
}

    즉 각 후보 i에 대해 posterior Beta(α₀ + likes, β₀ + max(views − likes, 0))에서 한 번 샘플을 뽑고, 그 값으로 상위 K개를 고른 다음, 그 안에서 원래 스코어가 가장 높은 후보를 선택한다.

    의미 (Thompson sampling A/B 배선)

    기본값이 off라는 사실이 중요하다. 이 릴리즈 시점에서 실제 유저에게 적용되는 콜드스타트는 여전히 max-score greedy이다. Thompson sampling은 A/B 인프라에 연결만 된 상태이며, 실제 반영 여부는 앞으로 나올 A/B 결과에 따라 결정될 것이다.

    ColdStartTrackedIds에 특정 계정이나 포스트 ID를 등록해 두면, home_mixer.cold_start_tracked_ids_total{id, source} 카운터가 그 계정이 콜드스타트 파이프라인의 어느 소스에서 몇 번 등장했는지 추적한다. 즉 특정 계정을 A/B 실험에서 직접 관찰할 수 있는 개별 관찰 훅이다. 예를 들어 정치인 계정 하나를 등록해 두면, 그 계정의 포스트가 어느 콜드스타트 경로로 몇 번 노출됐는지 셀 수 있다. 이 계측 훅이 존재한다는 사실은 계정 단위 라벨 조회를 열어 준 4세대의 under-the-hood 투명성 노선과 방향이 같다. 다만 이것은 X 내부용 계측이며 외부에 공개되는 자료는 아니다.

    새로 알게 된 것 — 문제와 해법

    논문은 ensemble ranking 단계에 고유한 문제를 다룬다. 산업용 비디오 추천 파이프라인의 다단계 구조에서, 상위의 멀티태스크 모델(멀티태스크 랭커이며, pctr, pvtr, pcmtr, pftr처럼 여러 태스크가 내놓는 예측 확률을 여기서는 pxtr로 통칭한다)이 출력한 예측을 하위의 앙상블 랭커가 입력 피처로도 쓰고 proxy preference 라벨의 출처로도 함께 쓰는 상황을 상정한다. 그런데 pxtr는 상위 모델의 출력이므로 노이즈를 포함할 수밖에 없고, 이 노이즈는 (a) proxy preference 라벨을 뒤집으며(supervision-side 노이즈), (b) feature-side 입력으로 흘러들어 순위 스코어를 흔든다(feature-side 노이즈).

    기존의 앙상블 랭킹 방법들은 pxtr를 신뢰할 수 있는 신호로 간주하고 노이즈를 무시했지만, DrEM은 이 노이즈를 양쪽에서 동시에 보정한다:

    • Supervision side (라벨 노이즈): pairwise flip probability(어떤 쌍의 실제 preference가 뒤집혔을 확률)를 추정하고, empirical risk를 그 확률로 정정하는 risk-denoising robust loss를 도입했다. flip probability 추정에 오차가 있더라도 basic pairwise loss보다 우월하다는 사실을 이론적으로 증명했다(Theorem 1).
    • Feature side (입력 노이즈): pxtr의 예측 노이즈 분포에서 perturbation을 샘플링하고, preference-preserving ranking consistency regularizer로 perturbation에 대해 출력이 안정적으로 유지되도록 학습한다.

    핵심은 두 correction이 공유된 노이즈 모델에서 유도된다는 점이다. supervision과 feature 양쪽의 correction target이 같은 노이즈 근원에 정렬되므로, 파라미터를 공유해서 서로 동기화된 보정을 수행할 수 있다.

    새로 알게 된 것 — 프로덕션 A/B 결과

    HTML 판 5.4절(RQ3)이 A/B 실험 설정을 명시한다 [확인]:

    "To answer RQ3 and validate real-world performance, we conduct online A/B tests on the industrial short-video platform. We set up two parallel experiment groups to verify the generalization of our DrEM on both representative backbones, applying our DrEM on top of production-grade EMER and EASQ backbone. The experiment runs for 7 days with 5.1% of the main traffic randomly split at the user level via hash-based assignment to each group." — arXiv 2608.12778, 5.4절

    메인 A/B 결과 [확인] — 5.4절 Table 2, 모든 지표가 p < 0.005이다:

    지표 EMER w/ DrEM EASQ w/ DrEM
    Comment +1.388% +0.178%
    Follow +1.197% +0.460%
    Video View +0.691% +0.117%
    Forward +0.683% +0.181%
    Like +0.625% +0.048%
    Long View +0.401% +0.043%
    App Stay Time +0.116% +0.124%
    LT7 +0.017% +0.020%

    저자가 같은 절에서 관찰한 내용을 요약하면 sparse behavior의 gain이 dense behavior보다 크다는 것이다. 팔로우(+1.20%)와 댓글(+1.39%)의 개선폭이 뷰(+0.69%)나 롱뷰(+0.40%)보다 압도적으로 크다. 이는 이론과 일치한다. 스파스 태스크(pcmtr, pftr)의 pxtr는 예측 분산이 크므로 flip probability도 크고, 그만큼 robust correction이 개선할 여지도 크기 때문이다. 5.5절(RQ4)의 flip-probability 계층화 heatmap도 같은 결론을 보여 준다. flip prob가 낮은 구간에서는 dense 태스크(pctr, pvtr)의 개선이 0이거나 약간 음수인데, flip prob가 높은 구간에서는 개선폭이 급격히 양수로 올라간다.

    두 백본의 gain 격차를 어떻게 해석할 것인가: 저자는 EASQ의 gain이 EMER보다 작은 이유를 이렇게 설명한다. EASQ는 이미 자체 questionnaire-signal alignment로 supervision-side 노이즈를 부분적으로 완화하고 있어서, DrEM의 supervision correction이 개선할 여지가 적다는 것이다. 즉 supervision 정정이 훨씬 큰 개선을 낳고, 그 부분을 이미 처리한 백본에서는 feature-side 정정만 남는다고 계층적으로 이해할 수 있다.

    정본 반영 radar.md DrEM 절 — 소속을 확정해 등급을 [추정]에서 [확인]으로 갱신하고, A/B 실험 설정(트래픽 5.1%, 7일)과 지표 8개의 실측값, 이론적 관찰(sparse > dense)을 추가했다. 정본(services/*)에는 아직 반영하지 않았다. Kuaishou 서비스는 정본 추적 대상이 아니기 때문이다.

    의미

    Kuaishou가 이번 달에 낸 프로덕션 논문 세 편 가운데 이 논문이 canon과 가장 밀접하다. 다른 서비스들도 같은 노이즈 문제를 겪는다. X의 26개 헤드 가중합, Meta의 다목적 랭킹, Netflix의 멀티태스크 FM은 모두 상위 pxtr가 하위 스코어러의 입력이자 라벨이 되는 구조를 갖는다. 다만 DrEM이 다루는 특정 문제, 즉 앙상블 랭킹 단계의 pxtr 노이즈가 X와 Meta, Netflix에서 별도 컴포넌트로 존재하는지, 아니면 다른 방식으로 완화되고 있는지는 문헌으로 확인되지 않는다. 두 번째 회사에서 비슷한 진술이 나온다면 topics/multi-task-ranking.md에 절을 새로 만들 후보가 된다.
