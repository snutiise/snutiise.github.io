1링크 복사 공유 가중이 닷새 만에 20.0으로 돌아왔다 — X

자료 xai-org/x-algorithm@9081b33 — xAI, 2026-11-18, 코드. 이 노트들이 붙인 번호로는 4세대+66이다(4세대+N은 2026-08-13 4세대 공개 뒤의 커밋에 이 노트들이 차례로 붙인 번호다).

배경 X For You의 랭킹 모델 Phoenix(Grok 계열 트랜스포머)는 후보 포스트마다 좋아요, 답글, 공유 같은 행동의 확률을 내고, 점수는 이 확률에 행동별 가중을 곱해 더한 가중합에서 출발한다. X는 가중의 운영 기본값을 크론 미러(프로덕션 설정을 매일 저장소 코드에 옮겨 적는 스크립트)로 공개하는데, 미러는 홈믹서(home-mixer, 피드 요청을 받아 후보를 모으고 점수를 매기는 서비스)용과 vm-ranker(가중합과 DPP 재순위를 계산하는 별도 서비스)용 두 파일이다. 2026-11-13 커밋(4세대+63)은 홈믹서 미러에서 링크 복사 공유의 가중을 20.0에서 0.0으로 내렸고, vm-ranker 미러는 20.0으로 남았다. 이번 커밋은 2026-11-17 sync를 반영하면서 그 값을 되돌렸고, 점수·광고·학습 데이터 쪽 장치 세 가지를 기본 off로 추가했다.

새로 알게 된 것A. 홈믹서 미러의 링크 복사 공유 가중이 다시 20.0이 됐다

  • 홈믹서 미러의 share via copy link 가중이 0.0에서 20.0으로 바뀌었다 확인 — home-mixer/params/param.rs:495-500.
    • 파일 헤더의 sync 시각은 2026-11-16T16:00:37Z에서 2026-11-17T16:00:33Z로 바뀌었다.
    • 이번 sync에서 바뀐 가중은 이것 하나다.
  • 두 미러가 다시 같은 20.0이 됐고, 링크 복사 공유는 다시 양수 가중 가운데 가장 크다 확인 — vm-ranker/params.rs.
  • 0.0이던 닷새는 실험이나 잘못된 설정을 되돌린 기간으로 본다 추정. 근거는 vm-ranker 미러가 그동안 한 번도 따라 내려가지 않았고, 다른 가중은 함께 움직이지 않았다는 점이다.

새로 알게 된 것B. 인네트워크와 OON 후보에 참여 항과 체류 시간 항의 배수를 따로 줄 수 있게 됐다

  • vm-ranker는 지금까지 OON(뷰어가 팔로우하지 않는 계정의 포스트) 후보 점수 전체에 배수 0.75 하나를 곱했다. 이제 후보 종류마다 참여 항과 체류 시간 항에 배수를 따로 줄 수 있다 확인 — xai-value-model/scoring.rs:338-364.

    • 체류 시간 항은 예상 체류 초에 cont_dwell_time 가중을 곱한 값이고, 0과 전체 점수 사이로 자른다. 참여 항은 전체 점수에서 체류 시간 항을 뺀 나머지다.
    • 작성자 다양성 감쇠는 이 점수 위에 그대로 곱한다.

  • 네 배수의 기본값은 −1.0이고, 음수는 미설정으로 처리하므로 지금 점수는 그대로다 확인 — vm-ranker/params.rs:247-270.

    • 한쪽만 설정하면 나머지는 기존 배수(OON 0.75, 인네트워크 1.0)를 쓴다.
    • 곱셈형 결합 모드(4세대+65)와 topic 요청, 신규 유저 요청에는 적용하지 않는다.

  • 테스트 config는 국가 조건으로 배수를 다르게 주는 예를 든다 확인 — vm-ranker/scoring/mod.rs.

    • FR 예시는 OON 참여 0.6, OON 체류 0.9, 인네트워크 참여 1.2, 인네트워크 체류 0.7이다. JP 예시는 OON 체류만 0.9다.
    • 테스트 값이라 운영 실험의 설정이라고 볼 근거는 없다.

새로 알게 된 것C. 서빙한 후보를 teacher 모델로 다시 채점해 저장하는 경로가 생겼다

  • 표본 요청에서 실제로 나간 후보와 탈락 후보 상위를 별도 Phoenix 클러스터로 다시 채점하고, 지정한 헤드의 확률을 캐시에 남기는 side effect(응답을 바꾸지 않고 뒤에서 도는 단계)가 생겼다 확인 — side_effects/teacher_score_side_effect.rs:60-81.
    • 나간 후보를 먼저 넣고, 탈락 후보 가운데 가중합이 양수인 것을 점수 순으로 채워 최대 64개를 만든다. 리트윗은 원본 id로 중복을 없앤다.
    • 결과는 학습용 요청 캐시와 같은 키 체계로 두 데이터센터 캐시에 50분 동안 쓴다.
  • 스위치 기본값이 off이고 표본 비율이 0, 클러스터 이름과 헤드 목록이 비어 있어 지금은 돌지 않는다 확인 — params/param.rs:1251-1287.
  • 큰 모델의 예측을 서빙 모델의 학습 목표로 쓰는 증류(distillation, 큰 모델의 출력을 작은 모델이 따라 배우게 하는 학습)용 데이터로 본다 추정. 근거는 이름이 teacher이고, 탈락 후보까지 채점해 학습 캐시 옆에 둔다는 점이다.

새로 알게 된 것D. 페이지 상위 포스트의 점수가 낮으면 광고량을 바꾸는 장치가 생겼다

  • For You의 slot-spread 블렌더(광고 자리를 페이지 전체에 고르게 먼저 정하는 광고 배치기)가 상위 20개 포스트의 평균 점수를 세 구간으로 나눠 구간마다 광고 비율과 간격을 정할 수 있게 됐다 확인 — ads/user_load.rs:39-94, 152-171.
    • 남길 광고 비율은 50~100%로 제한되고, 간격은 최소 간격 아래로 내려가지 않는다.
    • 가중합 모드일 때만 적용하고, Premium 구독자에게는 적용하지 않는다.
  • 구간별 값 목록이 비어 있고 두 경계값이 0.0이라 지금 광고량은 그대로다 확인 — params/param.rs:1111-1140.
  • 4세대+65의 활동 단계별 광고량 장치와 이 장치가 둘 다 설정되면 페이지 점수 구간 값이 덮어쓴다 확인 — 같은 파일.

새로 알게 된 것그 밖의 변경

  • VMRanker 요청과 DPP 이력 포스트마다 요청 종류(첫 로드, 새로고침 폴링, 아래로 더 불러오기)가 실린다. VMRanker 쪽 사용처는 공개되지 않았다 확인 — scorers/vm_ranker_request.rs

  • 학습 데이터를 Iceberg 테이블에서 읽는 경로가 생겼다 확인 — phoenix/xrex/data/recsys/iceberg_layout.py

2AI Discover는 LLM이 계획하고 기존 랭커가 타이틀을 고른다 — Netflix

자료 Engineering AI Discover — Netflix TechBlog, 2026-11-17, 블로그.

배경 Netflix 추천은 그동안 시청 이력에서 취향을 추론해 행으로 보여 주는 방식이었고, 회원이 직접 방향을 정할 수단은 thumbs 평가 정도였다. 2026-11 초에 TV 앱 일부 회원에게 AI Discover 탭이 열렸고, 회원이 "Quick Watches" 같은 테마를 고르면 맞는 타이틀 행과 설명, 다음 테마가 나온다. LLM에 화면 전체를 맡기면 없는 타이틀을 내거나 느려질 수 있어서, 무엇을 LLM에 맡기고 무엇을 기존 시스템에 남길지가 문제가 된다. 이번 글은 그 경계를 정한 intelligence layer(요청마다 LLM과 추천 시스템을 어떻게 조합할지 정하는 계층)의 구조를 밝힌다.

새로 알게 된 것A. 타이틀 선택은 기존 retrieval과 랭커가 맡고 LLM은 계획과 문구를 맡는다

  • 요청이 오면 controller가 계획을 정하고 executor가 실행한다. 계획은 승인된 단계들의 그래프다 확인 — AI Discover 블로그.
    • 단계는 capability(검색, 대규모 랭킹, 카탈로그 메타데이터 같은 기존 시스템을 감싼 작업 단위)를 실행한다. capability는 retrieval, ranking, generation, packaging 계열로 나뉜다.
    • 실행 전에 코드가 그래프를 검증한다. 모든 단계가 승인됐는지, 입력마다 만드는 단계가 있는지, 순환이 없는지, 끝이 페이지 하나인지를 본다.
  • 계획은 이미 시험한 기존 계획과 LLM이 그때그때 짜는 계획 가운데 Netflix가 통제하는 라우터가 고른다 확인 — 같은 블로그.
    • 플래너가 느리거나 계획이 검증에 실패하면 시험한 계획으로 돌아간다.
    • 블로그는 이를 plan-and-execute agent(LLM이 경로를 제안하고 코드가 실행 여부를 정하는 에이전트)라고 부른다.
  • LLM은 테마 생성, 행 제목과 설명 작성, 다음 테마 제안을 맡고, 타이틀은 retrieval과 랭커가 LLM과 함께 고른다 확인 — 같은 블로그.

"Every pick must be a real, available title from our changing catalog. Retrieval and rankers work in tandem with LLMs to choose titles that fit the member's taste and intent." — Engineering AI Discover, 2026-11-17 (블로그)

새로 알게 된 것B. 회원이 고른 조정은 Memory Hub에 남아 다음 방문에도 적용된다

  • 회원의 조정("don't recommend" 등)은 바로 적용되고 방문을 넘어 유지된다 확인 — 같은 블로그.
    • 저장소는 Memory Hub(회원별 저지연 기억 저장소)다.
    • 같은 곳에 MemberLLM(개인화 추천용 사내 언어 모델)이 시청 이력으로 미리 만든 취향 요약이 있다. 요청 경로 밖에서 만들어 둔다.
  • 이 조정을 기존 개인화 시스템과 어떻게 섞을지는 아직 답을 찾는 질문이라고 썼다 확인 — 같은 블로그.
  • 생성이 들어간 요청은 비동기로 처리한다. 누르면 바로 확인 응답이 오고, 결과가 준비되면 서버가 TV에 알린다 확인 — 같은 블로그.

새로 알게 된 것그 밖의 변경

  • 성숙도 등급 같은 규칙은 프롬프트가 아니라 코드로 강제한다. 플래너는 값 대신 자리표시자를 쓰고, 검증 뒤 controller가 채운다 확인 — AI Discover 블로그
  • 모델 교체 전에는 같은 과제를 자동 검사와 LLM judge로 채점하고, 과거 요청 기록을 새 프롬프트나 모델로 재생해 비교한다 확인 — 같은 블로그
