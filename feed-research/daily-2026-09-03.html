    배경 X는 2026-08-13에 4세대를 공개하면서 (a) 안전 파이프라인의 4단계 labeling path(Content Understanding → Labeling Rules → Storage → Visibility Filtering), (b) VF의 세 SafetyLevel(FilterAll·TimelineHome·TimelineHomeRecommendations)에 걸린 총 54개 규칙, (c) Phoenix 랭킹 모델의 학습 코드 + 프로덕션 크론 미러 param을 통째 공개했다. 그 이후 후속 커밋들이 매일 조금씩 이 스택을 정련해 왔다. 특히 2026-08-28의 4세대+11(bc8e5f0)에서는 RuleContext가 도메인 메서드 25여 개로 확장되고 13개 카테고리 90건 golden corpus + 배선-어설션 커플링이 배치됐다(테스트에 없는 rule을 배선하면 CI가 깨진다). 2026-09-01 새벽의 4세대+12(6384ca7)는 NSFW 게이팅 대상 16개국을 처음 코드에 명시했고 motion-reveal 기반 특수 영상 안전 파이프라인을 신설했다.

    이번 커밋(4세대+13, 같은 날 20:47 UTC, 6384ca7 뒤 20시간 만에)에서는 세 가지가 함께 열린다. 첫째, VF rules의 물리 구조가 struct-per-rule에서 data-driven spec으로 바뀐다 — 4세대+11이 골든 코퍼스로 표현을 잠갔다면, 이번엔 표현 자체가 데이터 리터럴로 얇아졌다. 둘째, Phoenix 랭킹 모델에 RQ-VAE 계열 semantic-ID 코드에서 dense vector를 되돌리는 recon 경로가 처음 코드에 노출된다 — X 내부에서 SID를 어떻게 학습된 랭커 입력으로 쓰는지가 처음 드러났다. 셋째, JAX 학습 → CUDA 서빙 핸드오프의 StableHLO 번들 export와 envelope-encrypted Orbax checkpoint writer가 인프라 층에서 표준화된다. 정책 변화는 없지만 코드 층에서 canon이 몰랐던 사실 여러 개가 확정된다.

    새로 알게 된 것

    A. visibility-filtering rules 재구조화 — struct-per-rule에서 data-driven RuleSpec enum으로

    삭제 9개 파일, 신설 3개 파일 [확인] — visibility-filtering/rules/rule_spec.rs (89줄 신규), visibility-filtering/rules/tweet_rules.rs (1,125줄 신규), visibility-filtering/rules/author_rules.rs (354줄 신규).

    삭제된 파일 9개(총 2,670줄): nsfw_age_gating.rs(639) · nsfw_interstitial.rs(242) · nullcast_rule.rs(79) · socialgraph_rules.rs(301) · tes_rules.rs(446) · tweet_flag_rules.rs(114) · tweet_label_drops.rs(327) · user_label_drops.rs(239) · user_rules.rs(283).

    새 공용 추상화 RuleSpec은 규칙 하나가 한 줄 리터럴이 되게 한다.

    #[derive(Clone)]
pub(super) enum RuleSpec {
    Tweet {
        name: &'static str,
        when: fn(TweetPredicates<'_>) -> bool,
        action: RuleAction,
        exempt_author: bool,
    },
    Author {
        name: &'static str,
        when: fn(AuthorPredicates<'_>) -> bool,
        reason: FilteredReason,
        exempt_follower: bool,
    },
    Custom {
        name: &'static str,
        evaluate: fn(&RuleContext<'_>) -> VfAction,
    },
}

    세 변형이 있다. Tweet은 트윗 조건 predicate + drop/interstitial 액션. Author는 작성자 조건 predicate + drop. Custom은 임의 함수 포인터로, 조건이 predicate로 잘 잡히지 않는 경우(예: 뷰어의 상태와 관계를 동시에 봐야 하는 규칙)에 쓴다. 액션은 Drop과 SensitiveMediaInterstitial 둘뿐이고, interstitial 액션은 뷰어의 sensitive-media 옵트인 상태를 자동으로 확인한다.

    공통 예외가 spec 필드로 흡수됐다. 예전에는 규칙마다 "저자가 본인이면 Allow", "팔로워면 Allow"를 개별 코드로 반복했지만, 이제 Tweet.exempt_author와 Author.exempt_follower 두 필드가 이 검사를 담는다. RuleSpec::evaluate가 한 곳에서 처리한다.

    규칙 그룹의 재정렬 — 옛 파일별 규칙이 그대로 이동한 것이 아니라, 정책 트리거 유형끼리 다시 묶였다.

    • nsfw_interstitial.rs가 label-triggered interstitial(홈 base 규칙에 속함, NSFW_MEDIA_INTERSTITIALS)과 author-flag-triggered interstitial(NSFW_AUTHOR_INTERSTITIAL)로 쪼개졌다.
    • tes_rules.rs가 홈 공통 규칙(stale + takedown, TES_HOME_DROPS)과 recs 전용 규칙(DMCA + geo-restricted media, RECS_MEDIA_DROPS)으로 쪼개졌다. 즉 recommendations 전용 규칙 축이 코드에서 처음 명시적으로 드러났다.

    Arc<NsfwGatingCountries>가 규칙에서 컨텍스트로 이동했다 [확인] — visibility-filtering/rules/tweet_rules.rs sensitive_viewer_no_stated_age. 4세대+12(6384ca7, 같은 날 새벽)에서 nsfw_age_gating.rs가 struct + Arc<NsfwGatingCountries> 필드로 국가 목록을 들고 있었는데, 이제 RuleContext가 참조를 갖고 context.nsfw_gating_country(code)로 조회한다.

    fn sensitive_viewer_no_stated_age(context: &RuleContext<'_>) -> VfAction {
    if context.viewer().has_no_stated_age()
        && context.viewer().country()
            .is_some_and(|country| context.nsfw_gating_country(country))
        && sensitive_base_condition(context)
    {
        VfAction::Drop(FilteredReason::ContainNsfwMedia)
    } else {
        VfAction::Allow
    }
}

    즉 규칙은 이제 상태를 갖지 않는 zero-sized data literal이다. 대신 Policies struct가 nsfw_gating_countries: Arc<NsfwGatingCountries> 필드를 갖고 evaluate 시 RuleContext::new(..., &self.nsfw_gating_countries)로 참조를 넘긴다. 규칙 이름 세 개(SensitiveViewerLoggedOutDropRule · SensitiveViewerUnderageDropRule · SensitiveViewerNoStatedAgeDropRule)는 감사 로그·회귀 테스트·투명성 리포트(Under the Hood)가 리터럴로 참조하기 때문에 그대로 유지된다.

    회귀 방지 테스트가 정책 변화 없음을 잠근다 [확인] — visibility-filtering/rules/registry.rs. 새 테스트 wired_rule_order_matches_pre_migration_sequence가 TimelineHome 28개, TimelineHomeRecommendations 추가 26개, FilterAll 1개의 규칙 이름을 순서까지 리터럴로 검증한다. 즉 이 커밋은 정책 시맨틱 변경이 아니라 순수 리팩터임이 코드로 못박혔다.

    base: !context.viewer().is_author() && tweet.has_media() && (tweet.has_safety_label(SafetyLabelType::NSFW_HIGH_PRECISION) || tweet.has_safety_label(SafetyLabelType::NSFW_HIGH_RECALL) || (tweet.is_nsfw_flagged() && !tweet.is_retweet())) ... if context.viewer().has_no_stated_age() && context.viewer().country().is_some_and(|c| self.gating_countries.contains(c)) && sensitive_base_condition(context) → Drop(FilteredReason::ContainNsfwMedia) (4세대+12 기준의 옛 코드, 4세대+13에서 위 형태로 옮겨졌다) — 4세대+12 visibility-filtering/rules/nsfw_age_gating.rs

    의미

    • 정책 변화 없음의 코드 어설션이 이번 커밋의 핵심 시그널이다. 4세대+11(2026-08-28)이 90건 골든 코퍼스로 규칙 판정을 잠근 뒤 사흘 만에, 표현 자체를 재구조화한 커밋이 나왔다. 즉 X가 VF 재작성 이후 회귀 방어 자산을 먼저 축적하고 그 위에서 리팩터를 굴리는 순서를 굳혔다.
    • 규칙 인벤토리·감사 용이성이 크게 좋아진다. 예전에는 "이 저장소에 어떤 NSFW/드랍 규칙이 있는가"를 확인하려면 파일 9개를 훑어야 했지만, 이제 tweet_rules.rs 하나만 열면 상수 그룹별로 모든 규칙이 한눈에 보인다. 규제 대응·투명성 리포트(Under the Hood)에서 이 형태가 원문 인용에 적합해진다.
    • recs 전용 규칙 축이 코드에 명시됐다. RECS_MEDIA_DROPS(DMCA/geo)가 별도 상수로 나온 것은 향후 recs 전용 규칙 추가가 홈 base와 섞이지 않고 이 상수에만 붙는다는 것을 뜻한다.

    B. Phoenix 랭킹 모델에 SID recon 모드 신설 — X가 RQ-VAE 계열 semantic-ID를 랭커 입력에 붙이는 배선을 코드로 처음 공개

    신규 파일 phoenix/xrex/models/recsys_sid.py(72줄) [확인] — phoenix/xrex/models/recsys_sid.py. 이 파일은 retrieval 모델이 아니라 랭커 입력용 decoder다. 오프라인에서 학습된 SID 아티팩트를 로드해 랭킹 시점에 SID 코드에서 dense vector를 되돌리는 함수 하나가 있다.

    아티팩트 형태. _load_sid_decoder(path)가 .safetensors에서 다음 텐서를 로드한다:

    • stages — 형태 (num_levels, codebook_size, code_dim). 즉 stacked residual codebook (RQ-VAE style — 레벨별 잔차 임베딩을 골라 sum). codebook 크기와 레벨 수는 아티팩트에서 결정되며 코드에는 하드코딩되어 있지 않다.
    • dec_w0 · dec_b0 · dec_w1 · dec_b1 — 2-layer MLP decoder (relu → linear).

    recon 함수 흐름. (a) codes = sids - 1로 1-based → 0-based 변환. sids[..., 0] == 0인 행을 missing으로 표시. (b) stages[l, code_l, :]를 레벨별로 뽑아 residual sum. (c) 2-layer MLP + relu로 dense vector 복원. (d) L2 정규화(eps=1e-12). (e) missing 행을 0으로 마스킹. (f) stop_gradient로 decoder 완전 frozen. (g) recon_dim → target_dim 선형 project 하나({prefix}_sid_recon_proj, 학습 가능)만 매개변수로 두고 랭커 post tower에 dtype 캐스팅해서 반환.

    config 게이트 [확인] — RecsysAggregatedModelConfig에 두 필드가 추가됐다:

    sid_embedding_mode: Literal["learned", "recon"] = "learned"
sid_decoder_path: str = ""

    기본은 "learned" — 기존 학습 SID 임베딩 테이블을 그대로 쓴다. "recon"으로 켜면 학습 SID 테이블을 우회하고 history_seq와 candidate_seq의 SID 코드에서 recon 벡터를 만들어 post tower 임베딩에 add한다. 요구조건: legacy build_inputs 경로, sid_hash_level 미사용, sid_cross_attn 미사용, sid_decoder_path 지정.

    의미

    • X SID 라인의 첫 코드 공개. 지금까지 X의 SID 관련 공개 자료는 (a) 4세대+3(11a71f8, 2026-08-18)에서 VMRanker에 sid_known·sid_k_l1/2/3·sid_gap_l1/2/3 필드가 배선된 것, (b) 4세대+4(aad7179, 2026-08-19)에서 Phoenix proto SlateContext.sid* 필드 신설, (c) 4세대+5(d0cef2f, 2026-08-20)에서 서빙 응답의 slate context에 SID가 실려 오는 것이었다. 이번 커밋은 그 SID 코드 자체를 어떻게 dense feature로 되돌리는지를 처음 코드로 노출한다.
    • decoder는 완전 frozen. stop_gradient + off-line artifact → 서빙에는 codebook + MLP 매트릭스만 배포하면 되고, 학습되는 것은 recon_dim → target_dim project 하나뿐이다. codebook 튜닝은 오프라인에서만 이뤄지고, 랭커 학습이 codebook을 흔들지 않는다.
    • retrieval 모델이 아니다. codebook에서 벡터를 복원해 랭커 입력에 붙이는 것은 후보 표현의 밀도를 높이는 것이지, 후보 생성 자체를 SID로 대체하는 것은 아니다. Kuaishou OneRec / Tencent TGR(이 daily의 §2)의 "SID를 autoregressive 생성 대상으로 삼는" 접근과는 계보가 다르다. X는 아직 캐스케이드 안에서 SID를 입력 신호로 쓴다.
    • wired-but-off로 기본 값은 "learned"다. 다음 커밋에서 sid_embedding_mode="recon"이 프로덕션 config에 등장하면 X SID 파이프라인이 "학습 테이블"에서 "오프라인 codebook + 서빙 시 recon"으로 이동했다는 신호다.

    C. StableHLO 번들 export 배선 신설 — JAX 학습 → CUDA 서빙 핸드오프의 표준화

    신규 파일 phoenix/xrex/train/recsys_bundle_export.py(634줄) [확인] — phoenix/xrex/train/recsys_bundle_export.py. build_bundle(trainer) 진입점이 랭킹 모델의 forward를 jax.export로 낮추고, jit(...).lower().as_text(dialect="stablehlo") + jax_export.export(platforms=("cuda",)).serialize()로 세 종류의 파일을 export한다: StableHLO MLIR bytecode(.mlirbc) + .jax_export 컨테이너 + MANIFEST.json.

    임베딩 조회가 export된 그래프 밖에 있다. forward의 입력이 merged_embeddings — 이미 조회된 임베딩 로우들이 concat된 텐서다. MANIFEST.embedding이 {rows, rows_padded, num_shards, width, dtype, merged_slices, hash_table}를 담아 서빙 측이 임베딩 서버 결과를 어떻게 concat할지 안다. 이것이 X 랭커의 서빙 아키텍처가 "임베딩 서버가 조회 → GPU 서버가 StableHLO 실행"이라는 분리 구조임을 코드에서 드러낸 사실이다.

    다중 batch bucket. export_bundle_bs_per_device 기본 "1,2,4". 버킷마다 별도 프로그램을 lower하고 서빙 시 요청 배치 크기에 맞는 버킷을 고른다.

    seqpack 제한. pallas_ranker_varlen_attn만 지원한다. FA4(cutedsl_ranker_varlen_attn) block-sparse 레이아웃은 명시적으로 NotImplementedError. 4세대+6(2026-08-21, 28e414f)의 GB300 config가 attn_impl="cutedsl_ranker_varlen_attn"을 쓰므로, GB300 학습 config를 그대로 export하려면 attn kernel을 pallas로 바꿔야 한다. 즉 학습에서 서빙으로 넘어가는 지점에서 attention impl이 달라지는 배선이 코드에 노출됐다.

    sid_num_levels가 매니페스트 prep_spec에 echo된다 — 서빙 측이 SID 레벨을 몇 개 배치에 실을지 안다. §B의 SID recon 모드와 짝을 이룬다.

    트리거 게이트. Trainer에 새 4개 필드가 추가됐다.

    export_stablehlo_bundle: bool = False
export_bundle_bs_per_device: str = "1,2,4"
export_bundle_history_seq_len: int = 0
export_bundle_candidate_seq_len: int = 0

    __post_init__에서 export_stablehlo_bundle가 켜졌지만 checkpoint_config.copy_port가 꺼지면 ValueError. 즉 export는 checkpoint 배포 파이프라인의 copy_port(hot checkpoint 배포)에 붙어서만 활성화된다. 매 copy_port 배포마다 {OUT_PATH}/.{prefix}/export/에 번들이 함께 나간다.

    의미

    • X가 JAX 학습 → CUDA 서빙 핸드오프의 StableHLO 표준화를 코드로 처음 공개했다. 이전까지 canon 이해는 "Phoenix가 JAX/Haiku로 학습되고 서빙은 별도 스택"이었는데, 이 커밋으로 서빙 스택이 컴파일된 StableHLO를 받아 실행하는 형태임을 확인할 수 있다.
    • 임베딩과 dense forward의 명시적 분리가 아키텍처 사실로 확정됐다. 이는 X가 임베딩 테이블 규모(4세대+4 xrecsys_search의 vocab 100M/100M/30M)를 GPU 하나에 담지 않고 별도 서버(임베딩 서버 + mm_embedding_client.rs)에서 조회한다는 canon 이해를 정확하게 뒷받침한다.
    • 기본 off. 이 커밋만으로는 프로덕션 서빙이 실제로 StableHLO 번들을 소비하는지 확정할 수 없다. 다음 커밋에서 export_stablehlo_bundle=True가 프로덕션 config에 등장하면 서빙이 이 경로에 붙었다는 신호다.

    D. envelope-encrypted Orbax checkpoint writer 신설

    신규 파일 orbax_encrypted.py(288줄) [확인] — phoenix/python/training/xai-checkpointing/xai_checkpointing/orbax_encrypted.py. Orbax PyTreeCheckpointHandler를 감싸 envelope encryption(AWS KMS 계열의 표준 패턴 — KMS가 발급한 마스터 키로 per-directory Data Encryption Key(DEK)를 감싸고, 데이터는 DEK로 대칭 암호화한다)을 in-tree로 구현했다.

    모든 파일이 매직 헤더 b"XAIENC01"로 시작해야 한다.

    def assert_all_enveloped(path: pathlib.Path) -> None:
    offenders = []
    for f in sorted(path.rglob("*")):
        if not f.is_file() or f.name in ("_DEK", "_DEK.claim"):
            continue
        with f.open("rb") as fh:
            if fh.read(8) != b"XAIENC01":
                offenders.append(f)
    if offenders:
        raise RuntimeError(
            f"encrypted save left plaintext at rest; not committing: {list(map(str, offenders))}"
        )

    _DEK와 _DEK.claim(KMS 발급 DEK 파일과 claim)만 예외로 두고, 나머지 파일 중 하나라도 헤더가 없으면 finalize 후 커밋을 거부한다. 오직 jax.Array 리프만 허용(_ArraysOnlyRegistry + _require_array_leaves)하고, 문자열·dict·Python scalar 리프는 명시적으로 거부한다 — 서빙 측에서 이 checkpoint를 로드할 때 임의 코드 실행 리스크를 없앤다. tensorstore KvStore도 암호화된 wrapper로 교체된다. _METADATA·_CHECKPOINT_METADATA·sharding metadata 모두 encrypt_write로 처리된다.

    downgrade 금지. checkpoint_write.py에 새 가드가 있다.

    if getattr(self, "_restored_encrypted", False):
    raise ValueError(
        "restored from an ENCRYPTED checkpoint but the orbax writer cannot "
        "produce encrypted saves — refusing to downgrade to plaintext saves"
    )

    암호화된 checkpoint에서 restore한 프로세스가 평문 저장을 시도하면 저장 자체가 실패한다. 실수로 암호화 상태를 잃는 것을 코드 레벨에서 원천 차단한다.

    config 필드. CheckpointConfig에 신설된 값:

    encrypt: bool = False
encryption_key_id: str | None = None
encryption_context: dict[str, str] = field(default_factory=dict)
encryption_chunk_size_bytes: int = 8 * 1024 * 1024

    encryption_context: dict[str, str]가 AWS-KMS의 encryption-context 패턴을 그대로 따른다 — KMS 호출자가 키 사용을 메타데이터에 바인딩할 수 있는 표준 필드다. 청크 크기 기본 8 MiB.

    의미

    • X가 학습 체크포인트를 rest에서 암호화한다는 사실이 코드로 확정됐다. 이전에는 인프라 층에서 처리하는 것으로만 짐작할 수 있었지만, 이제 xrex 학습 파이썬 코드에 envelope-encryption + KMS + 매직 헤더 강제가 in-tree로 있다. 규제 프레임워크(SOC2·FedRAMP·GDPR 등)를 소스에서 명시하지는 않았다.
    • downgrade 금지 가드가 특히 눈에 띈다. 4세대+7의 VF reference_compare 하니스가 APP_ENV=prod에서 부팅 시 panic으로 스테이징 전용을 강제했던 것과 같은 방향 — 정책을 config 값이 아니라 fail-close 어설션으로 코드에 굳힌다. 이는 X의 이번 사이클 전반의 패턴이다.

    2. TGR (Tencent Generative Recommendation) — 생성 패러다임 랭킹·retrieval·slate 생성·reason token을 한 프레임에 묶고 5개 지면에 배포 — 레이더 승격

    자료 TGR: Advancing Industrial Recommendation from Generative-Paradigm Ranking toward Unified Generation and Reasoning — arXiv 2609.00986, TGR Team 13인(Tencent PCG), 2026-09-01 제출, HTML로 소속과 본문을 확인했다.

    배경 TGR은 Tencent Platform and Content Group(PCG) 산하에서 낸 4-in-1 프레임워크다. 저자 13인이 팀 서명("TGR Team, Lei Cheng, Haonan Hu, Beibei Kong, Yudong Li, Zang Li, Yunsheng Pang, Hongyang Su, Jianchao Tu, Yunlong Wang, Bing Wen, Junzhang Zhu, Shaojie Zhu, Chengxiang Zhuo") 형식이다. 대상 지면은 §1 "Our setting"에서 "news feeds, short videos, long videos, music, and web novels"로 명시되어 있는데, PCG 산하로 좁히면 Tencent News, 후난발 Weishi, Tencent Video, QQ음악, 阅文/QQ阅读 계열을 포괄한다(다만 논문 본문에서는 다섯 지면을 Scenario 1~5로 익명화한다).

    이 프레임워크가 중요한 이유는 두 갈래로 나뉜다. 첫째, Kuaishou OneRec 계열에 대한 프로덕션 대응 진술로 회사 규모가 두 번째로 커진 사례다. Kuaishou는 OneRec-V1 → OneRec-V2 → OneRec-Think → OneReason으로 이어지는 단일 회사 시리즈였는데, Tencent PCG가 같은 방향(one-model recommendation)에 프로덕션 배포를 진술했다. 논문 §1이 명시적으로 *"Aligned with the one-model direction of OneRec at Kuaishou"*라고 밝힌다. 둘째, HSTU와 OneRec를 한 프레임 안에서 각각 대체 대상으로 명시한 첫 자료다. CCFormer가 Scenario 2~5에서 HSTU를 대체하고, BARGE·HiGR가 OneRec를 오프라인 베이스라인으로 대체한다. Meta HSTU 계보(랭킹)와 Kuaishou OneRec 계보(one-model)를 두 축으로 통합하려는 시도다.

    새로 알게 된 것

    A. CCFormer (TGR-GenRank) — 생성 패러다임의 Transformer 랭킹

    • 아키텍처: Transformer 랭커에 feature-field separated cross attention, subspace token mixing, hierarchical sequence compression을 도입. HSTU 계보를 이어받되 랭킹에 특화된 요소들이다.
    • 대체 대상: Scenario 1(비디오 추천)에서는 "long-standing, iteratively optimized DLRM ranker"를, Scenario 2~5에서는 "already deployed HSTU model"을 대체한다.
    • 배포 상태 (§3.6): "CCFormer was fully launched in Scenarios 1 and 2 and now serves the entire production traffic of both." Scenario 3~5는 A/B 상태로 명시.
    • 헤드라인 수치 (§3.6, Table 6):
      • Scenario 1: CTR +3.57%, UCTR +1.93%, Page View +3.86%, Video View +3.47%, Watch Time +1.29%, Ad revenue +1.64%.
      • Scenario 2(광고 랭킹): Ad revenue +1.71%.
    • 효율 (§3.5): "scales predictably at roughly half the GFLOPs of HSTU, trains 2.21× faster."

    B. BARGE (TGR-GenRec) — 계층 semantic ID 생성 retrieval

    • 문제의식 (Abstract): "two structural gaps in hierarchical semantic-ID generation — the loss of item boundaries when multi-token items are flattened and semantic drift caused by early prefix errors."
    • 세 구조: item context-aware attention(문서에서는 "item-boundary-aware"로도 부름) + hierarchical path reranking + orthogonal dual-path decoding.
    • 코드북: Table 1에 "OSQ-VAE (dual)"로 명시. §4.2의 상세 학습 목적은 이번 딜리 fetch 범위에서 확보하지 못했다 → 심층 분석 필요. TIGER 계열(Kuaishou HD-Rec / Alibaba MetaStrategy가 참조하는 RQ-VAE 계보)과의 관계는 표에서 "TIGER lineage"로 언급되지만 codebook 초기화 방식(RQ-KMeans 여부)은 확인 못했다.
    • 배포 상태 (Abstract): "is fully rolled out as a generative retrieval channel with parameters, beam width, and serving latency unchanged, delivering +0.60% CTR and +1.70% total reading time — gains that grew larger and more stable after full launch." 즉 retrieval 채널 중 하나로 전면 launch(다른 retrieval 채널과 병렬 존재).
    • 헤드라인 수치: 오프라인에서 "outperforms OneRec by 10.2–16.9% in Hit@5 across two industrial scenarios." 온라인 +0.60% CTR + 1.70% reading time.

    C. HiGR (TGR-GenRec) — 전체 슬레이트 생성

    • 아키텍처: PCRQ-VAE(Prefix-Contrastive RQ-VAE) 토크나이저 + Hierarchical Slate Decoder(HSD) coarse-to-fine 디코딩 + listwise multi-objective alignment.
    • OneRec와의 차이: 논문 Table 1에서 OneRec-V1/V2/Think와 축별로 비교한다. "prefix-structured semantic IDs"의 구체 구현과 HSD의 단계별 디코딩은 fetch 범위 밖 → 심층 분석 필요. Meituan OneSug와 Xiaohongshu RankMixer 언급은 이 논문 fetch 범위에서 확인되지 않았다.
    • 배포 상태 (Abstract): "serves whole slates below 50 ms P99 latency at roughly 60% lower GPU demand than full-sequence decoding." "consistently lifts engagement, traffic consumption, and commercial value across three A/B-tested scenarios" — 전면 launched라는 표현은 없고 A/B에 그친다.
    • 헤드라인 수치: 오프라인 "improves offline slate quality by 15.9–21.3% over matched-capacity OneRec with a 5× inference speedup." 온라인 3개 시나리오에서 +1.22% Average Watch Time + 1.73% Average Video Views + 0.68% CTR + 0.56% ad revenue.

    D. TGR-Reason — semantic-ID reason token 오프라인 생성 + 서빙 프롬프트 주입

    • 핵심 개념 (Abstract): "Offline, a LatentRec-trained Think model materializes complete semantic-ID reason tokens; Direct Reasoning Injection uses them as hierarchy-aligned prompts to condition online decoding."
    • reason token은 텍스트 CoT가 아니라 semantic-ID 형태의 사고 토큰이다 — Table 1 캡션이 "reasoning-enriched semantic IDs generated offline by a LatentRec-trained Think model"이라고 정의한다. 즉 Think 모델이 latent reasoning을 학습하고 그 결과를 semantic-ID 코퍼스로 오프라인 export하면, 서빙 시 이 SID를 프롬프트로 주입해 디코딩을 조건화한다. Kuaishou PushDualGen(SID + skippable copy)의 접근과 결이 유사하지만, 여기서는 copy가 텍스트가 아니라 SID다.
    • 배포 상태: "statistically significant gains" 정도만 표현되고 전면 launched는 아니다. "one of our commercial content platforms"라고 익명화.
    • 헤드라인 수치: 오프라인 "raises cold-start new-user Hit@1 by +477.8%"(베이스라인 절대값 미공개). 온라인 +1.75% Effective Consumption Rate + 13.09% new-user Exposure-to-Conversion Rate.

    "Within Tencent's Platform and Content Group (PCG), recommendation runs across a deliberately heterogeneous portfolio of surfaces — news feeds, short videos, long videos, music, and web novels — which together serve hundreds of millions of daily active users." — arXiv 2609.00986v1 §1

    E. 오프라인 벤치마크와 비교 베이스라인 (§3.4)

    • 산업 데이터셋 (§3.4): "industrial dataset of one month of production logs from a Tencent recommendation system: over 4 billion samples, 3 million users, and 10 million items."
    • 베이스라인: 공개 벤치에서 DIN, DeepFM, SASRec, MIMN, HSTU, OneTrans, STCA. 산업 벤치에서 HSTU, OneTrans, STCA.
    • Table 1 정성 비교 대상: HSTU, OneTrans, OneRec-V1, OneRec-V2, OneRec-Think, OneReason, GPR, PinRec. HLLM, PinnerFormer, TIGER, LC-Rec는 fetch 범위 내에서 명시적으로 등장하지 않았다.

    정본 반영 radar.md 생성형 retrieval / semantic ID 관찰 스레드에 "2026-09-03 추가 근거: Tencent PCG TGR ..." 절 추가. 이 스레드의 다섯 번째 회사(Kuaishou HD-Rec/PushDualGen + Yandex Music Gryphon-v2/Sona + Alibaba PailitaoGR + Snap CAMIE + 이번 Tencent TGR)이자 회사 규모가 두 번째로 큰 사례가 됐다. radar.md ## 이번 달 신규에도 별도 엔트리로 신규 등록(4-in-1 프레임임과 심층 분석 필요 항목 6개를 명시).

    의미

    • HSTU와 OneRec가 한 프레임 안에서 각각 대체 대상으로 명시된 첫 자료다. 지금까지 canon 이해는 (a) HSTU 계보가 Meta 랭킹의 표준이고 (b) OneRec 계보가 Kuaishou의 one-model 방향이라는 것이었는데, TGR은 이 두 계보를 각기 다른 컴포넌트(CCFormer가 HSTU 대체, BARGE·HiGR가 OneRec 대체)로 통합한다.
    • 가장 강한 배포 주장은 CCFormer이지 BARGE/HiGR가 아니다. CCFormer가 유일하게 두 Scenario에서 전체 트래픽을 담고 있고("fully launched, now serves the entire production traffic of both"), 다른 시나리오도 launched 방향으로 굴러갈 수 있는 상태다. BARGE는 retrieval 채널 중 하나로 launched, HiGR는 A/B 상태에 그친다. 즉 Tencent가 랭킹에서는 확신을 표현했고, retrieval과 slate 생성에서는 아직 아니다.
    • reason token이 SID다. Kuaishou PushDualGen이 SID + skippable copy(텍스트)로 조합했다면, TGR-Reason은 copy 자리에 텍스트가 아닌 semantic-ID를 넣는다. 텍스트 CoT가 아니라 SID CoT로 다시 해석할 수 있다. 이는 Spotify Research(2608.23154)의 "explicit reasoning trace가 SFT/RL 모두에서 offline effectiveness를 낮춘다"는 통제 실험과 정면으로 대비된다 — TGR-Reason은 텍스트 trace를 쓰지 않으므로 Spotify의 반증점을 우회하는 형태다.
    • 심층 분석 필요 항목 (다음 사이클): ① BARGE OSQ-VAE 코드북 학습 목적과 초기화(RQ-VAE인지 RQ-KMeans인지, TIGER 계열인지 신설인지), ② item-boundary-aware attention의 구체 구현(mask인지 loss term인지), ③ HiGR PCRQ-VAE의 Prefix-Contrastive 목적함수와 OneRec SID의 실질 차이, ④ Think 모델의 백본(Hunyuan? Qwen? 사내 LLM?)과 reason token 코퍼스 규모, ⑤ cold-start Hit@1 +477.8%의 베이스라인 절대값, ⑥ Scenario 1~5의 실제 Tencent 제품 매핑(외부 발표·블로그에서 확정 가능한지). 6개 모두 이 daily의 범위 밖이므로 심층 분석 필요로 표시하고 사람이 직접 시작하는 후속 작업으로 남긴다.

    • Tencent PCG TGR (arXiv 2609.00986) — 위 §2에서 정독. 통과 즉시 SID 스레드 정본 반영 + 이번 달 신규에도 별도 등록.
    • ByteDance ReST (arXiv 2609.01240) — radar.md 이번 달 신규에 추가. 저자 12명 전원 ByteDance 소속으로 TikTok Shop Ads에 배포한 rec-native Transformer 랭킹 프레임워크(ReST). Dual-gated attention + rotary positional/temporal embedding + stabilized residual normalization + training-only auxiliary objectives + heavy reusable encoder + lightweight cross decoder(projection-free KV attention) 조합. *"conduct a one-week online A/B test on TikTok Shop Ads, one of the largest advertising platforms"*이라고 명시했고, *"This latency-constrained configuration improves AUC by +1.31% and lifts Advv by a statistically significant +11.93% (p<0.01), while satisfying all other monitored production guardrails"*를 얻은 뒤 *"ReST has since been fully deployed in production"*으로 배포를 진술한다. 50 ms P99 지연 유지. 크기는 large 5.36M–5.69M 파라미터. 스케일링 법칙 스레드에 네 번째 회사 진술(Meta HSTU/Wukong/LLaTTE, Alibaba TransRetrieval에 이어)이다. LLM 스타일 Transformer 블록이 saturate하는 sequence length·depth·width에서 rec-native 설계가 일관되게 scaling된다고 주장.

    탈락 (28건) — 대부분 (a) benchmark/평가/RAG 방법론(플랫폼 프로덕션 진술 없음), (b) 도메인 제한(POI·의료·과학·전자상거래 학술 실험), (c) 저자 소속 확인 불가. 두 편만 인접 자료로 남긴다.

    • CoGR (arXiv 2609.00638) "It Takes Two to Match: Co-Evolving Generative Retriever with Reinforcement Learning" — Runpeng Dai(UNC Chapel Hill) + Kaili Huang · Changsung Kang · Ciya Liao(Apple 소속). GRPO 기반 co-evolving RL로 query·item 양쪽 keyword generator를 대칭 학습한다. 내부 데이터셋("Internal APP Marketplace")과 공개 벤치(WANDS)에서 sparse/dense/generative 10개 베이스라인 대비 F1을 각각 +10.9% / +36.1% 이겼다고 진술. 프로덕션 배포 진술 없음 — 오프라인 벤치마크만. Kang·Liao의 Apple 소속과 데이터셋 이름을 고려하면 App Store로 추정되나 회사명은 논문이 밝히지 않는다. radar 수용 기준의 프로덕션 조건을 못 넘겨 탈락. [관찰] 2026-09-03 — 소속 확인은 논문 HTML 저자 목록.
    • UEWM/WMG-RL (arXiv 2609.01067) "World Model-Guided Reinforcement Learning via Counterfactual User Engagement Simulation" — Ang Li 외 7인. 유저 시뮬레이터(UEWM)로 오프라인 reward supervision을 만들고 정책이 다중 후보를 제안하면 UEWM이 대응 피드백을 병렬 예측해 dense reward로 변환. 1.7B student가 큰 LLM을 downstream recommendation에서 매치/능가한다고 주장. 프로덕션 진술 없음으로 탈락. 유저 시뮬레이터 라인이 다른 회사에서 프로덕션 진술로 나오면 재고 대상.
