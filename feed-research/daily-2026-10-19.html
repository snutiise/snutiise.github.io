14세대+43 — 인기 포스트 라벨 분리, page_rl 가중치 변경, VF 보조 조회 best-effort화 — X

자료 xai-org/x-algorithm@bc3948b — xAI 공개 저장소, 2026-10-16 19:02 UTC 커밋, 코드. 2026-10-17 배치에서는 GitHub API 목록에 아직 보이지 않아 이번에 처음 다룬다.

배경 X는 For You 후보를 여러 소스에서 모은다. 2026-10-03(4세대+35)에 생긴 PopularPostsSource는 팔로워 상위 작성자의 조회수 빠른 글을 미리 뽑아 두는 소스인데, 지금까지는 Phoenix two-tower retrieval(유저 벡터와 포스트 벡터의 내적으로 후보를 찾는 방식)과 같은 라벨을 달고 나갔다. page_rl은 2026-10-14(4세대+41)에 공개된 immersive 세로 영상 지면용 재순위기다. 랭커 헤드 확률의 가중합(behavior score)으로 후보 풀을 자르고, 디코더가 한 슬롯씩 고르며, 이 점수의 softmax가 RL 학습에서 벗어나지 말아야 할 기준 정책이 된다.

새로 알게 된 것

  • 인기 포스트 후보의 served type이 ForYouPhoenixRetrieval에서 자체 값 ForYouPopularPosts로 바뀌었다 확인 — home-mixer/sources/popular_posts_source.rs:13.

  • page_rl behavior score의 기본 가중치가 바뀌었다. 품질 시청(VQV, 일정 시간 이상 실제로 본 영상 시청)은 0.5 → 1.0, 공유는 40.0 → 4.0이다 확인 — phoenix/xrex/models/page_rl.py:69-70. 디코더 서빙 스위치는 여전히 기본 off다.

  • 랭킹 요청의 PageDecodeParams에 RankingScoreWeights(13개 필드)가 생겨, 호출 측이 요청마다 behavior score 가중치를 보낼 수 있다. 값이 NaN이면 config 기본값을 쓴다 확인 — page_rl.py:319-324, recsys.proto:198-214.

  • 영상 캐러셀에 임베딩 기반 중복 제거가 기본 off로 추가됐다. 이미 고른 영상과 코사인 유사도가 0.72 이상이면 건너뛰고, 인용 포스트는 예외다 확인 — home-mixer/util/video_carousel.rs:72-105.

    • 임베딩은 Manhattan의 tweet_multimodal_embeddings에서 버전 v8_search_1(1024차원)을 100ms 타임아웃으로 읽는다 확인 — clients/post_v8_search_embedding_client.rs:12-17. home-mixer가 이 멀티모달 포스트 임베딩을 읽는 첫 코드다.

  • visibility-filtering(포스트마다 "이 뷰어에게 보여도 되는가"를 판정하는 서비스)에서 팔로우·차단 관계·대화 제어·뷰어 국가 등 13개 조회가 best-effort가 됐다. 300ms 안에 응답이 없으면 기본값으로 판정하고 결과를 완료로 친다 확인 — visibility-filtering/hydration/plan.rs:375-409, rules/registry.rs:167-175.

    • 테스트가 그 대가를 명시한다. 팔로우 조회가 실패하면 실제 팔로워에게도 비공개 계정의 포스트가 드롭될 수 있다 확인 — rules/rule_spec/laws.rs:262-293.

  • 학습 라벨 IsBrandEngagement가 생겼다. 좋아요·답글·리트윗·작성자 팔로우·클릭·링크 열기·프로필 클릭·사진 확대·캐러셀 넘기기 10개 행동을 positive로 보고, 영상 시청과 체류는 넣지 않는다 확인 — brand_engagement.rs:5-19. 이 라벨을 쓰는 헤드는 아직 없다.

정본 반영 services/x.md 랭킹 절 아래 변경 이력에 "4세대+43" 절을 새로 썼다. 후보 소스 표의 PopularPostsSource 행 라벨 문장, 4세대+35 절의 해당 서술, 4세대+41 절의 page_rl 가중치 불릿을 고쳤다.

의미 ⚠ 주장 변경: 정본은 인기 포스트 후보가 Phoenix retrieval 라벨로 섞여 하위 단계에서 구분되지 않는다고 적었는데, 이제 별도 라벨을 단다 확인. page_rl의 기준 정책은 공유보다 품질 시청을 더 무겁게 보도록 바뀌었다 확인(값).

24세대+44 — 캐러셀 중복 제거 기본 on, Who-to-Follow 우선, 참여자 목록 피처 — X

자료 xai-org/x-algorithm@862a123 — xAI 공개 저장소, 2026-10-17 00:44 UTC 커밋, 코드. 크론 미러 sync 시각은 2026-10-16T16:00:32Z다.

배경 X는 2026-10-08(4세대+38)부터 For You 6번째 자리에 세로 영상 3~5개를 묶는 캐러셀 모듈을 기본 off로 만들어 왔다. 같은 작성자나 비슷한 영상이 한 캐러셀에 몰리는 것을 막는 중복 제거 규칙은 2026-10-13(4세대+40)과 위 4세대+43에서 모두 꺼진 채로 추가됐다. Who-to-Follow(WTF)는 팔로우할 계정을 추천하는 피드 안의 모듈이다. 한편 지금까지 랭커는 포스트의 참여 수를 집계 카운트로만 받았다.

새로 알게 된 것

  • 캐러셀 중복 제거 세 가지가 기본 on이 됐다. EnableVideoCarouselAuthorDedupe false → true, VideoCarouselSemanticIdDedupeLevels 0 → 3, EnableVideoCarouselEmbeddingDedupe false → true다 확인 — home-mixer/params/param.rs:1095-1112. 캐러셀 자체는 여전히 기본 off다.

    • SID(Semantic ID, 아이템 임베딩을 계층 코드열로 양자화한 식별자) 앞 3단계가 같은 영상은 한 캐러셀에 하나만 남는다.

  • 같은 응답에 WTF 모듈이 있으면 캐러셀을 넣지 않는다. 파라미터가 없는 무조건 규칙이다 확인 — selectors/blender_selector.rs:50, 156-161.

  • 후보 포스트에 참여한 유저 ID 목록을 랭킹 요청의 새 필드 TweetInfo.postEngagers에 넣는 PostEngagers 피처가 생겼다 확인 — util/post_engagers.rs:7-8, 48-73.

    • positive 최대 32명, negative 최대 8명이며, 항목마다 행동 비트와 참여 후 경과 초가 붙는다. 뷰어 자신과 서빙 시각 이후의 참여는 뺀다.
    • 스위치 EnablePostEngagers는 기본 off지만 섀도 트래픽에서는 항상 켜진다 확인 — candidate_hydrators/post_engagers_hydrator.rs:43-45. 이 필드를 읽는 모델 코드는 이번 diff에 없다.

  • 새 필터 ZeroFavCodivertFilter(기본 off)는 treatment 뷰어에게 ZeroFav retrieval 채널(좋아요가 아직 없는 포스트를 찾는 채널)로만 들어온 후보를, 작성자도 treatment 버킷일 때만 남긴다 확인 — filters/zero_fav_codivert_filter.rs:44-80. 뷰어와 작성자를 함께 나누는 양면 실험 장치로 본다 추정 — 작성자 버킷별 카운터가 근거다.

  • two-tower retrieval 학습이 마이크로배치 여러 개에 걸쳐 후보 풀을 공유한다. 각 유저가 전체 풀을 in-batch negative(같은 배치의 다른 유저의 positive를 오답으로 쓰는 방식)로 쓴다 확인 — phoenix/xrex/models/recsys_two_tower_model.py:556-618. 이를 쓰는 프리셋은 아직 없다.

  • visibility-filtering·abuse-enforcement 변경은 이름 변경과 메트릭이고, 피드 필터링 대상이 바뀐 곳은 찾지 못했다 추정 — 모든 hunk를 줄 단위로 읽지는 않았다.

정본 반영 services/x.md 변경 이력에 "4세대+44" 절을 새로 쓰고, 피드 지면 절 캐러셀 항목에 중복 제거 기본 on과 WTF 우선 규칙을 추가했다. 열린 질문에 postEngagers 소비 모델 등 네 항목을 추가했고, ## 출처의 기준 커밋을 862a123까지 올렸다.

의미 캐러셀은 여전히 꺼져 있지만 중복 제거와 다른 모듈과의 충돌 규칙이 먼저 기본값으로 확정됐다 확인(값). PostEngagers는 참여 수 대신 "누가 반응했는가"를 신원과 행동 종류째 랭커에 넘기는 피처라서, 소셜 그래프 신호를 랭커 입력으로 직접 넣으려는 실험으로 본다 추정 — 근거는 proto 구조와 섀도 트래픽 상시 on이다.

3생성형 추천 추론 비용 — Spotify (레이더)

자료 Advancing Generative Recommendation Inference: our collaboration with NVIDIA on TensorRT LLM — Spotify Engineering, 2026-10-16, 블로그. Spotify와 NVIDIA 엔지니어 7인이 썼다.

배경 Spotify는 2026-01부터 팟캐스트 추천에 LLM을 쓴다 확인. LLM이 Semantic ID 토큰열을 생성하고 이를 카탈로그 아이템으로 바꾸는 방식이라, beam search(확률 높은 토큰열 여러 개를 동시에 탐색하는 디코딩)를 서빙 경로에서 돌려야 한다. 이 글은 그 비용을 TensorRT LLM(NVIDIA의 LLM 추론 엔진)으로 줄인 과정을 다룬다.

새로 알게 된 것

  • 워크로드는 두 가지다. beam search로 상위 SID 시퀀스를 생성하는 쪽과, 후보 마스킹으로 한 요청에서 여러 후보를 채점하는 쪽이다 확인.

    "these top sequences constitute semantic IDs that are then translated to catalog items to serve recommendations" — Advancing Generative Recommendation Inference, 2026-10-16 (블로그)

  • 개인화는 기존 유저 임베딩을 LLM 임베딩 공간의 soft token 하나로 투영해서 한다 확인.

    "learn a projection from an existing embedding space into an LLM's embedding space as a single soft token. The LLM is fine tuned using a subset of the weights to be able to use this soft token to personalize recommendation outputs." — 같은 글 (블로그)

  • Qwen3 1.7B 기준 비용 절감은 beam search 최대 54%, 채점 최대 7%다 확인. 비교 기준이 무엇인지는 글에서 분명하지 않다.

    "up to 54% cost reduction for beam search workloads and up to 7% cost reduction for scoring workloads" — 같은 글 (블로그)

  • 다중 시퀀스 반환 beam search, 다중 아이템 채점 Python API 등을 TensorRT LLM 본체에 기여했다 확인.

정본 반영 추적 서비스가 아니므로 정본에는 반영하지 않았다. radar.md의 "LLM-native 랭킹의 확산" 스레드에 근거 한 줄을 추가했다.

의미 같은 스레드의 Spotify GLIDE(2026-08-03)가 "서빙 경로의 LLM 후보 생성기가 A/B에서 이긴다"는 진술이었다면, 이번 글은 그 운영 비용을 줄이는 방법에 대한 진술이다 추정 — 두 글 모두 팟캐스트 지면의 SID 생성 모델을 다루지만, 같은 모델이라고 명시하지는 않았다.
