1grox에 스레드 chain 단위 두 번째 답글 스팸 판정 경로가 정식으로 연결됐다 — X

자료 xai-org/x-algorithm@9b0dc31 — 공개 소스코드, 2026-09-04 00:37 UTC, X.AI Corp. 이 노트들은 4세대 공개 뒤의 X 커밋에 차례로 번호를 붙여 부르며, 이 커밋은 4세대+15다.

배경 grox는 X의 nearline LLM 주석 파이프라인이다. 답글 품질 관리 축에서 grox는 지금까지 판정 흐름 두 개를 갖고 있었다. PlanReplyRanking은 답글 하나에 점수를 매기고, PlanCoordinatedSpam은 여러 계정이 담합한 반복 답글을 잡는다. 두 흐름 모두 4세대에서 통합 이력이 길다.

  • 4세대+3(2026-08-18, 11a71f8)에서 따로 있던 spam·comment·reply-ranking generator가 ReplyRankingTaskGenerator 하나로 합쳐졌다.
  • follower 게이팅 임계는 11일 동안 15k → 30k → 60k → 80k → 100k로 5단계에 걸쳐 올랐다.
  • Kafka-first 저장 순서, Manhattan monotone-only write, LM 프롬프트에 팔로워 수와 bio를 넣는 옵션 같은 신뢰성 장치는 4세대+9(45b48ba)·+10(24c6094)에서 갖춰졌다.

이번 커밋은 이 흐름에 세 번째 판정 경로인 PlanMultiStepReplySpam을 붙였다. 이름의 Multi-step은 "판정 단위가 개별 답글이 아니라 답글 chain 여러 개"라는 뜻이다.

새로 알게 된 것A. 한 저자가 자기 답글에 다시 답한 chain만 판정에 들어간다

  • 진입 필터는 아래 8가지 조건을 모두 통과한 답글만 판정에 넣는다 확인 — task_multi_step_reply_spam.py. 필터 클래스는 TaskMultiStepReplySpamFilter다.

    1. post.ancestors가 있고 그중 삭제(None)된 것이 없다. 즉 답글이고 스레드가 온전하다.
    2. 대상 포스트, 직계 부모, 스레드 root의 user가 모두 살아 있다.
    3. 답글 작성자가 스레드 root 작성자와 다르다. 원 포스터가 자기 스레드에 다는 답글은 건너뛴다.
    4. GROK_USER_ID·GORK_USER_ID는 건너뛴다. Grok과 Gork 자체가 다는 답글은 대상이 아니다.
    5. 스레드 깊이가 2 이상이다. "root → 첫 답글" 한 단계짜리는 들어오지 않는다.
    6. 직계 부모의 작성자가 대상 포스트의 작성자와 같다. 같은 사람이 자기 답글에 또 답글을 다는 chain만 진입한다.
    7. root 작성자의 팔로워가 1,000 이상이다("blast radius"). root 노출이 유의미한 스레드만 들인다.
    8. 답글 작성자가 high page-rank v2 유저나 grey badge 유저면 건너뛴다. 이미 자리 잡은 계정은 대상이 아니다. 두 여부는 UserStratoLoader.is_high_page_rank_v2_user와 is_grey_badge_user를 asyncio.gather로 병렬 조회해 확인한다.

    8개 조건 가운데 특히 6번이 이 파이프라인의 도메인을 정한다. 그 도메인은 자기 대화 chain으로 root 노출을 훔치는 답글 스팸 chain이다. 예를 들어 유명인의 트윗에 A가 답글을 달고, 그 답글에 A가 다시 답글을 달고, 또 A가 답글을 다는 식으로 chain을 잇는다. 이렇게 root 트윗의 노출을 자기 광고나 유인으로 끌어당기는 패턴이 대상이다.

    7번의 임계 1,000은 단발성 판정의 100k보다 두 자릿수 낮다. 이 파이프라인은 root 노출이 상당한 스레드에 폭넓게 돈다.

    — task_multi_step_reply_spam.py, 2026-09-04

새로 알게 된 것B. Gemma 2가 스레드 전체를 읽고 스팸인 포스트 번호들을 고른다

  • LM에 보내는 human 메시지의 구조가 코드에 그대로 드러난다 확인 — classifier_multi_step_reply_spam.py.

    • 메시지를 만드는 함수는 MultiStepReplySpamScorer._to_convo다.
    • 시스템 프롬프트는 README 정책(게이밍 방지)에 따라 export에서 빠졌다.
    • "Reply Author Info" 절은 답글 작성자의 유저 프로필(handle, follower count, name, bio)을 렌더링한다.
    • "Thread" 절은 스레드의 모든 포스트를 #### Post N 형식의 인덱스 번호와 함께 나열한다. root에는 "(root post — never flag)" 태그를, 마지막 포스트에는 "(the reply being evaluated)" 태그를 붙인다.
    • 스레드가 MAX_THREAD_SIZE = 10을 넘으면 앞 5개와 뒤 5개만 남기고 중간을 잘라 낸다.
    • 각 포스트에 include_follower_count=True와 max_media=2를 적용하고, root에만 include_bio=True를 적용한다.

    즉 이 파이프라인은 LM에게 포스트 하나하나가 스팸인지 묻지 않는다. 스레드 전체를 보고 스팸 인덱스 집합을 뽑아내라는 형태의 태스크를 준다. 응답은 JSON {"spam_post_indexes": [1, 2, 3], "reason": "..."}이다.

    — classifier_multi_step_reply_spam.py, 2026-09-04

  • 판정 LM은 Gemma 2다 확인.

    • 코드는 model_name = GEMMA_2이고, OaiSampler로 호출한다.
    • 4세대+9(45b48ba)에서 grox의 USE_GEMMA_CATEGORIES에 Spam이 들어간 뒤로 grox는 Gemma를 밀고 있고, 이번 선택은 그 흐름의 연장이다.
    • Multi-step reply spam이 처음부터 Gemma 전용이라는 점은 grok API 예산을 아끼는 방향과 들어맞는다 추정.

새로 알게 된 것C. LM의 답은 세 단계로 걸러진 뒤 스팸 라벨과 0점으로 저장된다

  • LM 출력을 그대로 믿지 않고 3단계 안전장치로 거른다 확인.
    1. _drop_if_newest_reply_not_flagged는 LM이 지목한 인덱스 집합에 판정 대상(스레드 마지막 포스트)이 없으면 결과 전체를 버린다. Task 진입 조건이 "이 반응이 스팸일 수 있어야 파이프라인이 도는 것"이므로, 마지막 반응을 스팸이 아니라고 본 결과는 정합성 위반이다.
    2. _drop_other_author_posts는 LM이 스레드의 다른 저자 포스트를 스팸으로 지목하면 그 포스트를 뺀다. 이 파이프라인의 대상이 "같은 저자가 자기 답글에 자기가 답한 chain"이므로, 다른 저자의 포스트가 결과에 나오면 무시한다.
    3. _drop_singleton은 결과가 정확히 1개면 버린다. chain 스팸은 정의상 "여러 후속 답글"이 대상이어서, 하나만 잡힌 결과는 유효하지 않다.
  • 저장 태스크는 걸러진 결과에서 지목된 포스트마다 스팸 라벨을 붙이고, 답글 랭킹 점수를 0.0으로 강제 저장한다 확인.
    • 태스크 이름은 TaskWriteMultiStepReplySpamReplyRanking이다.
    • 지목된 각 포스트에 _apply_reply_spam_label(post_id, author_id)를 적용한다. 단발성 판정과 같은 헬퍼다.
    • save_reply_ranking_score(..., ReplyRankingScore(score=0.0, reasoning=reasoning[-500:]))로 점수를 0.0으로 강제 저장한다. 가장 낮은 신뢰를 뜻한다. reasoning은 마지막 500자만 남긴다.
    • save_reply_ranking_kafka_v2(...)로 v2 Kafka에 emit한다.
    • DISABLE_RULES = [DisableTaskForNonProd]로 dev와 staging에서는 실제 label을 붙이지 않는다.

정본 반영 services/x.md에 "4세대+15 공개로 해소된 것 / 신규 (2026-09-04)" 절을 새로 만들었다. "Grox (LLM 주석)" 아래에는 새 소절 ### 4세대+15 (2026-09-04, 9b0dc31) — grox 스레드 단위 multi-step reply spam 분류기 신설 + PTOS ...을 추가했다. 헤더의 최종 갱신은 2026-09-04에서 2026-09-05로 올렸고, 출처 절에도 새 파일 6개의 링크를 추가했다.

의미 grox의 답글 스팸 판정에 세 번째 축이 붙었다. 한 저자가 자기 답글 chain으로 root 노출을 훔치는 시간축 담합 스팸이다.

  • 정본의 이전 판은 두 흐름을 알았다. 답글 스팸은 개별 답글을 대상으로 판정하고, coordinated_spam은 "여러 계정이 담합한 반복 답글"을 대상으로 한다. coordinated_spam이 계정 담합 축이라면 multi-step은 시간축 chain 담합이다.
  • 게이팅 임계가 root 팔로워 1k로 낮게 잡히면서, 이 파이프라인은 root 저자의 노출 자산이 상당한 스레드에 광범위하게 도는 것으로 보인다. 그리고 판정을 Gemma에 맡겨 grok API 예산을 아끼는 방향과 들어맞는다.
  • 기존 정본의 grox reply_spam 이해와 부딪히지 않는다. 오히려 정본이 다뤄 온 단발성 판정의 follower ≥ 100k 임계가 유지되면서, 훨씬 낮은 임계(≥ 1k)의 chain 판정이 새 층으로 붙는 두 층 구조로 넓어진 것으로 이해할 수 있다.

2PTOS 심판 모델이 카테고리마다 갈린 첫 실체가 확인됐다 — X

자료 xai-org/x-algorithm@9b0dc31 — 같은 커밋(4세대+15)의 grox/flows/ptos/classifier.py와 grox/flows/ptos/task_safety_ptos_policy.py.

배경 grox의 PTOS(Policy-based ToS 위반) 판정 스택에는 4세대 동안 first-pass 분류기 위에 심판(cross-validator) 계층이 차츰 붙어 왔다.

  • 4세대+2(2026-08-17, b089ce6)에서 성인 콘텐츠 disagreement 심판이 도입됐다. 이름은 SafetyPtosAdultContentCrossValidationJudge이고, 모델은 Grok 4.5 internal이었다.
  • 4세대+4~+6(2026-08-19~21)에서는 Grok 4.6 internal shadow가 10% → 30% → 100%로 늘며 4일 만에 primary를 대체했고, 4.5 internal은 코드에서 완전히 삭제됐다.
  • 4세대+7(2026-08-24, d011592)에서는 다른 4.5 엔드포인트인 EAPI_GROK_4_5_X_ALGO가 judge 전용으로 다시 들어오면서 SafetyPtosPolicyCrossValidator가 새로 생겼다. 이 심판은 ChildSafety, ViolentMedia, IllegalAndRegulatedBehaviors 3개 카테고리를 모두 단일 모델(4.5-X_ALGO)로 처리했다.
  • 정본은 이 상태를 "X는 primary(4.6-internal)와 judge(4.5-X_ALGO)를 서로 다른 모델 세대·튜닝으로 유지하는 이중 스택"이라고 요약했다. 그리고 심판 스택의 카테고리별 모델 분화가 다음 관측 포인트가 될 것이라고 남겨 뒀다.

이번 커밋에서 그 분화가 첫 실체로 확인됐다.

새로 알게 된 것A. IllegalAndRegulatedBehaviors 심판만 Grok 4.5에서 4.1-fast로 옮겨 갔다

  • 심판이 쓸 모델로 Grok 4.1-fast-X_ALGO가 새로 등록됐다 확인 — grox/flows/ptos/classifier.py.

    • 모델 이름은 EAPI_GROK_4_1_FAST_X_ALGO다.
    • SafetyPtosPolicyCrossValidator.__init__이 4.5-X_ALGO sampler 옆에 4.1-fast-X_ALGO sampler를 나란히 초기화한다.

    — grox/flows/ptos/classifier.py, 2026-09-04

  • IllegalAndRegulatedBehaviors 카테고리의 심판만 4.1-fast로 옮겨 갔다 확인.

    • 바뀐 함수는 _validate_illegal_and_regulated_behaviors다.

    — grox/flows/ptos/classifier.py, 2026-09-04

    • 서킷브레이커 guard도 사라졌다. 4.5-X_ALGO는 _eapi_4_5_x_algo_breaker로 감싸 호출했지만, 4.1-fast는 breaker 없이 직접 호출한다.
