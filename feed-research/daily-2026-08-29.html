    1-B. VF 안전-라벨 twemcache 미스에 대한 sampled async 워머

    visibility-filtering/safety_label_source/에 새 파일 warmer.rs(203줄)가 생겼고, 그 옆의 lookup.rs는 twemcache miss ID를 워머로 fire-and-forget 방식으로 흘려보내도록 배선됐다 [확인] — visibility-filtering/safety_label_source/warmer.rs, visibility-filtering/safety_label_source/lookup.rs.

    배경 정리 — VF는 매 요청마다 후보 수십~수백 tweet의 안전 라벨(visibility/baseTweetSafetyLabelMap Strato 컬럼)을 조회해서 3-tier 정책(base_home_rules() 28개 + OON 추가 26개 = 54 규칙)으로 Allow / Interstitial / Drop을 판정한다. 앞단에는 twemcache가 look-aside cache로 걸려 있고, miss가 나면 Manhattan으로 폴백한다. 이 조회의 hit rate가 VF P99 지연을 좌우하는 핵심 변수다.

    동작 흐름:

    1. RemoteSource::get(ids)가 twemcache 결과를 네 종류로 나눈다. Hit, NotFound(정의상 존재하지 않음), Miss(cache가 이 키를 모름), FallThrough(reason)(cache 에러나 타임아웃)이다. Miss인 경우에만 별도 벡터 warm_ids에 모은다. NotFound는 정의상 라벨이 없는 트윗이라 워머 대상이 아니고, FallThrough는 캐시 인프라 문제라 워머로 해소할 성격이 아니다. 이 3분법이 워머 도입의 원칙이다. 워머는 "캐시가 아직 채워지지 않은 상태"만 해소한다.
    2. Manhattan 폴백 요청이 나가기 전에 warmer.warm(warm_ids)를 fire-and-forget으로 호출한다. 요청 응답 지연에는 영향을 주지 않는다.
    3. SampledWarmer가 VF_CACHE_WARM_SAMPLE_PCT 환경변수(0–100, panic on out-of-range)로 확률 샘플링을 하고, 통과한 ID만 tokio mpsc::channel bounded queue(용량 1024)에 try_send한다. 채널이 가득 차서 실패하면 WarmKeyResult::DroppedChannelFull 카운터만 올리고 요청 처리를 계속한다. 워머 채널이 포화되더라도 요청 경로에는 backpressure가 절대 걸리지 않도록 설계했다.
    4. 백그라운드 drain 태스크가 큐에서 벡터를 pop한 뒤, 500ms linger 동안 뒤따라 오는 벡터를 합쳐 최대 50 ID까지 한 배치로 묶고, StratoWarmFetcher::fetch(chunk)로 Strato에 batch_call을 보낸다(WARM_COLUMN_PATH = "visibility/baseTweetSafetyLabelMap"). Strato가 write-back한 결과가 twemcache에 채워진다. 다만 warmer 코드가 fetch 응답을 직접 twemcache에 쓰지는 않으므로, 별도의 read-through 캐시 계층이 있는 것으로 추정한다 [추정].

    관측 카운터 record_cache_warm_keys(result, count)가 6종 outcome을 남긴다. EligibleMiss (miss로 워머 대상이 된 총량이며 샘플링 이전 수치다) · SampledOut · Enqueued · DroppedChannelFull · FetchIssued · FetchFailed이다. 이 6종으로 워머의 단계별 통과율과 병목을 관측한다. 예를 들어 FetchFailed / FetchIssued가 높으면 Strato 인프라 문제이고, DroppedChannelFull이 계속 발생하면 채널 용량(1024)이 부족한 것이다.

    같은 파일에서 config 정리 3건 — VF_GIZMODUCK_CLIENT_ID·VF_TWEMCACHE_CLIENT_NAME·APP_ENV 3개 env를 새로 만들었다. gizmoduck_client_id()는 설정된 값이 없으면 visibility-filtering-service.{APP_ENV|prod} 템플릿으로 값을 자동 조립한다. VF가 dark_traffic으로 staging에서 돌 때 staging용 gizmoduck 쿼터와 레이트리밋을 프로덕션과 분리하려는 목적으로 추정한다 [추정].

    정본 반영 ../services/x.md 안전성/visibility-filtering 절에 4세대+10 subsection을 추가했다. 워머 흐름과 bounded 채널 원칙, 6종 metric, config 정리를 담았다.

    의미 twemcache miss가 나는 경우는 두 가지다. (a) 트윗이 아직 어떤 라벨링도 받지 못한 신선한 상태여서 캐시는 물론 라벨도 없는 경우와 (b) TTL이 만료됐거나 evict되어 캐시만 비어 있는 경우다. 이 워머는 특히 (b), 즉 Manhattan에는 라벨이 있는데 캐시가 놓쳐서 매 요청마다 Manhattan을 때리는 낭비를 해소한다. sample-pct 게이트를 둬서 트래픽이 급증해도 워머 자체가 Strato 폭주를 유발하지 않도록 설계했다. VF_CACHE_WARM_SAMPLE_PCT를 낮게 시작해 점진적으로 올리는 dial-up 롤아웃도 가능한데, 4세대의 다른 dial-up 패턴(Grok 4.6 10%→30%→100%, 4세대+4→+5→+6)과 유사한 관행이다. VF의 요청 경로에 새 계층이 열린 것은 아니고 하부 인프라 최적화에 해당한다. 규칙 판정(3-tier / 54 규칙)은 그대로다.

    1-C. Phoenix trainer가 restore_streamed를 실제로 소비

    4세대+9(2026-08-26)에 도입된 load_checkpoint_streamed가 스캐폴딩만 배선된 상태였는데, 이 커밋에서 Trainer.maybe_load_checkpoint가 실제 소비자로 붙었다 [확인] — phoenix/xrex/train/trainer.py:1177-1330, phoenix/python/training/xai-checkpointing/xai_checkpointing/load.py.

    활성 조건은 세 가지가 모두 참일 때다. restore_streamed=True이고, format == "orbax"이며, save_method != "tensorstore"여야 한다. 하나라도 맞지 않으면 로그를 남기고 기존 load_checkpoint(전량 pinned-host 스테이지) 경로로 폴백한다. 즉 config를 잘못 설정했거나 orbax가 아닌 checkpoint(tensorstore 등)를 만나면 안전한 기본 경로로 fall-through하므로, 하위 호환이 유지된다.

    use_streamed_restore=True 경로는 그 자체로 checkpointing_load.copy_aliased_arrays(self.state)를 호출해 aliased state leaves를 미리 분리한다. 새 함수 _graft_replaced(pairs)는 loaded tensor를 원래 state tree의 자리에 in-place로 grafting하는데, aliased leaf가 두 자리에 걸쳐 있으면 어느 슬롯에 넣을지 모호해지므로 조기에 assertion으로 막는다(restore_streamed does not support aliased state leaves: multiple loaded tensors share one device array).

    load_checkpoint_streamed가 받는 새 인자 두 개도 이 커밋에서 라우팅됐다. window_gb는 해당 배치의 pinned-host 예산이고 None이면 auto-window로 동작하며, on_replaced 콜백은 완료된 배치의 old/new device array pair 리스트를 받아 호출자가 state tree에 grafting하도록 한다. window_cap_gb는 window_gb가 명시되지 않았을 때만 restore_concurrent_gb 값으로 세팅되는 안전벨트다. 이전 API의 concurrent_gb를 streamed 경로에서 window cap 상한으로 재활용했다.

    이 흐름의 핵심은 pinned-host에 optimizer state 사본을 만들지 않고, tensor를 하나씩 device로 옮긴 뒤 원래 참조 자리에 grafting하는 것이다. warm_start 케이스(pretrained params를 로드하고 opt state는 새로 만드는 경우)에서 특히 이득이 크다. 기존 do_not_load_opt_state=True 경로가 warm_purge(self.state)로 opt state 필드를 미리 잘라내고, streamed 경로에서는 host_state를 None으로 둔 채 loaded params만 grafting하기 때문에 opt state의 pinned-host 사본이 아예 생성되지 않는다. 4세대+6·+7의 Muon+GB300 flagship이 pretrained 파라미터에 새 optimizer를 붙여 시작하는 표준 흐름을, 이제 checkpoint stack이 원자적으로 지원하게 됐다.

    1-D. Phoenix gRPC compression 트레일러 유실 버그픽스 + zstd encode 시간 히스토그램

    GrpcCompressionService가 응답 본문을 zstd로 압축할 때, 이전 로직은 collected.to_bytes()로 body만 뽑아 새 axum::body::Body::from(data)로 다시 감쌌다. 이 과정에서 gRPC trailers(특히 grpc-status·grpc-message)가 통째로 유실됐다 [확인] — phoenix/crates/serving/xai-recsys-engine/src/grpc_compression.rs.

    gRPC 프레임은 body 뒤에 trailer로 상태 코드를 실어 보내는 구조인데, 그 부분이 버려진 것이다. 클라이언트 쪽에서는 응답이 정상으로 도착하면서도 status trailer가 없어 UNKNOWN이나 EOF로 처리됐을 가능성이 있고, 그렇다면 재시도 로직과 에러 로깅, 서킷브레이커가 모두 오작동했을 것이다. 새 코드는 collected.trailers().cloned()로 trailer를 미리 뽑아 두고, rebuild_response(parts, data, trailers) 헬퍼가 Full::new(data).with_trailers(async move { Some(Ok(tr)) })로 트레일러를 다시 붙인 뒤 응답 본문을 구성한다. 압축에 성공하든 실패하든 트레일러가 유지되도록 통일했다.

    회귀 테스트 두 개(compressed_response_forwards_trailers, non_compressed_response_forwards_trailers)로 이 동작을 명시했다. 이 두 테스트가 남아 있는 한, 나중에 비슷한 리팩터링으로 trailer가 다시 새면 CI가 잡아낸다.

    같은 파일에 새 히스토그램 **recsys_engine_response_compress_ms{method}**을 배선했다. tokio::task::spawn_blocking(compress_grpc_frame)에 들어가기 직전에 Instant::now()를 찍고, 완료된 뒤 elapsed().as_secs_f64() * 1000.0으로 관측한다. 즉 zstd 인코딩의 큐잉 시간과 CPU 시간을 method별로 나눠 볼 수 있다. buckets는 request latency 버킷과 공유한다(crate::request_metrics::latency_buckets_ms()).

    30건을 훑어서 수용 기준(플랫폼 기업 저자 / 프로덕션·A/B / 메커니즘 신규성 / 스케일)을 넘긴 것은 하나뿐이다. 나머지 29건은 순수 학술 증분이거나, 도메인이 한정되어 있거나, 프로덕션 진술이 없어서 탈락했다.

    자료 Scaling Graph Neural Networks for Friend Recommendation: Multi-Hash User Embeddings and Temporal Neighbor Sampling — arXiv 2608.27413, 2026-08-27 v1, CIKM 2026 accepted. 저자는 3명(Maksim Utushkin·Andrei Ovsiannikov·Alexander D'yakonov)이다. arXiv abstract 페이지에 소속이 표기되어 있지 않지만, 본문에서 참조하는 그래프 규모와 러시아어 저자명을 함께 놓고 보면 VK(러시아의 대형 소셜 네트워크)로 추정한다 [추정].

    배경 친구 추천(social platform의 People You May Know / Suggested Friends)은 유저 속성(관심사·나이·위치)보다 다중 홉 소셜 컨텍스트(친구의 친구, 공통 친구 수)가 관련성의 주된 신호다. 그래서 GNN(Graph Neural Network — 노드가 자기 이웃의 임베딩을 aggregate해서 자기 임베딩을 갱신하는 message-passing 모델)이 자연스러운 프레임워크가 된다. 다만 프로덕션 소셜 그래프는 수억 유저와 수백억 엣지 규모라, (a) 유저 ID 임베딩 테이블이 폭발하고 (b) 슈퍼노드(팔로우 수가 극단적으로 많은 계정)의 이웃 순회가 O(deg) 비용으로 병목이 된다. 이 논문은 이 두 시스템 문제를 정면으로 푼다.

    새로 알게 된 것

    • Multi-hash user embeddings로 ID 임베딩 테이블을 98% 이상 축소 [확인] — 각 유저 ID를 여러 해시 함수의 임베딩 lookup 조합으로 표현한다. hash collision은 감수하되 ranking quality는 유지한다. 원문
    • Temporal neighbor sampling — timestamp-sorted CSR(Compressed Sparse Row — 그래프 저장의 표준 자료구조로, 인접 리스트를 하나의 큰 array와 offset array로 압축한다) 저장과 binary search를 결합해 이웃 샘플링을 O(deg(v) + k)에서 O(log(deg(v)) + k) 로 단축했다 [확인]. 즉 팔로우 수가 큰 노드도 이웃 순회 비용이 로그 시간에 그친다.
    • 프로덕션 소셜 그래프의 규모는 194M users · 28B edges다 [확인].
    • Strong production baseline 대비 온라인 지표는 **friend additions from recommendations +16%, unique friend adders +11.5%**다 [확인].

    "On a graph with 194M users and 28B edges, our system increases friend additions from recommendations by 16 percent and unique friend adders by 11.5 percent over a strong production baseline." — arXiv 2608.27413 abstract, 2026-08-27

    레이더 반영 radar.md의 "이번 달 신규"에 새 항목으로 추가했다. LLM-native나 스케일링 법칙 흐름에는 걸리지 않지만, 명시적 그래프 도메인에서 GNN이 여전히 살아남는 사례로서 Meta ConnectionMind(그래프 위에서 LLM으로 경로를 추론하는 모델)와 대조하는 역할을 한다.

    의미 strong prod baseline 대비 두 자릿수 uplift(+16%)는 GNN 논문에서 드물다. GNN이 실무에서 결국 살아남는 도메인은 완전히 명시적인 그래프(친구 그래프, follow 그래프)라는 관찰이 강화된다. Meta ConnectionMind가 LLM으로 그래프 경로 추론을 시도하는 것과는 방향이 다르다. VK는 순수 GNN을 소셜 그래프의 스케일 한계까지 밀어붙였다. Multi-hash 임베딩 -98% 축소는 embedding table 크기가 서빙 인프라의 핵심 제약이라는 X SimClusters의 관측과도 방향이 같다. 서빙 지연을 늘리지 않고 적용했다는 진술은 abstract에 없지만, 두 최적화의 목적이 정확히 그것이다(테이블 축소와 이웃 순회의 로그화). 다음 관찰 포인트는 CIKM 2026(10월) 발표에서 소속과 인프라 세부가 추가로 공개되는지, 그리고 LinkedIn People You May Know와 Facebook People You May Know의 GNN 갱신 진술이 나오는지다.
