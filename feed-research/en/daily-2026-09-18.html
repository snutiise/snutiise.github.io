1A holdout filter that removes some popular posts per viewer was added — X

Source xai-org/x-algorithm@42266f3 — source code, 2026-09-17 05:09Z, GitHub commit. 64 files changed (+2288/−3627). These notes number X commits after the Gen4 release in sequence, and this commit is Gen4+23.

Background The 64 files are more than double Gen4+22 (26 files), and the 3627 deleted lines far exceed the 2288 added lines. VF (visibility-filtering) is the service that decides, per post, whether it may be shown to this viewer. Most of the large deletion came from the removal of the VF sub-repo's own twemcache client folder (3,234 lines) in full. This commit put three kinds of changes together into the ranking and filter stack of home-mixer (the service that receives For You and Following feed requests).

What we learnedA. A filter that removes a fixed share of popular posts per viewer was added at the end of the pipeline

A completely new filter was attached at the end of the home-mixer pipeline. This filter, which drops candidates, is named FavHoldoutFilter. It maps fav_count (a post's cumulative favorite count) to a holdout probability in steps. Through user-post deterministic hashing, it removes only a fixed share of popular posts per viewer.

  • Added a new filter FavHoldoutFilter to home-mixer that sets the holdout probability by fav count step verified — home-mixer/filters/fav_holdout_filter.rs (166 lines, new).

    • The filter is wired in home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs right after InventoryHoldoutFilter. It is the last slot of the Gen4 filter list.

    • The decision function is the following step table:

    • The share is 15% when fav_count exceeds 10,000, 15% above 5,000, 14% above 2,000, 13% above 1,000, 12% above 750, 11% above 500, 7% above 100, 5% above 20, ..., 3% above 2, and 2% above 1.

    • If fav_count is 1 or less, the share is 0%, and all viewers always see the post.

    • The holdout decision reuses InventoryHoldoutFilter::is_held_out(post_id, viewer_id, percent).

    • This function computes a 100-modular bucket for the (post_id, viewer_id) pair with a splitmix64-family double-mixing hash, and holds the post out if the bucket is below percent.

    • That is, the same user deterministically holds out the same post, and even for the same post, only a different subset is held out for each viewer.

    • The default param of FavHoldoutFilter is EnableFavHoldout = false. The param is defined as rust_home_mixer_enable_fav_holdout in home-mixer/params/param.rs.

What we learnedB. Three ratio params that the existing inventory holdout filter uses by post type were confirmed

  • The 3-tier holdout ratio params of the inventory holdout filter were confirmed verified — home-mixer/filters/inventory_holdout_filter.rs.
    • The filter is named InventoryHoldoutFilter. This resolves a long-standing undisclosed item.
    • The filter file references three params: InventoryHoldoutOriginalsPercent, InventoryHoldoutRepliesPercent and InventoryHoldoutRetweetsPercent.
    • Post type is determined as retweeted_tweet_id.is_some() → Retweet, in_reply_to_tweet_id.is_some() → Reply, and otherwise → Original. A quoted post is treated as Original.
    • Each of the three values is clamped with .min(100).
    • The filter is active only when EnableInventoryHoldout=true AND at least one of the three values is >0.
    • The holdout target is hashed deterministically on get_original_tweet_id() (the original for a retweet, otherwise the post itself). In other words, a retweet shares the same holdout decision as the original.

What we learnedC. The click-dwell ranking term can now use the product of dwell and click probability instead of the low-fav penalty

In ranking scoring, the term that adjusted the dwell prediction by the fav rate was deleted, and a much simpler gate took its place. What was deleted is the previously introduced EnableClickDwellLowFavRatePenalty logic, a term that adjusted the dwell prediction as (fav/baseline)^alpha by multiplying four tuning parameters. When the new gate EnableCdwellOnImpr is on, the click_dwell_time prediction is multiplied by the click probability (dwell × click). Since the click_dwell head has been a binary classification probability since the 2026-09-16 commit (Gen4+22), this product is a per-impression probability, not seconds.

Why it matters Three kinds of changes came together in this commit: the popular-post holdout, the redefinition of the click_dwell term, and the relaxed cold-start gates. A change in the Phoenix proto adds a fourth layer on top.

  • First, home-mixer ranking gained a new axis: a per-viewer deterministic holdout of popular posts.
    • Where InventoryHoldoutFilter was a 3-tier holdout by type (original, reply, retweet), FavHoldoutFilter is a 23-tier step holdout by popularity (fav count).
    • The two filters are each deterministic for a viewer-post pair but make independent decisions. So home-mixer can now run two kinds of counterfactual holdout experiments in parallel, at a stage still before scoring.
    • One is a uniform holdout by post type, and the other is a stepped holdout by popularity.
    • Why a popularity holdout? If 15% of posts with 10K+ fav are held out, it becomes possible to observe how those viewers respond to the next-best candidate without that post.
    • That is, infrastructure opens up to capture, through a measured experiment, the marginal contribution of top popular posts (the user loss when this post disappears from Home).
    • Paired with the three-stage response diversity observation side effect in Gen4+21, X's ranking measurement infrastructure is expanding along two axes: diversity as a set-level counterfactual and holdout as a post-level counterfactual inferred.
    • If the diversity statistics observation in Gen4+21 observes slate (the bundle of candidates shown at once) composition without an A/B experiment, the holdout filter runs an A/B experiment automatically inside the filter.
  • Second, the definition of the click_dwell ranking term changed completely.
    • The former EnableClickDwellLowFavRatePenalty was a heuristic penalty that lowered the dwell prediction of low-fav-rate posts by (fav/baseline)^alpha, to suppress misjudgment based only on inflated dwell.
    • In Gen4+22, as the click_dwell head changed to sigmoid BCE binary classification, the effective scale of the head had been reduced 60×.
    • This commit cleaned up by removing the fav-based penalty (four tuning params and the corresponding fields were deleted).
    • EnableCdwellOnImpr, which took its place, is an alternative approach. It multiplies the click_dwell prediction (dwell probability or time given a click) by the click probability to convert it into a per-impression expected value.
    • Since this redefinition multiplies the signals of two heads, it reduces the problem of the "dwell-raising head" and the "click-raising head" offsetting each other or double counting.
    • This redefinition aligns with the practice of Netflix N-tower and YouTube ranker. They have long trained the dwell head as a conditional probability (P(dwell|click)) and then multiplied it by P(click) in serving to produce an unconditional expected value.
    • ⚠ Claim changed: Yesterday's (2026-09-17) canon described "the effective contribution of the click_dwell_time head as reduced by ~60× from before". However, if this head is redefined as a product with click_score while ContClickDwellTimeWeight is not adjusted, the effective scale changes again.
      • More precisely, there are two cases. If EnableCdwellOnImpr=false (default), the 60× reduction is maintained.
      • When it is on, the term becomes a product of probabilities (0-1 × 0-1). The previous term multiplied the click_dwell value by a fav-rate multiplier (with the gate off, the click_dwell value as is), and there was no term multiplying by click probability verified — ranking_scorer.rs diff.
      • If the absolute weight is maintained, the effective scale could go to a much larger reduction rather than a 60× reduction, and the ranking contribution of this head could effectively be absorbed by the remaining heads.
      • Whether it is actually deployed would be observed in whether the EnableCdwellOnImpr mirror is switched in the next commit and ContClickDwellTimeWeight is retuned inferred.
  • Third, two gates on the Treatment arm of the cold-start scorer were relaxed together.
    • The removal of the is_phoenix_moe requirement means cold-start targets are now activated in the Treatment experiment without an MoE label.
    • This gate, created in the 2026-09-04 commit (Gen4+16), was an experiment condition limiting the Phoenix MoE head to be used in training only for cold-start candidates; relaxing it presumably requires a judgment that the measured results showed the condition was unnecessary or even a loss inferred.
    • The expansion of max age from 24h to 48h means the new-author boost window doubled. Since this cap applies to post age, not author tenure, posts within 48 hours of creation also become cold-start targets.
    • In the Treatment arm, both changes increase cold-start volume. In contrast, the Control and Holdout arms, which had no cap, newly get a 48-hour cap, so their condition actually tightened verified — the author_cold_start.rs diff in D above.
  • As the fourth layer, the two Phoenix proto changes indicate how future ranking signals will be organized.
    • The vacating of the two LLM_JUDGE_* labels after five days is a signal that xAI has, for now, folded its direction of transplanting LLM judge labels as a separate axis into search relevance ranking training.
    • There are two possibilities. The judgment may have been routed in another way (e.g., reusing the existing CLIENT_TWEET_RELEVANT_TO_SEARCH=105 label channel as is), or the label axis itself may have been left waiting for redefinition.
    • The newly added CLIENT_TWEET_LIVE_STREAM_REPLY (107) appears to be a client signal for live-stream replies; we need to watch whether the next commit folds it into the training signals.
    • The 3-tier expansion of delayed conversion attribution is the most solid ads-infrastructure link in this commit.
    • If the ads conversion observation window had two kinds so far, "immediate" and "delayed", delayed is now split into tier 2 and tier 3 as well, and each observation lag is routed to a separate head.
    • This matches the standard approach in the literature (Chapelle 2014, Yasui & Sakata 2020 family), where delayed training applies per-lag masks to reduce lag bias inferred.
    • Read together with the ADS_WEB_CT_PURCHASE_VALUE Huber ratio loss formally wired in Gen4+22, X's ads training stack is moving toward value regression and per-lag delayed heads.
  • The VF twemcache removal and the evaluate_tweets RPC expansion are not on the ranking axis, but they are worth observing.
    • VF began expanding its client → server response from a sigil enum to a full Thrift Action object.
    • If this direction continues, home-mixer may consume richer policy verdicts where it has so far consumed VF responses only as FilteredReason.
  • The introduction of the UTH label reproduction job stack is infrastructure for the daily recomputation of audit labels for the Under-the-Hood transparency tool that X announced.
    • This line serves a user audit tool rather than ranking, so it is not a candidate for a canon update. However, it is meaningful that it sits in the same repo as the ranking code in the repository's file layout.
    • It leaves the intent that X keeps, in the same repository as ranking and safety, a line that lets users look up directly "why was my post treated this way."
