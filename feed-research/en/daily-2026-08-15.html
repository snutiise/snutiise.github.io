1X released ranking weights and a safety verdict pipeline in Gen4 code — X

Source xai-org/x-algorithm @ 47c1bcd — "Open-source X Recommendation Algorithm" — xai-org public repository, commit of 2026-08-13 17:09 UTC, public source code. These notes call this release public-source Gen4. A commit that tidied .gitattributes, a389166, followed. One commit changed +363,246 / −11,640 lines. The files number more than 300 in total; because of the GitHub API pagination limit, the exact file count was reconstructed from the tree. The main evidence documents are README.md #latest-update--august-13th-2026 and docs/BIDIRECTIONAL_BOOST_CHANGE.md. The main code files are home-mixer/params/param.rs and visibility-filtering/rules/registry.rs.

Background For the past 3 months, this repository's services/x.md has kept "public-source Gen3" as the canon. The three generations are:

  • 2023 Scala first release
  • 2025 Scala refresh: c54bec0, introduced tweet-mixer
  • 2026 Rust rewrite: aaa167b·e414c17·0bfc279, 216 files in total

The canon had two especially empty sections:

  • First, weights. It was confirmed that the objective function is a weighted sum, but the actual values appeared in none of the three generations.
    • In the 2026 Rust code, the crate::params module itself was missing from the repo, so symbols such as FavoriteWeight appeared only at call sites and no definition could be found.
    • The widely quoted "reply 13.5 / good_profile_click 12.0 / report −369" table comes from a single 2023-04-05 snapshot. Even that document carried the author's own caveat that it "may differ slightly from production".
  • Second, the safety family, that is, the visibility-filtering and labeling pipelines.
    • The home-mixer code applied VFFilter and AncillaryVFFilter as fail-closed, but who attaches the labels those filters consult, and when and how, was a complete black box.
    • The grox/ (nearline content classifier) sub-repo had been released only partially, as an annotation pipeline skeleton.
    • Account-level judgments, PageRank, inauthentic behavior detection, NSFW media classification, the rule engine, and the enforcement service were not even mentioned.

This commit overturned both sections: the new README opens with an item saying it added key configuration parameters, including weights: "Adds key configuration parameters (including weights used to blend predicted action values into a score for a post)". Accordingly, 1084 lines of home-mixer/params/param.rs were newly added; together with the following item "Adds code for systems that impact whether a post is filtered from the For You feed", 15 or more subsystems were introduced. Phoenix (X's Grok-based Transformer recommendation model) also received training code, a synthetic data generator, and a QUICKSTART, so it can be run end-to-end. The new SimClusters sub-repo is wired in as an OON (out-of-network, accounts the viewer does not follow) retrieval source of home-mixer.

This note reads the character of this release as having shifted from "showing the shape of the logic" to "presenting values and rules in a verifiable form" inferred; this assessment is not in the README or the commit message (the single line "Open-source X Recommendation Algorithm"). The basis is that caveat list #1 of the Gen3 canon (services/x.md at this repository's e65f30f) wrote "what was released is the shape of the logic; the values and wiring were missing", and this release filled in those missing values. Paired with this, x.com/i/under_the_hood, an account-level label transparency tool, was released as a pilot. According to the new README's claim, users can look up the visibility labels attached to their account and posts, and the tool is designed so they can check those labels against this repo's code to see why they were treated that way.

What we learnedA. The weights are real values in a mirror file that carries production defaults

The numbers in the newly released weights file are not "examples" or "demo defaults"; they are a mirror that a cron job builds by pushing production primary values every day. The upper bound on accuracy is the last sync time, 2026-08-12 04:09 UTC. Representative values are reply 5.0, favorite 0.5, report −234, and share via copy link 20.0 verified.

home-mixer/params/param.rs holds the production defaults stated in the code. The comment in the file header defines the nature of this file precisely.

// mirrored from config feature-switch defaults; last sync 2026-08-12T04:09:22Z — home-mixer/params/param.rs:1

The new README's "Experiments and Configuration" section states the meaning of this mirroring as follows:

"To help people understand the production defaults, we run cron scripts that set the defaults in this repository's code to be the primary production values, for example in home-mixer/params/param.rs." — README.md #experiments-and-configuration

The weights reflect both the value an action has in ranking and the frequency (propensity) with which that action typically occurs on the network verified. The three comment lines directly above the weight block say so, and they do not write the formula for combining the two factors.

"These weights reflect a combination of how much an action is valued in ranking and typical propensities of these actions across the X network (e.g. negative feedback is overall rare)." — home-mixer/params/param.rs:279-281

This note reads the magnitude of report −234 not as the "relative importance of one report" but as the product value × 1/propensity inferred. The basis for thinking the absolute value is large because reports are so rare is "negative feedback is overall rare" in the comment.

What we learnedB. The OON multiplier, diversity, and VMRanker constants were all released too

The OON multiplier, diversity, and VMRanker (a remote service that reorders the candidate bundle to send to the feed) constants, which the canon had long recorded as "all four values undisclosed", have all been released.

  • The decay factor multiplied into OON posts equals the value in the 2023-04-05 snapshot verified.
    • OonWeightFactor = 0.75, and the snapshot's out_of_network_scale_factor is also 0.75.
  • For topic requests, the OON decay is applied more strictly verified.
    • TopicOonWeightFactor = 0.5
  • The new-user routing threshold is 0 seconds verified. A threshold of 0 seconds means that this code path is effectively mirrored as inactive inferred.
    • NewUserAgeThresholdSecs = 0
  • Author-diversity decay is on, and the decay rate and floor values were released verified.
    • AuthorDiversityDecay = 0.5, AuthorDiversityFloor = 0.25, EnableAuthorDiversity = true
    • The 2nd post by the same author is multiplied by (1−0.25)·0.5¹+0.25=0.625, and the kth post by (1−0.25)·0.5ᵏ⁻¹+0.25.
    • The exponent in the code is the number of earlier posts by the same author, and the first post is 0 verified — home-mixer/scorers/ranking_scorer.rs:614-665.
  • VMRanker is on, uses DPP (a selection technique that prevents mutually similar candidates from being picked together), and has no fallback verified. Therefore the canon's observation that on failure it is silently skipped as fail-open remains valid.
    • This is a direct answer to the canon's open question "Is VMRanker/DPP on?".
    • VMRankerDppTheta = 0.65, VMRankerDppMaxSelectedRank = 150, EnableVMRanker = true
    • VMRankerValueModelId = "dpp", VMRankerClusterId = "Experiment3", VMRankerEnableFallback = false
  • The legacy tweet-mixer is mirrored as off by default, and SimClusters replaces it verified.
    • Maximum results per source: PhoenixMaxResults = 1000, ThunderMaxResults = 1200, TweetMixerMaxResults = 800
    • Source switches: EnableTweetMixerSource = false, EnableSimclustersSource = true, EnablePhoenixSource = true
  • Shadow traffic of 30% flows to the new Phoenix cluster by default verified.
    • ShadowTrafficDefaultPercent = 0.3
  • The point where the canon recorded "no mechanism for new items" is actually defined by an impression threshold verified.
    • ColdStartImpressionThreshold = 1000
    • A post with fewer than 1000 impressions is classified as a "new author/post" and boosted by PostUnexploredWeight in C below.

What we learnedC. There are three score adjustment factors, and the third, absent from the canon, is the new-author boost

The new README states three scoring adjustment factors explicitly verified. The third, the New-Author Boost, lifts posts from authors whose impressions are below the threshold toward a target position verified. The three factors are written in the README.md #scoring-and-ranking section as follows:

"Author Diversity ... Out-of-Network Discount ... New-Author Boost: posts from authors whose impressions are below a threshold are lifted toward a target position." — README.md #scoring-and-ranking

The canon had recorded only two adjustment factors:

  1. Author-diversity decay
  2. OON multiplier

A third one, the new-author boost, is added to these.

  • By default it is an additive boost; the multiplicative form is disabled; and it applies only in-network verified.
    • Definition in param.rs: PostUnexploredWeight = 0.02·PostUnexploredWeightInNetworkOnly = true
    • EnableMultiplicativePostUnexplored = false·MultiplicativePostUnexploredAlpha = 0.0
    • ColdStartImpressionThreshold = 1000

What we learnedD. SimClusters came back as a candidate source for posts from accounts the user does not follow

The candidate sources were reorganized into the following four:

  • Thunder (an in-network source that keeps recent posts from followed accounts in memory)
  • Phoenix retrieval
  • SimClusters
  • The legacy tweet-mixer, set to off by default

For a long time the canon recorded "SimClusters, TwHIN, UTEG/GraphJet, FRS, Earlybird, Lists, Communities — none of these names appear anywhere in home-mixer/"; of these, SimClusters was overturned. The new README describes the candidate sources as follows:

"In-Network thunder/ keeps recent posts from the accounts a viewer follows in memory · Out-of-Network phoenix/ retrieval and simclusters/ find posts from accounts the viewer does not follow" — README.md #overview

This README statement means that a SimClusters sub-repo is newly created and that the core algorithm of simclusters/ (2020 KDD) is included here. The core finds KnownFor communities not with SVD but with Sparse Binary Factorization based on Metropolis-Hastings verified — UpdateKnownForSBFRunner.scala:5-9.

  • This file imports com.twitter.sbf.core.MHAlgorithm and SparseBinaryMatrix verified. topics/embedding-retrieval.md also describes the same stage as Metropolis-Hastings community detection.

Confirming the details requires a deep dive into all of simclusters/.

What we learnedE. Filters increased, and there was also one filter the canon missed

Filters grew from 14 to 17 verified — README.md #filtering. Three filters were newly added, and one more filter that the canon missed is listed here.

  • OONRetweetReplyFilter filters out retweets and replies from accounts the user does not follow, as well as replies without a parent post. It is separate from the existing RetweetDeduplicationFilter verified (README).
  • OONNsfwSimclustersFilter drops posts from adult-content accounts that come from the SimClusters source for users who do not follow them. It was introduced alongside SimClusters verified (README).
  • NewUserMinEngagementFilter removes, from OON posts shown to new users, those below an engagement threshold verified (README).
    • The related params are NewUserMinEngagementThreshold, NewUserMinEngagementFilterMetric, NewUserMinEngagementFilterUseRatio, NewUserMinEngagementFilterMaxAccountAgeSecs, and NewUserMinEngagementFilterMaxResurrectionAgeSecs.
  • InventoryHoldoutFilter deterministically hashes user × post and holds out the configured share of inventory (sets it aside from impressions). It is a filter the canon missed and did not list verified (README).

The canon's observations, such as the no-op behavior of BackupFilter and the hardcoded supertopic in TopicIdsFilter, remain valid.

What we learnedG. Visibility rules apply 28 to following posts and 54 to recommended posts

The rules file of the visibility-filtering sub-repo defines three policies verified.

  • FilterAll drops everything verified.
  • TimelineHome is the default rule applied to following targets verified.
  • TimelineHomeRecommendations applies to recommendation targets and adds OON-only drops to the default rules verified.
  • The rules file is visibility-filtering/rules/registry.rs, and it is 912 lines verified.

There are 28 rules applied in common to following and recommendations verified. These rules in base_home_rules() run in the following order:

  • Account status: SUSPENDED_AUTHOR_DROP, DEACTIVATED_AUTHOR_DROP, ERASED_AUTHOR_DROP, OFFBOARDED_AUTHOR_DROP, ProtectedAuthorDropRule
  • Viewer relationship: ViewerBlocksAuthorRule, ViewerMutesAuthorRule, MutedRetweetsRule
  • Tweet labels: PDNA_DROP, BOUNCE_DROP, SPAM_DROP, FOR_EMERGENCY_USE_ONLY_DROP, FOSNR_HATEFUL_CONDUCT_DROP, FOSNR_VIOLENT_SPEECH_DROP, FOSNR_ABUSE_DROP, FOSNR_CIVIC_INTEGRITY_DROP
  • Tweet status: NullcastedTweetDropRule, DropStaleTweetsRule, DropLegalTakendownPostRule, DropLocalLawsTakendownPostRule
  • NSFW viewer gating: SensitiveViewerLoggedOutDropRule, SensitiveViewerUnderageDropRule, SensitiveViewerNoStatedAgeDropRule
  • Exclusive tweets: DropExclusiveTweetContentRule
  • NSFW interstitials (handling that leaves the post in the feed but overlays a warning screen): NSFW_HIGH_PRECISION_INTERSTITIAL, GORE_AND_VIOLENCE_INTERSTITIAL, NSFW_CARD_IMAGE_INTERSTITIAL, NsfwAuthorInterstitialRule

Recommended posts get the 28 above plus 26 OON-only rules, for 54 verified. The rules added by timeline_home_recommendations_policy() run in the following order:

  • 2 DMCA and geo-restricted media rules
  • 4 NSFW account rules
  • 9 rules for tweets carrying NSFW, violence, DoNotAmplify, and spam labels
  • 11 user-label rules related to NSFW, spam, impersonation, deactivated, and adult

This is the substance of the "different safety levels for in-network and OON" that the "Worth noting" bullet in the filter section of the canon (x.md) had already observed. Following users get only the 28 rules, and OON recommendations get 54. Evaluation is short-circuit, ending at the first drop verdict, and the OON-only rule group can issue only catch-up drops, with no interstitial or allow verdict (consistent with the same bullet in the canon).

We confirmed what the fail-closed bullet in the canon's filter section pointed to. The policy return value in visibility-filtering/rules/registry.rs is a Verdict struct, and the README states that interstitial is passed to UI handling and drop counts as actual filtering verified — README.md #labeling-path.

"interstitial ──► the post stays in the feed; nothing in this repository draws the interstitial"

What we learnedH. The roles of the subsystems that attach labels were officially documented for the first time

The new README organizes the label-attaching process as a 4-stage "Labeling Path". The stages run in the order Content Understanding → Labeling Rules → Storage → Visibility Filtering. The role of each subsystem was officially documented for the first time verified.

  • grox/: a nearline content classifier. It was already partially reflected in the canon.
  • media-model-proxy/: a proxy that serves image and video models (NSFW, violence/gore, hate symbols, topic classification, known-media matching).
  • clip/: trains CLIP image and text embedding models. They become the input to the media classifiers.
  • adult-content/: trains and calibrates the adult media classifier.
  • pnsfwmedia/: an adult media discriminator that combines CLIP embeddings with account scores.
  • agatha/: an offline batch. It attaches labels based on how other accounts reacted to this account's posts, using the ratio of favorites to blocks, reports, and spam reports.
  • bdsm/: extracts inauthentic/abusive signals from an account's time-series behavior sequence. It consists of Rust, proto, training, and tests subdirectories.
  • user-cred-v2/: runs PageRank over follow and engagement edges to produce an account credibility score.
  • scarecrow/: an event-reactive rule runner. It embeds botmaker/ as its rule engine.
  • botmaker/: holds the rule DSL, compiler, and runtime.
  • botmaker-rules/: the actual rules scarecrow loads. Some were not released, to prevent gaming.
  • abuse-enforcement-service/: decides account actions (labeling, challenge, suspension) based on model scores.
  • safety-label-user-agg/: aggregates the labels received by posts an account owns to the account level.
  • visibility-filtering-client/: the client library of the visibility-filtering service.
  • under-the-hood/: an account-level label transparency report builder. It consists of a daily batch and a serving-layer aggregation.

Of these 15, the subsystems other than grox had not been reflected in the canon by even one line until today.

What we learnedI. Only Phoenix can now be run from training to serving

The statement "the whole repo does not build" that the canon observed in "How to read the source — caveat list" #1 was partially resolved. Only Phoenix was shipped in a form that can run end-to-end through training and serving. The other crates still have undisclosed dependencies verified.

  • Examples of the remaining undisclosed dependencies are xai_service_runner and xai_kafka.
  • crate::params, crate::util, and crate::clients, which Gen3 lacked, were released this time together with their files verified — home-mixer/lib.rs.
    • lib.rs declares pub mod params;, pub mod clients;, and pub mod util;, and the tree has files under home-mixer/params/, util/, and clients/.
  • The new commit added several Cargo.toml files, concentrated in the phoenix subtree.

The new README states:

"Elsewhere, code may not necessarily include build- or deployment-related files or generally self-explanatory infrastructure imports (e.g. xai_service_runner or xai_kafka). ... phoenix/ ships a Cargo workspace, a pyproject.toml, a quickstart and synthetic data generation, so a small model can be trained and served end-to-end." — README.md #deployment-related-code

What we learnedJ. The Phoenix retrieval index consults the visibility verdict before a post is added

A new index service for Phoenix retrieval was also released verified — README.md #retrieval-index.

  • phoenix-rankall/ maintains the post index that Phoenix retrieval looks up. It is updated each time an event arrives verified (README).
  • phoenix-rankall-strato/ is the event layer that decides which index a post belongs to. This layer consults visibility-filtering first verified (README).

The indexing pipeline is already synced with the ranking-side visibility rules, so a visibility judgment is attached before a post enters the index. This is an architectural fact the canon had not grasped at all.

What we learnedK. Five caveats must always be stated when citing the statements above

  1. The weights are a mirror that a cron job pushes daily, so there is a time lag. Changes made in production after the sync time in the header may not yet be reflected verified.
  2. Propensity must be considered when interpreting the sign and magnitude of the weights. The file comment (param.rs:279-281) says only that the weights reflect both the value of the action and propensity verified. Reading this as value × 1/propensity is this note's interpretation inferred.
    • The ratio of absolute values, report −234 to favorite 0.5 (468×), does not directly mean that "a report is 468 times more important than a favorite".
  3. The mirroring scope is limited to params inside home-mixer.
    • The internal constants of the VMRanker remote service, phoenix training hyperparameters, and botmaker rule constants are still outside the repo verified.
    • The score normalizer that the Gen3 canon expected to be in crate::util is not in the Gen4 tree, and home-mixer/util/mod.rs does not declare it either verified.
    • vqv_weight, which the same canon pointed out, was released this time verified — home-mixer/util/candidates_util.rs:19.
  4. Phoenix training code is "trainable", not "identical to production".
    • The README makes clear that the scale differs: "a small model can be trained and served end-to-end".
    • Actual production checkpoints, data, and infrastructure are not public.
  5. Some botmaker rules were not released, to prevent gaming. The README states this explicitly. It means that for some of the labels visibility-filtering consults, the rules are not public verified.

What we learnedL. The process of changing one parameter was documented from the A/B start to the downward adjustment

One new document is a model for how parameter changes will be documented as code diffs going forward. The document is docs/BIDIRECTIONAL_BOOST_CHANGE.md, and the case it covers is the bidirectional follow reply boost of 2026-07.

  • On 2026-07-10, an A/B started. BidirectionalFollowReplyWeightBoost was randomly assigned from 5/10/15/20, and 0 was applied to most users.
  • On 2026-07-13, the initial broad rollout was run, expanding to 20.
  • On 2026-07-24, it was lowered from 20 to 15 in response to user feedback received on X. The feedback pointed out that relevant posts were scarce while the World Cup was under way.

The document carries this summary as is:

"In plain language, the bidirectional follow boost boosts original posts from people you mutually follow by increasing the weight on the predicted probability that you'll reply to a post from one of those authors who you mutually follow." — docs/BIDIRECTIONAL_BOOST_CHANGE.md

  • In the code, the boost is attached only to original posts, and replies and retweets are not targets verified. This rule is very specific logic that the canon lacked verified.
    • home-mixer/candidate_hydrators/bidirectional_follow_hydrator.rs (new): looks up mutual-follow status via SocialGraphClient and sets it in PostCandidate.is_mutual_follow_author.
    • home-mixer/models/candidate.rs: added one field.
    • home-mixer/scorers/ranking_scorer.rs: defines bidirectional_boost_eligible(c) as in_reply_to_tweet_id.is_none() && retweeted_tweet_id.is_none() && is_mutual_follow_author == Some(true), and when the condition holds, adds the boost to the reply and dwell weights.
    • The condition applies only to pure originals; replies and retweets are excluded, and anything that is not a mutual follow passes through unchanged.
