1Refactored visibility rules with no policy change, added 90-case golden corpus — X

Source xai-org/x-algorithm@bc8e5f0 — commit of 2026-08-28T22:37:32Z (24 files, +1950/−1175), public source code. These notes number X commits after the Gen4 release in order, and this commit is Gen4+11. The commit message is a single line, "Open-source X Recommendation Algorithm", as is the convention in the generation series, so the actual content can only be read from the diff. It shares its UTC calendar date with 24c6094 (2026-08-28T01:00:41Z, Gen4+10), which yesterday's daily covered, but it is a follow-up commit that came 21 hours later. Yesterday's daily closed with only 24c6094 folded in. At +1950/−1175 and 24 files it is smaller than Gen4+10 (+2071/−265, 41 files), but it is notable for its large deletion of 1,175 lines. The commit as a whole is a net gain of 775 lines, and most of the deletions (1,144 lines) came from the rules/ layer. The breadth of subsystems touched is narrow and deep. The changes are in 14 files of the visibility-filtering rules/ layer, 3 Phoenix serving files, 4 home-mixer (the service that assembles the For You feed) files, 2 proto files and 1 README. Of the 14 files in rules/, 3 are new.

Background This commit splits into two branches. One is a refactor of the visibility-filtering rule layer with no policy change, and the other is a parameter and infrastructure expansion of the Phoenix ranker and serving. Visibility-filtering (VF) is the service that decides, post by post, whether a post may be shown to a viewer. The VF sub-repo was rewritten in Rust in early Gen4 (2026-08-13), and throughout August it has been removing safety nets and building regression-defense assets inside.

  • Gen4+4: wired up xai-vf-shadow mirroring, which duplicates requests to the shadow service
  • Gen4+7: wired up the reference_compare.rs harness, which compares the VF rewrite's verdicts against the actual verdicts
  • Gen4+9: removed all of the media fallback cache in TesHydrator, which calls TES (X's internal tweet metadata lookup service)

This Gen4+11 commit (bc8e5f0) is the next step: a refactor that thins out the expression of individual rule files and puts a regression corpus inside the code.

What we learnedA. Rules now use methods that name the basis of a verdict instead of data fields

  • The context that rules use to check conditions was split into its own file and exposes about 25 domain methods verified — visibility-filtering/rules/context.rs.

    • What was split out is RuleContext, and the new file is 214 lines.
    • Previously, each rule file accessed data fields directly, as in context.candidate().nsfw.user.
    • Now they are unified in a language that states the basis for a verdict, such as context.has_tweet_nsfw_user_flag(), context.viewer_country_in([...]) and context.legal_takedown_in_viewer_country().
    • The WORLDWIDE_COUNTRY_CODE = "xx" constant and the takedown reason extraction function moved from tes_rules.rs to this file.

  • Individual rule files kept their logic and only became thinner in expression verified.

    • For example, in tes_rules.rs, DropStaleTweetsRule shrank from three early returns (the retweet check, the source_tweet_id.is_some() check and the is_stale check) to two lines.

  • The callbacks of the flag rules and user rules were also changed to take the context instead of data verified.

    • In tweet_flag_rules.rs and user_rules.rs, the fn(&TweetFeatures) -> bool callbacks became fn(&RuleContext<'_>) -> bool.
    • The closure bodies moved from |t| t.nsfw.user to |context| context.has_tweet_nsfw_user_flag(), for example.

What we learnedB. A 90-case golden corpus pins the verdicts, and every wired rule is required to have a deciding case

  • A golden corpus (a set of test cases with fixed expected verdicts) of 90 cases in 13 categories was added, and three assertions run against it verified — visibility-filtering/rules/golden_corpus.rs.
    • The categories are filter_all, baseline, author_state, relationship, tweet_label, tweet_shape, age_gating, exclusive_content, interstitial, oon_media, oon_tweet_label, oon_user_label and interaction.
    • The cases are listed as a table of the form Case { name, level, viewer, candidate, expected_action, expected_decided_by }.
    • golden_corpus_pins_policy_verdicts checks that every case still yields the same action and the same decided_by.
    • every_wired_rule_decides_a_corpus_case checks that subtracting the set of names the corpus used as deciders from the set of wired rule names leaves the empty set. Every rule wired into Policies must have at least one decider case in the corpus (a case where that rule issued the verdict), and CI enforces this.
      • For this assertion, a new helper, #[cfg(test)] pub(crate) fn wired_rule_names(level) -> Vec<&'static str>, was added to registry.rs.
    • corpus_case_names_are_unique prevents case names from overlapping.
  • Of the −298 in registry.rs, about half appears to be individual rule tests moved into the corpus, and the other half the removal of repeated inline setup such as Viewer::LoggedIn(999) inferred.

What we learnedC. A reranker head tag is wired into Phoenix requests, but no server-side logic reads it yet

The two Phoenix changes are in a separate context from the VF refactor. The reranker head tag (RerankerHeadTag) starts as a home-mixer parameter, and its default is 0. The value goes out as a field in the two recsys.proto files, Rust and Python, and then comes back in the scoring response. This commit has no logic showing how the server actually consumes the tag (the head routing logic).

  • The tag is wired from the home-mixer parameter through the Phoenix request to the proto fields, and no logic consumes the tag on the server verified — home-mixer/params/param.rs.

    • The parameter name is RerankerHeadTag, newly defined as param!(RerankerHeadTag, i64, "rust_home_mixer_reranker_head_tag", 0).

    • A pub reranker_head_tag: Option<u32> field was added to PostCandidate.

    • PhoenixScorer puts this value into the request with reranker_head_tag: Some(query.params.get(RerankerHeadTag) as u32).

    • phoenix_request.rs also attaches this value to scoring_sequence with sequence.reranker_head_tag = Some(...).

    • The same field was added symmetrically in two places in the proto. The Rust proto and the Python proto were updated at the same time with the same field number.

    • This commit has no head routing logic on the server side that reads RerankerHeadTag.

What we learnedD. Moved the embedding download copy work from tokio runtime threads to the blocking pool

The emb_table (the embedding table module of the Phoenix serving engine) gRPC callback change is part of the ongoing process in which the infrastructure serving large embedding tables refines the boundary between the tokio runtime and CPU-bound work. It follows the same line as the load_tensor_into core split in the 2026-08-20 commit (Gen4+5) and the copy_port shuffle in Gen4+10.

  • Split the copy work that the gRPC callback was doing into the blocking pool verified — phoenix/crates/serving/xai-recsys-engine/src/emb_table.rs.

    • The change in this file is +79/−12.

    • Previously, the gRPC proto callback itself performed the non-temporal copy and the Adler-32 computation.

    • The new code pushes 4 MiB chunks into a sync_channel(2), and the consumer runs inside tokio::task::spawn_blocking.

    • In the RDMA path as well, everything up to the final Adler-32 summation was moved to spawn_blocking.

    • The new helper JoinOnDrop<T> collects the result with join().await on the normal path, and when dropped it always terminates the blocking task with block_in_place and block_on(handle). Its purpose is presumably to prevent handle and file descriptor leaks inferred.

What we learnedOther changes

  • An idiom repeated in the copy_port client was extracted into a single helper, with no change in behavior verified.
    • The file is copy_port_client.rs, and the new helper is join_transfers.
    • What join_transfers replaces is the four-line join_all(...spawn) → collect → map_err idiom that appeared in two places.
    • The test names that were added when yesterday's commit (Gen4+10) introduced the deterministic shuffle ("_despite_spawn", "_between_spawned_batches") were cleaned up.
  • The proto parser gained a new callback type that can take chunks by ownership transfer verified.
    • In proto_parser.rs, a Bytes callback was added next to the earlier Str callback.
    • The signatures are FnMut(usize, &[u8]) for Str and FnMut(usize, Bytes) for Bytes.
    • In this commit emb_table still uses the Str signature, so a true zero-copy path is a checkpoint to watch in a follow-up commit.

Why it matters The two branches show different maturation trends.

  • On the VF side, the early Gen4 "removal of safety nets" (reference_compare harness → media fallback cache removal) has now continued into "accumulating regression-defense assets inside".
    • The policy is unchanged. However, it now makes the basis of a verdict readable in domain language, alongside the file names, whenever rules are added or fixed later.
    • It also blocks "wiring without tests" at the source, at the CI level.
    • Deletions are 1,175 lines, but the commit as a whole is a net gain of 775 lines, and regression-defense coverage also grew.
    • This direction matches the practice X has repeated throughout August of "put it on first, then remove it while accumulating hardening" (the BSR-V2 3→7 journey, the Grok 4.6 10%→30%→100% dial, the TES media cache being introduced and then removed, etc.).
  • The Phoenix side is different. RerankerHeadTag is still a switch the server does not read.
    • However, because the connection is complete through the home-mixer parameter, the proto fields and the round trip, an A/B experiment becomes possible immediately once the next commit opens the serving consumption logic.
    • Training several reranker heads and routing to them by tag at serving time is a pattern that commonly appears in the A/B maturity phase. This pattern is likely to combine with Gen4's other dial-up practice (shadow deployment → dial-up commit → production promotion).
    • The field being attached symmetrically in two places (ScoreInfo and UserActionSequence) also suggests that the request and response are symmetric. If so, the request side is an instruction to "score with this head," and the response side is a confirmation that "this head was actually used."
  • Splitting out the emb_table gRPC callback is a narrow, clear infrastructure optimization.
    • If the gRPC callback performs the non-temporal copy and the Adler-32 computation for a long time on a tokio runtime thread, other tasks on the same runtime (request routing, admission decisions, health checks) are delayed.
    • With this change the gRPC receive thread only forwards chunks, and the CPU-bound copy goes out to the blocking pool.
    • The 2026-08-20 commit (Gen4+5) split the emb_table core to be pyo3-free, and Gen4+10 equalized peer load with the copy_port shuffle. Together with this blocking pool split, these changes are part of the ongoing refinement of the boundary between the tokio runtime and CPU-bound work in the infrastructure serving large embedding tables.
    • Introducing the Bytes callback type leaves open the possibility that this line leads to a true zero-copy path in the next commit.
  • The checkpoints to watch:
    1. When and in what form the server-side consumption logic for RerankerHeadTag opens (the point when a head routing function is added to the Phoenix Python serving code)
    2. When emb_table consumes the Bytes callback (the true zero-copy path)
    3. The channel that verifies whether the 90 golden corpus cases exactly match prior production verdicts. If the Gen4+7 reference_compare harness is still running after this refactor, then in effect real-traffic verification is happening.

2Named the artwork and video preview personalization system MAPS — Netflix

Source MAPS: Netflix's Multimodal Asset Personalization at Scale — Netflix Tech Blog, 2026-08-28, blog post. The eight authors are Emma Yanyang Kong, Aditya Deshpande, Asad Abbasi, Bowei Yan, David Fagnan, Ashish Rastogi, Dhaval Patel and Ray Zhang. The academic version of the same system, arXiv 2608.18322 (2026-08-18), is already folded into the canon.

Background Netflix's discovery experience consists of two kinds of visual material. One is artwork (the still image of each title), and the other is the video preview (a short clip that autoplays while browsing). This repository calls these assets. Deciding which asset to show each member is itself a personalization problem.

The previous system treated assets only as opaque IDs. It is the 2017-2018 Artwork Personalization bandit lineage. The model could not see what was in the image. New titles and new assets have no interaction history, so cold start relied on exploration and a popularity fallback.

MAPS is a production system that uses CLIP and MediaFM embeddings to let the model "see and hear" the content of an asset, so that personalization works even before interaction history builds up. Here, multimodal is used at two levels.

  1. CLIP is an image-text shared space.
  2. MediaFM is tri-modal, handling visual, audio and text together.

What this blog post newly establishes relative to the arXiv paper is not quantitative figures but architectural context and a description of the infrastructure. There are five new axes.

  • The system name MAPS itself
  • Measured holdback results from the 2025 TV home screen overhaul
  • The ablation of V1/V2 alone (flat) vs V3 (significant)
  • The naming of the Netflix Embedding Store and its two properties
  • The plan to extend to a common image, text and video semantic space

What we learnedA. Bundled artwork and video preview personalization into one system, MAPS

  • The blog post bundles CLIP artwork, query-aware artwork and MediaFM video previews into one system, MAPS verified — MAPS blog post.
    • So far the canon described "artwork personalization" and "video preview personalization" as separate axes.
    • The common underlying infrastructure is the Embedding Store.

What we learnedB. In the artwork experiments, only V3, with both ideas on together, got a significant lift

  • V1 and V2, which each turned on one idea, were flat both offline and online verified — MAPS blog post.
    • V1 turns on only the image embeddings, and V2 turns on only the canvas unification.
    • A canvas is the screen format in which artwork is placed, such as a billboard or a short panel, and previously each canvas had its own model.
    • Both the offline IPS (inverse propensity scoring, a method that corrects the bias of the logged impression policy to evaluate a new policy offline) and the online core member metric were non-significant.
  • Only V3, with both turned on together, got a significant lift and was deployed to production verified (MAPS blog post).
    • In short-panel, V3's offline IPS relative lift was +5.691%, larger than the sum of V1 and V2.
    • This is a case where the observation "turning on just one content feature does not move the metrics" is stated explicitly.
  • In the holdback measurement during the 2025 TV home screen overhaul, V3 also got significant lifts in both the core discovery metrics and streaming hours verified — MAPS blog post.
    • It was a cold-start situation in which the UI overhaul suddenly made short-panel the dominant canvas.
    • V3 was deployed just before the overhaul, and a holdback A/B ran for a month. A small control group kept the previous per-canvas models.
    • Both metric lifts were statistically significant, and larger than in the steady-state ablation.
    • This is a case where signal transfer across canvases in a single model was measured.

What we learnedC. Query-aware artwork was built by blending scores, without a new model

  • The additional modeling effort for query-aware artwork is effectively zero verified — MAPS blog post.
    • The ranking score is blended as α · personalization + (1−α) · cos(text_emb(query), image_emb(asset)), and α is tuned with an online A/B test.
    • Because CLIP embeddings were already in the asset representation, no new model needed to be trained.
    • Playthrough rate rose by +0.36% (p<0.05).

What we learnedD. In video previews MediaFM won, and new MediaFM versions are screened with a linear probe

  • The video preview A/B ran for 5 weeks on all device platforms; MediaFM got a significant lift on core streaming metrics and was deployed to all platforms verified — MAPS blog post.
    • The ranking is MediaFM > SeqCLIP > ID-only.
    • The gain was largest on TV.
  • The linear probe proxy was adopted as the gate for every new MediaFM version release verified — MAPS blog post.
    • A linear probe trains only a linear classifier on top of frozen embeddings, to measure the information contained in the embeddings.
    • This probe is a binary classification that predicts from embeddings alone "which asset will win under an unpersonalized policy". The label is the debiased popularity winner from exploration data.
    • It was adopted for gating because all three signals agreed: probe accuracy, offline IPS and online A/B.
    • Only after the candidate space is pruned does it move on to A/B.

What we learnedE. The Netflix Embedding Store decouples foundation model updates from personalization model deployments

  • The Netflix Embedding Store has no training-serving skew and decouples FM updates from personalization deployments verified — MAPS blog post.
    • FM is short for foundation model (a model pretrained at large scale and reused by many downstream models).
    • The Embedding Store is an AI Platform component that hosts dense embeddings of titles, games, member profiles and multimedia assets.
    • First property: it serves exactly the same embeddings at training time and at online inference time, so there is no skew.
    • Second property: after a new embedding (or a new version of an existing one) is registered, backfilled across the catalog and self-validated, downstream can switch to it with a single config line.
    • Embedding generations switch without changing the training or serving code of downstream models.
  • As a next plan, it explicitly states that it will extend the Embedding Store to a common image, text and video semantic space, opening up cross-modal retrieval and unified asset ranking verified — MAPS blog post.
    • This means the picture in which the 2025 member-side FM and the 2026 item-side MediaFM flow through the same store will be maintained going forward.

What we learnedF. The blog post hid the online A/B figures and described them only qualitatively

  • The blog post's concealment of the online A/B figures is notable observed 2026-08-30.
    • The blog post describes its online A/B results only qualitatively, as in "statistically significant lift" and "gains largest on TV".
    • The figures (+0.127% and others) are in the arXiv paper (2608.18322) and are already folded into the canon.
    • The online panel in the last figure hides its values with "values withheld". The blog post shows only offline IPS relative lifts in the figure.

"Neither idea moved our online core member metrics on its own. V1 and V2 were both flat and non-significant, and only V3 won a statistically significant lift. It is what runs in production today." — MAPS: Netflix's Multimodal Asset Personalization at Scale, 2026-08-28

"We shipped V3 ahead of the launch and measured it with a month-long holdback A/B test, keeping a small control group on the prior per-canvas model. V3 absorbed the shift immediately, with statistically significant gains on both our core discovery metric and streaming hours, and larger gains than in the steady-state ablation." — MAPS: Netflix's Multimodal Asset Personalization at Scale, 2026-08-28

Why it matters The blog post does not overturn the generational flow the canon already set (2017 bandit → 2026 CLIP two-tower and MediaFM). However, it establishes three new perspectives.

  • First, three products were bundled into one system.
    • So far the canon described "artwork personalization" and "video preview personalization" as separate axes. The blog post bundles CLIP artwork, query-aware artwork and MediaFM video previews into one system, MAPS, and the common underlying infrastructure is the Embedding Store.
    • This updates the earlier view that "the member-side FM was unified, but the item side still has several axes".
  • Second, the Netflix Embedding Store was named as a separate component of the FM stack.
    • The picture in which the embeddings of the FM (2025, member) and MediaFM (2026, item) flow through the same store becomes clear. The earlier observation that member-side embedding batch production and the item-side embedding pipeline are symmetric is settled by a single infrastructure name.
    • The decouple property is especially important. If a new embedding generation can be deployed with only register, backfill and validate, the update cadence of the FM stack and the deployment cadence of personalization models are completely separated.
    • This means that the member-side FM's "monthly retraining + daily fine-tuning" cadence (see the training cadence section of the canon) and the item-side MediaFM release cadence can each be optimized independently.
  • Third, the ablation of V1/V2 alone (flat) vs V3 (significant) is empirical evidence for the observation "turning on just one content feature does not move the metrics".
    • That the blog post states this explicitly is itself new. It squarely acknowledges the opposite of the "won offline but flat online" case common in recommender systems (offline and online both being flat).
    • This becomes a case that can be cited as evidence when similar experiment results appear later.
  • It is reasonable to regard the 2017 bandit as superseded. As evidence, the blog post states the limitation of the earlier generation explicitly with "for years, our models answered the first question well and the second poorly", and says outright that V3 is production.
  • GenRec and GenPage are the ranking and page-generation axis, and MAPS is the asset axis, so they do not directly overlap. However, because all three systems are FM stacks centered on member and item embeddings, the architectural direction is the same.

What to check next

For X, watch when the mechanisms this commit added start to be used; for Netflix, watch the direction in which MAPS and the Embedding Store expand.

  • The commit that opens the server-side consumption logic for RerankerHeadTag — the point when a head routing function is added to the Phoenix Python serving code is the signal that the A/B turns on.
  • The first experiment promotion of RerankerHeadTag — look for a commit where the parameter default changes from 0 to 1+ or the tag is exposed through a GrowthBook gate.
  • The commit where emb_table consumes the Bytes callback — the signal that a true zero-copy path opens.
  • The first case where the golden corpus actually catches a regression — post-hoc verification that the 90 cases exactly match prior production verdicts depends on whether the Gen4+7 reference_compare harness is still running.
  • Expansion of the Netflix Embedding Store's shared semantic space — look at what architecture actually implements the common image, text and video embedding space. This will settle whether it extends CLIP-style contrastive training or trains a separate tri-modal fusion.
  • MAPS's next product expansion — we check where the asset axis goes after artwork and previews (trailers? audio previews? UI elements?).
