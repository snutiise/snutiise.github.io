1For You ranking can receive slate context from Phoenix serving — X

Source xai-org/x-algorithm @ d0cef2f — "Open-source X Recommendation Algorithm" — 2026-08-20 20:22 UTC, public source code. These notes number X commits after the Gen4 release in order, and this commit is Gen4+5. It changed 14 files, at a scale of +479/−200, which is about 1/7 the scale of Gen4+4 (2026-08-19, aad7179, 79 files +3.3k/−0.7k).

Background After the Gen4 release, follow-up releases have continued in the X repository on a daily commit rhythm. The order is 8/14 Gen4+1 (c65aa17) → 8/17 Gen4+2 (b089ce6) → 8/18 Gen4+3 (11a71f8) → 8/19 Gen4+4 (aad7179, large). What the canon (this repository's canon documents) had folded in from Gen4 through Gen4+4 went only as far as "proto and config are ready." The 8/20 commit is small because it follows the large expansion of Gen4+4, but it is the first commit in which two scaffoldings that Gen4+4 had only prepared in proto and config reach the actual serving and ranking pipeline.

  • What Gen4+4 prepared: the new SlateContext.sid* fields in the Phoenix (X For You's ranking model) proto, the new RewardOutputs, and the xrecsys_search config.
  • This commit is the first place in the code where SlateContext is confirmed to flow along the Phoenix prediction response into home-mixer (the service that assembles the For You feed).

Three concepts are new in this commit:

  • AI trend is an item that appears on X's "Trending" surface (events many people are talking about).
    • Before this commit, the home-mixer pipeline had no logic that attached an "AI trend" label to tweets.
    • Strato is the internal system that X code goes through to look up or store data.
    • An upstream pipeline in which Grok looks at a tweet, decides which AI trend it belongs to, and stores the result in Strato likely existed (the batch_get_tweet_ai_trend API), but that pipeline is outside this repository inferred.
  • SlateContext is the context vector that each slot holds in a DPP (a diversity technique that selects items as a set so that the score drops when similar items are picked together) re-ranking slate.
    • k is the slot index, pool_rank is the rank in the original score ordering, and pool_rank_gap is the pool rank difference from the slot above.
    • fatigue, pre_diversity_score, and sid_known are added to these.
    • sid_k_l1/l2/l3 hold the slot index for each of the three SID (semantic ID, a token sequence that represents an item as hierarchical codes) layers.
    • sid_gap_l1/l2/l3 hold the inter-slot gap for each SID layer.
    • It is the same field set as when seven SID fields were added to VMRanker (the service that handles DPP slate reordering) in the 8/18 commit, Gen4+3.
  • The served slate context is a schema field in which the Phoenix serving response returns, for each candidate, the material used for re-ranking.
    • The material is the pool rank, fatigue, pre-diversity score, three SID layers, and three SID gap layers.
    • In the Gen4+4 proto it was only defined; this commit connected the consumption path.

A hydrator that attaches AI trend labels to original posts in For You was added

This commit adds a new stage that selects standalone original posts among For You candidates and attaches AI trend labels verified. At most 2 labels are attached per page, and the gate that turns on this stage is false by default verified.

  • A hydrator that fills AI trend information into candidate posts was added as a new 157-line file verified — home-mixer/candidate_hydrators/ai_trend_feedback_context_hydrator.rs.

    • The pipeline wiring is at phoenix_candidate_pipeline.rs:424-428.
    • It was added right after the existing TopicFeedbackContextHydrator, side by side. Topic feedback context is a context label used to infer the user's topics of interest.

  • This hydrator runs only when all three gate conditions are met verified — ai_trend_feedback_context_hydrator.rs:59-63.

    • The gate parameter rust_home_mixer_enable_ai_trend_feedback_context must be on. It is false by default.
    • The request must not be a topic request (so that it does not overlap the topic surface).
    • The request must not be for the Following surface (requests that receive only posts from followed accounts). This condition applies per request and does not check whether a candidate is from a followed account.
    • The hydrate loop (L65-75) also filters only by the original-post condition below, so candidates from followed accounts that are mixed into a For You request are also targets.
    • It is not wired into the Following pipeline.

  • Candidates pass a four-part condition that keeps only the "standalone original post" verified — ai_trend_feedback_context_hydrator.rs:19-24.

    • A candidate is dropped if it is a reply, is a retweet, has a conversation ancestor, or is a post that a followed user replied to. Meeting any one of the four drops it.
    • In effect, AI trend labels can be attached only to original posts that are not replies, reposts, posts with conversation ancestors, or posts that followed users replied to. Whether a post is a quote post is not checked.

  • The Top-2 trends are chosen by candidate frequency, and one candidate is picked at random per trend to receive the label verified — ai_trend_feedback_context_hydrator.rs:24-52.

    • The procedure has five steps.
      1. For each candidate that meets the conditions, look up the trend_id with Strato batch_get_tweet_ai_trend.
      2. Build a frequency histogram of the candidates' trend_ids.
      3. Pick the top 2 trends. On a tie, the smaller trend_id takes priority.
      4. For each trend, pick one candidate at random.
      5. Look up the display name of that trend with Strato batch_get_ai_trend_name.
    • In effect, at most 2 AI trend labels are attached per page, and each trend's label goes on only one candidate.
    • It is a suppression mechanism that prevents the same label from being attached repeatedly to multiple candidates in the same trend.

  • On screen it goes out in the same form as a topic label, and AI trend is used only when there is no topic feedback verified — home-mixer/util/urt/post_marshaller.rs:72-110.

    • At the render stage it joins the topic path of the URT (X's response rendering schema) TweetContext as a fallback.
    • Both go out in URT as the same context type, ContextType::TOPIC.
    • The AI trend path differs from the topic path in two ways: landing_url is filled, and TopicFeedbackContext.topic_id is None.
    • So when a user taps the topic-style chip attached above this tweet, it goes to x.com/i/trending/{trend_id}, the trend surface, rather than the topic feedback page.

    "https://x.com/i/trending/{trend_id}" — post_marshaller.rs:92

The following four items are not public:

  • The definition of AI trend (who creates trend ids and how, and whether tweets are clustered with Grok or curated by people)
  • The upstream pipeline of batch_get_tweet_ai_trend
  • Whether EnableAiTrendFeedbackContext is actually deployed
  • The tuning history of TOP_TREND_COUNT = 2

Because the rust_home_mixer_ prefix in the gate name follows the same convention as other rust-migration gates in this repository, an A/B experiment may be in progress inferred.

Why it matters X opened a second context channel alongside the topic feedback context it has used so far. It is a fallback structure in which topic wins if it already exists and AI trend enters only when it does not, so the two do not overlap.

  • The observation signals widen as well. A user's reaction of tapping, dismissing, or ignoring this chip becomes a label source for judging whether this user is interested in this AI trend.
  • This is a different direction from the "layer expansion of the safety pipeline" folded in from Gen4 through Gen4+4. It confirms a trend of widening the signal source upstream of ranking itself.

The ranking stage consumes the slate context that Phoenix computed at serving

The SID fields created in the Phoenix proto in the 8/19 Gen4+4 commit (three SID layers and three gap layers for each slot) were connected to an actual pipeline consumption path in this commit. The proto field name is SlateContext.sid*. Four places opened at the same time:

  • The candidate struct gained one more slot for slate context, so it now has two verified — home-mixer/models/candidate.rs:26-27, 76-77.

    • The struct is named PostCandidate, and the new field is served_slate_context.
    • The existing slate_context is a value that home-mixer computed and cached.
    • The new served_slate_context is a value that Phoenix computed at serving and sent in the response.

  • The conversion impl between proto and Rust renames the proto's short field names to home-mixer names verified — candidate.rs:99-118.

    • It renames the proto's sid_k1/2/3 and sid_gap1/2/3 to the home-mixer naming convention sid_k_l1/l2/l3 and sid_gap_l1/l2/l3.
    • Here "l" stands for level.

  • PhoenixScorer extracts the slate context from the Phoenix prediction response and fills the new field verified — home-mixer/scorers/phoenix_scorer.rs:107-125.

    • When the Phoenix prediction response carries SlateContext alongside the 24 candidate scores (engagement probability heads), PhoenixScorer sets that value in served_slate_context and passes it down the pipeline.
    • The value is taken from candidate_slate_context() of the prediction response.

  • RankingScorer decides the slate context with a three-way fallback verified — home-mixer/scorers/ranking_scorer.rs:700-710, 806-825, 875-895.

    1. If the UseServedSlateContext gate is on and Phoenix sent slate context for all candidates, that value is used as is.
    2. If the gate is off or the data is incomplete, and the Redis warming cache hits, the slate context stored for a previous request is reused.
    3. Otherwise, it is computed locally with compute_slate_contexts(candidates, weighted_scores).
    • This order applies identically to both ranking branches.

  • The gate that turns on this path came in with a default of false. Only the gate has been created, and the actual rollout is deferred to a later parameter change.

    • The gate name is UseServedSlateContext.

Why it matters This is the first step of a migration in which the point that computes slate context moves from home-mixer locally to Phoenix serving. Phoenix already knows each candidate's pool rank, fatigue, pre-diversity, and three SID layers at the moment it produces predictions, so it can send them in the serving response instead of home-mixer recomputing them.

  • That saves ranker CPU.
  • The richer context that Phoenix holds can be reflected in re-ranking. For example, the three SID layers cannot be computed without Phoenix.
  • The direction is for home-mixer to keep shrinking into a thin layer that handles only candidate allocation and re-ranking.
  • The direction is the same as SID being connected to VMRanker in the 8/18 commit (Gen4+3). By definition SID is a Phoenix training output, so home-mixer cannot compute it locally, and this commit resolved that problem at serving time.
  • The point at which a commit promotes UseServedSlateContext to true is the point at which Phoenix serving's slate context output reaches production traffic.

The core logic of the embedding table loader was separated from the Python bindings

The embedding table loader of the Phoenix serving engine was split into a Python-side wrapper and a core that does not depend on pyo3 verified.

  • The core logic was split out of emb_table.rs as load_tensor_into, and the existing load_tensor was redefined as a thin wrapper around that core verified — phoenix/crates/serving/xai-recsys-engine/src/emb_table.rs.

    • The file overhaul is +189/−169, and it is essentially an equivalent refactor.
    • The existing load_tensor was tied to pyo3 types and pyo3 errors, so it could not be reused in non-Python contexts.
    • The tied types were Bound<'py, PyString>, PyReadwriteArray1<'py, u8>, and Bound<'py, PyList>, and the errors were PyValueError, PyOSError, and PyTypeError.
    • The new core does not depend on pyo3; it takes a &mut [u8] interface and returns Result<(), String>.

  • Safety was also tightened.

    • Replaced the unwrap() on tokio runtime creation with map_err. The changed code is map_err(|e| format!("tokio runtime: {e}")).
    • Added a checkpoint path too short guard. The condition is prefix.len() < 3, and the message is checkpoint path too short: {path}.
    • Unified modulo checks such as row_segment_size % num_row_segments != 0 to the is_multiple_of API.

Why it matters By exposing the embedding table loader core through a pure Rust interface, this change prepares it for reuse without the pyo3 stack in training pipelines or other paths of Rust-native serving code. The direction is the same as the Phoenix xrecsys_search vocab growing to 100M/100M/30M in the 8/19 commit (Gen4+4). It suggests a growing need to load large embedding tables in multiple serving and training contexts.

The share of calls sent to Grok 4.6 at two judge call sites rose from 0.1 to 0.3

In grox (the Grok-based nearline classifier sub-repo), the Grok 4.6 dial introduced by Gen4+4 on 2026-08-19 rose 3× in a day, from 10% to 30% verified. This dial is the probability of sending calls to 4.6 instead of Grok 4.5 at two judge call sites (child-safety cross-model validation and deluxe 4.3 category reclassification). Because the 4.6 response is used for verdicts just like 4.5's, it is a dial that splits live traffic, not a shadow that discards results verified — classifier.py:281-290@aad7179.

  • What changed is one constant line verified — grox/flows/ptos/classifier.py:114.

  • The circuit breaker configuration and the places where the dial applies are unchanged.

    • The parameters of the _EAPI_4_6_INTERNAL_BREAKER_CONFIG circuit breaker (failure rate 50%, window 600 seconds, recovery 600 seconds, half-open 5 calls) did not change.
    • The two places where the dial applies, child-safety cross-model validation and deluxe 4.3 category reclassification, are also unchanged.

Why it matters This increase supports the view that, in the gradual rollout from 4.5 to 4.6, 4.6 did not trip the circuit breaker with 10% of live traffic and that verdict quality was within the acceptable range inferred. Otherwise the dial could not have been raised 3×.

  • The Grok 4.5 judge layer introduced by Gen4+2 is being refined daily, and this commit is the fourth in that flow. The flow is +2 introduction → +3 finer logging → +4 4.6 dial 10% → +5 30%.
  • If the next commit jumps to 50% or 100%, the full switch to 4.6 is close; if the dial drops again, a regression was observed.

Grok streaming responses can now be cut off midway when a condition is met

The grox Grok sampler gained a callback that ends a streaming response early, and it increments a counter each time it cuts one off verified.

  • A stop_predicate callback was added to grox/libs/grok_sampler/llm.py verified — that file.

    • The scale is +27/−13.
    • The existing _sample_streaming kept consuming tokens from the raw stream as they arrived.
    • Now it wraps the raw stream in an explicit context with async with aclosing(...), which guarantees cleanup even on early termination. Tokens are received inside this async with aclosing block.
    • After each token is yielded, it checks stop_predicate(resp); if True, it breaks immediately and increments the counter llm.sample.early_stop.count.

Why it matters This change can be read as a sampling infrastructure optimization to handle the traffic increased by the Grok 4.6 dial introduced in Gen4+4 inferred. The basis is the circumstance that it is in the same commit as the change raising the dial to 30%.

  • Safety verdict responses often arrive wrapped in a JSON tag (<json>...</json>), and once the tag closes, the tokens that follow are meaningless.
  • Cutting off early with a callback such as stop_predicate=lambda r: "</json>" in r reduces token cost and also the latency after TTFT.

Grok classifiers can now reference the author's profile image

A profile image field was added to the User schema of the grox data loader verified. The field is filled when the author metadata has a profile image URL verified.

  • The Grox User data loader gained a profile_image field verified.

    • The type is profile_image: Image | None.
    • The changed files are grox/core/data_loaders/data_types.py and post_mapper.py.
    • If AuthorMetadata.profileImageUrl exists, it is filled with Image(url=...).
    • Previously the User schema held only the URLs, the affiliated business, and recent posts, with no profile image.

Why it matters Grok classifiers can now reference the profile image as verdict context. For example, one can imagine ads brand-safety verdicts checking whether a profile image contains adult content. This may be upstream data wiring prepared for the adult content cross-validation judge introduced in Gen4+2 or for later expansions of the verdict layer inferred.

2OneModel unified ranking across three surfaces: organic, ads, and merchant — Xiaohongshu

Source OneModel: A Unified Foundation for Platform-Scale Multi-Scenario Ranking (arXiv 2608.18606) — submitted to arXiv on 2026-08-19 (v2; v1 was the initial submission), paper. It has 14 authors (Yinqi Zhang, Peiyu Hu, Yuntian Tang, Siying Gu, Jiahao Liang, Longxin Kou, Haiqing Hu, Shuman Zhuang, and others). The abstract states that the deployed service is Xiaohongshu (小红书, a Chinese lifestyle social platform).

Background Xiaohongshu is a service the canon does not yet track. Even so, serving multiple business streams (organic recommendation, ads, merchant products) in one app through a unified system is unusual compared with the per-service fragmented rankers at X, Meta, and Netflix. This paper is a production deployment claim that three surfaces were unified into one ranker, and it adds a new angle to the following three lines of production claims:

  • Netflix Foundation Model (FM) placed per-service heads on top of a single FM.
  • Meta GEM built a backbone that unifies IG and FB within the ads domain.
  • Yandex Music Gryphon-v2/Sona unified retrieval and ranking.

OneModel moves to a different angle: one backbone serves different business streams (organic, ads, merchant) at the same time.

What we learnedA. Final ranking for three streams is unified in one framework based on shared event sequences

  • The abstract points out that keeping a separate ranking system per stream fragments user representations and raises engineering cost, and it proposes OneModel, which merges final ranking into one.

    "Platform-scale recommender systems often span multiple business streams such as organic recommendation, advertising, and merchant services, where user behaviors form a continuous cross-stream trajectory. Maintaining separate ranking systems fragments user representations and increases engineering cost. We propose OneModel, a unified framework for multi-stream final ranking. OneModel maps heterogeneous behaviors into shared event sequences, learns long-context user representations with an action-oriented backbone, and introduces Scenario-aware Information Modulation to balance cross-stream transfer and stream-specific specialization."

    — OneModel (arXiv 2608.18606) abstract (paper)

  • There are three core architecture elements:

    • The shared event sequence unifies user behavior from the three streams (organic, ads, merchant) into one event sequence schema.
    • The action-oriented backbone is the part that learns long-context user representations. The abstract does not give the specific architecture.
    • Scenario-aware Information Modulation balances cross-stream transfer and stream-specific specialization through switching and gating. The former corresponds to sharing, the latter to dedicated handling.

  • The abstract lists six optimization elements for production deployment.

    • stratified user representation
    • multi-objective training
    • feature decomposition
    • user feature prefetching
    • shared user-tower computation
    • graph-level inference optimization

What we learnedB. In Xiaohongshu production A/B tests, metrics rose on all three surfaces

  • The A/B results came from the Xiaohongshu production deployment.

Its direction differs somewhat from the LLM-native ranking thread.   • The first is Netflix FM (service diversity, from foundation to head).
  • The second is Meta GEM (surface diversity within the ads domain).
  • The third is Xiaohongshu OneModel (business stream diversity).
