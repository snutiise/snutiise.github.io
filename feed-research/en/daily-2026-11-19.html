1The link-copy share weight returned to 20.0 after five days — X

Source xai-org/x-algorithm@9081b33 — xAI, 2026-11-18, code. In these notes' numbering, this is Gen4+Gen66.4+N is the number these notes assigned in order to commits after the 2026-08-13 Gen4 release).

Background X For You's ranking model Phoenix (a Grok-family Transformer) outputs probabilities of actions such as like, reply, and share for each candidate post, and the score starts from a weighted sum that multiplies these probabilities by per-action weights. X publishes the production default weights through cron mirrors (scripts that copy the production config into repository code every day), which are two files: one for home-mixer (the service that receives feed requests, gathers candidates, and scores them) and one for vm-ranker (a separate service that computes the weighted sum and DPP re-ranking). The 2026-11-13 commit (Gen4+63) lowered the link-copy share weight in the home-mixer mirror from 20.0 to 0.0, while the vm-ranker mirror stayed at 20.0. This commit reverted that value while folding in the 2026-11-17 sync, and it added three switches for scoring, ads, and training data, all off by default.

What we learnedA. The home-mixer mirror's link-copy share weight is 20.0 again

  • The share via copy link weight in the home-mixer mirror changed from 0.0 to 20.0 verified — home-mixer/params/param.rs:495-500.
    • The sync time in the file header changed from 2026-11-16T16:00:37Z to 2026-11-17T16:00:33Z.
    • This is the only weight that changed in this sync.
  • The two mirrors have the same 20.0 again, and link-copy share is once more the largest of the positive weights verified — vm-ranker/params.rs.
  • We infer that the five days at 0.0 were an experiment or a reverted misconfiguration inferred. The evidence is that the vm-ranker mirror never followed it down in the meantime, and no other weight moved with it.

What we learnedB. In-network and OON candidates can now get separate multipliers for the engagement term and the dwell-time term

  • Until now, vm-ranker multiplied the entire score of OON (posts from accounts the viewer does not follow) candidates by a single 0.75 multiplier. Now each candidate type can get separate multipliers for the engagement term and the dwell-time term verified — xai-value-model/scoring.rs:338-364.

    • The dwell-time term is the expected dwell seconds times the cont_dwell_time weight, clamped between 0 and the total score. The engagement term is the total score minus the dwell-time term.
    • The author-diversity decay is still multiplied on top of this score.

  • The default of all four multipliers is −1.0, and negative values are treated as unset, so current scores are unchanged verified — vm-ranker/params.rs:247-270.

    • If only one side is set, the other uses the existing multiplier (OON 0.75, in-network 1.0).
    • They do not apply to the multiplicative combination mode (Gen4+65), topic requests, or new-user requests.

  • The test config gives an example of different multipliers by country condition verified — vm-ranker/scoring/mod.rs.

    • The FR example is OON engagement 0.6, OON dwell 0.9, in-network engagement 1.2, and in-network dwell 0.7. The JP example sets only OON dwell to 0.9.
    • These are test values, so there is no basis to treat them as the settings of a production experiment.

What we learnedC. A path now exists that re-scores served candidates with a teacher model and stores the result

  • A side effect (a step that runs in the background without changing the response) now re-scores, on a separate Phoenix cluster, the candidates actually served and the top dropped candidates for sampled requests, and leaves the probabilities of the specified heads in the cache verified — side_effects/teacher_score_side_effect.rs:60-81.
    • It puts the served candidates in first, then fills in dropped candidates whose weighted sum is positive in score order, for up to 64 candidates. Retweets are deduplicated by original id.
    • Results are written for 50 minutes to the caches of two data centers, using the same key scheme as the training request cache.
  • The switch is off by default, the sample rate is 0, and the cluster name and head list are empty, so it does not run now verified — params/param.rs:1251-1287.
  • We infer that this is data for distillation (training in which a smaller model learns to imitate a larger model's output), where a large model's predictions serve as the training target of the serving model inferred. The evidence is that it is named teacher and that it scores even dropped candidates and places them next to the training cache.

What we learnedD. A mechanism now changes ad volume when the page's top posts score low

  • The slot-spread blender for For You (an ad placer that first spreads ad slots evenly across the whole page) can now split the average score of the top 20 posts into three bands and set the ad ratio and spacing for each band verified — ads/user_load.rs:39-94, 152-171.
    • The ad ratio to keep is limited to 50–100%, and the spacing does not go below the minimum spacing.
    • It applies only in weighted-sum mode and does not apply to Premium subscribers.
  • The per-band value lists are empty and both boundary values are 0.0, so ad volume is unchanged now verified — params/param.rs:1111-1140.
  • If both the Gen4+65 activity-stage ad volume mechanism and this mechanism are set, the page-score band values override it verified — same file.

What we learnedOther changes

  • Each VMRanker request and DPP history post now carries the request type (first load, refresh polling, load more on scroll down). How VMRanker uses it is not public verified — scorers/vm_ranker_request.rs
  • Subscription tier can now be used in feature switch conditions. A test pins that only the premium_plus condition matches Premium+ viewers verified — models/fs_recipient.rs
  • Phoenix training code gained, off by default, a semantic ID feature for ad products and a per-request CREAD restoration option for four dwell-time-family heads verified — phoenix/xrex/models/recsys_model.py
  • A path to read training data from Iceberg tables was added verified — phoenix/xrex/data/recsys/iceberg_layout.py
  • abuse-enforcement-service (a service that takes actions such as account suspension based on scores) excludes test accounts from enforcement. It does not touch feed ranking verified — service-lib/src/safety_checks.rs
  • grox (Grok-based annotation pipeline) gained an option, off by default, to pick the sharpest frame in a video. Labels and thresholds are unchanged verified — grox/libs/video_tools/video_frames.py

2In AI Discover an LLM plans and the existing rankers pick titles — Netflix

Source Engineering AI Discover — Netflix TechBlog, 2026-11-17, blog.

Background Netflix recommendations have so far inferred taste from watch history and shown it as rows, and the only way for members to set direction themselves was something like thumbs ratings. In early 2026-11, an AI Discover tab opened to some members in the TV app; when a member picks a theme such as "Quick Watches", rows of matching titles, descriptions, and next themes appear. Leaving the whole screen to an LLM can produce titles that do not exist or slow things down, so the question is what to give the LLM and what to leave to existing systems. This post describes the structure of the intelligence layer (the layer that decides how to combine the LLM and recommendation systems for each request) that sets that boundary.

What we learnedA. Existing retrieval and rankers choose titles; the LLM handles plans and wording

  • When a request arrives, a controller decides the plan and an executor runs it. The plan is a graph of approved steps verified — AI Discover blog post.
    • Steps run capabilities (task units wrapping existing systems such as search, large-scale ranking, and catalog metadata). Capabilities fall into retrieval, ranking, generation, and packaging families.
    • Before execution, code validates the graph. It checks that every step is approved, that each input has a step that produces it, that there are no cycles, and that the graph ends in a single page.
  • A router controlled by Netflix chooses between an already tested existing plan and a plan the LLM drafts on the fly verified — same blog post.
    • If the planner is slow or the plan fails validation, it falls back to a tested plan.
    • The blog post calls this a plan-and-execute agent (an agent where the LLM proposes the path and code decides whether to execute it).
  • The LLM handles theme generation, row titles and descriptions, and next-theme suggestions, while titles are chosen by retrieval and rankers together with the LLM verified — same blog post.

"Every pick must be a real, available title from our changing catalog. Retrieval and rankers work in tandem with LLMs to choose titles that fit the member's taste and intent." — Engineering AI Discover, 2026-11-17 (blog)

What we learnedB. Adjustments a member picks stay in Memory Hub and apply on the next visit

  • Member adjustments (such as "don't recommend") apply immediately and persist across visits verified — same blog post.
    • The store is Memory Hub (a low-latency per-member memory store).
    • The same place holds a taste summary that MemberLLM (an in-house language model for personalized recommendation) prebuilds from watch history. It is built outside the request path.
  • The post wrote that how to blend these adjustments with the existing personalization systems is a question it is still looking for an answer to verified — same blog post.
  • Requests that involve generation are handled asynchronously. A tap returns an immediate acknowledgment, and the server notifies the TV when the result is ready verified — same blog post.

What we learnedOther changes

  • Rules such as maturity rating are enforced in code, not in the prompt. The planner uses placeholders instead of values, and the controller fills them in after validation verified — AI Discover blog post
  • Before a model swap, the same tasks are scored with automatic checks and an LLM judge, and past request logs are replayed with the new prompt or model for comparison verified — same blog post
