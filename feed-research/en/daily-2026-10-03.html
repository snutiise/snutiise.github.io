1Retrieval that generates SIDs to pick candidates is wired in as a For You candidate source — X

Source xai-org/x-algorithm@76843a5 — xai-org, 2026-10-02T02:06:55Z, code. These notes number X commits after the Gen4 release in order, and this commit is Gen4+34. The scale is +5227/−756 across 105 files.

Background X's recommendation stack has been reorganized around Phoenix (the GPU ranking stack rebuilt in 2026) over the past four months. Within it, "retrieval" was split into two branches.

  • One is two-tower retrieval: the traditional OON (out-of-network, posts from accounts the user does not follow) source that runs ANN search on the inner product of user-tower and item-tower embeddings. In the 2026-09-30 commit, xrecsys_two_tower.py was promoted to a 6-preset catalog, and SID 6-level, seqpack, and sharing of two heads (Home/Immersive) were stated explicitly.
  • The other is generative retrieval (SID generation). Items are compressed into multi-stage token sequences (semantic ID, SID for short) with RQ-VAE or a similar quantization, and a Transformer then generates SID tokens conditioned on the user history. Lines such as Google TIGER (NeurIPS 2023, arXiv 2305.05065), Alibaba PailitaoGR (2025), Kuaishou OneRec (2025), Tencent BARGE (2026), and ByteDance GEAR (arXiv 2026-09-30 v1, 2026-10-02 daily) belong here.

Until now X had exposed SID tokens through sid_num_levels in the training config. The two-tower model used them as input features of the item tower. A generative retrieval path that generates SIDs and picks candidates from them directly had never been released.

On 2026-09-04 (Gen4+15) there is a record that the "SID retrieval sidecar was removed entirely from the Phoenix serving engine". At the time, the sidecar was a lookup that converted each post ID in the user history of a Phoenix request into an SID, and that role was absorbed by loading SIDs into the request beforehand. Until then, X's "SID retrieval" had the narrow meaning of an item ID → SID token lookup.

This commit completely changes that narrow meaning. Among the new files, SID-related code comes in five groups, and the following three things arrived together:

  • Phoenix gained a training config, model, trainer, and inference runner for a Transformer dedicated to SID generative retrieval.
  • home-mixer (the service that assembles the For You feed) gained a SidSource candidate source that calls this service.
  • This source attaches shared_prefix_depth to response candidates as the score and passes them on labeled ForYouPhoenixRetrievalMoe.

What we learnedA. home-mixer now has a candidate source that calls a separate SID retrieval service

  • home-mixer has a new candidate source, and it calls a generative SID retrieval microservice split out as a separate service verified — home-mixer/sources/sid_source.rs (new, +112).
    • The source is named SidSource.
    • The client that makes the call is home-mixer/clients/sid_retrieval_client.rs (new, +246).
    • The target endpoint is https://xai-recsys-sid-retrieval.prod.fou.twitter.biz:443.
  • The request carries seed post IDs, a result cap, and a prefix-depth range, and the response carries a post ID and shared prefix depth for each candidate verified.
    • The gRPC service is SidRetrievalServiceClient.
    • The request type is RetrieveRequest { seed_post_ids, max_results, max_per_seed, min_prefix_depth, max_prefix_depth, caller }.
    • The response type is RetrieveResponse { candidates: Vec<Candidate> }, and each Candidate holds post_id and shared_prefix_depth.
  • These proto symbols come from outside the repo, and the repo also released a separate crate that holds only the SID lookup proto verified.
    • The symbols are imported by the xai_recsys_sid_retrieval_proto crate from outside (private or generated).
    • The separately released crate xai-recsys-sid-proto contains only sid_lookup.proto.
    • sid_lookup.proto covers only the post_id → SID code array mapping. It is the return of the lookup sidecar that disappeared on 2026-09-04.
      • The definition is SidLookupService { LookupSids(repeated int64 post_ids) → repeated PostSids { repeated int32 codes } }.
    • The generative retrieval proto is not included in the repo.
  • This means that the production code visible in the repo and the proto definition dedicated to that "generative retrieval" are separated inferred.
  • SidSource is enabled by the AND of five conditions, all of which must be true verified — sid_source.rs:58-64.
    • The EnableSidSource param is on (default false).
    • The request is not a topic request.
    • The request is not in-network only.
    • There are no cached posts (cold path).
    • has_post_signals(query) is true.
    • The last condition reuses exactly the same function as SimclustersSource, meaning the source runs only when the user has positive engagement signals.
    • The design is declared so that the two sources branch from the same seed set (post IDs the user interacted with through fav/retweet/reply and so on).
  • The source calls the SID service with posts the user reacted to as seeds, and gives the returned candidates the same label as the existing Phoenix MoE (mixture-of-experts) source verified.
    • First it takes the user's positive engagement post IDs from post_signal_ids(query) and truncates them to the SidSourceMaxSeeds cap (default 50).
    • It assembles a RetrieveRequest and calls via gRPC. The 300ms deadline is hardcoded in sid_retrieval_client.rs:21.
    • Each response Candidate is converted to a PostCandidate. It is marked served_type = ForYouPhoenixRetrievalMoe, which is the same label as the existing PhoenixMOESource.
    • shared_prefix_depth goes into the score field as an f32.
    • Finally, it fills in the author, creation time, and so on with CoreDataCandidateHydrator, and then removes candidates with author_id == 0.
  • Five parameters were introduced under the names rust_home_mixer_sid_source_*, and their defaults were released verified — home-mixer/params/param.rs. This file is a cron mirror of the production feature-switch defaults.
    • EnableSidSource=false
    • SidSourceMaxResults=800
    • SidSourceMaxSeeds=50
    • SidSourceMaxPerSeed=100
    • SidSourceMinPrefixDepth=3
    • max_prefix_depth: 0 is hardcoded in RetrieveRequest (no cap).
    • min_prefix_depth=3 is a request-side filter asking for only candidates whose shared prefix matches at least 3 of the 6 SID levels.
    • There are at most 100 posts per seed and a total cap of 800. The theoretical cap is 50 × 100 = 5000, but it is tightened again to 800.
  • The gRPC client runs two paths in parallel: it sets up the xDS path first and falls back to the DNS path if that fails verified.
    • It first sets up the load balancer with xDS P2C. This path uses the discovery-authority-based xdstp://discovery-*/envoy.config.endpoint.v3.ClusterLoadAssignment/fou-xai-recsys-sid-retrieval.prod.prod:grpc-tls.
    • If the xDS build does not finish within 10 seconds or there is no bootstrap, it falls back to the DNS path (RotatingChannel, refresh every 60 seconds).
    • The response size cap is MAX_DECODING_MESSAGE_BYTES = 16 MiB.
    • The metric SidRetrievalClient.retrieve{result=success|timeout|failure, path=xds|dns} records the call result and path as labels. Call latency goes into the SidRetrievalClient.retrieve{path} histogram.
    • The service's own readiness probe is GET /readyz on port 29180.
    • Keep-alive is set to a 30-second interval, a 10-second deadline, and idle=true.
  • The source-side metric measures three stages separately: the number of seeds, the number of RPC responses, and the number remaining after hydration verified.
    • The metric is SidSource.retrieved{type=seeds|retrieved|hydrated}.
    • The seeds count is the amount sent in the RPC, the retrieved count is the RPC response, and the hydrated count is the survivors with author_id!=0.

What we learnedB. Training and serving code for a dedicated Transformer that generates SIDs was released in Phoenix

  • Phoenix gained new files for the training config, model, trainer, and inference runner of the SID generative retrieval model verified — phoenix/xrex/configs/xrecsys_sid_retrieval.py (new).
    • The other three files are also new.
      • phoenix/xrex/models/recsys_sid_retrieval_model.py
      • phoenix/xrex/train/trainer_sid_retrieval.py
      • phoenix/xrex/inference/sid_retrieval_runner.py
  • The training config xrecsys_sid_retrieval.py discloses all of the model's hyperparameters verified — xrecsys_sid_retrieval.py:11-45.
    • The input sequence length is 1030: 1 user prefix token, 1023 user action history tokens, and 6 SID target tokens. The candidate sequence is 64.
    • The SID is a 6-level hierarchy with 256 codes per level. In theory the SID space is $256^6 ≈ 2.8 \times 10^{14}$ entries.
      • sid_num_levels=6, sid_codebook_size=256
      • sid_embed_dim=1024(= EMB_TABLE_WIDTH), sid_prediction_hidden_dim=512
      • sid_level_loss_decay=1.0 means there is no per-level loss weight decay. In other words, all 6 levels get the same weight.
      • sid_hash_level=True, sid_cross_attn=True
    • The Transformer has 8 layers and uses GQA (grouped-query attention) at a 5:1 ratio.
      • query_heads=20·kv_heads=4, key_size=128, emb_size=2560
      • attn_logit_cap=80.0 with attn_logit_cap_method="soft_sign", rotary, causal
      • widening_factor=2 with gated_mlp=False (plain MLP), remat WHOLE
    • The input vocab figures exactly match those of the two-tower config released on 2026-09-30 (Gen4+32). This means the two models share the same vocab space.
      • User vocab=0, item raw vocab=0, item hash vocab=100M, author vocab=30M, 60 action types, 8 continuous actions.
      • It pads to a multiple of 512 with _round_up(..., 512).
      • It applies double hashing with two pairs of hash functions (linear scale × modulus prime) for each of user/item/author.
    • Training uses the Adam optimizer and a constant learning rate, and splits with expert-parallel and no data-parallel.
      • Adam optimizer (b1=0.95, b2=0.98), weight_decay=1e-3, constant learning rate 2e-3
      • batch size per device = 128, parallel setting is ep=128, dp=1 (128-way expert-parallel, no data-parallel)
      • max_steps = (1e11 / 32) − 100 ≈ 3.125B steps
    • The dataset is in aggregated_kafka mode, and the path is a filler value.
      • PhoenixDataset with path="/path/to/offline_kafka_dump" (filler), num_kafka_partitions=1024
      • include_candidate_post_ids=True, use_post_sid=True, multimodal_embedding_type=None
    • The checkpoint settings were also released.
      • checkpoint_every_n=100·checkpoint_keep_every_nth=1000·checkpoint_keep_last_n=10·verify_checksums=True
      • replica_axis="replica"·checkpoint_chunked=False·checkpoint_compressed=False

  • The model code appears to keep SID token embeddings in a separate table per level and raise them to 1024-dim through a projection per level verified — recsys_sid_retrieval_model.py:72-100.
    • The related names are the Haiku transformed function _embed_sid_token(code, level) and the per-level table sid_emb_level_{level} (size [256, 128]).
    • The name of the projection after each level is sid_emb_proj_{level}.
  • The model's only positive action is SERVER_TWEET_FAV verified — line 40. The positive is narrowed to fav alone.
    • Seven hard-negative actions are used for negative supervision.
      • The list is CLIENT_TWEET_REPORT, _NOT_INTERESTED_IN, _SEE_FEWER, _UNFOLLOW_AUTHOR, _BLOCK_AUTHOR, _MUTE_AUTHOR, _NOT_RELEVANT.
  • The evaluation settings of the serving-side beam decoder are eval_num_batches=20, eval_beam_width=128, and eval_bs_per_device=8 verified.
  • The inference runner separates a stage that generates SIDs with beam search from a stage that turns the generated SID prefixes back into an actual set of post_ids verified — sid_retrieval_runner.py:21-80.
    • The runner file is sid_retrieval_runner.py, and SidPostIndex/SidBeamResolver handle the stage that turns prefixes back.
    • Among the runner's hyperparameters, beam_width and decode_levels are flags. If decode_levels < 6, generation stops at the prefix level and returns the prefix-sharing set (prefix retrieval).
    • This pairs with home-mixer SidSourceMinPrefixDepth=3. The server generates 3–6 levels, but every post matched at level 3 can be returned with prefix depth 3 as its score.
    • Fields such as _CorpusView.sentinel_idx, post_ids_with_sentinel, and author_ids_with_sentinel show that the corpus is loaded as a prebuilt index (SID → posts).
    • That is, at serving time the corpus is "an SID trie plus the set of post_ids held at the leaves", and when beam search picks the top-K paths on the trie, the posts under those paths become candidates inferred. In the code, the detailed structure of SidBeamResolver is in another file (xrex/inference/sid_post_index.py), which does not appear in this commit's diff.

This design overlaps with the published generative retrieval family: Google TIGER (NeurIPS 2023), Alibaba PailitaoGR (2025), Kuaishou OneRec (2025), Tencent BARGE (2026), and ByteDance GEAR (2026-09-30). The X version differs in the following points:

  • It uses a comparatively narrow 6-level × 256-codebook space (TIGER uses 3-level × 256 plus one collision-disambiguation token, and OneRec uses 3-level × 1024).
  • It feeds the 1023-token user action history in as the condition as is (TIGER limits the user history to at most 20 items in training).
  • It passes shared_prefix_depth to the upstream ranking as a score (TIGER uses the generation probability).
  • It shares its vocab design with the two-tower model. However, the embedding tables are currently separate for each model (see the implications below).

Two-tower runs ANN in vector space, while SID retrieval runs beam search in code space. In effect, the two are declared as a complementary structure, not a duplication.

What we learnedC. Phoenix gained a bundle of CUDA kernels that handle embedding tables sharded by row

  • A new bundle of CUDA kernels handles embedding tables sharded by row verified — phoenix/xrex/cuda/row_emb/.
    • It is a 12-file bundle with 3,180 new lines in total.
    • row_emb_api.cc(+766) · row_emb_comm.cc(+1,104) · row_emb_kernel.cu(+629) · row_emb.py(+290) · row_emb_comm.hpp(+256) · comm_utils.cc(+146)
    • row_emb_kernel.hpp(+135) · row_emb_common.cuh(+82) · cuda_error_utils.hpp(+68) · comm_utils.h(+57) · comm_utils.py(+47) · __init__.py(+2)
  • If Phoenix's existing async_emb kernel handles embedding tables sharded in the column direction, the new row_emb handles tables sharded in the row direction verified.
    • With N vocab entries, N / group_size rows are loaded onto each rank.
  • This design matters when the vocab grows to hundreds of millions (item 100M, author 30M) and the embedding table has to span tens to hundreds of GPUs inferred. Each token lookup only has to query the rank it belongs to, and the all-to-all occurs when sending tokens to the lookup rank inferred.
  • The Python binding row_emb.py registers 6 JAX FFI targets on the CUDA platform and passes the shard spec bundled in a single NamedTuple verified — row_emb.py:30-80, 100-290.
    • The names of the FFI targets are below.
      • xrex_row_emb_lookup_start, _lookup_done, _stage_update
      • _rowwise_adagrad_update_start, _rowwise_adagrad_lazy_update_start, _rowwise_adagrad_update_done
    • The NamedTuple is RowEmbContextHandle, and it bundles the values below.
      • context_id · group_size · flatten_replicas · tokens_per_rank · emb_width · rows_per_rank
      • recv_capacity · num_devices_per_node · mesh · table_axis · data_axis

There are 3 key design decisions.

  1. Lookup is split into two stages. A window opens between the two FFIs in which other operations can run, and all-to-all communication overlaps with computation inside that window. This is a pattern like Pathways/MegaScale.
    • lookup_start takes token_ids and the local shard table and returns table_out and lookup_pin (a float32 scalar). lookup_done takes the pin and returns embeddings.
    • tokens_per_rank is set as tokens_per_batch / group_size.
    • The receive buffer cap is reserved in advance as recv_capacity = min(ceil(tokens_per_rank × recv_factor), tokens_per_rank × group_size). If recv_factor is small, drops occur when there are many collisions, and if it is large, the buffer is wasted.
  2. Rowwise Adagrad is fused into the same 2-phase structure as lookup.
    • rowwise_adagrad_update_start takes the table, row_state (the accumulator of each row), and gate, and returns the table being updated itself. It updates in place with input_output_aliases={0:0, 1:1}.
    • rowwise_adagrad_update_done returns a completion signal.
    • rowwise_adagrad_lazy_update_start is a variant that takes last_step and step and lazily updates only the rows that were accessed. This is a common pattern for sparse embedding tables.
  3. A gate input guarantees the XLA execution order.
    • Every FFI function takes gate: jax.Array as input and mixes a float32 scalar into its output. This explicitly creates a side-effect chain that XLA cannot freely reorder.
    • attrs() passes communicator identifiers such as context_id and flatten_replicas as FFI attributes. The same context_id reuses the same communication group.
  • Validation checks the following conditions:
    • vocab_rows % group_size == 0 (even distribution of row shards)
    • tokens_per_batch % group_size == 0 (even distribution of token shards)
    • emb_width % 8 == 0 (a multiple of 8). This appears to be a bf16 tiling requirement inferred.
    • recv_factor > 0
    • The table_axis axis must be contained in the data_axis axis. If it is not, a ValueError is raised saying "there is not exactly one token shard per communicator rank".
  • Phoenix's async embedding utility was rewritten as an adapter layer that accepts both kernels verified. It now supports both column and row sharding strategies.
    • The file is phoenix/xrex/utils/recsys_async_emb.py (+112/−36), and the kernels it accepts are async_emb and row_emb.
    • It distinguishes row from column with an is_row_sharded(context_handle) branch. If row-sharded it returns table_spec as P(table_axis, None), and if column-sharded as P(None, table_axis).
  • This kernel bundle is an extension of the general Phoenix embedding table design, not dedicated to the SID retrieval model, but in the context of being released together in this commit, the appearance of a model that needs row-sharded embeddings (that is, a model with a very large vocab) appears to be the trigger inferred.
    • Two-tower can also run column-sharded, but for a generative model row-sharded is more natural given the lookup pattern, because each token references only a specific range of its own vocab level.

Why it matters A path that generates SIDs directly and returns them as candidates has been released in X code for the first time. However, the default is off, so the checkpoint to watch for real-traffic use is the day the FeatureSwitches cron turns it on. Three facts overlap in this commit.

  1. This is the first commit in which X released generative SID retrieval as three complete parts: a "separate microservice + dedicated Transformer training and serving stack + home-mixer candidate source wiring".
    • Until now, X's SID has appeared indirectly in two places. One is an input feature of the two-tower item tower (the use_post_sid flag in xrecsys_two_tower.py, released 2026-09-30). The other is the 800k backfill QPS cap in phoenix-rankall (SID_BACKFILL_QPS_CAP = 800_000, released yesterday).
    • No line that generates SIDs directly and returns the result as candidates had been released.
    • Today's commit releases the whole chain below at once.
      • On the Phoenix side, it introduced four files for a dedicated Transformer model (8-layer, GQA 20:4, 1030-length context, 6-level × 256-codebook): config, model, trainer, and runner.
      • It released the gRPC client of the separate microservice xai-recsys-sid-retrieval.prod.fou.twitter.biz and its request shape (seed_post_ids, shared_prefix_depth scoring, prefix retrieval condition min_prefix_depth=3).
      • The home-mixer SidSource sends candidates labeled with the same ServedType as PhoenixMOESource.
    • Had these three parts been scattered across separate commits, it would have been a "work in progress" signal, but the fact that they were released together in one commit means the wiring is close to complete.
    • However, since EnableSidSource=false is the default (off), the checkpoint to watch for real-traffic use is the day it is turned ON in the FeatureSwitches cron.
  2. Two-tower retrieval and SID generative retrieval are designed as "two layers over the same vocab space", not as "replacements for each other".
    • The two models share the same user, item, and author hash vocab (100M · 30M · identical double hashing scales/biases). Comparing xrecsys_sid_retrieval.py:30-45 with the figures in xrecsys_two_tower.py, released 2026-09-30, shows this.
    • Generative retrieval is costly in the two ways below, so X appears to have chosen a complementary structure in which two-tower first handles the broad recall that can run with ANN, and SID retrieval handles supplementary recall by prefix-sharing degree inferred.
      • One is the time complexity of SID generation (beam_width × decode_levels × codebook size).
      • The other is the cost of maintaining the SID index on the corpus side.
    • With the same vocab, both models could run on a shared embedding table. However, in the config released now, each model has its own embedding table. Whether they are unified into a shared embedding has to be observed in the next commit.
  3. The row-sharded embedding CUDA kernel bundle is a two-axis extension of the Phoenix embedding design itself.
    • The 3,180-line row_emb was not added solely for the generative retrieval model. However, in the context of this commit bundle, it is natural to read the huge-vocab embeddings that SID generative retrieval requires (100M · 30M · 6-level × 256 codebook) as the trigger.
    • The shared adapter recsys_async_emb.py lets a model choose between the existing column-sharded kernel async_emb and the new row-sharded kernel row_emb, in effect leaving room to pick the best sharding per model.
    • Two-tower can keep the user tower and the item tower each column-sharded, but in the SID generative model each token refers only to its own vocab range during the generation stage, so row-shard likely yields a more compact communication pattern inferred.

Radar

0 papers passed all the radar acceptance criteria. The criteria are the following three:

  • ① Platform authors or a production A/B test
  • ② Mechanism novelty
  • ③ Large-scale results

The scope is the arXiv cs.IR window 2026-09-30–2026-10-01; of 30 requested, all 30 <entry> items were parsed. The three items below were borderline, but all were rejected.

  • arXiv 2610.02057 Optimizing Effective Training Time for Large-Scale Recommendation Systems. Rejected because it is an operational case of Meta's recommendation training infrastructure.
    • Confirmed as a Meta affiliation. "Meta Platforms, Inc.", "Meta Engineering Blog", and "Meta internal" appear many times in the PDF strings.
    • It is a fleet-scale operational case that raised the ETT% (Effective Training Time) of the recommendation training fleet from 80% → 90%+. It covers asynchronous checkpointing, communication removal, pipeline overlap, dynamic shapes, PyTorch 2 compile cache reuse, and more.
    • The reason for rejection is that it is an operational win in recommendation training infrastructure. Its nature differs from the retrieval and ranking mechanism novelty of radar criterion ②. "Training throughput" is also not an item that enters the service canon, so it was not folded in.
  • arXiv 2610.01533 Neither Black nor White: Balancing Semantic and Collaborative Signals with Graph-Informed Semantic IDs (GrIS). Rejected because it makes no production deployment claim.
    • Confirmed that all authors are affiliated with Huawei Ireland Research Centre.
    • It covers a mechanism that mixes SID and collaborative signals through a graph, but makes no production deployment claim.
    • The reason for rejection is that the platform and deployment condition of ① is empty.
  • arXiv 2609.39043 Routing Between Generative and Collaborative User Profiles: A Serving-Time Gate for Controllable Novelty. Rejected because it is not a tracked service.
    • The authors are affiliated with Comcast Technology AI and DePaul University.
    • The paper proposes a structure in which a "serving-time routing gate selectively routes users between an LLM-profile model and a collaborative sequential model". Within an NDCG loss budget of 5%, it gains Novelty@10 +6.5% and routes only 12.5% of users.
    • The mechanism is interesting (cost-aware selective LLM use).
    • The reason for rejection is that Comcast's Xfinity Stream is not a tracked service, and its value as a feed/ranking platform to track is low (video recommendation for streaming TV).
