1Safety filter waits longer on backends and caches authors for failed lookups — X

Source xai-org/x-algorithm@fee1d0f — public source code, 2026-09-10, 33 files, +1587/−391. These notes number X commits after the Gen4 release in sequence; this commit (2026-09-10, fee1d0f) is Gen4+19.

Background Since the Gen4 release on 2026-08-13, X has mirrored the For You pipeline source code to xai-org/x-algorithm about twice a day. visibility-filtering (VF, code in visibility-filtering/) is the gRPC safety filter service of the X home timeline and a Gen3 stack rewritten in Rust. When home-mixer (the service that assembles the For You feed) builds the candidate list, VF fetches tweet metadata and author labels for each candidate from two backends, fills them in, and feeds them to the rule engine. This commit is a medium-sized diff focused on VF; it fixes the time budget and failure handling of the backend lookups and shrinks the author label data structure.

The step in which VF fetches data from the backends and fills it in is called hydration. Tweet metadata comes from TES (Tweet Entity Service, X's core tweet lookup service). Author labels come from Gizmoduck (the user profile service). Hydration involves three intertwined decisions: how long to wait for the two backends, how far to proceed with verdicts when a lookup fails, and where latency is spent. This commit touched all three.

The changes fall on two main axes.

  • Axis 1 is the hydration time budget and failure handling. The wait time was increased, a path was opened to evaluate author-based rules from the cache even on failure, and recording of where latency is spent began.
  • Axis 2 is author label reduction and preparation of a cache primitive. Only the 11 labels the rules use remain, and the new cache is not yet used.
  • There are also side changes outside axis 2. The proto constants and model code of the recommendation model, an ads log field, a batch job of the label transparency tool, and the image builder changed.

What we learnedA. Unified the wait time for both backends into one 390 ms constant, raising it substantially

  • VF's hydration timeout was replaced by one unified constant, and the timeout of Strato (the X internal system that code goes through to look up or store data) calls rose from 100 ms for TES and 80 ms for Gizmoduck to 390 ms verified — visibility-filtering/hydration/mod.rs

    • Other files covered by the same change: visibility-filtering/server_deps.rs, visibility-filtering/hydration/gizmoduck_hydrator.rs, visibility-filtering/hydration/tes_hydrator.rs

    • A new crate-internal constant was added to visibility-filtering/hydration/mod.rs:

  • This constant is used in two layers. The first is the hydrator layer. The client timeout of the TES and Gizmoduck hydrators had been a local constant of 150 ms each since the Gen4 release; both now reference this constant verified (same commit).

    • The CLIENT_TIMEOUT of the two hydrators was previously a local constant of 150 ms each, and now both reference crate::hydration::HYDRATION_TIMEOUT.

  • The second is the Strato client layer. The timeout constants hardcoded per service were both replaced by the value of this constant verified (same commit).

    • Before: TES 100 ms (TES_STRATO_REQUEST_TIMEOUT_MS: u64 = 100), Gizmoduck 80 ms (GIZMODUCK_STRATO_REQUEST_TIMEOUT_MS: u64 = 80)
    • After: both HYDRATION_TIMEOUT.as_millis() as u64

  • That is, the timeout that Strato callers actually wait for rose 3.9× and 4.9× for the two services respectively verified (same commit). It is a decision to give the VF service a much more generous latency budget for hydration.

  • Timeout-induced disagreements were possibly observed in the verdict-comparison canary introduced by Gen4+7 (reference_compare.rs, 2026-08-24) inferred, and this increase reads as the response to that.

What we learnedB. Even when the TES lookup fails, author-based rules are evaluated with the author id left in the cache

  • The priority in which resolve_candidate picks the author id is request, TES core, then cache verified (same commit).

    • If the request carries the author id directly, that is used; otherwise it is taken from the TES core if present; otherwise the cache fallback is used. If no author id is obtained from any of the three paths, that candidate skips verdict evaluation.

A and B are effectively one project. While A allows hydration to take longer by raising the timeout 2.6–4.9×, B builds an automatic fallback path for the case where it still fails.

This fallback does not reverse the "TesHydrator media fallback cache removed wholesale" observed in Gen4+9 (2026-08-26). The media fallback cached and reused the media information TES returned; this author-id fallback revives the previous value only for tweets TES could not respond for, and makes a partial verdict that evaluates only the author-side rules. In other words, it is the revival of a partial verdict, not the reuse of a result.

This change reads as narrowing the remaining robustness gaps after the large VF hydration simplification in Gen4+15 (2026-09-04) thinned the code by a net reduction of 800+ lines.

What we learnedE. A new sharded cache primitive arrived, but nothing uses it yet

  • A new 32-way set-associative × 64-shard CLOCK cache primitive arrived in VF, but it is not yet connected anywhere verified — visibility-filtering/clock_cache.rs

    • Other file changed with it: visibility-filtering/lib.rs
    • visibility-filtering/clock_cache.rs is a new file of 446 lines, registered in visibility-filtering/lib.rs with the single line pub(crate) mod clock_cache;. No code in this commit references this file.

  • The 32-way × 64-shard cache that arrived as the new file clock_cache.rs (446 lines) carries a dead_code attribute that suppresses the compiler warning verified (same commit). From this we infer it has no consumer yet, and which hydrator consumes the cache in clock_cache.rs in the next commit is the thing to watch.

    • File header:

    • It tells the compiler explicitly: "In non-test builds, we know this module is dead; do not emit a warning; the reason is that no consumer is attached yet."

  • It takes capacity capacity as an argument, creates set_count = capacity / WAYS sets, and distributes them across 64 shards verified (same commit). One shard holds several sets, and one set holds 32 slots (ways).

    • The value stored in a slot is the tuple (key: u64, generation: u64, value: Option<V>).

    • Main definitions:

  • The CLOCK algorithm runs as follows verified (same commit).

    • Insert (insert(generation, key, value)): if the same key already exists and the stored generation is larger, it is skipped. This is to keep an old value from overwriting a new one. Otherwise it overwrites in place and marks it Mark::Referenced. If the key is absent, the hand rotates, decaying Referenced → Cold, and inserts at the first Cold or Empty slot it meets.
    • Lookup (get(key)): if it finds the same key, it promotes it to Mark::Referenced and returns Lookup::Found(value). If absent it is Miss, and if the stored value is None it is NotFound.
    • Generation: for each request, begin_request() -> u64 assigns a monotonic value. This value decides whether a later request may overwrite an older cache value.

  • This cache is a primitive separate from the existing FallbackCache verified (same commit).

    • The existing FallbackCache is hydration/fallback_cache.rs, folded into the canon in Gen4, and is a TinyLFU based on moka::sync::Cache protected by a single mutex.

  • The two caches differ in locking unit, replacement policy, slot layout, value type, and concurrency verified (same commit).

Axis Existing FallbackCache (moka and Mutex) New ClockCache
Locking unit One Mutex for the whole cache One Mutex per shard (64)
Replacement policy TinyLFU (probabilistic frequency) CLOCK (Referenced ↔ Cold decay)
Slot layout Dynamic hash map Fixed 32-way set-associative array
Value type Arbitrary (Clone) Copy constraint (suited to values around the size of u64)
Concurrency Can bottleneck on one mutex Mostly non-blocking with 64-way sharding

That is, it reads as a new hot-path cache that is far more resistant to write throughput and lock contention. The main thing to watch is which hydrator (TES author_id? Gizmoduck AuthorFeatures? SafetyLabel expiring cache?) it connects to as a backend in the next commit.

Radar

Added one Kuaishou cascade recommendation paper to "New this month" in radar.md. The UniRec proposed in the paper is a method that aligns the fusion of the pre-ranking and ranking stages of a cascade recommender through joint learning of the two stages, and in the Kuaishou production A/B it raised app usage duration by +0.616% verified — arXiv 2609.11052, submitted 2026-09-10.

  • The problem it addresses is that the cascade stages of industrial recommendation (pre-ranking, ranking) are optimized separately under different objectives, feature spaces, and latency constraints verified (same paper). The upstream filters out items the downstream prefers, and the downstream fusion offsets upstream improvements.
  • The two fusion agents share part of the input embedding and are trained together in a single computation graph, so gradients flow between stages verified (same paper).
  • Dual-axis preference alignment works in two directions verified (same paper).
    • Vertical: transfers downstream pairwise preference to the upstream fusion score.
    • Horizontal: recasts dozens of pairwise objectives over heterogeneous prior signals as bidirectional preference evidence.
  • In addition, attribute group-relative regularization suppresses the side effect of unconstrained end-to-end fusion over-concentrating on particular attribute groups verified (same paper).
  • In a 21-day production A/B, app usage time showed a +0.616% relative gain, and the model was fully deployed on the Kuaishou platform verified (same paper).
