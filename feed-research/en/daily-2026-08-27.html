1-1. A general path for scorers to request account actions directly was added

AES (abuse-enforcement-service) now accepts and runs action requests that scorers attach directly, in addition to static YAML rules. Only requests that pass the action kinds fixed in code and the dynamic allowlist run, and rejected requests are logged with a reason.

Background abuse-enforcement-service/ (AES) is a sub-repo that was fully revealed at the first Gen4 release. AES is a rule engine that takes model scores and maps them to actual account actions.

  • Examples of the model scores it receives are the BDSM (fraudulent-account detection over account behavior sequences) bot head, the LLM slop label, and PandaReports.
  • The account actions are label / bounce_captcha / bounce_arkose / spam_liveness_check / suspend.

Previously, the AES rules were statically encoded in abuse-enforcement-service/service-lib/rules/enforcement_user.yaml and enforcement_post.yaml. The approach states explicitly, as CEL expressions, a mapping of which action to take when a label is attached. For example:

This approach had the limitation that the AES YAML had to be edited every time a new scorer was added. Gen4+8 broke that coupling.

  • If a scorer attaches a list of requests directly, AES runs only those that pass the fixed allowlist.

    • This general passthrough is connected by generic_actions.rs (663 lines, new) and two corresponding YAML rules (act_requested_actions and platform_row_without_requested_actions).
    • The full path of the new file is abuse-enforcement-service/service-lib/src/generic_actions.rs, and all 663 lines are new.
    • The request list a scorer attaches is the requested_actions list.

  • The action kinds a scorer can request are fixed as code constants.

    • Only 5 kinds can be requested for the user entity and 2 for the post entity. A client cannot invent an arbitrary kind string.

    • At most 16 actions can be requested per message.

  • Requests go through a double fail-closed (reject if a condition is not met) verification. The verification in action_to_spec(entity_type, action, allowlist) has the following five steps:

    1. The request must pass hardcoded_kinds. If it does not, the result is "unknown_kind", and if the kind belongs to a different entity type, it is distinguished as "entity_type_mismatch".
    2. The kind must be in the dynamic GenericActionAllowlist.kinds. If it is not, the result is "kind_not_allowlisted".
    3. For the suspend or suspend_author kind, the policy must be in allowlist.suspend_policies. If it is not, the result is "policy_not_allowlisted".
    4. For the label or post_label kind, all three conditions must be met.
      • action.labels must not be empty ("no_labels").
      • Every label must be in allowlist.labels ("label_not_allowlisted").
      • ttl_msec >= 0 must hold ("invalid_ttl").
    5. Duplicates are removed. If the same spec is already in the list, the result is "duplicate_action".

  • Rejected actions are not simply discarded but observed.

    • Rejected actions are collected into a SkippedRequestedAction { kind, head, reason, count } struct and attached as JSON to outcome.info["requested_actions_skipped"].
    • They are also aggregated in a separate metric, GENERIC_ACTION_TOTAL{entity_type, kind, outcome=resolved|skipped, reason}.
    • In other words, the reason a request failed to pass is left in the log as is. The scorer team can immediately see why its request was rejected.

Two YAML rules were added as a pair to enforcement_user.yaml.

  • If a scorer has declared the general action pipeline with its own label (abuse_platform_requested_actions) but the actual action list is empty, the request is skipped.
  • If there is at least one action, it is routed to the verification pipeline above through the act_requested_actions decision.
  • enforcement_post.yaml gained only one symmetric rule; the post side has no platform_row skip rule.

The AES decision also gained a new variant that handles the request list.

  • A new Decision::ActRequestedActions variant was added to abuse-enforcement-service/service-lib/src/lib.rs (+276/−19).

  • When run_enforcement_inner meets this variant, it handles it as follows:

  • If no action passes the allowlist, the result is Skip(REQUESTED_ACTIONS_DENIED), and if at least one does, it is Act(specs).

  • In other words, even when all requests are rejected, the outcome is explicitly skip, so what was requested and why it was rejected remain in the JSON in outcome.info.

A path from dynamic_config to generic_action_allowlist was also added.

  • A new method was added to growthbook.rs (+126).
  • GrowthBook appears to be X's dynamic config and feature-flag system inferred.
    • If so, the allowlist, that is, which kinds a scorer may request and which policies and labels it may use, can be gated by A/B at runtime.
    • When attaching a new scorer, allowlist entries can be switched on and off in the GrowthBook console without deploying code.

The first client of this structure, panda_reports_embedding_v10_rough_spam, came in with it. A new rule was added to enforcement_user.yaml.

  • This rule itself is a static mapping in the old style. However, the label name itself carries new information.

1-2. VM Ranker drops local computation and uses the scores the server returns as they are

In the VM Ranker path, the local computation layer that home-mixer (the service that serves X home timeline feed requests such as For You and Following) used to run is gone. Now home-mixer uses the scores returned by the rank server as they are, and diversity is handled by the server-side DPP (a diversity re-ranking technique).

Background VMRanker is a remote gRPC service that acts as the slate reranker in home-mixer. It performs DPP (Determinantal Point Process)-based diversity re-ranking over the candidate scores that Phoenix produced, with parameters θ=0.65, K=150. Until now, home-mixer/scorers/vm_ranker.rs supported two value models.

  • For author_diversity, home-mixer computed locally a value that applies author-diversity decay based on the MPN fold-back and passed it to the rank server.
  • For default, the score returned by the rank server was used as it was.
  • The 7 SID field connections of Gen4+3 (2026-08-18) were attached to this vm_ranker. SID (semantic ID) represents an item as a sequence of discrete token IDs.

Gen4+8 greatly simplified this path. It removed the 88 lines of ranking_scorer::effective_head_weights and the 128 lines of MPN fold-back.

  • The author-diversity value model and the MPN fold-back logic were deleted from the VM Ranker scorer (home-mixer/scorers/vm_ranker.rs, +11/−128).

    • The deleted code:

  • The only newly added constant is const DPP_VALUE_MODEL_ID: &str = "dpp";. That is, one value model ID (author_diversity) was deleted and replaced with another (dpp).

  • The new score() passes the score returned by VM Ranker straight through and does not recompute it locally. Both the MPN fold-back and the AuthorColdStart post-processing are gone.

  • The 88-line method that combined weights for each candidate and sent them to VMRanker was also deleted (home-mixer/scorers/ranking_scorer.rs, +28/−201).

    • The deleted method is ScoringWeights::effective_head_weights.
    • This method was logic that built an xai_vm_ranker_proto::HeadWeights protobuf for each candidate and sent it to VMRanker.
    • It combined weights per candidate, for example the post_unexplored multiplier computation, the low-fav-rate penalty on click_dwell_time, the quoted_vqv duration check, and the per-candidate adjustment of the reply weight, and all of it is now gone.

This simplification has four implications:

  • Diversity computation moved from the client, home-mixer, to the server, VMRanker.
    • Previously, home-mixer built head weights carrying the diversity requirements for each candidate and sent them to the rank server.
    • Now the rank server handles diversity with its own DPP logic, and home-mixer only consumes the returned scores.
  • What the rename from author_diversity to dpp actually amounts to is still unclear.
    • This commit alone cannot settle whether dpp really refers to the DPP of the existing re-ranking section (θ=0.65, K=150) or to a different DPP instance used only inside the rank server inferred.
    • Traces of tidying up the VMRankerValueModelId parameter also remain in home-mixer/params/param.rs (a net decrease, +10/−29).
  • AuthorColdStart did not disappear; it changed place.
    • The file home-mixer/scorers/author_cold_start.rs still exists and was modified by +12/−9.
    • Because it was removed only from the VMRanker post-processing, it may still be applied at other points such as RankingScorer or the Phoenix pipeline.
  • The values the deleted effective_head_weights computed now appear to be computed by the server with its own logic, or the concept of head weights itself appears to have been replaced in another way.
    • The head weights this method computed are favorite, reply, retweet, share, dwell, quoted_vqv, and so on.
    • It is more natural to interpret that VMRanker consumes the original phoenix score as it is and applies only its own DPP inferred.

This simplification extends the main direction of Gen4, that is, the trend of stripping local computation and caches from home-mixer and preferring served outputs. It pairs with how the UseServedSlateContext gate of Gen4+5 moved slate context computation from local to Phoenix serving.

1-3. The Following feed also follows blocks by quoted and retweeted original authors

The Following feed extends its block-relationship check to quoted authors and retweeted authors. If the original author has blocked the viewer, the viewer does not see the post even when someone the viewer follows quotes or retweets it.

Background The Following surface is a reverse-chron pipeline that shows only the latest in-network posts. Since Following got its own VF hydrator branch in Gen4+3, this pipeline has kept being refined. This time, work was added to extend block-relationship handling to quoted authors and retweeted authors.

  • The new hydrator (a stage that fills in fields on each candidate), FollowingBlockedByHydrator, asks SocialGraphClient which of the quoted author and the retweeted author is blocking the viewer.

    • The file is home-mixer/candidate_hydrators/following_blocked_by_hydrator.rs (65 lines, new).

    • For each candidate, it collects the user_id lists of the quoted author and the retweeted author and asks in one call.

    • The result is set on two candidate fields. author_blocks_viewer is true if the retweeted author blocks the viewer. quoted_author_blocks_viewer is true if the quoted author blocks the viewer.

  • A new condition was wired into AuthorSocialgraphFilter, a filter already in Gen4, and it now removes the candidate if any of 6 conditions is true.

    • The filter file is home-mixer/filters/author_socialgraph_filter.rs.

    • Previously, it checked only block and mute from the viewer toward the author. Now it expands to six branches, including the direction from author to viewer and the original authors of quote and retweet chains.

  • The two stages were wired into the reverse-chron pipeline, and the filter was placed before the VF filter (home-mixer/candidate_pipeline/reverse_chron_posts_pipeline.rs, +27/−2).

    • AuthorSocialgraphFilter sits before the VF filter. That is, candidates filtered out by block or mute skip the VF verdict lookup itself, so performance also improves.
    • SocialGraphClient is a client in the XAI candidate_pipeline component_library. It connects to flock over TLS S2S, and the service itself is not public.

This change has three implications:

  • The meaning of a block has widened transitively.
    • Previously it was "if you do not follow A, A's posts are not shown to you", but now it extends to "even if you follow A, if A retweeted original author B and B has blocked you, the post is not shown".
    • B's block of you is respected regardless of the following relationship.
    • It is a broad-scope policy decision, and we interpret it as a signal that X has started to explicitly block bypass exposure through quotes and retweets inferred.
  • On performance, one more remote lookup to SocialGraphClient is added per request.
    • However, because it is a batch lookup that asks check_blocked_by for the quoted and retweeted user_ids of all candidates at once, the cost grows sub-linearly with the number of candidates rather than being fixed.
  • This hydrator is wired only into Following.
    • The hydrator list of the For You (algorithmic) pipeline does not yet include this hydrator.
    • If the wiring is symmetric, it may be attached to For You in the next commit inferred.

  2. It removes posts from these accounts in the For You pipeline.
  3. It makes an exception for accounts the viewer explicitly follows.

The way the list is included reflects a transparency practice.

  • As a compromise between open source and user privacy (preventing leaks of internal user_id), it keeps verifiability while hiding X's internal user_id mapping.

    • The exact number of accounts has to be computed separately by counting diff lines. If each account takes 2–4 lines in a 4947-line file, the scale is roughly 1200–2000 accounts inferred.

1-5. The Phoenix index also loads data from before the minimum-age condition is met

For each window that has a minimum age since posting, Phoenix's offline indexing pipeline now also loads data that has not yet met that condition, as a separate snapshot. This change went into the base repository of the Phoenix rankall pipeline.

Background phoenix-rankall/ is Phoenix's offline indexing and aggregation pipeline. It maintains the candidate pool split into several windows, for example 1fav_uec_1day, video_14day, and evergreen_video_1825day. Gen4+8 continued the flow of the two changes below and expanded the base repository of phoenix-rankall itself.

  • Gen4+1 added the video_14day SID window.
  • Gen4+6 shrank the EVERGREEN retrieval dataset from evergreen_video_1825day to video_4to14day.

The change consists of new constants and loading logic in phoenix-rankall/src/store/base.rs (+202/−61).

  • If a window has a min_age condition, the data from before min_age that has not yet passed the condition is kept in a separate prefloor_<window>.parquet file and loaded together.
    • An example of a min_age condition is "this pool includes only items at least N hours past posting".
  • PREFLOOR_SLACK_SECS = 6 hours is the slack time during which prefloor data is kept until it crosses the min_age threshold.

Canon update Added the subsection "Gen4+8 (2026-08-25) — rankall prefloor snapshot wiring" to the Phoenix training and index section of services/x.md.

Why it matters This change continues the flow of Gen4+2 removing the favoriteCount>=1 gate in phoenix-rankall-strato. Previously a candidate had to pass the condition to enter the index, but now rankall keeps candidates that have not yet passed in a separate pool so they can reach production immediately when they pass. This is an improvement for cold start and freshness, and it is likely to reduce index latency for new posts inferred.

1-6. The Phoenix download client now actually respects its concurrency cap

An issue was fixed where the actual number of concurrent downloads could exceed the configured cap when Phoenix serving downloads embedding tables and checkpoints. 2 new regression tests were also added.

  • copy_port is the client that downloads embedding tables and checkpoints from object storage (S3/xai-o2) in Phoenix serving.

    • The file is phoenix/crates/serving/xai-recsys-engine/src/copy_port_client.rs (+155).

  • The previous code ran several downloads in parallel with join_all(futures).await.

    • However, when join_all polls the futures sequentially inside a rate limit batch, the actual in-flight concurrency could exceed max_concurrent.

  • After the fix, each future is wrapped in a separate task with tokio::task::spawn. This tokio::spawn hardening fixes the rate limit so it respects the in-flight cap without parallel polling.

    • Wrapped this way, the runtime scheduler actually runs them in parallel.
    • The rate limit logic (join_rate_limited) decides precisely when to issue the next batch based on the in-flight count.

  • The two new regression tests check the following.

    • rate_limit_caps_in_flight_despite_spawn checks whether peak in-flight is exactly 2 when a concurrency=2 cap is applied to 6 downloads.
    • rate_limit_paces_between_spawned_batches checks whether pacing between batches is maintained.

Why it matters This change is hardening that fixes the accuracy of parallel download throttling at serving time, and it pairs with Gen4+7's multi-node hardening of the Phoenix checkpoint loader, which fixed an OOM in the restore path. Both are an extension of the maturation cycle of training and serving infrastructure that followed Muon and GB300 training being formally included in the export in Gen4+6. The fact that such stability fixes attach to commits every day is itself evidence that X keeps devoting organizational resources to keeping the Gen4 open-source release verifiable and trustworthy in production.

2Tlow raised production CTR with a flow-based tokenizer — WeChat

Source Tlow: Flow-based Item Tokenizer for Recommendation — arXiv 2608.24176, 2026-08-25 v1, paper. There are 6 authors (Nian Li, Chonggang Song, Jingtao Ding, Lingling Yi, Yong Li, Qingmin Liao). The HTML version of the abstract states a production A/B at China's largest social media platform WeChat, so we confirmed the affiliation.

Background The item tokenizer, a core component of the Semantic ID (SID) line, is the module that converts each item's semantic embedding into a sequence of discrete token IDs. The de facto standard is RQ-VAE (Residual-Quantized VAE). After Google's 2023 TIGER paper, several production systems adopted it, including Netflix Foundation Model and Kuaishou PushDualGen. However, RQ-VAE has three known problems.

  • Codebook collapse occurs, so most code slots die and only a few are used.
  • Quantization error accumulates in the residual, so the error grows in deep quantization layers.
  • Because of discontinuity, similar items map to completely different token sequences, which makes training difficult.

A flow-based model transforms the embedding space into a learnable distribution with an invertible neural network and inverts it back. This paper (Tlow) approaches the problems above with a normalizing flow, and the authors claim that flow-based tokenization is better than RQ-VAE on two axes: codebook utilization and semantic locality.

What we learnedA. In the production A/B, the CTR gain was larger for new items

  • In the production A/B, global CTR rose +10.32% and new-item CTR rose +11.64% verified.

    "The retrieval model based on token IDs improves user CTR by 10.32% globally and by 11.64% for new items." — Tlow abstract, 2026-08-25

    • A larger gain on new items suggests it is especially strong at cold start verified — same abstract.
    • The key benefit of the semantic tokenization line, namely obtaining meaningful representations even for cold items, was confirmed in production metrics verified — same abstract.

3TAGR raised revenue by +16.1% in live-commerce ads — anonymous platform

Source TAGR: Temporally Adaptive Generative Recommendation for Industrial Live-Streaming Advertising — arXiv 2608.24034, 2026-08-25 v1, paper. There are 10 authors (Wencai Ye, Guangyi Liu, Chaoyi Wang, Wenbin Luo, Shengyu Wang, and others). The author affiliation and platform name are not stated in the abstract. The abstract says only "a large-scale e-commerce live-stream advertising platform".

Background Live-streaming ads place strong freshness requirements on the recommender, because content, products, and user feedback change in real time. So far the generative recommender (SID-based) line has mostly assumed a static catalog. In live streaming, the time scale at which streams open and close is in minutes, so a static token vocab stays valid only briefly. This paper (TAGR) presents generative recommendation tailored to rapidly changing live content, products, and user feedback.

What we learnedA. In the production A/B, entry rate, cart click rate, and revenue all rose

  • The production A/B results are as follows verified.
    • live-room entry rate +8.5%
    • shopping-cart click rate +7.4%
    • revenue +16.1% over production baseline

What we learnedB. The abstract does not give the concrete mechanism for adapting to the time axis

  • The architecture is Temporally Adaptive Generative Recommendation.
    • The abstract describes it as "designed for rapidly changing live content, promoted products, and user feedback".
  • Concrete time-axis adaptation mechanisms such as the tokenizer retraining cycle or online updates do not appear in the abstract. The body text needs to be checked, but we skipped it in this batch.
