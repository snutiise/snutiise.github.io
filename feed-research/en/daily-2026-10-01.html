1Six Home feed cold-start parameters changed and VF lookup was rewritten — X

Source xai-org/x-algorithm@77d431a — xai-org/x-algorithm public repository, 2026-09-30 03:53:42Z (UTC), commit. Line counts are +3,306/−1,489, and 69 files changed. These notes number the X commits after the Gen4 release in order, and this commit is Gen4+32. It came one day after yesterday's commit Gen4+31 a707cc2.

Background The hydration layer of visibility-filtering (VF, X's tweet filter pipeline) flipped three times over four days, from 2026-09-25 to 09-29. Hydration is the stage that fills in the original data needed for a verdict by looking it up in batches from backend services.

  • Gen4+29 (2026-09-25, bf7db1b) expanded the Hydrator enum from 7 to 17 variants and introduced three data-driven plan/execute/sources files.
  • Gen4+30 (2026-09-26, 4c5cfe8) split the state inside it into store.rs and the execution into execute.rs.
  • Yesterday's Gen4+31 (2026-09-29, a707cc2) extracted retweet.rs as a separate module and merged in-batch sources and fetched sources with a double-hydrate pattern. The double-hydrate pattern hydrates the request batch and then fills only the retweet sources with a second hydrate call.

This commit (Gen4+32) simplified the double-hydrate pattern into a single-hydrate with in-flight expansion pattern. In-flight expansion grows the request list by looking at results that arrive first while the lookup is still in progress. It also rewrote the eight Option<HydrationBatch> fields of Store as a new Fetcher<V> trait array, so that calling the same hydrator again does not re-request keys that are already claimed.

At the same time, two axes evolved separately. The xrecsys_two_tower.py of Phoenix (the ranking model stack of X For You, whose training code was released in Gen4) was added to the registry as a formal catalog. Along with this, the SID (semantic ID)-based candidate tower and sequence packing were locked into six presets. SID is a discrete code hashed across several codebook layers instead of a post embedding. Sequence packing concatenates several user sequences into one batch row. ads_head_masking, used to train the ads conversion head, moved from the JAX training graph to the numpy data loader, which made it possible to train two axes, web conversion and app (MMP, Mobile Measurement Partner) conversion, separately.

What we learnedB. VF fills retweet originals within a single call, without a second hydrate call

  • The double-hydrate pattern that filled retweet sources was simplified into single-hydrate with in-flight expansion verified — retweet.rs.
    • The changed file is retweet.rs (+562/−110).
    • Until yesterday, it filled the original batch with filter_tweets.hydrate(request), picked retweet source candidates with source_ids, and fired a second filter_tweets.hydrate(...) for the sources not in the request batch.
    • Today it calls filter_tweets.hydrate_with_retweet_sources(request) only once.
  • This single call attaches retweet sources to the request internally at the moment the pure_cores response lands verified — store.rs:308-330.
    • pure_cores is tweet core data containing the author id, the body, and the original tweet id.
    • The function that runs at this point is store.join_retweet_sources().
    • This function appends those source_tweet_ids of pure_cores that are not in the request to request_tweets and returns Landing::SourcesJoined.
  • Once sources are attached, the executor puts the initial groups back into the ready state and fires an expanded batch only for the fetched sources verified — execute.rs:112-118.
    • When execute.rs receives Landing::SourcesJoined, it puts the inputless() groups (the initial groups with no pure_core dependency) back into ready.
    • Thanks to the claim dedup of Fetcher, keys that were already in the request batch are not re-requested.
  • The new Fetcher<V> trait holds a lookup state per key, picks only the keys not yet present, and returns them as the keys to send in the actual RPC verified — fetcher.rs.
    • The new file visibility-filtering/hydration/fetcher.rs (NEW +113) contains the Fetcher<V> and AnyFetcher traits.
    • Internally it is a single HashMap<u64, State<V>>, and the state is enum State<V> { Pending, Landed(Hydrated<V>) }.
    • claim(keys) -> Vec<u64> marks only the keys not yet present as Pending and returns only the keys to send in the actual RPC. Dedup and the join with earlier calls happen together here.
    • land(&[u64], HydrationBatch) fills responses into the claimed keys and fills keys without a response with Hydrated::NotFound.
    • has_incomplete/is_incomplete/has_claimed/is_claimed decide whether to call again.
  • All eight fields that Store held were replaced with Fetcher verified — store.rs:54-84.
    • What changed is the Option<...> fields of store.rs, and the new type is Fetcher<V>.
    • Each Edge gets its own Fetcher<bool>, bundled in the array edges: [Fetcher<bool>; Edge::VARIANTS.len()]. Edge has eight variants: Follows/Blocks/Mutes/MuteRetweets/BlockedBy/SuperFollows/FollowedBy/SecondDegree.
    • The new CallRequest<'p> struct encapsulates the details of actually firing one group. Its fields are group, is_first, keys, key_count, queries, viewer_id, batch_size, and counts.
    • offer(&mut self, group) -> Option<CallRequest> claims the keys of the group, builds a CallRequest, and hands it to the scheduler.
    • On the second call (is_first=false), the record_expanded_batch metric is emitted.
  • The edge representation in the lookup plan was unified into a single eight-variant enum verified — plan.rs:8-20.
    • Part::Edge(Graph, EdgeDirection) in plan.rs became Part::Edge(Edge).
    • Edge::flock() returns the flock RPC parameters as Option<(Graph, EdgeDirection)>. Only SecondDegree is None, and it is routed through Wingman.
    • Hydrator::RootFollowsViewerSecondDegree, which was Part::Column yesterday, was promoted today to Part::Edge(Edge::SecondDegree) and is routed uniformly through the fetcher array.
  • Groups gained position and reader list fields, so the offer→land→ready schedule is computed in O(readers) per group verified — plan.rs:172-207.
    • The new fields are position: usize and readers: Vec<usize> of Group.
  • A metric that records retweet sources in three cases was added verified — filter.rs:62-79.
    • The metric is RetweetSources::{NoSource, InBatch, Fetched}.
    • The test each_request_kind_labels_its_phase_samples pins the three cases: [2] → NoSource, [1,2,3,5] → InBatch, [1,2,3,4] → Fetched verified — retweet.rs:721-738.

Why it matters Three axes overlap.

  1. The home-mixer cold start was set with production parameters. Gen4+30 added a code path to the HOME_COLD=13 channel, which was introduced in Gen4+28 (44d37eb) together with HOME_HOT=14, and today the parameters were set.

    • ImpressionThreshold was lowered from 1000 to 200, so only posts with fewer than 200 Home impressions became cold-start targets (narrower target set) verified — author_cold_start.rs:294. Thompson sampling was also turned on.
    • If cold start has so far been a narrow exploration aimed at tracked authors or new users, this parameter setting combines an extremely strict 2h freshness limit with a widely open author pool.
    • Whether this tuning holds up in the A/B is the checkpoint to watch at the next cron sync.
  2. VF hydration gained the ability to re-expand. The four-day run from Gen4+29 (09-25) to Gen4+31 (09-29) completed the data-driven pipeline skeleton and the retweet.rs module extraction.
    • Today the Fetcher<V> trait was added on top, which made claims idempotent.
    • This makes possible the Landing::SourcesJoined flow, which expands request_tweets in flight the moment pure_cores lands and re-fires the inputless groups.
    • The double-hydrate pattern of retweet.rs was simplified into single-hydrate with in-flight expansion.
    • The metric axis (NoSource / InBatch / Fetched) is set as labels, so the actual rate of expanded batches can be observed.
    • The VF client response was also promoted from Thrift Action to TweetFieldsResultState, moving to a form where the caller can build the tweet-service response directly.
    • treatment.rs isolating the rules → thrift/proto/metric projection in one file and tying dashboard.py and the six metric labels together with golden tests also completes this simplification.
  3. Phoenix retrieval two-tower was promoted to a catalog. Until now xrecsys_two_tower.py existed as a file and had minor edits across several commits, but the registry catalog itself was not locked.
    • The minor edits were the introduction of the three options qk_norm=True, attn_logit_cap=-1, and right_anchored_rope=True in Gen4+6, and the switch of the H100 attn kernel from pallas_ranker_varlen_attn to cutedsl_ranker_varlen_attn in Gen4+21.
    • Today six presets (the default, immersive-only and its GB300 version, combined and its GB300 version, and nano) were locked into MODEL_CFGS and migrated to connect to the production data pipe inferred. The evidence is that the only in-file dataset is aggregated_kafka and that the presets are well defined as hardware-aware.
    • Notably, SID-only (a 6-level codebook hash instead of post embeddings), seqpack, the H100/GB300 hardware presets, and the sharing of two heads, Home and Immersive, are organized in one file.
    • Paired with the "wiring of sid_codes into the DPA ads product too" observed in Gen4+13, this gives the SID vocabulary a large potential to unify three uses: organic posts, ads DPA, and the retrieval two-tower.
  4. The ads conversion head split along web/app axes. The delayed feedback split introduced in Gen4+6 and the ads_head_masking knob unified in Gen4+24 moved today from a float multiplier inside the training graph to a boolean mask precomputed by the data loader.
    • This secures compile stability by making the graph independent of sample_source.
    • It also trains the web conversion head and the app (MMP) conversion head separately, so that different sample subsets can be used for the keep_web / keep_app axes.
    • The mask semantics still keep the same late-window twin suppression logic; it is an exact refactor that changes only where the computation happens.
    • The mutual-exclusion assert with use_seqpack was newly added because candidate slot correspondence breaks down under seqpack.
    • Introducing the two actions ADS_ATTRIBUTED_MACT_MMP_{CLICK, VIEW}_INSTALL = 194, 195 in the proto creates a channel to formally fold MMP-side app-install conversion into the training head.

Adding nine handles to the Brazil 2026 election filter is list maintenance with no logic change. Deleting Composition.rs removes duplication by reusing the shared candidate-pipeline library.

2HELIX raised GMV per user by about 6% in a TikTok e-commerce A/B test — Radar

Source HELIX: Purified and Unified - Rethinking Feature Interaction and Sequence Modeling for Large-Scale Recommendation — arXiv 2609.37183 v1, 2026-09-29 (arXiv submission), paper. There are 21 authors. The v1 HTML renders as a 404, but the abstract contains the phrase "Deployed in TikTok's e-commerce recommendation system", so we infer the affiliation is TikTok (ByteDance) inferred.

Background Industrial recommendation ranking models generally scale along two axes.

  • heterogeneous feature interaction: combines user / item / context / cross features and lets them interact.
  • sequence modeling: encodes long, multi-type user behavior sequences.

The HELIX authors observe that scaling only one axis gives a suboptimal scaling-law slope, and they propose a "unified" ranking architecture that expands both axes together.

What we learnedA. Deployed in TikTok e-commerce, and online A/B raised GMV per user by about 6%

  • The abstract states that HELIX was deployed in TikTok's e-commerce recommendation system and consistently improves ranking metrics such as offline CTR AUC and CVR AUC verified (direct quote from the abstract).
  • In the online A/B test, e-commerce video GMV per user rose by about 6% verified (direct quote from the abstract).

"Deployed in TikTok's e-commerce recommendation system, HELIX consistently improves offline CTR AUC, CVR AUC, and other ranking metrics. In online A/B tests, it achieves an approximately 6% increase in e-commerce video GMV per user." — HELIX abstract, 2026-09-29

What we learnedB. The core view is that both axes must be scaled together for the scaling law to escape suboptimality

  • HELIX is a "purified and unified" ranking architecture that scales the feature-interaction axis and the long/multi-type user-behavior sequence axis simultaneously verified (abstract wording).
  • The paper's core view is the observation that the two axes must be expanded together for the scaling law to escape suboptimality verified (abstract wording).

What we learnedC. Service scale is not disclosed

  • The paper does not state user counts or request counts.
  • We infer that using a GMV per user metric implies large-scale e-commerce traffic inferred.

Canon update Added a 2-line pointer to "new this month" in radar.md. It is not directly tied to the service canon (X·Meta·Netflix).

Why it matters This is the first time TikTok has formally named and published a ranking architecture for e-commerce recommendation that scales feature interaction and long sequences together.

  • Until now, releases in this area have continued from the EGA (Elastic Generative Auction, ads auction and ranking) family and the GreenLightning family. GreenLightning is a single inference service.
  • The view that the scaling law requires expanding both axes at once suggests that the sequence-only expansion of the Meta HSTU (Meta's generative sequential recommendation architecture) / GEM family and the feature-interaction expansion of the DCN·xDeepFM family are each suboptimal.
  • However, this is an abstract-based triage stage, so the detailed architecture (which interaction structure, which sequence encoder, the measured scaling-law slope) is a subject for a deep dive.
  • It is not folded into the service canon and stays in the radar.

3Snap's GRP merged retrieval, ranking, and reward into one model — Radar

Source GRP v0.1 Technical Report — arXiv 2609.36688 v1, 2026-09-29 (arXiv submission), paper. The v1 HTML page renders the organization name Snap Inc., so the affiliation is Snap verified.

Background Industrial recommendation systems are generally built as a multi-stage cascade of retrieval → pre-ranking → fine-ranking → reward re-ranking. Because each stage is trained and deployed as a separate model, replacing the whole stack together is difficult. The GRP in this paper (presumably Generative Recommendation Platform) presents a framework that unifies these stages into a single encoder-decoder model. The model generates multimodal Semantic IDs, and a joint MHP (Multi-Head Prediction) doubles as candidate scoring and the frozen reward for RL post-training.

What we learnedA. View time and shares rose in an A/B comparing retrieval only and in an A/B applying bypass and source replacement together

  • In the retrieval-only comparison, view time rose by 0.46% and shares by 0.77% relative to production verified (direct quote of the A/B).
  • In a separate comparison applying bypass and source replacement together, view time rose by +0.82% and shares by +2.56%, and platform-level guardrails were neutral verified (direct quote of the A/B).

"In a retrieval-only comparison, view time increases by 0.46% and shares by 0.77% relative to production. A separate comparison combining bypass and source replacement yields increases of 0.82% in view time and 2.56% in shares, with neutral platform-level guardrails." — GRP v0.1, 2026-09-29

What we learnedB. With the retrieval bypass combination, views and shares rose and view time fell

  • The additional axis of the retrieval bypass combination is these figures: "+0.24% views, −0.24% view time, +2.30% shares (p<0.05)".

What we learnedC. Unifies retrieval, ranking, and reward into a single encoder-decoder

  • GRP is a generative recommendation framework that unifies retrieval, ranking, and reward into a single encoder-decoder.
  • It generates multimodal Semantic IDs, and a joint multi-head prediction (MHP) doubles as candidate scoring and the frozen reward for RL post-training. The RL post-training is mGRPO (reference-anchored margin).

What we learnedD. Serving optimization reduced retrieval latency

  • User counts and request counts are not stated.
  • Serving optimization reduced end-to-end retrieval latency by 69%.
  • The paper is 26 pages with 11 tables.

Canon update Added a 2-line pointer to "new this month" in radar.md. Snap is outside the tracked services, so it is not folded into the service canon.

Why it matters GRP is a new statement on the "unified serving path for generative recommendation" angle we have been watching since early this month.

  • Kuaishou OneTrans-V2 bundled the 3-stage cascade of retrieval, pre-rank, and fine-rank into a single Transformer and gained GMV +9.74% (2026-09-28 radar). Tencent PCG TGR bundled ranking, retrieval, slate generation, and reason tokens into one frame and deployed it on 5 surfaces. GRP goes in the same direction as both.
  • GRP adds two axes to this. One is the mGRPO joint MHP axis, which handles reward inside the same model, and the other is the multimodal Semantic ID generation axis.
  • The serving latency of −69% is a large reduction relative to the multi-stage cascade, and it signals that whether the encoder-decoder unification justifies the latency budget is the key criterion for adopting industrial-scale generative recsys.
  • It is not folded into the service canon and stays in the radar.
