1The Following tab ad threshold dropped to 2 post groups — X

Source xai-org/x-algorithm@ed78e06 — xAI, 2026-11-20, code. In these notes' numbering, this is Gen4+Gen68.4+N is the number these notes assigned, in order, to commits after the 2026-08-13 Gen4 release).

Background X's Following tab is a feed that shows posts from followed accounts in reverse chronological order, and it uses an ad blender separate from For You (code that decides ad slots among organic posts). This blender inserts no ads at all when too few posts would be placed on the screen. The param.rs file in home-mixer (the service that assembles For You and Following requests) is a mirror that copies internal feature-switch defaults every day. This commit lowers that threshold and adds several new ranking and carousel paths that are off by default.

What we learnedA. Following tab ads are placed even with only 2 post groups

  • The minimum number of post groups for the Following tab ad blender changed from 5 to 2, and because this value is a default, it takes effect immediately verified — params/param.rs:1080-1085
    • The param is AdsFollowingMinPosts (rust_home_mixer_ads_following_min_posts), and the mirror sync time is 2026-11-19T16:00:34Z.
    • The Following blender selector passes this value to the blender as min_posts (selectors/following_blender_selector.rs:41).
  • When the number of groups is below the threshold, all ads are dropped and the reason "too few posts" is recorded verified — ads/following_ad_blender.rs:142-151
    • Consecutive posts that share an ancestor post are treated as the same conversation and counted as one group (same file, lines 72-92).
    • The reason code is AdDropReason::TooFewPosts. The ad spacing calculation is unchanged, so how many ads fit on a screen with 2 groups depends on the spacing.

What we learnedB. A path now exists for the Phoenix ranker to handle the VMRanker call

  • With the switch on, home-mixer attaches VMRanker call information to the Phoenix prediction request verified — scorers/phoenix_scorer.rs:120-123, 195-203
    • VMRanker is the service that computes a weighted sum of Phoenix's per-action probabilities (Phoenix is a Grok-based Transformer ranker) and reorders slates with a DPP (a probabilistic model that keeps similar candidates from being picked together).
    • The attached values are the VMRanker host name, eta, and prior_tau. The first comes from VMRankerClusterId, and the other two come from PageDecodeEta (default 0.0) and PageDecodePriorTau (default 0.2).
  • If the Phoenix response contains a VMRanker response, the VMRanker scorer in home-mixer uses that response instead of calling VMRanker separately verified — scorers/vm_ranker.rs:171-176
    • If the response is missing, is an error, or fails to decode, it calls directly as before. Results are counted in the VMRanker.ranker_vm_rank metric as sent, received, used, missing, and error.
  • The EnableRankerVmRank switch is off by default verified — params/param.rs:345-357
  • The same commit has no code in which the Phoenix server receives this request and calls VMRanker verified — the commit's changed-file list contains only the proto definitions.
    • The proto gained VmRankSpec (the request) and VmRankResult (the serialized VMRanker response and an error string).
    • Because two parameters named after the decoder are sent together, we infer this is preparation for using the VMRanker result as the prior distribution of the page decoder inferred. The only evidence is the name prior_tau and the fact that the call is made from the Phoenix side.

What we learnedC. Phoenix MoE retrieval can now be turned on for the video carousel only

  • With the new switch on and the carousel enabled for a request, the Phoenix MoE retrieval source runs even when the main feed switch is off verified — sources/phoenix_moe_source.rs:28-35
    • Phoenix MoE retrieval is one of the For You candidate sources, and its main feed switch EnablePhoenixMOESource is off by default.
    • The new switch is EnableVideoCarouselMoeSource (default false) (params/param.rs:1520-1525). The carousel itself (EnableVideoCarousel) is also off by default.
  • In this mode, candidates that came only from MoE are removed from the main feed top selection and go, with their scores cleared, only to the carousel candidate pool verified — selectors/top_k_score_selector.rs:15-29
    • Candidates that also came from other sources stay in the main feed competition as before (util/video_carousel.rs:26-38).
    • A test confirms that a MoE candidate with a score of 1000 does not enter the top selection, and that it ranks first when the main feed switch is turned on (same selector file, lines 196-225).

What we learnedD. In the multiplicative mode, video watch time moved into the time multiplier

  • In the multiplicative combination mode, which is off by default (scoring as how unlikely a skip is × engagement value × dwell-time multiplier), the two post-open video watch-time terms are removed from the engagement term and added to the dwell-time multiplier verified — xai-value-model/scoring.rs:89-114
    • The two terms are video_continuation and user_video_continuation, and a negative sum is clipped to 0.
    • The test expectation changed from a time multiplier of 3.0 to 3.015 (weight 0.003 × open probability 0.5 × 10 seconds).
  • In the training reward of the page decoder (an RL re-ranking model that picks one page in slot order from the ranker's top candidates), the video quality view (VQV) term was moved in the same way verified — phoenix/xrex/models/page_rl.py
    • The sum in additive mode is the same as before, and only in multiplicative mode does it become time = 1 + max(dwell, 0) + max(vqv, 0).

What we learnedOther changes

  • A settings screen was added under Under the Hood (the transparency screen where users see information about their own account and feed) that lets users turn the For You trace display on and off verified — timeline_trace.tsx
    • The notice text says that refreshing For You shows a trace of the code that found, filtered, and ranked candidates, and that each stage links to the public code. The screen opens only to users who have a separate switch turned on.
  • In the Phoenix shadow traffic ratio (replicating the same request to an experiment cluster without using the response for live serving), Experiment19Fou changed from 0.3 to 0 verified — params/param.rs:91-108
  • The teacher score storage that was turned on yesterday now writes to the cache in one data center instead of two verified — teacher_score_side_effect.rs:158-169
  • The viewer's follower count was added to the feature-switch targeting attributes verified — models/fs_recipient.rs
  • Five app conversion events (purchase, add to cart, level achieved, tutorial completed, sign-up) were added to the ads purchase value reference values verified — purchase_value.rs
    • The same commit added an ads CTR bucket embedding option to the Phoenix model (default dimension 0) and a per-viewer ads engagement aggregation field to the ads proto.
  • Changes with no policy change were also included: a path that runs the candidate pipeline hydrators as a separate parallel task, Grox skipping already-annotated posts, and cleanup of abuse-enforcement-service verified — commit diff

2An LLM agent selects ads ranking model features — Meta

Source Cost-Aware Agentic Feature Optimization System for Fleet-Scale Ranking Models — Meta, 2026-11-19 v1, paper.

Background Large platforms run tens or hundreds of ranking models together, and each model must choose which of tens of thousands of features in a shared feature pool to use. Adding features raises accuracy, but feature pipeline cost and serving throughput (QPS) can exceed their limits. This paper reports a system that automates this selection by combining an LLM agent with deterministic experiment tools.

What we learnedA. The feature selection was handed to an agent and deployed

  • All 9 authors are affiliated with Meta, and the target is a fleet of ads ranking models verified — HTML version
    • The body calls the system "Agentic ML Exploration (A-MLE) for Ads Ranking".
  • An LLM generates cross-feature candidates, several feature importance metric rankings are blended, and a Researcher agent adjusts the selection through 10–25 asynchronous trials within a cost limit verified — arXiv abstract
    • For multi-task models, per-task rankings are blended with a Pareto front (the set of choices that cannot improve without making some task worse).
  • On production models it reports an average 0.31% NE improvement (normalized entropy, a log-loss metric where lower is better) and +0.20% on the primary online A/B metric after deployment verified — same abstract
    • It states that a final cleanup stage cut feature pipeline cost by 2.3% and that no regression exceeded measurement noise.

"The optimized models were launched, and in online A/B tests they improved a primary online metric by 0.20%." — Cost-Aware Agentic Feature Optimization System for Fleet-Scale Ranking Models (paper), 2026-11-19

Canon update Because this concerns ads ranking rather than the organic feed, we did not add it to the canon and instead added an entry to "new this month" in radar.md.

Why it matters Two pieces of evidence in one week now show Meta putting agents into the ads ranking development process itself. We see it as part of the same trend as the 2026-11-18 Meta Engineering post on ads ranking AI agents, but we have not confirmed whether the paper cites that post, so we treat it as an inference.

3A fix on the behavior sequence side for the CTR model depth bottleneck — Alibaba

Source DNA: Unlocking Depth Scaling in CTR Models — Taobao Search, 2026-11-19 v1, paper.

Background Long user behavior sequences are the strongest signal for CTR (click-through rate) prediction, and industrial rankers process them at linear cost with cross-attention (attention in which the request representation reads the behavior sequence). However, stacking more of these layers barely improves performance. This paper locates the cause in "every layer re-reads the same sequence" and proposes a structure in which the sequence is also updated at each layer.

What we learnedA. Updating the sequence at each layer makes depth effective again

  • On Taobao Search, expanding the cross-attention stack from 16 to 28 layers raises AUC by only 0.02pt verified — arXiv abstract
  • In DNA, at each layer the request representation reads the sequence, and then each behavior token reads the updated request representation to correct itself verified — same abstract
    • The update happens once per request and all candidates share the result, so computation stays linear in sequence length.
  • It states that AUC is 0.08–0.26pt higher at the same compute, and that deploying DNA-4 on Taobao Search gave CTR +0.8% and GMV +0.5% in an A/B test verified — same abstract

Canon update Because this is not a tracked-services source, we attached it as additional evidence to the "recommendation model scaling law" thread in radar.md.

Why it matters This adds one more claim that the scaling bottleneck on the depth axis lies in the key-value side input rather than in the model side. Because the surface is search, whether the same result holds for feed ranking remains open.
