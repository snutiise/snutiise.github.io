1Home-mixer's experimental dwell-regret alternative scoring was rolled back — X

Source xai-org/x-algorithm@8b25829 — GitHub commit, author commit 2026-09-18T23:55:39Z, 41 files, +2,877/−1,828. These notes number the commits that came after X's public source Gen4 (2026-08-13, 47c1bcd) in order; this commit is Gen4+25.

Background This commit was registered 22 hours after the commit covered yesterday, Gen4+24 (c279172), on the same date (2026-09-18). The 1,828 deleted lines roughly balance the 2,877 added lines, but the deletions are concentrated in three intertwined files (item A below). The commit rolls back one experimental scoring mode in home-mixer and also touches several other areas.

The commit covers five axes.

  • A. In the ranking scoring of home-mixer (the service that receives X's feed requests, gathers candidates, and ranks them), one experimental scoring mode introduced early in Gen4 was dropped.
    • Deleting the whole file home-mixer/scorers/value_model_gate.rs (−537) also cut home-mixer/scorers/ranking_scorer.rs substantially, by −465 lines.
    • home-mixer/params/param.rs lost 18 related parameters, at −110 lines.
  • B. A cold-start slice, distinguished by a dataset_type tag, was formally wired into Phoenix (X's For You ranking and candidate retrieval model stack) retrieval.
  • C. Phoenix bundle export was extended from ranking only to also support two-tower (a retrieval model that embeds users and posts separately and matches them) retrieval.
    • In the Phoenix serving/train line, recsys_bundle_export.py was substantially reworked at +559/−107.
  • D. VF (visibility-filtering, a service that decides per post whether it may be shown to this viewer) gained a server implementation of the evaluate_tweets gRPC, which was a stub until yesterday. A hydrator also appeared that replaces the visibility fields TES (Tweet Entity Service, an X-internal tweet metadata service) used to supply. This hydrator fetches fields from Strato (an X-internal system that code goes through to read or store data) columns.
    • On the addition side, two new files appeared: visibility-filtering/evaluate_tweets.rs (+258) and visibility-filtering/hydration/tes_composite.rs (+607).
  • E. In infrastructure cleanup, the CUDA kernels were split out of the xrex repo into the external package xrex_cuda_kernels. Also, fav-count-based reasoning gating was added to the adult spam clone detection flow of grox (a Grok-based nearline classifier sub-repo).
    • The name of this detection flow starts with media_injected_adult_infrared.

Of the five axes, A and D are events in different directions: the unwinding and the maturing of experiment infrastructure that has built up in Gen4. A is the cleanup of a separate scoring mode introduced early in Gen4, because the measured results were poor (no evidence is public; it is observed only as the deletion of whole files). D is a maturing flow in which a stub that had only the client interface open in Gen4+24 yesterday now extends to server logic.

What we learnedA. The experimental scoring mode gated dwell-regret and its user gate were rolled back entirely

  • The mode that used dwell-regret scoring through a gate, and the file that defined its per-user gate, were both rolled back verified.

    • The evidence file home-mixer/scorers/value_model_gate.rs does not exist at 8b25829.
    • The mode is gated_dwell_regret, and the file is value_model_gate.
    • In the earlier Gen4 open-source history, this file defined GateModel::from_params().
    • GateModel normalized 19 user-state features with log1p, then produced a gate score as a logistic linear combination. It then flipped the assignment by request hash only within a hysteresis band.
    • The feature list is seq_len·n_fav·n_reply·n_rt_quote·n_vqv·n_click·n_bm_share·n_profile_follow·n_photo·n_negfb·n_7d·n_1d·active_days·active_days_7d·days_since_last·span_days·followers·followings·account_age_years.
    • The patch of the rollback commit shows this entire logic deleted, at −537 lines.

  • GateModel fired in ranking_scorer.rs only when the ValueModelMode parameter was in gating mode. At that point, depending on per-user conditions, it decided whether to use a dwell-regret-family alternative score based on dwell time.

    • ValueModelMode had three values (weighted / dwell_regret_sigmoid / gated_dwell_regret).

  • 8b25829 removed all three value branches.

    • Negative weights were placed on the remaining interaction counts (n_click, n_bm_share, n_profile_follow, n_1d).

The experimental alternative function that sat beside ranking scoring in Gen4 (modulating dwell time by engagement signals) and its user gating were removed all at once, and ranking scoring narrowed back to a single weighted path. How to reflect the dwell signal here appears to have moved to adding heads at training time and redefining score combination inferred. Examples are the click_dwell_time sigmoid BCE (threshold=10s) formally wired in Gen4+22 and the EnableCdwellOnImpr (click × dwell product) of Gen4+23 inferred. The evidence is that the timing of the two flows is adjacent, and the observation that once the circuit modulating dwell through a separate scoring function disappeared, only circuits treating dwell as a head itself and as a combination term remain.

Until now, X's cold-start handling had two axes:

  • Users whose history is below a threshold are routed to a separate model fleet. Retrieval and ranking each have Phoenix*NewUserInferenceClusterId.
  • New authors (at or below ColdStartImpressionThreshold=1000) get a PostUnexploredWeight=0.02 boost, and there is the Thompson sampling option from Gen4+1.

This wiring opens a third axis at the candidate level. Within the candidate set returned by the same Phoenix retrieval RPC, a separate cap is placed on the "cold" subset by the dataset_type tag, and it is observed. That is, Phoenix retrieval itself appears to have been extended to always return a cold candidate slice together, regardless of user history inferred. The evidence is that the default is 0, so it has not yet entered the production default, but the observation stat lines were also wired symmetrically, which indicates that the A/B infrastructure is complete.

What we learnedC. Phoenix bundle export can now export the forward program of two-tower retrieval as well as ranking

  • Phoenix bundle export was extended to export the two-tower retrieval forward in addition to the ranking forward verified.

    • The evidence file is phoenix/xrex/train/recsys_bundle_export.py (+559/−107).
    • This file was introduced at 634 lines in Gen4+13 (2026-09-01, 7ba7768). It exported the ranking model (RecsysAggregatedModelConfig), lowered with jax.export, to StableHLO MLIR bytecode, .jax_export, and MANIFEST.json.
    • This commit attached retrieval two-tower program export alongside it. Two new axes appeared.

  • Axis 1: the number of program kinds grew to two verified. Two constants distinguish the program kind within the export bundle.

  • Axis 2: because the retrieval export must carry additional resources in the bundle, new data structures and wire keys were introduced.

    • The new dataclass RetrievalExport holds five attributes that must be extracted from the trainer's RetrievalModelRunner at export time. The attributes are large_k, retrieval_dataset_types, enable_async_topk, enable_radix_select_topk, and enable_dataset_slice_topk.
    • The manifest block carries the items below.
      • large_k
      • target dataset types (a list of name·value pairs)
      • post table geometry (rows·width·dtype)
      • three data keys (POST_TABLE_KEY·POST_DATASET_TYPES_KEY·POST_IDS_KEY·AUTHOR_IDS_KEY)
      • topk_unordered flag

  • The retrieval forward extracts a user embedding with the user tower, matches it against the whole post table, and returns top-K for each target dataset type verified — new function _make_retrieval_forward_fn.

    • Each target dataset type yields two outputs (indices_<name>, scores_<name>). This naming rule is defined in the RetrievalExport.output_names property.

  • For two-tower, the rule for computing the serving sequence length differs.

    • _make_export_config also gained two arguments, two_tower: bool = False and mesh_devices: int = 1.
    • The ranking export's serving sequence is prefix + history + candidate, but the retrieval export has only prefix + history. There is no candidate axis, and it emits only the user embedding.
    • The overrides of _make_export_config also use model_config.user_tower_config.model_config.sequence_len instead of model_config.model_config.sequence_len.

  • The third new addition is distributed export. The retrieval bundle is exported over a mesh and can be distributed across multiple devices.

    • The reason is also stated explicitly. Ranking is served with one executable per GPU, but retrieval has to split the post table across several devices, so it is exported with SPMD.
    • _export_mesh checks export_cfg.parallel_config.mesh_shape() to build the devices. _retrieval_shardings specifies NamedSharding for batch/params/post_table/dataset_types.
    • Embedding rows are partitioned across the data axis, and params are replicated.

  • Several constraints are imposed explicitly.

    • enable_int8_post_table, enable_bloom_filter, and enable_topic_filter are not supported. These options are supported only by the native runtime, and StableHLO export uses a bf16 post table with no per-post filter.
    • enable_dataset_slice_topk=True is ignored and a warning is raised. The export program always compiles only the mask-then-topk-over-whole-table path.
    • The using_seqpack + two_tower combination is prohibited. Packing does not fit the SPMD model.
    • With DEBUG_ALLOW_RANDOM_INIT=1, the export itself is refused. This is because exporting without a mask would emit an invalid program.

  • build_bundle now accepts both kinds of models.

Until now, Phoenix serving carried only the ranking forward in a StableHLO bundle. With this commit, preparation for carrying retrieval two-tower in the same bundle frame is complete. Because infrastructure for exporting retrieval distributed across several devices via SPMD was attached too, the direction is for Phoenix retrieval's serving stack to be unified under the same bundle format as ranking. It may not be a coincidence that this landed at the same time as the PhoenixColdStartMaxResults wiring in B above inferred. In effect, while the retrieval serving axis was being tightened, the slice observation interface via the dataset_type tag settled alongside it inferred.

What we learnedD. VF now has a server that receives verdict requests, and takes the visibility fields for verdicts from a Strato column instead of TES

  • A server implementation of the gRPC that receives verdict requests was attached to VF, and the visibility fields TES used to supply moved to a Strato column hydrator verified.
    • New files: visibility-filtering/evaluate_tweets.rs (+258), visibility-filtering/hydration/tes_composite.rs (+607)
    • Files changed together:
      • visibility-filtering/server.rs(+86/−2)
      • visibility-filtering/filter.rs(+336/−13)
      • visibility-filtering/hydration/tes_hydrator.rs(+113/−320)

    • This gRPC is evaluate_tweets.

This axis splits into two sub-axes.

D1. The verdict-request RPC that was a stub until yesterday was filled in with server logic by this commit.

  • daily/2026-09-18.md records the observation that Gen4+23 (42266f3) on 2026-09-17 opened only the client interface of the evaluate_tweets RPC and the Thrift decoder for the response payload. According to the same observation, the server implementation was Err(Status::unimplemented("EvaluateTweets is not served yet")).

  • This commit fills that evaluate_tweets stub with server logic. The server.rs patch directly shows the unimplemented stub being replaced with a real implementation.

  • The new server endpoint EvaluateTweetsEndpoint (258 new lines) receives a request, runs the internal filter, and fills the response with a per-tweet Outcome.

    • It receives the request's three fields (viewer_id, country_code, safety_level) and a tweet list.
    • safety_level is converted from the Thrift enum to the internal Rust SafetyLevel enum. Only three values are allowed: FILTER_ALL, TIMELINE_HOME, and TIMELINE_HOME_RECOMMENDATIONS.
    • It then calls FilterTweets::run.

  • Three metrics (evaluate_tweets_requests, evaluate_tweets_latency_ms, evaluate_tweets_batch_size) are recorded for each request.

  • The evaluate_tweets_loopback integration test pins the fact that the server logic is wired in. This test starts the gRPC server on a tokio TCP listener and makes a round-trip call with XaiVfClient.

D2. Besides the verdict, an evaluation status is attached to the result.

  • An EvaluationStatus axis was added to FilterOutcome. A new enum appears in filter.rs.

  • Previously the filter could emit only one Verdict per tweet. Now one of three statuses is attached next to the verdict.

    • A tweet whose hydration succeeded is Evaluated.
    • A tweet whose author did not come out of hydration is UnresolvedAuthor, and its verdict is Verdict::unresolved_author().
    • A tweet that hit the rules with insufficient fields because hydration itself failed is Failed.
    • HydrationOutput also gained a new field failed_ids: HashSet<TweetId> to distinguish the third case (Failed).

  • The axis names line up with the client-side EvaluationResult { Evaluated(Box<Action>), NotEvaluated, Failed } (introduced in Gen4+23), and we infer that the server and client axes mesh as follows inferred.

    • EvaluationStatus::UnresolvedAuthor + Verdict::unresolved_author() → EvaluationResult::NotEvaluated
    • EvaluationStatus::Failed → EvaluationResult::Failed
    • EvaluationStatus::Evaluated + Verdict::* → EvaluationResult::Evaluated(Action)
    • It is left as an inference because the patch does not show the mapping directly, only the assembly of EvaluateTweetsResponse. However, the value names of the two axes are symmetric.

D3. The seven visibility field kinds that TES handled moved to a separate Strato column hydrator.

  • tes_hydrator.rs shrank substantially, by −320 lines, and most of the deleted part is the TweetHydration struct.

  • These seven axes were unified into a single TweetHydrationBatch<TweetForVisibility>. TweetForVisibility is an 11-field struct defined in the new file tes_composite.rs.

  • The source that fetches this data is a fetch operation on a Strato column, not TES verified — visibility-filtering/hydration/tes_composite.rs.

    • The column is tweetypie/federated/tweetForVisibility.Tweet, and the operation is fetch.
    • ProdTweetForVisibilitySource::get_tweets_for_visibility sends the list of tweet_ids as a batch call to this column. The response is decoded as MVal (Strato), and the Thrift-defined Tweet is flattened with TweetForVisibility::project() and returned.
    • In other words, a VF-specific Strato column interface separate from TES was opened.

  • TesHydrator still exists, but it now orchestrates two sources.

    • From TES it still receives PureCoreData (corpus-dimension signals such as author_id, text, and source_tweet_id).
    • From TweetForVisibilitySource it receives the flag/label axes that the visibility rules require.
    • That is, corpus data and visibility data were split onto different Strato backends.

Until now, VF had referenced TES's broad tweet fields as they are. It now breaks from that practice and looks up only the minimum field set needed for visibility rules from a separate Strato column. Three axes settled together:

  • In Gen4+13, the VF rules were restructured into a two-way tweet/author split.
  • Gen4+23 deleted its own twemcache subtree of 3,234 lines entirely and moved to the company-wide xai_cache, while opening the evaluate_tweets client interface as a stub.
  • Today the server implementation and the TES separation are completed.

That is, in Gen4 VF was reorganized layer by layer in the order rules → dependencies → serving interface.

What we learnedE. grox's adult spam video detection turns on reasoning mode only for posts whose like count is at or above a threshold

  • Reasoning mode was attached to the grox detection flow through fav-count (like count) gating verified.

    • The evidence file is grox/flows/ptos/task_safety_ptos_media_injected_adult_infrared_video_spam_detection.py (+14/−9).
    • The target is the media_injected_adult_infrared_video_spam_detection flow. It was introduced in Gen4+24 and compares a reference video bundle with the VLM storyboard of the candidate video.

  • For posts whose fav count is at or above the threshold, a path where the model thinks explicitly opens.

    • It strips the "thinking restrictions" from the system prompt and leaves the THINKING_CONTROL_END marker of the assistant response empty.

  • The value of the threshold MEDIA_INJECTED_REASONING_FAV went into grox/flows/ptos/constants.py, but the value is not exposed in the patch.

  • The SafetyPtosPolicyCrossValidator of Gen4+7 (2026-08-24) turned on reasoning only for the categories USE_REASONING_CATEGORIES = {ViolentSpeech, SuicideOrSelfHarm}. This time, reasoning is gated on the individual post axis by fav count.

This gating is a typical binary branch for spending cost only on threads with high fav counts. It is in the same family as the oai-gemma4-26b-reply-spam binary branch of Gen4+22 (2026-09-16) (threads over 150k followers). The deluxe_fav_count_threshold special-video entry gate of Gen4+12 (2026-09-01) is in the same family too.

Canon update Added a Gen4+25 row to the top-level timeline table of ../services/x.md and created a detailed section at the bottom.

Why it matters X's open source, which had been moving in an additive direction through yesterday's commit (Gen4+24), today for the first time in Gen4 also carries a rollback. In addition, Gen4 is "maturing" on three axes.

  • The rolled-back value_model_gate (the 19-feature user gate) and the two scoring modes dwell_regret_sigmoid and gated_dwell_regret were introduced early in Gen4.   • What was rolled back was an experimental path not in the canon, so the canon gets no new claim, only the observation that "this axis was tried and then cleaned up".
  • The first axis that is maturing is the dataset_type axis of Phoenix retrieval (B above). The server is complete through dataset_slice_topk, and the open-source code exposes only the candidate slice cap and observation stats.
  • The second axis is Phoenix bundle export (C above). The format, which could previously carry only ranking, was extended to carry the retrieval two-tower as well, and SPMD distributed export was attached.
  • The third axis is VF (D above). Three layers were organized in this order: rules (Gen4+13) → deps (Gen4+23) → serving interface (today). Through Gen3, VF was a "label consumer"; in Gen4, VF is taking shape as "a separate service that stores, looks up, and serves labels".
