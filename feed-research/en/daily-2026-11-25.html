1A popular-video source dedicated to the video carousel was added — X

Source xai-org/x-algorithm@e005f95 — xAI, 2026-11-24, code. In these notes' numbering, this is Gen4+Gen70.4+N is the number these notes assigned, in order, to commits after the 2026-08-13 Gen4 release).

Background X For You has a video carousel that places 3–5 vertical videos in the 6th slot of the feed, and this module has been off by default since it was introduced on 2026-10-08. Carousel candidates are picked from the videos among the main feed candidates, but recent commits are building a candidate path just for the carousel. The 2026-11-20 commit added a switch that turns on the Phoenix MoE retrieval source (a mixture-of-experts candidate search in the Phoenix ranker family) for the carousel only, and the 2026-11-21 commit built a popular-video index that collects only videos with more than 10,000 views and 100 likes within 48 hours. This commit adds a carousel-only popular-video source to home-mixer (the service that receives For You requests) and also changes the teacher-score cache and the automated enforcement service.

What we learnedA. Candidates from the popular-video source are used only in the carousel, and the source is off by default

  • home-mixer gained a popular-video source that fetches up to 100 video candidates from one Phoenix retrieval cluster verified — home-mixer/sources/popular_video_source.rs

    • The source runs only when its switch is on, the request has the carousel enabled, the request is not Following-only, and the request is not reusing cached candidates.
    • Fetched candidates get a new served type (a label for the path a candidate came through), ForYouPhoenixRetrievalPopularVideo.

  • The source switch, cluster name, and maximum count were newly added to the cron mirror (a parameter file that syncs production feature-switch defaults daily), and the source is off by default verified — home-mixer/params/param.rs:1544-1567

  • Candidates that came only from this source are always dropped from the main feed's top selection and remain only as carousel candidates verified — home-mixer/util/video_carousel.rs

    • The decision function is_carousel_only is true when all of a candidate's served types are popular-video. For MoE candidates, it is true only when the MoE carousel-only switch from the 2026-11-20 commit is on.
    • Videos that also came in through another source stay in the main feed competition.
    • The test popular_video_posts_are_carousel_only pins that a popular-video candidate with a score of 1000 does not enter the top selection and is attached as a spare carousel candidate without a score.

  • A switch that limits carousel candidates to videos from the popular-video source was also added, and it is off by default verified — home-mixer/util/video_carousel.rs

    • If it is turned on together with the MoE-only switch from the 2026-11-21 commit, only videos that came in through one of the two sources become carousel candidates.

  • We infer that the cluster this source queries is the popular-video index from the 2026-11-21 commit inferred.

    • The evidence is only the source name and the served type name. No code in the public repo links the cluster name "Experiment26Fou" to the index configuration.

What we learnedB. The teacher-score cache lasts 3 hours and also holds next-page posts

  • The default cache retention time for teacher scores (the per-action probabilities that production Phoenix produced for posts actually served, kept as training labels) increased from 3,000 seconds to 10,800 seconds verified — home-mixer/params/param.rs:1306-1311
    • That is 50 minutes becoming 3 hours. This path has been on by default since the 2026-11-19 commit, so actual behavior changes.
  • Next-page requests that reuse cached candidates now also record teacher scores verified — home-mixer/side_effects/teacher_score_side_effect.rs:127-190
    • A next page does not create a new entry; it appends its posts to the first-page entry of the same prediction request ID only if that entry still exists (append_if_exists_ex).
    • If the first-page entry has already expired, it records the result as no_entry and writes nothing.
    • The test pins that for request 7, first-page post 1 and next-page post 2 go into one entry, and that for request 8, which had no first page, no entry is created.
  • We infer that the retention time was extended to buy time for next pages to attach inferred. The only evidence is that the two changes came in the same commit.

What we learnedC. Replies written after a parent-post mention are excluded from automated action

  • When abuse-enforcement-service (a service that applies label, challenge, and suspension actions to accounts and posts based on model scores) processes a reply post, it reads the parent post and skips the action if the parent's text mentions the reply's author verified — abuse-enforcement-service/service-lib/src/safety_checks.rs
    • The new safety checks are invited_reply ("the reply's parent post mentions the reply's author in its own text") and invited_reply_unknown.
    • Only mentions inside the parent post's visible text range (visibleTextRange) are counted.
    • We infer that this range condition is meant to exclude the mention prefix that is automatically attached before a reply inferred. The only evidence is the phrase "in its own text" in the check's description.
    • Parent lookup results are cached in memory for 10 minutes and failures for 30 seconds, and the lookup time limit is 3 seconds by default — invited_reply.rs.
  • The action is also skipped when the parent post could not be read verified — same file
    • This is a fail-open design: a lookup failure is handled by skipping, not by enforcing.
  • This check has no switch, and it only changes an action the rules had already chosen into a skip verified — service-lib/src/rules.rs
    • If a rule has already chosen to skip, for example because the follower count is high, the original reason is kept. The test invited_replies_stop_post_decisions_last_on_both_paths pins this.

What we learnedOther changes

  • The path in grox (the Grok-based safety annotation pipeline) that decides on a spam cluster's representative post no longer counts click-bait and reply-bait verdicts as enforcement decisions verified — task_write_live_cluster_anchor_verdict_sink.py:35-53
  • grox gained a configuration slot for X review reports, and the media loader can now read high-popularity posts while leaving out their child replies verified — grox/config/config.py
  • The Phoenix serving engine gained a gateway (about 6,400 lines, including tests) that sets by policy which model checkpoint each serving pod receives verified — checkpoint_gateway.rs
  • The training code now retries reading data metadata up to 6 times, and when one reader has finished reading the data, all hosts stop together verified — phoenix/xrex/train/trainer.py

2An LLM agent edited recommendation model weights directly — Pinterest

Source Weight Coding: Evolving Web-Scale Recommenders through Direct Weight Edits with LLM Agents — Pinterest, 2026-11-22, paper.

Background Large recommendation models are usually improved by retraining or fine-tuning, and the metric gain from each improved release is small. On 2026-11-19, Meta announced A-MLE, which uses an LLM agent to select features for an ads ranking model, and this radar is watching the trend of agents taking over model development. This paper reports the results of applying a method, in which an agent directly edits trained weights without training, to Pinterest production models.

What we learnedA. A retriever with directly edited weights increased saves by up to 10.7% in an online A/B test

  • An LLM agent runs a loop in which it inspects the model structure and parameters, forms a hypothesis, edits the weights, and decides the next edit from the evaluation result verified — arXiv 2611.29613
    • It uses a cache engine that runs only forward-pass evaluation quickly, without backpropagation.
    • Edits start from local changes and expand to targeted search and combination.
  • The main case is a 147M-parameter two-tower retriever for Pinterest Image Search (a model that finds candidates with two towers that embed the user and the item separately) verified — HTML version
    • Held-out recall@10 rose by up to 15.0 points (+24% relative) over the production model, at about 1/4 of the GPU time of a full post-training finetune.
    • It reports that after randomly re-initializing the 13.6M-parameter interaction module, searching only 2,448 mixing and normalization parameters was still 9.8 points higher than production.
  • It was deployed with no serving changes, and in the online A/B test, closeups per user for the edited retrieval source rose by up to 7.6% and saves by up to 10.7% verified — same HTML version
    • It reports that the offline improvements span dense retrieval, generative retrieval, and ranking, and cover models up to 1.37B parameters.

"Online A/B tests of the edited two-tower retriever increase closeups by up to 7.6% and saves by up to 10.7% per user for the edited retrieval source, with engagement and exposure changes aligned with the objectives." — Weight Coding (HTML), 2026-11-22

Why it matters There is one more production case in which an LLM agent took on editing model weights, beyond designing experiments for a recommendation model. Because the main case is an image search retriever rather than the home feed, it is not added to a service canon.
