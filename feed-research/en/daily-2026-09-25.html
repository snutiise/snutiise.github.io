1home-mixer and vm-ranker ranking scores now come from one shared crate — X

Source xai-org/x-algorithm@44d37eb — GitHub public source code, 2026-09-24, +2,569/−2,257 (62 files). These notes number X commits after the Gen4 release in sequence, and this commit is Gen4+28. A shared crate called xai_value_model began to appear in yesterday's Gen4+27 commit 1b3fec20. That commit inlined xai_value_model::compute_value_scores() into the vm-ranker process, and today the shared crate was released as actual files.

Background X's For You ranking takes the weighted sum of 24 engagement probabilities (favorite, reply, retweet, dwell, report ...) predicted by the ranking model Phoenix and obtains one scalar score. That score is multiplied by author diversity, an OON (out-of-network, posts from accounts the user does not follow) multiplier, and a new-author boost. This computation, which the code calls the value model, happens in two places: home-mixer, the Rust service that assembles the For You feed, and vm-ranker, a separate gRPC service attached behind it. vm-ranker handles DPP diversity (a diversity technique that makes similar candidates less likely to be picked together) and the rank server role. When two processes implement the same formula twice, people have to catch every drift between the mirrors by hand. This commit tidies up the practice of counting which process uses which parameters and how many parameter mirrors there are. It releases the shared crate that appeared yesterday as six actual files and deletes home-mixer's 1,255-line ranking scorer (ranking_scorer.rs) entirely.

What we learnedA. The home-mixer ranking scorer is gone, and the shared crate handles score computation

  • The home-mixer ranking scorer of 1,255 lines was deleted entirely verified — home-mixer/scorers/ranking_scorer.rs.

    • We confirmed ranking_scorer.rs in the previous commit's tree.

    • The only thing taking its place is the new 114-line file home-mixer/scorers/value_model.rs.

    • This file does three things:

      1. weights_for(query) pulls 33 values from the home-mixer FS parameters and builds ValueModelWeights.
      2. scoring_inputs(query, weights, candidate) turns the candidate's Phoenix engagement probabilities and its in-network, mutual-follow and vqv conditions into CandidateScoringInputs.
      3. weighted_score(query, weights, candidate) calls the shared crate's fuse_heads as is.

      — home-mixer/scorers/value_model.rs, 2026-09-24. What the home-mixer ranking scorer does is now compressed into these three lines. The actual formula lives inside the shared crate's fuse_heads.

  • A new shared crate was released with 6 files and 807 lines in total verified — xai-value-model/lib.rs (+14).
    • The crate name is xai-value-model.
    • The other five files are inputs.rs (+35), phoenix_scores.rs (+28), proto.rs (+92), scoring.rs (+444) and weights.rs (+194).
  • The symbols the crate exports are listed below verified. The list is exactly what lib.rs re-exports with pub use.

What we learnedC. Even if the vm-ranker call fails, home-mixer serves the score it computed locally

  • If the vm-ranker RPC fails, home-mixer now serves the locally computed weighted sum as is verified — home-mixer/scorers/vm_ranker.rs (+84/−76).
    • The previous code propagated the failure as a per-candidate Err.
    • home-mixer's vm_ranker.rs was restructured from "request assembly" to "local-first, RPC-refine".
    • The new function local_scores() first computes a local weighted sum for each candidate with value_model::weighted_score(). It then attaches the cold start lift and author_policy_zeroed decisions with AuthorColdStart::apply_with_decisions().
    • After that it sends a refinement request to the vm-ranker gRPC.

What we learnedD. Phoenix retrieval splits the cold pool and popular candidates at data loading time

  • A popular-candidate slice was newly introduced in Phoenix retrieval (the candidate source that finds OON candidates with Phoenix) verified — phoenix/xrex/data/retrieval_dataset.py (+103/−8).
    • The new slice is named HOME_HOT. It was registered as HOME_HOT = 14, next to HOME_COLD = 13 in the RetrievalDataset enum.
    • Both slices are drawn from the same 1fav_1day.parquet source and are split by two masks in the new phoenix/xrex/data/cold_pool_filter.py (+78).
      • cold_pool_mask(post_ids, meta_path, max_favs=8, max_views=500)
      • fresh_post_mask(post_ids, max_age_seconds): computes the posting time directly from the tweet id using the Twitter Snowflake epoch.
    • HOME_COLD is cold_keep = cold_pool_mask & fresh_post_mask, and HOME_HOT is its complement.
    • The cold pool is now cut at data loading time in the training and serving stages, and only the remaining popular candidates are managed in a separate index.
    • default_cold_pool_metadata_path() is ${PHOENIX_INDEX_BASE:-/data/phoenix_index/prod}/post_author_pairs_metadata/metadata_1day.parquet.
  • When a Phoenix bundle is exported, per-target index metadata is attached verified — phoenix/xrex/train/recsys_bundle_export.py (+170/−46).
    • Four fields were added to the RetrievalExport dataclass.
      • dataset_capacities
      • rows_from: decides, per target, which source dataset's rows to reference.
      • max_age_seconds: the maximum age per target.
      • optional_targets
    • The structure in which HOME_COLD and HOME_HOT split the rows of the same source (HOME) is expressed by exactly this rows_from.
    • The manifest exposes two constants, POST_SCALES_KEY and DATASET_RANGES_KEY.
    • The new gating consists of three flags: enable_int8_post_table, enable_bloom_filter and enable_topic_filter. These gates decide whether to include the int8 post table (per-post absolute-max scale) in the export.

What we learnedE. When judging a retweet, the verdict on the original tweet is merged in

  • Logic that merges the retweet verdict and the original tweet verdict was added to VF (visibility-filtering, the service that judges per post whether it may be shown to this viewer) verified — visibility-filtering/models/verdict.rs (+60).

    • The new function is Verdict::merge_retweet_verdict(retweet, source). There are four merge rules:

      1. If source is Withheld, source is always adopted. If the original tweet is withheld, the retweet is withheld too.
      2. If retweet is Withheld, retweet is kept. This is the case where the rule that withholds the retweet itself won.
      3. If retweet is Shown{media: None, engagement: None} (no restrictions), it inherits source.
      4. Otherwise, retweet is kept.

      — visibility-filtering/models/verdict.rs, 2026-09-24

    • The flow that actually runs this merge was implemented in visibility-filtering/evaluate_tweets.rs (+157/−18).

      • It collects the evaluated retweets with source_tweet_id.is_some() from the first-pass evaluation results.
      • It splits those source ids with HashSet.contains() into in_batch (already in the same batch) and fetched. fetched are those that need to be looked up again.
      • It calls filter_tweets.run(...) a second time on the fetched list to obtain the source verdict.
      • For each retweet, it looks up the source verdict and applies merge_retweet_verdict.

    • The new metric is evaluate_tweets_retweet_sources{outcome=in_batch|fetched}.

  • As a change supporting the merge, pure_cores: TweetHydrationBatch<PureCore> was added to the hydration result tuple in visibility-filtering/hydration/mod.rs (+244/−18).
    • PureCore is thin core information that holds the retweet's original id (source_tweet_id).
    • PureCoreFallbackCache caches ids that failed the first time so they can be retried in the next request.
    • A source_tweet_id: Option<TweetId> field was added to RawCandidate (introduced after Gen4+22) and is filled in during hydration.

What we learnedG. The follower boundary separating reply spam and reply ranking tasks rose to 250,000

  • In grox reply handling, the GROK_GEMMA_FOLLOWER_SPLIT follower threshold rose from 225,000 to 250,000 verified — grox/flows/reply_spam/constants.py.
    • The constant's name is GROK_GEMMA_FOLLOWER_SPLIT.
    • In the code, this constant splits task eligibility verified — task_filter.py. Conversations where the root or the replied-to account has more followers than this value go to the reply ranking task, and conversations where both are at or below it go to the reply spam task.
    • The constant's name suggests a Grok and Gemma boundary, but the threshold that picks the spam verdict model is a separate one, GEMMA_REPLY_SPAM_MIN_FOLLOWERS = 150_000 verified — same constants.py.
    • This extends an upward series that has run for about 42 days since the Gen4 release (15k → 30k → 40k → 60k → 80k → 100k → 120k → 150k → 180k → 200k → 225k → 250k) verified — per-commit values in task_filter.py and constants.py.
    • As the threshold rises, the range of conversations handled by the reply spam task widens.

Why it matters This commit carries two architectural signals:

  • First, X's ranking computation converged on a single library.
    • Previously, home-mixer and vm-ranker implemented the same formula (the sum of Phoenix probabilities × weights) twice, and so the parameters were mirrored twice as well.
    • Even as of yesterday, how consistency between the two processes was maintained was an open question.
    • With today's commit, home-mixer's copy is gone, and the computation lives only inside the crate.
    • The home-mixer param.rs mirror also got thinner (22 ranking-computation parameters deleted). However, the value model weights remain in both mirrors, home-mixer and vm-ranker/params.rs.
  • Second, home-mixer now has a degraded mode for vm-ranker RPC failures.
    • Previously, when vm-ranker died, an Err was thrown per candidate to downstream code; now the locally computed weighted sum is served as is.
    • This degraded mode became possible because the shared crate physically exists inside home-mixer.
  • Two other things were reflected today:
    • Phoenix retrieval split HOME_HOT, the popular (hot) slice, into a separate index so it no longer mixes with cold.
    • In VF, the last unfinished connection in the rule engine rewrite that has been under way for the past two months was completed. It is a merge that makes a retweet's visibility actually follow the original tweet's visibility.

  • The paper that passed is When LLM-Based User Profiling Adds Value in Production Streaming Recommendation by Comcast Technology AI authors verified arXiv 2609.27183, 2026-09-23.
    • In the HTML version we confirmed that 3 of the 4 authors are affiliated with Comcast Technology AI. They are Neeraj Sharma, Sardar Hamidian and Shaghayegh Agah, with affiliation locations in Sunnyvale and Washington DC.
    • The first author, Milad Sabouri, is affiliated with both DePaul University and Comcast Technology AI.
    • Comcast owns Peacock streaming and Xfinity.
    • The paper's content is a factorial comparison of four content-based user profile types on a production dataset. The four types are combinations of (aggregate vs LLM-generated) × (temporal disentanglement on/off).
    • There are two kinds of profiles:
      1. aggregate: averages the user's recent and past item embeddings.
      2. LLM: feeds the user history into an LLM to get a natural-language summary, then vectorizes it with a text encoder.
    • Because the LLM approach is much more expensive than aggregate, the paper asks "when is that cost justified".
    • There are no online A/B results. It reported only offline accuracy and beyond-accuracy metrics (diversity and others).
    • It does not state which Comcast product the production dataset comes from.
    • It was added to radar.md. Comcast/Peacock were not previously on this repository's watch list, so it is recorded as the first signal from a production stack.

What to check next

  • Check how the relationship between the two mirrors, home-mixer param.rs and vm-ranker/params.rs, gets documented — as of yesterday's commit (Gen4+27), how the home-mixer param.rs and vm-ranker/params.rs mirrors are synchronized with each other was undocumented. In this commit (Gen4+28), the weights again remain in both mirrors. We will watch follow-up commits for whether this change is recorded in the README or under docs/.
  • Check how often home-mixer's local degraded mode actually turns on — vm_ranker.rs was changed to serve the local weighted sum on RPC failure, but the rate at which this path is actually triggered has not been observed. We will watch follow-up commits for whether a VMRanker.local_fallback metric family appears, or whether the existing vm_ranker_value_model_fallback_total{reason=...} is simply reused.
  • Check when the HOME_HOT slice is loaded as an actual index in serving — for now it is only defined in the data pipeline. We will watch for when a second index publication cron that consumes RetrievalDataset.HOME_HOT is scheduled.
  • Check the ratio of VF's evaluate_tweets_retweet_sources{outcome=in_batch} — the probability that a retweet's source is in the same batch depends on traffic patterns. On For You, the original and the retweet often show up together. If the in_batch ratio is low, the fetched path adds latency.
  • Check the actual payload of the grox AgeGatingHarmfulText policy — confirm whether the body of the age_gating_harmful_text_policy.j2 template is released in the next commit. The verdict criteria for each of the five subtypes are the substance of this policy axis.
