1A GPU path and a CPU path co-serve ultra-large-scale personalized search — Meta

Source Hybrid GPU–CPU Retrieval for Personalized Search at Ultra-Large Scale — arXiv 2609.21281, v1 submitted 2026-09-18, KDD 2027 accepted, paper. All 21 authors are affiliated with Meta Platforms (Menlo Park). Affiliations were confirmed in the HTML version.

Background Meta's personalized search must handle two kinds of queries with different characteristics. One depends heavily on the user's interaction history, such as people names, groups, and interests; the other, such as navigational queries and exact-name queries, needs broad item coverage. To cover the latter broadly, the inventory itself must be held largely in the serving index. To handle the former well, cross-feature interaction between user and item must enter the inference path, beyond the dot product of two towers (two encoders that turn the user side and the item side into vectors separately).

The paper calls this the "personalization–scale paradox": the full serving inventory is too large for GPU memory, and an interaction-heavy model is hard to fit into a latency budget on CPU. Few infrastructure papers on Meta search have been published. In the cited literature, there has been no production architecture statement for a long time after Embedding-based retrieval in Facebook search (EBR, KDD 2020) in 2020 and Que2Search (KDD 2021) in 2021. This source claims to resolve the paradox through co-serving orchestration rather than a new model class, and fills that gap with production A/B figures.

What we learnedA. The GPU path goes deep and the CPU path goes broad, each handling an independently selected inventory

  • The source corpus is multi-trillion scale, and the inventory loaded for serving is selected from it separately verified.
    • The 4-trillion figure is on a "before selection" basis and is not the target of the ANN (approximate nearest neighbor search) scan.
    • After passing policy, quality, language, freshness, and duplicate checks, hardware-specific selectors build the GPU snapshot and the CPU snapshot independently.
  • The GPU path runs two-tower retrieval and interaction pre-ranking fused in one process over a billion-scale inventory verified.
    • Pre-ranking is a stage that scores the candidates retrieval picked once more and trims them before handing them to the main ranker.
  • The CPU path handles a tens-of-billions inventory, roughly 20× the GPU side, and uses only the dot product verified.
    • It combines a dedicated dense embedding index, eager term-at-a-time scoring, bulk scanning, and finer clustering.
    • No cross features are used between user and document vectors.
  • Per request, the two paths can run one only, both, or each be turned off independently. Candidates are deduped at the top-level aggregator before moving to the downstream ranker verified.

What we learnedB. The GPU path is slower only at P99, and the CPU path delivers a 4× throughput improvement over the reference implementation when only vector ops are compared

  • On serving latency, the GPU path is faster at P50 and P95 and 16% slower only at P99 verified.
    • This is because it feeds 224 candidates, including interaction pre-ranking, into the shared ranker; it is not a pure kernel comparison.
    • The dense CPU path passes 59 after dedupe.
  • From a capacity plan viewpoint, the CPU path delivers a 4× throughput improvement over a certain reference dense retrieval implementation. However, this compares only vector ops, excluding shared ranking, networking, and the GPU path verified.

What we learnedC. In the full-system A/B, model-scored relevance and substantive engagement both rose over the legacy CPU-only configuration

  • In the full-system A/B, model-scored relevance and substantive engagement both rise against the legacy CPU-only configuration verified.
    • When the two paths were A/B tested separately, each was also positive within its own deployment scope.
  • The metric is GSRR (Good Search Result Rate), which the paper itself defines as a retention-oriented substantive engagement metric.
    • The daily assigned population is in the millions, randomly assigned per account and split roughly in half.

"We present a hybrid GPU–CPU co-serving system that resolves the paradox through orchestration rather than a new model class. A high-depth GPU pathway fuses retrieval and interaction pre-ranking over a curated online pool on the order of a billion documents, while a high-breadth CPU pathway searches an independently selected online inventory roughly twenty times larger with lightweight personalized scoring." — arXiv 2609.21281, 2026-09-18

"The system is deployed in production. A full-system A/B test against the legacy CPU-only configuration improves model-scored relevance and substantive engagement, while separate pathway experiments show positive value at their own deployment scopes." — Same source

Canon update None. Facebook Search is not a canon service of this repository (a service this repository tracks with canon documents), whose services center on Facebook Feed. The paper's results are folded into "new this month" in radar.md. If a second company such as Google, Bing, or Yandex publishes depth-breadth heterogeneous co-serving with production A/B figures, we watch it as a promotion candidate for topics/retrieval-heterogeneous-compute.md.

Why it matters This source is the first statement that opens Meta's production retrieval infrastructure one layer further down. Over the past five years, the published architecture literature on Facebook Search had effectively stopped at two papers, EBR (2020) and Que2Search (2021). This paper shows what is done at the heterogeneous compute layer.

  • However, taken together with the context of the VDD paper, this "Search" spans an integrated search surface within Facebook where search leads to video consumption, rather than pure web search. The evidence is that both papers use GSRR.
  • Its architecture differs from candidate generation in Facebook Feed, which this repository tracks, but it suggests that the two surfaces share a good part of their infrastructure. The evidence is that Xue et al., 2026 is cited as the "existing GPU platform".

2A human-gated LLM automated experiment ran for 37 days on video retrieval — Meta

Source Verify, Don't Trust: Agentic Model Development for Video Discovery Retrieval at Scale — arXiv 2609.21257, v1 submitted 2026-09-18, KDD 2027 accepted, paper. The five authors are Hao Fu, Baiting Zhu, Minglei Chen, Yinjie Huang, and Shuai Ding, all affiliated with Meta Platforms (Menlo Park). Four of these five overlap with the list of 21 authors of source 1.

Background The surface name VDD (Video Deep Dive) appears in the paper corpus for the first time with this source. The original text calls this surface only "VDD", and the surface names Facebook, Instagram, and Reels appear only in the cited literature. VDD is described only as an online follow-on discovery surface that serves "hundreds of millions of users". It is a surface that, when a user opens a seed video, continues with videos worth watching next in a search-ranking manner.

An autoresearch loop in which an LLM agent cycles through code changes, execution, and evaluation already exists, and running minutes-long iterations inside a self-contained script is well known, so that is not what this source addresses. The subject is the failure modes that arise when an automated agent tries to run hours-long executions and weeks-long campaigns in an online system where training, indexing, and serving run hourly across multiple subsystems. Examples are a code change that is actually a no-op, a leaked data window, silently changed evaluator semantics, or control and treatment passing through different serving funnels; even then the campaign can "finish" successfully, but its conclusion is not valid. The source claims to guard against this fragility with a human-gated verification protocol (verification with a gate where a person checks) called EvoPilot, and demonstrates it with a 37-day campaign on VDD's model-based retrieval system.

What we learnedA. VDD's retrieval picks candidate videos by looking at the seed video, the pivot query, and user information together

  • A request is a triple (s, q, u), made of the seed video s, the machine-generated pivot query q, and the user/context profile u verified.
  • MBR (model-based retrieval) is a dense candidate generator, not a downstream ranker, and approximates f(s,q,u,d) in two stages verified.
    • The first stage is ANN based on the two-tower dot product.
    • The second stage is conditional non-linear scoring and is optional.
  • The request tower Q takes the request-side features of the pivot query, user context, and seed video, and the candidate tower D takes only candidate video features verified.
    • Both vectors are normalized, so the dot product and cosine induce the same order.
  • The primary training loss is out-of-session in-batch InfoNCE. To keep co-engagement from contaminating the negatives, examples from the same session within a batch are excluded from the negatives verified.
    • InfoNCE is a contrastive loss that trains the model to distinguish the positive pair from many negative candidates.
  • The interaction head G(h_r, h_d, a(d)) is a candidate-specific function that outputs a weighted binary cross-entropy on click and engagement-derived auxiliary labels verified.
    • The total loss is a weighted sum of InfoNCE and BCE.
  • The relevance output of the interaction head remains for interface compatibility, but its training weight is 0 in the VDD setting verified.
  • Only the embeddings and the index are republished every hour, and the weights themselves are not retrained every hour verified.
    • The D tower is applied to the servable inventory to build an ANN index at the scale of "hundreds of millions of videos" on the "existing GPU platform (Xue et al., 2026)", and the index is refreshed every hour.
  • At request time, ANN picks the top P by affinity a(d), and a deterministic weighted sum of task scores keeps the top-K. The baseline configuration is P = K = 3000 with the interaction head inactive, which gives pure two-tower ANN results verified.
    • When candidate-conditioned scoring is on, the interaction head scores each of the P candidates in between.
  • Above MBR sit the downstream retrieval funnel and a ranker on top of it. This source does not cover the layers above.

What we learnedB. In the campaign, EvoPilot's verification found a defect in evaluation code, and the interaction head became the default serving configuration

  • The campaign ran experiments for a total of 37 days over 7 directions on the VDD MBR pipeline, varying the interaction head, data, objective function, and more verified.
  • The primitive autoresearch attempt concluded that the interaction head lowers the offline hit-rate by 22 percentage points, but the conclusion was wrong verified.
    • The interaction head had originally been turned off because manual experiments confirmed no improvement, and this attempt retried that direction.
  • EvoPilot traced this drop through human-gated verification; the cause was not the interaction head but a pre-existing defect where the evaluation code computed the output depth as 600 instead of 3,000 verified.
    • After the defect was fixed, the offline metric improved by 3.20 percentage points in the matched comparison.
  • In a 7-day randomized online experiment instrumented on a US·Canada slice at the scale of tens of millions of accounts, GSRR on the VDD slice rose significantly by a relative +0.66% verified.
  • After the experiment review, the interaction head treatment was adopted as the default serving configuration of VDD MBR and remained enabled at the manuscript cutoff verified.
  • The post-study replay and mutation test filtered out invalid comparisons and let valid comparisons pass. This verifies that the controls added this time hold up under post-hoc reproduction.
  • Recovering interrupted rounds from durable state and saving about 5 GPU-hours of artifact regeneration cost is a separate empirical result.

"We formalize a VDD request as a triple (s, q, u): the opened seed video s, the machine-generated pivot query q, and a user/context profile u. From a servable inventory 𝒟, the system must retrieve a short ranked list of videos worth watching next. Retrieval is conditioned jointly on (s, q, u). This differs from intent-driven search, which uses a user query alone, and from next-item recommendation, which uses s and u without a query, search relevance, or a retrieval funnel." — arXiv 2609.21257, 2026-09-18

"Publishing applies D to the servable inventory and builds an ANN index of hundreds of millions of videos on an existing GPU platform (Xue et al., 2026). Candidate embeddings and the index are refreshed hourly, but the neural weights are not retrained every hour." — Same source

"After the experiment review, the interaction-head treatment became the default VDD MBR online configuration and remained enabled at manuscript cutoff." — Same source

Canon update None. The VDD surface is not in the list of canon services this repository tracks (Facebook Feed, Instagram, Threads, Reels, X, Netflix). The source is folded into the radar from two angles. One is that, together with source 1, it is one axis showing layer information of Meta's production retrieval stack; the other is that it is the first production-depth statement of an industry LLM autoresearch protocol.

Why it matters This source sets up two new viewpoints. One is that a mixed search-and-recommendation surface within Meta has its own retrieval stack. The other is that it is the first case study showing that industry LLM automated experiments on a production pipeline need a verification layer with a human-checked gate.

  • It is the first statement, with production detail, that a surface inside Meta that mixes "search + recommendation" and uses a seed video and a pivot query together has its own retrieval stack.
    • It is a discovery surface on a different axis from Facebook Feed, whose axis is the friend graph, and Instagram Reels, whose axis is the playback sequence.
  • This source is the first case study showing that when industry LLM automated experiments actually run on a production pipeline, a specification alone is not enough and a human-gated verification layer that catches even evaluator code defects is needed.
    • In radar.md, this angle differs from the spread of LLM-native ranking thread being watched. That thread puts the LLM inside the model architecture, and this source puts the LLM on top of experiment automation.
    • This source is also the first large-scale production statement of the latter angle.

3Confirmed that all authors of the ads retrieval paper ANGLE are affiliated with Tencent — Tencent

Source One-Step Retrieval Framework for Real-Time Sponsored Search Ads Using Hierarchical Text Representations — arXiv 2609.18296, paper. The HTML version confirms that all 8 authors are affiliated with Tencent Inc. and that the email domain is @tencent.com.

Background This paper was left as a source with "affiliation confirmation deferred" on the radar in daily/2026-09-20.md. Today we opened the HTML version and confirmed the affiliation. Now that the production affiliation is confirmed, we fold the confirmation into radar.md, at its ANGLE entry, and update the status from "Watching (awaiting affiliation confirmation)" to "Watching (Tencent confirmed)".

Canon update Only the affiliation and status lines of the ANGLE entry are updated in radar.md. The source does not state its relationship to Tencent WeChat/Weixin ads, so it is not promoted to a service canon.

Why it matters There is added evidence that Tencent joins the LLM-native ranking trend, one of the threads this repository is watching, through the sponsored search ads angle. Its role differs from Tencent PCG's TGR (generative ranking deployed on 5 surfaces). TGR is organic content ranking, and ANGLE is retrieval unification for sponsored search ads.
