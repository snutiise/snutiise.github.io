1TransX scales a behavior-sequence ranking model by component and splits serving into three stages — LinkedIn (radar)

Source TransX Technical Report: Scaling Sequence Transduction for Recommendation — arXiv 2610.20913, 2026-10-14 v1, paper (technical report). There are 8 authors, and the email domain of the authors other than the corresponding author is @linkedin.com (confirmed in the HTML version).

Background Ranking models that read user behavior sequences with a Transformer (Meta HSTU family) improve in quality as the model grows. However, recomputing the whole sequence for every candidate makes serving cost grow in proportion to model size. This paper (TransX) addresses the problem in two directions.

  • Split the model into a sequence encoder, behavior memory and candidate-conditioned fusion, and size each separately.
    • Behavior memory is a fixed-length compressed state of the user history, independent of the candidate.
    • Candidate-conditioned fusion is the part that uses the candidate as the query and reads the memory with cross-attention.
  • Disaggregate serving, which moves expensive computation out of request time.
    • Serving disaggregation is a setup that hands computation formerly done on one server to different stages and resources according to its nature.

What we learnedA. Three variants were A/B tested separately on a large-scale social recommendation surface, and all improved metrics over their baselines

  • The evaluation surface is a "social recommendation application" with about 20K requests per second and 0.5K–1.2K candidates per request verified.

    • The paper does not disclose which LinkedIn product this is.
    • We infer it is likely the LinkedIn feed inferred. The evidence is only the author affiliation and the phrase "social recommendation".

    "We evaluate TransX in a large-scale social recommendation application serving approximately 20K requests per second with roughly 0.5K–1.2K candidates per request." — arXiv 2610.20913 §1 (paper), 2026-10-14

  • Production A/B ran separately for each variant, and the baseline differs by variant verified.

    • The core model (TransX-Base) shows CTR +6.02% and conversion +4.45% over the existing production sequence model.
    • The variant post-trained for retrieval shows CTR +2.96% over the two-tower (a structure that embeds the user and the candidate with separate towers and scores by dot product) sequence model.
    • The ranking variant shows conversion +1.33% over a DLRM (a deep learning recommendation model architecture that combines sparse feature embeddings and an MLP) learning-to-rank baseline.

    "In separate production A/B experiments, TransX-Base improves click-through rate (CTR) by 6.02% and conversion by 4.45% over the production sequential model baseline; TransX-Retrieval improves CTR by 2.96% over the sequential two-tower production model baseline; and TransX-Ranking improves conversion by 1.33% over a DLRM learning-to-rank baseline." — same source §1

What we learnedB. Serving is split into three stages, so the same cost buys about 5× the FLOPs per request of an HSTU-family baseline

  • Behavior memory is independent of the candidate and finite in size, and holds recent actions at high resolution and older actions as lower-resolution summaries verified (§3.2).

    • Because it is independent of the candidate, a memory computed once can be shared by all candidates in the request.

  • Serving is split into three stages: offline bulk state construction, nearline incremental update and online prediction verified (§5.3).

    • The abstract says this split cut total serving cost by nearly 80% against colocated serving (a setup that does all computation on one server) at the same traffic and SLO.

    "TransX therefore disaggregates serving into three stages: bulk state construction, nearline incremental maintenance, and online prediction." — same source §5.3

  • As a result, the same total serving cost allows about 5× the FLOPs per request of an HSTU-family production baseline verified.

    • The abstract says that matching FLOPs per request gives about 4× request throughput per H200. Training infrastructure raised supervised target throughput by 84% under the same conditions verified (abstract).

What we learnedC. The quality gain from scaling differs by component

  • Scaling returns differ by component (anisotropic) verified.

    • With memory resolution and fusion capacity fixed, scaling encoder depth can saturate beyond moderate depth.
    • Increasing supervision shifts the optimal allocation toward fusion.
    • The memory resolution needed to preserve quality stays roughly constant as the model grows.

    "encoder scaling may saturate beyond moderate depth at fixed memory resolution and fusion capacity; increasing supervision shifts the allocation frontier toward candidate-conditioned fusion; and the memory resolution needed to preserve quality remains roughly stable as model capacity grows." — same source §1

Canon update None. LinkedIn is not a tracked service. Added an entry to "New this month" in radar.md and one evidence line to the "Recommendation model scaling law" thread.

Why it matters The scaling-law thread's question continues to shift from "does growing help?" to "where do we grow, and how do we afford the cost?" inferred. The evidence is that Meta released an equal-compute architecture comparison for its ads foundation model GEM in the 2026-10-13 blog post (2026-10-14 daily), and today TransX offers per-component allocation and serving disaggregation. If HELIX, already on the radar, said that "both the feature interaction and sequence axes must be scaled together", TransX makes the same kind of claim by splitting the inside of the sequence model into encoder, memory and fusion. However, we could not confirm the A/B duration or whether it was fully rolled out.
