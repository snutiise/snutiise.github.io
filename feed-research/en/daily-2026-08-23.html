1Phoenix gained 20 ad conversion actions and a delayed feedback training branch — X

Source xai-org/x-algorithm @ 28e414f — "Open-source X Recommendation Algorithm" — 2026-08-21 19:10 UTC, public source code. These notes number X commits in sequence after the Gen4 release; this commit is Gen4+6 by number and 28e414f by sha. It changed 35 files, with a scale of +856/−152. Compared with Gen4+5 (d0cef2f, 2026-08-20, 14 files +479/−200) it is nearly 2× the scale, but it is about 1/4 of the large Gen4+4 expansion (79 files +3.3k/−0.7k). What is new in this commit falls on three axes: the number of actions in the ad revenue prediction stack, delayed feedback handling, and the Muon recipe export. The rest tidies up work that began in Gen4+2 and +4 (Grok 4.6 judge, dark_traffic shadow, SlateContext wiring).

Background Phoenix is the ranking model of X For You. It puts the user history and candidates in one sequence and predicts an engagement probability for each candidate. After Gen4, the X repository has continued its follow-up releases on a daily commit rhythm. The order is 8/14 Gen4+1 (c65aa17) → 8/17 +2 (b089ce6) → 8/18 +3 (11a71f8) → 8/19 +4 (aad7179, large) → 8/20 +5 (d0cef2f) → 8/21 +6 (28e414f, this one).

The canon (this repository's X canon document) from Gen4 through +5 has covered three threads. This commit points in the same direction as these three, but differs from Gen4 through +5 in that it adds a new axis: breaking down the ad revenue prediction head.

  • First is the expansion of signal channels in the ranking pipeline (topic feedback → AI trend feedback, SID 3 layers, RewardOutputs·rewardRerankSlotProb, SlateContext).
    • SID (semantic ID) is an ID that represents a post as a codeword sequence over coarse → fine layers.
  • Second is the generation change of the PTOS judge layer (safemodel↔PtOS disagreement → Grok 4.5 judge → 4.6 dial 0.1 → 0.3).
    • PTOS (PtOS) is the layer in the grox safety pipeline that decides violation categories on a policy basis.
  • Third is VF and grox resource tuning (visibility-filtering shadow, grox reply_spam follower threshold).
    • visibility-filtering (VF) is a service that decides, post by post, whether a post may be shown to this viewer.
    • grox is a Grok-based nearline annotation pipeline.

The six new concepts, in brief:

  • MACT (Mobile App Conversion Tracking) is a measurement framework that attributes in-app events in mobile app ads to ad impressions and clicks.
    • In-app events include in-app purchases, tutorial completion, and sign-ups.
    • When an advertiser logs an in-app event through the SDK, the X ads system matches which impression or click led to that event.
    • The existing X ranker proto had only one, ADS_ATTRIBUTED_MACT_CLICK_INSTALL, which attributes an app install to a click. This time it grew to 12: 6 in-app events times 2 kinds, click and view.
  • View-through conversion refers to the case where a user saw an ad but did not click it, and later reached a conversion (purchase, sign-up, etc.) through another path.
    • It contrasts with click-based attribution (click-through), and is a measurement approach that credits an ad with an effect from the impression alone.
    • This time the X ranker introduced 8 view-through actions: purchase·add_to_cart·checkout_initiated·sign_up·site_visit·session·landing_page_view·upper_funnel.
  • Delayed feedback refers to the phenomenon in ad conversion where the time of the impression or click and the time of the actual conversion (e.g., sign-up, in-app purchase) are separated by anywhere from hours to days.
    • At training time it is hard to tell whether a label that has arrived means "not yet happened" or "will not happen", which distorts the loss.
    • In the ranker literature, delayed conversion prediction has become an established research area of its own (since Chapelle 2014).
    • In this commit, X added an is_delayed_feedback column to each training sample. It also split the loss mask so that ad conversion heads train only on delayed samples and engagement heads only on fresh samples.
  • Muon optimizer is an optimizer that approximately orthogonalizes the gradient momentum matrix with Newton-Schulz orthogonalization.
    • It spread through the Keller Jordan 2024 original text and the LLM training of the Moonshot Kimi K2 family.
    • It was introduced in Gen4+4 (aad7179) as the default dense-parameter optimizer of the X Phoenix ranker, but TRAINING.md still stated that the export Python code used AdamW.
    • In this commit the docs, config, and reference training script were rewritten to state explicitly that flagship and nano are trained with Muon, which narrowed the gap between the export and production.
  • NVIDIA GB300 (Grace Blackwell 300) is NVIDIA's 2025–2026 datacenter GPU. It belongs to the Blackwell generation and succeeds the B200.
    • Each GB300 node supports large-capacity HBM3e and attention kernels based on CUTLASS/CUTe DSL.
    • X exposed hardware-specific config (batch size, expert parallelism, remat policy, attention impl) explicitly in code for the first time.
  • The xai-o2 object storage is S3-compatible object storage presumed to be an xAI internal storage system.
    • In this commit the client crate interface was released, but the actual implementation was left out of the open-source build.
    • This is a signal suggesting that production checkpoint and data storage go through xai-o2 inferred.
    • The open-source build must substitute the standard object_store crate.

20 new ad conversion actions were added at proto numbers 171–190

The new actions are 12 that split MACT in-app events into click and view, and 8 view-through conversions verified.

  • 20 ad conversion actions were newly defined in the action list of the Phoenix proto verified — phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto.

    • They are defined in enum ActionName.

    • The first group is 12 (171–182): the 6 MACT in-app events times click/view.

      • The events are purchase, add_to_cart, level_achieved, tutorial_complete, sign_up, and custom.
      • purchase is an in-app purchase, level_achieved is reaching a game level, tutorial_complete is tutorial completion, sign_up is account registration, and custom is an advertiser-defined custom event.
      • Each event has two families, MACT_<event> and MACT_VIEW_<event>.
      • The former is click-attributed: an event that occurred in the app after the user clicked the ad. The latter is view-attributed: an event that occurred in the app after the user only viewed the ad, without a click.
      • Previously only ADS_ATTRIBUTED_MACT_CLICK_INSTALL (=140) existed, so only app installs were predicted. Now the 6 post-install engagement events are predicted by 12 heads, one each for click and view.

    • The second group is 8 view-through conversions (183–190).

      • They cover purchase / add_to_cart / checkout_initiated / sign_up / site_visit / session / landing_page_view / upper_funnel.
      • Each uses the name <conversion>_VIEW_THROUGH.
      • View-through counterpart heads were introduced to pair with the existing click-attributed conversions (ADS_PURCHASE_CONVERSION = 200, etc.).
      • The 8 web conversions (advertiser site visit, purchase, sign-up, etc.) are now also predicted as view-through.

ads_slim and the ads_conversion_view_through engagement group mapping

12 MACT entries were added to the ad conversion mapping, and a new metric group that the ads ranking config can pick was created verified.

  • A new mapping was added to constants.py verified — phoenix/xrex/data/recsys/constants.py.

    • 12 new MACT mappings were added to the existing ads_conversion_engagement_to_action_types.

    • It also created a metric group called ads_slim. In addition to 7 signals, it includes only the non-primary entries filtered from the preceding conversion click mappings.

    • That is, the ad ranker's "slim" line trains only 3 positive signals, 4 negative signals, and non-primary conversion clicks.

      • The 3 positive signals are open link, external link long dwell, and video quality view.
      • The 4 negative signals are not interested, block, report, and mute.

    • "ads_slim": ads_slim_engagement_to_action_types was also registered in the metric group routing dictionary, so that the ads ranking config can pick this group.

  • A list of conversion heads to be used in the delayed feedback branch below was introduced.
    • The name is SOURCE_SPLIT_CONVERSION_HEAD_INDICES.
    • It is a list that concatenates the click-conditioned action index list and the view-through action index list.
  • When a user is dissatisfied with search results and rewrites the query, this is included in the negative feedback heads. Search surface ranking will learn this signal.
    • CLIENT_TWEET_SEARCH_QUERY_REFORMULATED was added to NEGATIVE_FEEDBACK_HEAD_INDICES.
    • This signal connects to the xrecsys_search config expansion in Gen4+4.

A setting that branches delayed feedback out of the training loss was added

With the new setting on, delayed samples train only the conversion heads and fresh samples train only the engagement heads verified.

  • A new sample_source field was added to the batch verified — phoenix/xrex/data/recsys/recsys_batch.py:980.

    • If the kafka/parquet record batch has an is_delayed_feedback column, its value goes into the batch as sample_source; otherwise the field is filled with all False.
    • True means this sample is a delayed feedback re-observation.
    • Adding the two columns is_delayed_feedback and conversionKeepMask to the required columns list in feature_config.py confirmed the upstream indicator.

  • The loss mask splits by sample state verified — phoenix/xrex/models/recsys_model.py.

    • The branch is in the loss() function.

    • Each training sample is in one of two states, fresh or delayed. Fresh is the original impression, and delayed is the re-observation after the conversion arrived.

    • Fresh samples train only the engagement heads (favorite·reply·click, etc.) and set the conversion heads to mask=0.

    • Delayed samples train only the conversion heads and set the engagement heads to mask=0. Here the conversion heads are the 20 new ones above plus the existing click-conditioned actions.

  • Metric slices were introduced. A branch was added to build_metric_masks so that the three slices can be observed.

    • fresh: delayed=0
    • delayed_clicked: delayed=1 & clicked=1
    • delayed_non_clicked: delayed=1 & clicked=0

  • Because condition_conversion_on_click is a required precondition (assert), even delayed samples keep the conditional training that predicts conversion under the condition "was there a click".

  • mact_in_app_loss_weight is a loss weight multiplied only into the 12 MACT actions, and its default is 1.0.

    • It is exposed as a config parameter, so the training strength of the 12 ad conversion heads can be adjusted.
    • It is observed through stats["mact-in-app-loss-weight"].

  • train_view_through_heads is a gate that decides whether to train the 8 view-through heads.

    • When set to False, it sets the loss mask of the view-through heads to 0 so they are not trained.
    • That is, view-through prediction has to be turned on as an opt-in in the config.

  • conversion_keep_mask / conversionKeepMask is a mask that marks, for each candidate, whether to exclude it from conversion training.

    • from_record_batch reads the kafka conversionKeepMask column and replaces null rows with True (= keep).
    • In loss(), this mask is ANDed with target_padding_mask to exclude entries from conversion training.
    • One caution: sequence packing allows only all(True), and the not-yet-connected case explicitly fails with an assert.

Why it matters delayed feedback modeling is a standard problem in ad conversion prediction. X now sends delayed re-observations as separate kafka events, and built a setting that branches the loss in ranker training so that fresh samples train on engagement and delayed samples on conversion. That setting, split_head_training_by_source, defaults to False, so it is still opt-in verified — recsys_model.py:560@28e414f. This is a loss-consistency device for the duplicate labeling problem (logging the same impression twice, as a fresh event and a delayed event), and also infrastructure support that keeps the training signal of each head sufficiently refreshed as the conversion prediction heads grow to 20.

GB300 hardware-specific overrides appeared for the first time

The config defines GB300 hardware-specific overrides verified. The nano config included in the export also inherits these overrides.

  • _GB300_OVERRIDES is defined verified — phoenix/xrex/configs/xrecsys.py:330-345.

    • bs_per_device=512 is 8× larger than the previous _home_direct_packed_nano value of bs_per_device=64. It reflects the ample HBM capacity of the GB300.
    • ep=64 sets expert parallelism to 64-way. It is MoE (mixture-of-experts) style sharding.
    • attn_impl="cutedsl_ranker_varlen_attn" is a variable-length attention kernel based on NVIDIA CUTLASS/CUTe DSL. It is a new attention implementation optimized for the GB300.
    • remat_policy=RematType.SAVE_GB300_RECSYS is a rematerialization policy tuned to the GB300 memory hierarchy. It decides what to checkpoint and what to recompute.
    • unroll_layer_stack=True compiles the Transformer layer stack unrolled (listed explicitly instead of looped). This gives XLA more room to optimize.
    • learning_rate=5e-4 is slightly lower than the Gen4+4 flagship base LR of 7.1e-4. It appears to be an adjustment matched to the 8× larger bs_per_device inferred.
    • checkpoint_every_n=300 saves a checkpoint every 300 steps.

  • _home_direct_packed_nano inherits this override.

    • Previously it set learning_rate=2e-3 separately.
    • In this commit it inherits the LR, optim_config, and emb_optim_config of _GB300_OVERRIDES as they are.
    • In other words, even the "nano" model included in the export is tuned on the assumption of GB300 training.

Why it matters This is the first case of X exposing a hardware generation change in code; the earlier canon said "which GPU Phoenix runs on is undisclosed", but there is now a strong signal that GB300 is the production standard hardware. NVIDIA GB300 began shipping in the second half of 2025 and succeeds the Blackwell B200. It is the latest generation that LLM companies acquire in bulk, and xAI applied it directly to ranker training and serving pipelines. cutedsl_ranker_varlen_attn may be a kernel xAI built itself, since this name is absent from the open-source kernel catalog inferred.

The interface of the xai-o2 storage crate was released

An interface crate for an S3-compatible object storage client was newly added verified. In the open-source build, trying to create this client always returns an error.

  • The xai-o2 crate was introduced verified — phoenix/crates/storage/xai-o2/.

    • The description in Cargo.toml reads:

      Client interface for the xai-o2 (S3-compatible) object storage backend

    • There are 3 files, 134 lines in total.

      • base_client.rs (12 lines) is the BaseO2Client async trait. It is a minimal interface that defines only put(key, data) -> Result<()>.
      • O2ClientBuilder in o2_client_builder.rs (115 lines) exposes 15 builder methods. The first eight are endpoint·bucket·prefix·access_key_id·secret_access_key·allow_anonymous·timeout·io_timeout. The other seven are retry_max_times·retry_min_delay·retry_max_delay·write_chunk_size_mib·write_chunk_concurrency·max_concurrent_write_requests·trace_always.
      • lib.rs (7 lines) contains only pub mod declarations.

  • In the open-source build, O2ClientBuilder::build() always returns the following error:

    • The error message returned by build() is "the xai-o2 backend is not included in this build; use the default object_store backend".
    • That is, only an interface stub was released, and the actual implementation is not included in the open-source build.
    • The xai-recsys-engine crate does declare the dependency as xai-o2 = { workspace = true }, but using it in practice requires substituting another backend.

Why it matters It was confirmed for the first time that xAI has an internal S3-compatible object storage system named xai-o2. The 15 builder parameters are meaningful because they list the items actually tuned in production. The test (build_fails_loudly_after_full_configuration) contains values close to real operation: chunk 8MiB, concurrency 16, max_concurrent 64, retry 6 times, min/max delay 1/32s, timeout 300s. This is a signal that production checkpoint and data storage connect here inferred; the open-source build must substitute the standard object_store crate (AWS S3, etc.).

grox reply_spam follower threshold rose from 60k to 80k (4th increase, 1.33×)

The follower threshold used for spam verdicts and for reply ranking rose from 60,000 to 80,000 in both places verified.

  • The two threshold constants in task_filter.py changed together verified — grox/flows/reply_spam/task_filter.py.

  • The threshold went through five stages over 8 days starting 2026-08-13 verified.

    • 15,000 (before 2026-08-13)
    • 30,000(2026-08-14, Gen4+1)
    • 40,000(2026-08-17, Gen4+2) — task_filter.py@b089ce6
    • 60,000(2026-08-18, Gen4+3)
    • 80,000(2026-08-21, Gen4+6)

  • The previous three steps were 2×, 1.33×, and 1.5× (15→30, 30→40, 40→60), and this 1.33× is a smaller increase than the one before.

Why it matters Only replies whose thread root and reply target are both at or below this threshold receive the grok spam verdict, so as the threshold rises, the spam verdict covers replies from larger accounts. The reply ranking scoring that a reply receives when either one exceeds the threshold narrows by the same amount verified — task_filter.py:77-92, 214-225. One of three explanations may account for the slowdown at 80k: the grok budget bottleneck is near, larger accounts attract fewer spam replies so marginal utility fell, or the next step is preparing a full rollout with no threshold inferred.

Retrieval post-embedding computation is now processed in 65k chunks on even shards

Retrieval post-embedding computation splits a shard into chunks of at most 65,536 rows only for even shards; otherwise it processes the whole shard at once as before verified.

  • Refactored maybe_build_retrieval_post_embeddings and introduced a _forward_chunked helper verified — phoenix/xrex/train/trainer_recsys.py.
    • Previously, the whole shard was computed in a single candidate_tower_forward_jit call.
    • Now it enters chunking with _chunk_rows = min(_shard_rows, 65536) only in the even-shard case where total_samples % data_world_size == 0.
    • Otherwise it processes the whole shard at once (_chunk_rows = _shard_rows).
    • For each chunk, it computes in the order jax.make_array_from_process_local_data → _lookup → candidate_tower_forward_jit → local shard concatenate, and concatenates at the end.
    • Even when head_dataset_mapping has several heads, it calls _forward_chunked for each head and chunks in the same way.

Why it matters When the retrieval two-tower post embedding batch grows, there is a risk of OOM at XLA compile and execution time, so it is cut into 65k-row units and processed sequentially. This stabilizes the subroutine as training scale grows with the Muon promotion and the GB300 config.

--hotswap_malloc_trim CLI added to inference hotswap

An option was added that calls glibc's memory trim function at the end of every inference hotswap cycle, and its default is True verified.

  • A new option entered the inference code verified — phoenix/xrex/inference/model_runner.py, launch_inference.py.
    • The InferenceModelRunner field hotswap_malloc_trim: bool = True was added.
    • The CLI argument --hotswap_malloc_trim was added, and its default is True.
    • The _malloc_trim_after_swap() method calls _glibc_malloc_trim() (= libc malloc_trim(0)) at the end of every hotswap cycle.
    • Observation is done with metrics_publisher.checkpoint_reload_step_seconds.labels(step="malloc_trim").observe(secs).

The CLI help states this problem explicitly.

glibc malloc_trim(0) on the coordinator thread after each applied hotswap; returns the cycle's freed pages (glibc slots otherwise ratchet ~196 MiB/cycle). No-op under jemalloc.

Why it matters The documentation reveals for the first time that embedding table hotswap in Phoenix serving has been leaking about 196MiB of RSS per cycle under the glibc memory allocator. Embedding table hotswap periodically swaps a new embedding checkpoint in-process. Calling libc malloc_trim(0) returns the freed pages to the OS, and it has no effect under the other allocator, jemalloc. This is a small patch that polishes production serving, but it also shows that hotswap is long-running infrastructure in production, where enough load accumulated to make this patch necessary.

Three options added to the nano config of two-tower retrieval
