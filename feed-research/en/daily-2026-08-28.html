Source xai-org/x-algorithm@45b48ba — GitHub commit, 2026-08-26T20:04:12Z (36 files, +873/−525), public source code. These notes number X commits after the Gen4 release in sequence, and this commit is Gen4+9.

  • The commit message is a single line, "Open-source X Recommendation Algorithm", as is the convention in this series of generations. So the actual content can only be read from the file diffs.
  • By size, it falls between Gen4+7 (+1,418) and +6 (+856).
  • However, the breadth of subsystems touched is wide (6 areas: Phoenix training, Phoenix serving, VF, ads proto, grox, home-mixer).

The previous commit, Gen4+8 (0d3cdd8), was a broad release that touched six subsystems side by side with the following changes:

1-A. Host memory caps were introduced on both the save and restore sides of Phoenix checkpoints

Both the code that saves Phoenix checkpoints and the code that restores them explicitly introduced a cap on RSS (resident set size, actual host memory occupancy). This change follows the restore-side hardening in Gen4+7 (2026-08-24). At that time, the concurrent_gb throttle and node-lock were applied only to restore. Gen4+9 applies the same principle to saving, and restore gained one more streamed variant.

  • The changed files are phoenix/xrex/utils/checkpointing.py (+215/−6) on the save side and phoenix/python/training/xai-checkpointing/xai_checkpointing/load.py (+311/−88) on the restore side.
  • The save side gained a new handler that splits tensors into batches and performs D2H (device-to-host copy) and write verified — phoenix/xrex/utils/checkpointing.py:88-181.
    • It is named ThrottledD2HArrayHandler. It inherits Orbax's ocp.type_handlers.ArrayHandler and overrides serialize(values, infos, args).
    • It iterates over the tensor list, accumulating each tensor's addressable_nbytes (the actual bytes of the shard the current process is responsible for), and flushes the batch when it exceeds the concurrent_bytes limit.
    • It calls super().serialize() for each batch and waits with future.result() for D2H and write to finish before moving to the next batch.
    • In other words, instead of staging all tensors at once and consuming pinned-host memory all at once, it stages the next batch only after the D2H and save of one batch have finished.
  • The throttle size is given as an argument of the save function. If it is not given, the same stock Orbax handler as before (stage everything) is used, so backward compatibility is kept verified — same file.
    • The form of the argument is save_checkpoint(..., save_concurrent_gb=<N>).
    • Depending on whether compression is used, multiple inheritance is split into ThrottledD2HArrayHandler (compressed) and ThrottledNoCompressionArrayHandler (non-compressed).
  • There is also a node-level flock. When the env is on, it prevents multiple processes on the same node from saving at the same time, the same pattern as on the restore side verified — same file.
    • When the XAI_SAVE_NODE_SERIALIZE=1 env is on, it takes fcntl.LOCK_EX on /dev/shm/xai_save_node_lock (or /tmp/... if absent).
    • The env on the restore side is XAI_RESTORE_NODE_SERIALIZE.
  • The log records the leaves count and GiB per batch, and warns explicitly if max_leaf exceeds the budget ("that leaf still D2Hs in one shot") verified — same file.
    • It is a device that tells the user there is room for tuning when the throttle size is smaller than a tensor.

"save node-serialize ACTIVE (flock per batch) lock=%s pid=%d num_batches=%d" — phoenix/xrex/utils/checkpointing.py, 2026-08-26

Why it matters Host OOM caused by the D2H stage outside wait_until_finished, when multiple workers save checkpoints at the same time on the Muon+GB300 generation, was probably observed inferred. This change is fully symmetric to the logic by which Gen4+7 introduced hardening on the restore side. It can be read as the result of confirming by measurement that the old stock Orbax setting ("write-limiter default 96GB, D2H of everything") is actually insufficient for saving large models, after Gen4+6 formally included flagship Muon training in the export.

  • The restore side gained a new streamed loader that puts only one batch of tensors into pinned-host memory at a time verified — phoenix/python/training/xai-checkpointing/xai_checkpointing/load.py:365-528.
    • It is named load_checkpoint_streamed.
    • The existing load_checkpoint first built host_state (a pinned-host copy of all tensors) and then did read into shards batch by batch.
    • The streamed version keeps device_state. For each batch it goes through: stage only that batch's tensors to pinned-host → read files → device_put to device → update device_state → release the batch's pinned-host.
    • In other words, at any point the upper bound of pinned-host usage equals the size of the current batch.
  • A reasonable window is chosen automatically even if the user does not set the window value verified — same file.
    • If window_gb=None (the default), it is set to _auto_window_bytes = min(max(max_leaf, total/16), 32GB).
    • In other words, the window is the larger of max_leaf and total/16, but does not exceed 32×10⁹ bytes verified — load.py:365-372.
    • So the target is roughly 16 batches or fewer. If max_leaf is larger than 32×10⁹ bytes, the window can be smaller than max_leaf.
  • When a batch completes and the device_state references are replaced with new arrays, the list of old and new pairs is passed to the on_replaced callback verified — same file.
    • The caller uses this list to delete old arrays immediately or to swap links in other data structures.
    • If no callback is given, the full list is returned.
  • There is a helper that handles in advance the aliased case, where the same array object is referenced twice verified — same file.
    • The helper is copy_aliased_arrays. From the second reference onward in the jax tree, it makes an actual copy with may_alias=False device_put.
    • It is handled in advance so that aliased references do not lose the original when streamed load swaps in new arrays batch by batch.
  • Larger tensors are processed first to secure window packing efficiency verified — same file.
    • The sort code is plan.sort(key=lambda item: item[3], reverse=True).
    • A tensor of max_leaf or more fills a batch by itself anyway, so such tensors are gathered at the front.
  • A staging hook for warm start was added. When restoring only params from a checkpoint and reinitializing opt_state, no copy of opt_state is made in pinned-host either.
    • The hook is Trainer.warm_start_staging_spec (phoenix/xrex/train/trainer.py:1160-1165).
    • Previously, device_put with the staging sharding for restore moved the entire state structure to pinned-host.
    • Now warm_purge(self.state) cuts out opt_state in advance, stages to pinned-host, and device_puts only the loaded part again. The original opt_state field is left as is.
    • RecsysTrainer.warm_start_staging_spec overrides this in the subclass to support the keep_emb_opt_state=True option.
    • Why it matters: warm start restore has become much lighter. This suggests that the flow where flagship Muon training starts from pretrained params and restarts the optimizer fresh has become standard inferred.

    • The diff gives no clue why it is needed, but it appears to be meant for resetting the EWMAs immediately after a hot-swap or a sharp change in traffic profile inferred. It points in the same direction as the _glibc_malloc_trim() post-swap processing in Gen4+6.

1-B. If either dense or embedding fails the grad-norm check, both updates are skipped

In Phoenix training code (trainer_recsys), if the grad-norm check fails for either dense or embedding, both are now kept as the originals. Previously, if dense passed and only emb failed, dense params were updated to new values while only emb was rolled back, and this asymmetric state could last for a few steps. Now params and the embedding table move in lock-step.

  • The parameter update condition was unified across the two training loops (dense sync and async_no_deferred) verified — phoenix/xrex/train/trainer_recsys.py:1331-1400.
    • The file change is phoenix/xrex/train/trainer_recsys.py (+29/−19).

Previously the updates went in this order:

  1. Check the dense grad-norm with valid_step = is_valid_step(gradients).
  2. Update dense params: jnp.where(valid_step, updated, original)
  3. After segment_sum, check the emb grad-norm with is_valid_step(emb_gradients).
  4. Update the emb table: sparse_update(..., valid_step=emb_valid_step)
  5. Record valid_step = valid_step & emb_valid_step in the metric.

After the change, the updates go in this order:

  1. Check the dense grad-norm to get valid_step.
  2. First run segment_sum and the emb grad-norm check to get emb_valid_step.
  3. Compute keep_step = valid_step & emb_valid_step.
  4. Update dense params: jnp.where(keep_step, updated, original)
  5. Update the emb table: sparse_update(..., valid_step=keep_step)
  6. Record valid_step = keep_step in the metric.
  • The async path (update_async_deferred) was unified in the same way.
    • pending=jnp.asarray(True) changed to pending=keep_step. As a result, the asynchronous emb gradient update reflects this step's gate result, which decides whether it is actually applied at the next step.
  • The async path also actually uses the grad-norm threshold now. Previously, the async deferred path was assumed to be incompatible with grad-norm gating.
    • This threshold is grad_norm_keep_threshold. The assert self.grad_norm_keep_threshold is None in _create_async_emb_executables was removed.

Why it matters The dense grad and embedding grad probably spiked at different scales on the Muon+GB300 generation inferred. Lock-step gating blocks the effect of this divergence from the start. It is a consistency adjustment for reproducible training.

1-C. The reply spam verdict prompt can now include follower count and bio, and the reply ranking score written to Manhattan can only go down

In the grox reply spam (reply_spam) flow, the change has two parts. The LM verdict context was expanded, and a monotone-only gate was added to the Manhattan write. Both changes touch the reliability of reply spam and ranking verdicts as well as serving stability.

  • The user metadata fed to the LM verdict was expanded verified — grox/core/lm/post.py (+18/−6).

    • The file changed together with it is grox/core/lm/thread.py (+25/−4).

    • Previously PostRenderer.render() emitted user metadata as the single line Metadata: <name> @<handle>; now it splits it into three:

      User Handle: @<handle>
[User Follower Count: <N>]     # when include_follower_count=True
User Name: "<name>"
[User Bio: "<bio>"]              # when include_bio=True

    • ThreadRenderer._render_thread gained a new include_follower_count argument.

    • Every post in the thread gets the follower count, and bio goes only into post 0 (the original, the thread root).

    • The last post, the reply target (reply-under-eval), also gets the follower count.

    • A # Reply Author Info header was added before the message, explicitly giving the LLM a context hint that "this information is about the author of the reply to be evaluated".

Why it matters Follower count was probably a strong signal for reply spam and low-quality verdicts to begin with. The grox reply_spam pipeline was already using this signal to filter out bulk spam through the follower threshold in task_filter.py. Now the LM verdict itself also refers to this figure directly.

Bio is strong evidence for detecting spam and bots (a bio may contain spam hints such as "link in profile", or reveal affiliation with political or commercial organizations and interests). So exposing the profile of the original post's author as well raises verdict reliability. However, bios of the other participants in the reply thread are not included, which keeps the context from growing too long, and only the profiles of the two authors, the original post and the reply-under-eval, are expanded.

  • When writing the reply ranking score to Manhattan, the write is skipped if the new score is greater than the existing one verified — grox/flows/reply_spam/task_write.py:113-138.
    • The change is +22 lines.
    • _publish_to_reply_ranking_manhattan first looks up the existing score with ReplyRankingScoreStratoLoader.fetch_reply_ranking_score(post.id).
    • If the new score is greater than the existing one, it skips the write and increments Metrics.counter("task.write_reply_ranking_manhattan.skipped.count", reason="higher_than_existing"); if it is lower, it writes as is.
    • In other words, a reply ranking score sent out on this channel only decreases over time and never increases.

Why it matters If a reply's first verdict is low, the reply keeps a low score, and the serving score is not updated even if a later verdict becomes more lenient. Conversely, a reply whose first verdict is high (lenient) is lowered if later verdicts become stricter. This matches the monotone safety direction of reply spam verdicts, that is, once a reply is caught as spam it keeps being treated as spam, and only reclassification from normal to spam is allowed; it also removes oscillation of the reply ranking score over time, so the ranking of the same reply does not go up and down in the UI and in A/B tests. inferred Label flapping was probably actually observed in reply spam and ranking observation.

Canon update Added two subsections, LM context expansion and Manhattan monotone write, to the reply_spam section of services/x.md.

1-D. VF removed the media fallback cache it kept against TES lookup failures

The 1M-entry LRU-based fallback cache that VF used when looking up media entities from TES (Tweet Entity Service, X's internal tweet metadata service) was deleted entirely. Two related env flags and the code that wired them in disappeared as well.

  • The cache lived in TesHydrator, in the file visibility-filtering/hydration/tes_hydrator.rs (+4/−292).
  • The two related config envs were also removed from visibility-filtering/config.rs (0+/20−).
    • VF_MEDIA_FALLBACK_CACHE_SERVE_STALE_ENABLED, VF_MEDIA_FALLBACK_CACHE_POPULATE_ENABLED
  • The code and arguments that wired in the cache were deleted together.
    • The wiring code in server_deps.rs (9 lines)
    • The arguments in hydration/mod.rs (2 lines)
    • The media_fallback_cache_mode parameter of HydrationPipeline::new

The logic before deletion was as follows:

  • VF looked up media entities from TES, and if TES failed and no media feature came out, it kept the result of a previously successful lookup in the cache. When a later lookup failed, it substituted the stale but valid media feature (FallbackCacheMode::ServeStale).
  • There was also a mode that only filled the cache without using it for serving (FallbackCacheMode::Shadow).
  • The cache size was 1,000,000 (CACHE_CAPACITY = 1_000_000), and eviction was LRU.
  • A large part of the 292 deleted lines were two regression tests using the MediaFailingAfterFirstClient mock.
    • media_stale_recovery_respects_cache_mode, no_media_tweets_cache_default_entries_that_serve_stale

Why it matters This fallback cache was likely a safety net for the stabilization period after the early VF rewrite (the Gen4 headline release) inferred. If a failure occurred while the TES infrastructure was being rewritten, a candidate would be caught by fail-close filtering without media features; the cache mitigated that destructive result. Its removal now means the following three things:

  • The VF rewrite can now be audited for consistency with the Gen4+7 reference_compare harness.
  • The failure rate of the TES media path has dropped, so the marginal utility of the fallback cache has shrunk.
  • The direction is the same as the major simplification of VMRanker in Gen4+8: "removing the safety net once things have stabilized".

However, the fallback caches of other hydrators (such as gizmoduck) are kept, so the fallback_cache_mode env also remains.

Canon update Added a subsection on removing the media fallback cache to the VF section of services/x.md.

1-E. The canary workload no longer enters dark traffic mirroring

The canary workload is dropped from VF's dark traffic mirroring. It is also not mirrored when the workload name is not set.

  • The function that decides whether to mirror was extended to take the workload as well verified.
    • The target is the should_enable(ordinal, max_ordinal) function in visibility-filtering/dark_traffic_setup.rs (+40/−17). It was extended to should_mirror(workload, ordinal, max_ordinal).
    • Added rule: if workload=None (env WORKLOAD_NAME is unset), it fails closed and does not mirror.
    • Added rule: if workload.ends_with("-canary"), it does not mirror. In other words, a canary workload never enters dark traffic mirroring.
    • Otherwise it decides by ordinal < max_ordinal as before.
  • Two new tests were also added (canary_never_mirrors, missing_workload_name_fails_closed).
  • The log message was also generalized from "disabled (ordinal >= max)" to "disabled (not a mirror host)".

Why it matters The dark_traffic that Gen4+4 created was migrated from shadow to staging in Gen4+6. This change prevents the incident where a canary workload is mirrored by mistake and canary issues contaminate the shadow verdict. The production and canary workloads appear to share the same name prefix inferred, so suffix matching alone is sufficient.

1-G. The retrieval user tower can now give history tokens a dedicated segment id

In Phoenix's two-tower retrieval model (a model that embeds users and items separately), the user tower's history tokens can now be given a dedicated segment id. A config flag turns this behavior on and off, and it is off by default.

  • The user tower's attention segment id can now be set to the history-token-specific HISTORY_SEGMENT_ID instead of zeros verified.
    • The file is phoenix/xrex/models/recsys_two_tower_model.py (+12/−1).
    • HISTORY_SEGMENT_ID is imported from xrex.pallas.ranker_attention_utils.
    • The flag name is use_history_segment_ids, defined as RecsysTwoTowerModelConfig.use_history_segment_ids: bool = False. It is off by default.
  • The new function user_tower_segment_ids(batch, seq_len, use_history_segment_ids) fills the whole shape (B, T) with HISTORY_SEGMENT_ID when the flag is on. When it is off, it fills with zeros as before.
    • When on, the user history tokens are grouped into one segment.
  • Related defaults were also added to the xrecsys_two_tower.py config.

Why it matters This prepares for stating segment boundaries inside the user history sequence when the pallas flash-attention varlen kernel cuts the attention scope with a segment mask. Previously everything was a single zeros segment, so the segment mask itself was meaningless. Now special tokens with a different segment id (for example, the user_features token) can be isolated from the history tokens so they do not attend to each other. The accuracy of varlen packing improves.

2AMBER, one token per interaction event, is served on Facebook — Radar (Meta)

Source AMBER: An Event is Worth One Token — arXiv 2608.25546 — arXiv, submitted 2026-08-26, paper. All 15 authors are listed as "AI at Meta", which we confirmed in HTML v1. The affiliation notation is ∗Core contributors, †Correspondence, AI at Meta.

Background LLM-based recommendation re-expresses the "user interaction sequence" as tokens and performs autoregressive prediction. However, earlier approaches (text, semantic ID, a few categorical features) carried shallow information at each position. As a result, the query context weakened, and this fed back in as the context of the next position, so performance degradation accumulated with sequence length. This paper (AMBER) presents Event Tokenization, which compresses one interaction event into one Event Token.

What we learnedAMBER compresses one event into one Event Token and encodes billions of events per day on Facebook

  • Event Tokenization compresses the "temporal snapshot" of one interaction event (user, item, context and outcome signals, all of them) into one compact Event Token verified.
  • This Event Token has taken its place as a new input type for LLMs. It improved the "compute-quality Pareto frontier" on industry-scale offline ranking and retrieval benchmarks verified.
  • The Event Token can also be transferred to non-LLM rankers as a feature (transferability), and showed a statistically significant improvement verified.
  • It serves the encoding of billions of events per day on the Facebook surface verified. The HTML says "supporting online encoding for billions of events per day".

Why notable A fourth production claim is added to the LLM-native ranking thread. The three earlier claims are as follows:

  • Netflix GenRec: scoring
  • Meta ConnectionMind: graph reasoning
  • Taobao MetaStrategy: offline policy compiler

Meta AMBER follows these from the input tokenization angle. Rather than placing an LLM in the serving path, it takes an offline or nearline encoder approach, while leaving downstream uses wide open. It is unusual that it is served as online encoding on the Facebook surface and also transfers to non-LLM rankers. Read together with Meta's ConnectionMind (graph path reasoner), it is a signal that LLM-based recsys approaches have split into at least two tracks even within Meta.

Canon update Added an AMBER entry to the new this month section of radar.md.

Why it matters It shows the architecture spectrum of "where to place the LLM" widening. The GenRec thread split into four branches (Netflix's scoring function, Meta's graph path reasoner, Alibaba's offline policy compiler and Meta's input encoder), so serving location, role and compute budget diversified in different directions. However, online A/B figures are stated in neither the abstract nor the HTML. The Facebook production deployment is confirmed, but the ranking metric lift is not public.

3TransRetrieval scales Transformer ads retrieval and raises revenue — Radar (Alibaba)

Source TransRetrieval: Scaling Up Transformer-Based Retrieval for Industrial Recommendation — arXiv 2608.25528 — arXiv, submitted 2026-08-26, paper. Of the 10 authors, 6 are affiliated with Alibaba (Taobao & Tmall Group Beijing) and 4 with Renmin University. We confirmed the affiliations in HTML v1.

  • The Alibaba authors are Yunfei Liu, Bin Liu, Ziru Xu, Han Zhu, Jian Xu and Bo Zheng, senior authors of the Alimama ads line.
  • The Renmin University authors are Zhifei Zheng, Qiren Zhu, Hanbing Liu and Qi Qi.

Background Several companies have tried applying LLM scaling laws to retrieval in recommender systems (HSTU, Wukong, LLaTTE). However, because of feature heterogeneity, simply stacking Transformer layers yields diminishing returns. Different fields produce token norms of different scales, so attention is dominated by features with large norms and signals are not mixed evenly. This paper (TransRetrieval) presents an aggregator that suppresses the token-norm divergence among heterogeneous fields so that the Transformer can be scaled.

What we learnedScaling ads retrieval with a Transformer still raised revenue under the same latency constraint

  • Weighted average aggregation is an aggregator that suppresses the token-norm divergence among heterogeneous fields so that the Transformer can be scaled verified.
  • Target token compression cuts the computation per candidate by 85% verified.
  • Position-style domain embedding unifies cross-domain data with minimal overhead verified.
  • A one-month production A/B was run on Alibaba's display ads platform verified.

"lifts platform revenue by 2.53% under the same end-to-end latency constraint as the production baseline" — TransRetrieval HTML, 2026-08-26

  • The exact figures are below, and P99 latency stays at ~40ms verified.
    • revenue +2.53% (95% CI [2.22%, 2.70%], p<0.0001)
    • RPM +1.28% (CI [1.14%, 1.56%], p<0.0001)
    • Spread across 4 domains: Domain A +1.72%, B +2.51%, C +5.39%, D +0.87%

Why notable The scaling law thread gets its first claim from Alibaba and Alimama. Until now the thread body cited two companies as evidence, Meta (HSTU, Wukong, LLaTTE) and Netflix (FM), and the Alibaba ads line is added to them. Counting entries outside the thread in order of submission date, ByteDance TM20K (08-07) and Ant Densing Law (08-24) fall in between. It is notable above all as a claim that applies scaling to the retrieval stack, because most companies started with the rank stack.

There is a dispute between LLaTTE's "no scaling without semantic features" and HSTU's "scaling alone works". In this dispute, TransRetrieval offers a third answer: "scaling is possible if field heterogeneity is handled explicitly". And because revenue +2.53% came under the same latency constraint, it is a strong production claim.

4SWIM scores re-ranked lists per session in the Kuaishou main feed — Radar (Kuaishou)

Source SWIM: Step-Wise Integrated Measure for Session-supervised List Evaluation in Generative Re-ranking — arXiv 2608.25104 — arXiv, submitted 2026-08-25, paper. There are 9 authors, and we confirmed the affiliations in HTML v1.

  • Kuaishou Technology (Beijing), 6: Chenghao Zhang, Chao Feng, Xunyong Yang, Xiang Li, Yongqi Liu, Kaiqiao Zhan
  • USTC, 2: Yuanhao Pu, Defu Lian
  • Kun Gai(Unaffiliated)

Background Today's industrial recommender systems widely adopt a Generator-Evaluator (G-E) architecture in the re-ranking stage. The generator produces several candidate lists, and the evaluator scores those lists and picks the best one. In short-video apps such as Kuaishou, users keep interacting over several requests within one session, but earlier evaluators optimized only a single-request metric for one list (for example, expected watch time) and so missed the view of the whole session. SWIM in this paper is an evaluator that scores a list by how much the current list contributes to the session objective.

What we learnedSWIM scores lists with a session-level survival process and was deployed to the Kuaishou main feed

  • SWIM models user behavior as a finite-horizon prefix session-level survival process verified.
  • It factorizes how much the current list contributes to the session objective into a recursive survival distribution and reached-position conditional rewards verified.
  • It was deployed to production in the re-ranking of the Kuaishou main feed verified.

"Kuaishou short-video application (>400M DAU, >2 hours average daily engagement) ... 7 days, 5% traffic allocation" — SWIM HTML, 2026-08-25

  • The exact figures are below verified.
    • App stay time +0.351% (95% CI [0.27%, 0.42%])
    • 7-day retention +0.048% (CI [0.01%, 0.09%])
  • The deployment approach replaces the previous evaluator, CAVE, with SWIM, and keeps the upstream retrieval and generator unchanged.

Why notable SWIM is the third production recommendation paper Kuaishou has put out this month alone: the earlier two are PushDualGen and DrEM, while HD-Rec from the same month reported only benchmark results. This time the evaluator itself of the G-E architecture was redesigned as a session-level survival process, which is a different axis from the SID (semantic ID)/CoT debate or the pxtr noise debate. It appears to signal that the Kuaishou infrastructure team is revisiting the re-ranking evaluator literature across the whole stack inferred. However, the app stay improvement of +0.351% is large compared with other Kuaishou claims this month (for example, DrEM App Stay Time +0.116%); in effect, it explicitly sets a large room for evaluator-level intervention to affect downstream metrics.
