1The default ads blender changed to slot-spread — X

Source xai-org/x-algorithm 9106e9f — X (xAI), 2026-10-31, code. In these notes' numbering this is Gen4+54 (Gen4+N is the number these notes assign, in order, to commits after the Gen4 release on 2026-08-13).

Background X For You (a recommendation timeline that also mixes in posts from accounts the user does not follow) places ads between organic posts and decides their positions by looking at the brand-safety grade (Safe, Low, Medium, High) of the posts directly above and below each ad. The component that does this is the ads blender; the 2026-10-29 commit introduced two new blenders that follow the same safety rules (slot_spread, least_movement), but only as options. At that time the default was still multi_risk, in use since 2026-09-01. This commit changes the default blender to slot_spread, turns on the HighRisk filter for the video carousel, and adds off-by-default options to ads training and the transparency report.

What we learnedA. The default ads blender changed to slot_spread

  • The default of the switch that selects the ads blender changed from multi_risk to slot_spread verified — home-mixer/params/param.rs:937-942.

    • The switch name is AdsBlenderType (rust_home_mixer_ads_blender).
    • The mirror sync time on the first line of the file is 2026-10-30T22:59:56Z. This file is a mirror that copies the defaults of X's internal feature switches.

  • slot_spread first fixes ad slots evenly across the whole page, then pulls the nearest safe post above and below from each slot verified — daily 2026-10-30.

    • High posts cannot appear next to any ad, and Medium posts appear only next to ads whose advertiser allows sensitive context (BSR-high). These conditions are the same as in multi_risk.
    • The comparison test in the 2026-10-29 commit pinned that slot_spread does not serve fewer ads than multi_risk verified — ads/tests/blender_comparison_test.rs.

  • The blender was promoted to the default two days after it was created verified. Whether it went through an experiment stage cannot be known from public code inferred. The basis is that this mirror holds only defaults, not experiment assignments.

What we learnedB. The filter that removes HighRisk posts from the video carousel was turned on

  • The switch that removes brand-safety HighRisk posts from the candidates of the vertical video carousel (a module in For You for swiping horizontally through several videos) became on by default verified — home-mixer/params/param.rs:1245-1250.
    • The switch name is EnableVideoCarouselHighRiskFilter. It was introduced as off by default in the 2026-10-28 commit (Gen4+51).
    • This filter also removes posts that have no safety verdict verified — filters/video_carousel_filter.rs:29-39.
  • The carousel module itself is still off by default, so the user-facing screen currently does not change inferred. The basis is that this diff has no change to the carousel enable switch.
  • Made the embedding version used for carousel dedup selectable with a switch verified — home-mixer/clients/post_v8_search_embedding_client.rs.
    • The default is v8_search_1, the same as the previous constant, so behavior is the same.

What we learnedC. An option to separately train late conversions of ad link opens and long dwell was added

  • An option to add two "late window" heads, for ad link opens and link long dwell, to Phoenix (X's Grok-based ranking model) training was introduced, off by default verified — phoenix/xrex/data/recsys/ads_late_window.py:48-97.

    • A late-window head is a twin head that predicts only behavior that is not visible in the short observation window right after the impression but arrives later. X has used the same structure for ad conversions since 2026-09-01 and for view-through conversions since 2026-10-24.
    • The new actions are ADS_OPEN_LINK_LATE_WINDOW (112) and ADS_LONG_DWELL_LATE_WINDOW (113), and their twins are the existing CLIENT_TWEET_OPEN_LINK and CLIENT_TWEET_EXTERNAL_LINK_LONG_DWELLED.
    • The training option is ads_late_window_heads and the serving composition option is serve_late_window_composed; both default to False. The former requires ads_head_masking, and the latter requires the former.

  • Turning on serving composition adds the late-window probability to the existing head's probability and outputs the sum as the "probability that it happens at some point" verified — same file.

    • The raw late-window output is clipped at 0.5 and then converted to b/(1−b). This appears to be a correction that undoes the difference in training sample construction, but no comment states the reason inferred.

What we learnedD. The Under the Hood report prepared to list labeled posts

  • A feature in the Under the Hood report (an X transparency tool where users look up the visibility-limiting labels applied to their account and posts) that lists the post IDs for each label was introduced, off by default verified — under-the-hood/strato/lib/params.strato:30-37.
    • If a label has 3 or fewer posts, all of them are shown.
    • A label that covers more than 5% of that month's posts shows only a notice instead of a list.
    • Otherwise it shows up to the latest 50, and country-specific takedown labels show the latest 50 regardless of the ratio.
  • From the same commit, the report no longer carries the appeal notice for account labels verified — under-the-hood/strato/columns/underTheHoodReport.User.strato.
    • The country-specific appeal links changed from Brazil to a list of Japan and EU countries.

  • DM share and copy-link share were added to the debias target head names of VMRanker (X's ranking service that computes the weighted sum of scores and diversity) verified — vm-ranker/scoring/debias.rs.

  • The sentence "this video was selected because it shows signs of a hidden layer" was removed from the video hidden-layer detection prompt of grox (a Grok-based content safety pipeline) verified — grox/core/lm/convo.py.

2Meta authors released the long-history ranker LWR — radar

Source Read More, Reason Deeper: Latent Workspaces for Long-Sequence Recommendation — Meta-affiliated authors, 2026-10-29 v1, paper.

Background A sequence ranker that uses long user histories spends more computation in every layer as the history grows, so it is hard to scale history length and model depth separately. HSTU (Meta's generative-recommendation sequence Transformer) carries the same coupling. This paper proposes a structure that keeps the history in a store that each layer can reread and passes only a fixed-size workspace per candidate along the layers.

What we learnedA. Meta authors reported a long-history ranker that is cheaper and better than HSTU offline

  • At a history length of 10K, they write that it improves NE (normalized entropy, a prediction loss where lower is better) by 0.19% over HSTU and cuts forward GFLOP per request by 69.6% verified — arXiv abstract.
    • The author email domain is @meta.com (confirmed in the HTML version).
    • It also reports results on two billion-scale ranking surfaces (anonymized as Surface 1 and 2), but these are offline metrics verified.
  • We found no online A/B test or deployment claim verified. Whether it is used in Meta feeds (Facebook, Instagram) is unknown, so we keep it on the radar inferred.

"At 10K history, it improves NE by 0.19% over HSTU while using 69.6% fewer forward GFLOP/request. It also outperforms existing baselines on two billion-scale ranking surfaces." — Read More, Reason Deeper, 2026-10-29

Canon update Not folded into the canon. Added an entry to ## New this month in radar.md.

Why it matters There is one more piece of evidence in the Meta sequence ranking lineage on "which structure is better at the same compute". Without a deployment claim, it is not raised to the canon.
