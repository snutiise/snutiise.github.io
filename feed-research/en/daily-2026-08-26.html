Background Since the first release on 2026-08-13 (47c1bcd, +363,246/−11,640), the Gen4 open-source release of the X For You timeline has received follow-up commits every day or every other day. This commit (Gen4+7, d011592) touched three broad areas.

1-1. Staging VF compares verdicts against the reference VF on every request and logs only when they differ

The stack that validates the VF rewrite with production traffic now has three stages with this commit verified. The VF deployed to staging also calls the reference VF on each request, compares verdicts strictly, and keeps only the cases where the results differ.

VF is the sub-repo whose full source was first released in the initial Gen4 release. The rewrite is in progress while it runs alongside the previous-generation Gen1·Gen2 Scala VF. However, VF has the fail-closed design noted in item 1 of the canon caveat list, so changing policy carries a large risk, because it treats every result without a verdict as drop. Infrastructure to counter this risk is now in place in three stages. When production traffic sent by dark_traffic arrives at the staging VF, the staging VF computes its own verdict and at the same time compares it against the previous-generation Strato-based reference.

What we learnedA. A three-stage validation stack of traffic mirroring, staging validation, and verdict comparison is complete

  • The VF validation stack is complete in three stages verified. In the first, dark_traffic only forwards traffic; in the second, the dark_traffic target is switched to staging so that staging is validated with production traffic; in the third, reference_compare compares verdicts inside staging.
    • Stage 1, Gen4+4 (aad7179, 2026-08-19): dark_traffic_setup.rs (109 lines, new) mirrors production traffic requests in parallel to xai-vf-shadow.prod.visibility. This stage consumes only traffic resources.
    • Stage 2, Gen4+6 (28e414f, 2026-08-21): The dark_traffic target name changed to xai-vf-service.staging.visibility:grpc. This means the staging deployment, not shadow prod, is validated with production traffic.
    • Stage 3, Gen4+7 (d011592, 2026-08-24): For each request, reference_compare.rs (812 lines, new) calls the Strato-based reference VF in parallel inside the staging deployment (Strato is the internal system X code goes through to look up or store data). It compares verdicts strictly and logs only the cases where results differ, as JSON lines.
    • The full path of the new file is visibility-filtering/reference_compare.rs (812 lines), and the client on the reference side is StratoVfClient.
    • Regression audits of the fail-closed safety sub-repo, where policy changes are risky, can now be run at production traffic scale, and the risk of applying VF changes dropped substantially.

What we learnedB. The comparison runs off the response path and strictly checks that verdicts exactly match the reference VF

  • The main path only hands its own verdict to the harness task, so the comparison work does not affect the response (read-only).
    • begin_compare(viewer_id, country_code, safety_level, tweet_ids) spawns a separate tokio task, and the main path passes the verdict through a oneshot::channel.
    • The timeout is 1.5 seconds.
  • The comparison does no normalization and strictly requires the action label and FilteredReason to match exactly.
    • The comparison function is is_exact_match(&VfAction, &Option<FilteredReason>).
  • StratoVfClient is the identity of the reference VF inferred. The code does not state whether the actual VF stack that StratoVfClient wraps is a remnant of the Gen1·Gen2 Scala VF or a separate reference implementation.
    • Since it identifies itself in the form client_id = "visibility-filtering-service.{APP_ENV}", a separate instance appears to be running inferred.

What we learnedC. Verdict differences are logged grouped by combination, so the log does not explode even when many tweets diverge in the same way

  • Diff logging was optimized by grouping by combination verified. Tweet IDs of the same (service, reference) combination are grouped into one log line, and when the 12KiB budget is exceeded they are split evenly.
    • That is, the number of log lines is proportional to the number of diff combinations, not to the number of tweet_ids, so the log does not explode even if many tweets diverge in the same way.
  • Diff logging groups tweet_ids of the same (service_verdict, reference_verdict) combination, chunks them to fit the 12KiB line budget, and writes them to stdout.

    • The output is println!("{line}"), and each line has the following format:

      {"h":"vf_reference_compare","v":1,"batch":"...","chunk":[1,1],"build":"<12자 SHA>","dc":"atla","level":"TimelineHome","viewer":<u64>,"diffs":[["drop:AuthorIsSuspended","allow",[123, 456]], ...]}

What we learnedK. Reasoning is turned on only for violent speech and suicide/self-harm, and the parent thread is read together when present

  • Reasoning is turned on only for the two categories ViolentSpeech and SuicideOrSelfHarm. Other categories still suppress thinking and respond quickly and cheaply.
    • The setting is USE_REASONING_CATEGORIES = {ViolentSpeech, SuicideOrSelfHarm}.
    • Only for these two categories, SafetyPtosPolicyClassifier.build_convo() applies _strip_thinking_restrictions to the prompt and leaves the assistant message empty so the model can think freely.
    • Other categories suppress thinking with THINKING_CONTROL_END.
  • Only for the same two categories, if the post has ancestor posts, the entire parent thread is rendered as the user message.
    • The setting is USE_THREAD_RENDERER_CATEGORIES = {ViolentSpeech, SuicideOrSelfHarm}. If the post has ancestors, ThreadRenderer renders it.

    • For violent speech too, the context of quotes and replies decides the verdict.
    • In contrast, other categories such as adult content, NSFW media, and illegal behavior carry the signal in the target post itself, so there is no need to extend to the thread.

1-4. The Phoenix checkpoint loader changed to withstand concurrent restores by multiple workers

Since Phoenix training with the Muon optimizer and the GB300 GPU generation has grown beyond its previous scale, practical issues in checkpoint restore have been addressed. The load function now accepts partial loading and a cap on concurrently decoded bytes, and a lock that serializes restores on the same node was introduced.

What we learnedL. The checkpoint load function accepts partial load, tag, and a concurrent decoding cap

  • Three new arguments were added to the load function.
    • The function is load_checkpoint, and the file is xai_checkpointing/load.py (+178/−36).
  • A slice to read can be specified per tensor. It is used to load only specific tensors partially, or to specify a slice when the local shape differs from the checkpoint shape.
    • The argument is domains: dict[str, Any] | None, and it specifies a ts.IndexDomain slice per tensor.
    • Two formats are supported: a JSON spec and an indexing expression.
  • The practice of keeping checkpoints of multiple tags under one base path entered the code.
    • The argument is tag: str | None = None. The default is "orbax-ckpt", and it names the checkpoint subdirectory.
  • A cap can be placed on the bytes of tensors decoded concurrently.
    • The argument is concurrent_gb: float | None, and the cap is int(concurrent_gb * 10**9).
    • Reads are cut into batches. When the sum of cur_bytes and nbytes exceeds the budget, the batch is flushed and drained before moving on to the next.
    • If None, reads are issued in parallel without throttling.

What we learnedM. Workers on the same node restore only one batch at a time using a file lock

  • Restore is serialized at the node level. It prevents multiple JAX workers on the same node from restoring simultaneously, forcing each node to process one batch at a time.

    • The default lock file path is /dev/shm/xai_restore_node_lock, and if that path does not exist it uses /tmp/....
    • It logs a message when it waits for 1 second or more.

  • Between batches, free memory held by the glibc allocator is returned.

    • It calls gc.collect() and ctypes.CDLL("libc.so.6").malloc_trim(0).

Why it matters This loader change is a signal that Gen4's training stack is maturing. Gen4+6 (2026-08-21) rewrote TRAINING.md and the README so that flagship Muon and the GB300 override are formally included in the export. Batch verification in that generation may have found a problem of exceeding node memory when multiple workers restore simultaneously inferred. Before Muon, model sizes were small and such infrastructure was unnecessary, but at GB300 scale node-lock and concurrent_gb became essential.

2HEGM watch-time prediction raised metrics in a 1.5-month production A/B — Radar (VK)

Source Hierarchical Exponential-Gaussian Mixtures for Watch-Time Distribution Prediction — arXiv 2608.23356, 2026-08-24 v1, paper. The four authors are Sofia Gulevskaia, Mikhail Trapeznikov, Aleksandr Poslavsky, and Alexander D'yakonov. All four are affiliated with both AI VK and Lomonosov Moscow State University, and we confirmed the affiliations in the HTML version. Code and models are released at github.com/rw404/HEGM.

Background The core regression target in short-video ranking is watch time, that is, how long a user will watch a given video. Three overlapping properties make this prediction hard.

  • near-zero-inflated: a very high share of users skip within 3 seconds, so the distribution mass concentrates heavily near zero.
  • long-tailed: a small number of users watch for a very long time.
  • multimodal: there are several modes, such as casual skimming and immersed watching.

The SOTA for this problem is EGMN (Exponential-Gaussian Mixture Network). EGMN models the whole conditional density with a Gaussian mixture, so it can predict CDF-based events such as "probability of watching 3 seconds or more" rather than a single point estimate. This paper (HEGM) starts from three EGMN failure modes, adds five fixes, and releases 1.5-month production A/B results verified.

What we learnedA. EGMN breaks in three ways in large-scale reproduction

  • EGMN has three failure modes verified.
    • variance collapse: MLE training pushes σ_k(x) of a particular component toward 0, creating a likelihood spike on that sample, and as a result the distribution itself becomes meaningless.
    • component redundancy: several Gaussians converge to μ_i≈μ_j and σ_i≈σ_j, effectively duplicating the same component.
    • inactive components: most mixture weights collapse to 0, and this happens even with an entropy regularizer.
    • The finding that these three failures recur in large-scale reproduction studies is HEGM's starting point.

What we learnedB. HEGM made five fixes, including modeling skipping and engaged watching separately

  • HEGM introduced five fixes verified.
    • Hierarchical skip-watch decomposition: a sigmoid gate predicts the skip probability (p_skip(x) = σ(W_skip · h + b_skip) ∈ (0, 1)). The final density is exponential × p_skip + Gaussian mixture × (1−p_skip). Because it separates "quick skip = indifference" from "engaged viewing" at the decision layer, the model is easier to interpret, and different sub-models handle different failure modes.
    • It adds KL-based variance regularization to address variance collapse.
    • It applies structured initialization.
    • It removes the forced Gaussian shift.
    • It removes the entropy regularizer.

What we learnedC. In the 1.5-month production A/B, session depth and shares rose, and skips and dislikes fell

  • Detailed production A/B figures are published very specifically in the results section of the HTML version verified.
    • Surface: short video. We infer it is VK inferred. The authors do not state it explicitly, but the phrase "serving millions of active users" and the AI VK affiliation strongly suggest it.
    • Duration: 1.5 months (1 month forward and 2 weeks reverse swap).
    • Traffic: the treatment and control groups are 5% each, with about 11M requests per group per day.
    • All results are statistically significant.
      • session depth +9.26%
      • deep watch (≥10s) +5.75%
      • non-short watch (≥3s) +4.59%
      • skips (<3s) −6.23%
      • shares +14.59%
      • dislikes −8.34%

"A 1.5-month production A/B test confirms statistically significant engagement lifts." — HEGM abstract, 2026-08-24

3A law for tokenization capacity as user behavior data grows — Radar (Ant/Alipay)

Source Towards a Densing Law for User Representation Learning at Billion-Scale Capacity — arXiv 2608.23392, 2026-08-24 v1, paper. There are nine authors (Bin Dou, Junru Zhang, Zhaoyi Yuan, Wuliang Huang, Letian Gong, Baokun Wang, Huan Li, Yu Cheng, Weiqiang Wang). Ant Group's DeepFind Team and Zhejiang University collaborated, and we confirmed the affiliations in the HTML version. DeepFind Team appears to be the line at Ant Group related to user representation learning.

Background Industrial-scale user representation learning scales along three axes: number of users, behavior sequence length, and model size. The paper points to two fundamental problems.

  • Raw text scaling has a bottleneck. At billion scale, adding raw behavioral text input hits diminishing returns in performance. Tokenization, which converts behavior into discrete tokens, does mitigate this.
  • There was no quantitative analysis of how much tokenization settings must grow along with data scale.

This paper formalizes the relationship as the densing law and presents ALGN, which uses the law as a guideline verified.

What we learnedA. The log of tokenization capacity and the log of data scale are roughly linear

  • According to the densing law formula, the log of data scale and the log of tokenization capacity are roughly linearly related verified.

    • This is a single-dimension formula that scales only one of user count or sequence length.

      ln C*(s) = β + α ln(s / s_0)

    • This is a multi-dimensional formula that scales user count and sequence length together.

      ln C*(s) = β + Σ_i α_i ln(s_i / s_{i,0})

    • Here C* is the minimum sufficient tokenization capacity, s is the data scale, and α is an exponent that varies with data characteristics and tokenization approach.

    • This relationship carries the one that Densing Law (arXiv 2412.04315) named for LLMs over to the tokenization axis of the recommendation domain.

What we learnedB. ALGN adjusts tokenization capacity guided by this law, but the abstract gives no improvement figures

  • ALGN (Adaptive Length Group Nested) is a variable-length approach that adaptively adjusts tokenization capacity to data scale, with Densing Law as its guideline verified.
    • The abstract gives no specific improvement figures and says only: "ALGN outperforms existing baselines".

What we learnedC. Evaluation is only an offline benchmark on billion-scale Alipay data, with no production deployment claim

  • The evaluation scale is the billion-scale Alipay PayBill dataset verified. There are three downstream tasks: classification, text-based retrieval, and user-to-user retrieval, and each held-out test is about 0.5M users.
  • There is no production deployment claim verified. Only offline benchmarks are presented.
    • Neither the abstract nor the HTML version states that ALGN was folded into the Alipay serving stack.
    • There is only a data-scale statement, "billion-scale Alipay dataset"; production claims such as A/B results, uplift figures, and serving latency are missing.

"we conduct a pilot study on raw & tokenized scaling comparison on billion-scale Alipay dataset" — Densing Law abstract, 2026-08-24

Why it matters Ant joined the scaling-law thread on a different axis, following Meta, Netflix, and ByteDance. This paper addresses tokenization capacity scaling. It is a law on how large a tokenization vocabulary and structure must be as data scale grows.

  • The companies stated earlier addressed other axes. Meta's HSTU·Wukong·GEM and Netflix Foundation Model stated scaling laws for parameters and data, and ByteDance ads' TM20K solved sequence scaling with KD (knowledge distillation).

4Reasoning traces hurt offline recommendation in a controlled test — Radar (Spotify)

Source The Disconnect Between Better Descriptive Reasoning Trace Quality and Recommendation Effectiveness — arXiv 2608.23154, 2026-08-24 v1, paper. All six authors are at Spotify Research. They are Gustavo Penha, Juan Elenter, Claudia Hauff, Hugues Bouchard, Paul Bennett, and Mounia Lalmas, and we confirmed in the HTML version that the email domain is @spotify.com.

Background Over recent months, in the generative recommender line, attaching chain-of-thought reasoning traces to Semantic ID (SID, an ID that represents an item as a learned token sequence) prediction has appeared in several papers and production claims.

  • The representative case is Kuaishou PushDualGen (arXiv 2608.07989). It was deployed to production with a two-stage generation structure that first produces the SID and then attaches skippable explanatory text (copy), and recorded an effective play rate of +8.50% and a dissatisfaction rate of −37.70%.
  • Other SIDReasoner-family work also claims that traces improve SID inference.

The problem is that these lines mostly support their claims with their own offline metrics or a single production A/B, and controlled comparisons are lacking. This paper fills that gap. It is a 2×2 factorial controlled experiment that independently varies two factors: whether the item representation is an SID or a natural-language title, and whether a reasoning trace is present. The backbone is unified to Qwen3-1.7B, and three Amazon product domains were used.

What we learnedA. Adding descriptive reasoning traces lowers offline recommendation performance

  • The key negative result is that adding descriptive reasoning traces lowers traditional offline recommendation performance under standard SFT and RL training verified.

    "introducing explicit descriptive reasoning traces reduces traditional offline recommendation effectiveness under standard SFT and RL training" — abstract

    • In the Office Products domain, combining the Titles representation with SFT training, adding a trace lowers R@10 (the share of cases where the correct item is within the top 10 recommendations) from .1587 to .1416, about −11%.
    • Across all domains, Titles range from −19% to 0% and SIDs from −9% to 0%.

What we learnedB. Natural-language titles produce better traces, but recommendation metrics get worse

  • Titles produce better traces, but the metrics get worse verified.
    • SID is an opaque learned identifier, so it is hard for an LLM to reason over it like natural language. Only with extensive alignment, additional training that aligns SIDs with natural language, do traces barely become grounded.
    • Natural-language titles yield grounded, interpretable traces even without alignment.
    • However, even when the trace improves, recommendation R@10 drops. In other words, trace quality and recommendation effectiveness are independent of each other.

What we learnedC. A richer reward narrows the gap somewhat, but does not fully catch up with the no-reasoning baseline

  • A richer reward signal partially mitigates the problem verified. In RL training, if the reward is changed from recommendation R@10 itself to a richer signal, the gap narrows somewhat. However, it still does not fully catch up with the no-reasoning baseline.

What we learnedD. No industry cases are cited; this is a conditional observation from the paper's own controlled experiment

  • There is no reference to industry cases verified. The SIDReasoner family appears in the related work section, but the paper does not explicitly cite Kuaishou PushDualGen or similar production deployments.
    • The paper's tone is also less about judging whether "this trend is right" and more about summarizing conditional observations from its own controlled experiment.

"R@10 drops from .1587 to .1416" — Office Products domain, Titles condition Section: Results, arXiv 2608.23154 HTML

Canon update Added a ### Descriptive reasoning traces reduce recommendation effectiveness (Spotify Research) — first rebuttal claim for the SID+CoT line section to "new this month" in radar.md.

Why it matters The two results do not directly contradict each other; they are different observations obtained under different conditions. However, what matters is that the line that attaches CoT to SID now has one reproducible counterpoint.

  • What matters is under which conditions the negative result holds. The conditions of the two sources differ.
    • Kuaishou PushDualGen: it used the push surface, a production A/B, and a real catalog, and the reward was designed around production objectives such as effective play and dissatisfaction rate.
    • Spotify: it used Amazon reviews and a Qwen3-1.7B backbone in an offline setting, and the reward was designed as standard R@10.
    • When future production claims combine SID and CoT, conditions such as backbone size, whether the setting is offline or online, and reward design will be key.
  • One can speculate why Spotify does not deploy a line that combines SID and CoT to production. Spotify is a company that has already moved seriously into the SID (semantic tokenization) line (see the PRS 2025 semantic tokenization talk).
    • If its own experiments gave a negative result, that result may also have been reflected in the company's production roadmap inferred.
    • We can predict that Spotify's production will adopt SID but not attach CoT.
  • The point to watch is a similar-experiment statement from a second company. If one appears, it becomes a candidate for a new, separate section in topics/llm-in-recsys.md titled "SID + reasoning trace: production vs benchmark debate".
