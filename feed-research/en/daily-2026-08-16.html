What we learnedA. X stated directly that weights multiply predicted probabilities, not action counts

  • The header comment of the parameter file of home-mixer (the service that serves the For You feed) puts this interpretation rule first verified — home-mixer/params/param.rs:281-306.

    "Each weight multiplies the predicted probability of that action (P(favorite), P(repost), …) or a continuous value e.g. watch time -- the weights do not multiply raw engagement counts. One common misinterpretation is that you can read these weight ratios as count equivalences, e.g. the incorrect statement that 'one report cancels 468 likes' -- this is incorrect because the weights apply to the predicted probabilities rather than raw counts." — home-mixer/params/param.rs:283-292

  • The canon has used statements such as "reply 13.5 vs favorite 0.5 → 27×", quoted through Gen3, in several places (e.g., multi-task-ranking.md). X's own comment settles that this statement is wrong in principle.

    • Weights multiply predicted probabilities, so they are not ratios of raw counts.
    • In effect, by releasing the parameter mirror in Gen4, X explicitly acknowledged that without a reading guide these values cause misunderstanding.

  • The same comment goes on to explain why the absolute value of the report weight looks so large.

    "And the baseline probability of a Report is more than 1000x lower than a Like, so it's weighted more to allow the prediction to affect the final ranking at all."

    • The size of the report value −234 is the product of value × 1/propensity. Propensity is the base probability that the action occurs.
    • The absolute value appears large because the propensity of a report is 1/1000 or less of that of a like.
    • Yesterday's canon update also noted a caveat in the same direction; this time X described it itself in the code.

  • The same comment also rejects the misconception about mass reporting, for two reasons.

    "It's predicting your likelihood of the action, not summing up raw weights on counts. Also, recommendations are personalized, so reports from bad actors will primarily affect recommendations for users who are similar to the bad actors, rather than having the same effect on the post's ranking to everyone."

    • In sum, even if bot accounts file reports in bulk, two things hold.
      1. The score is your predicted probability. So mass reports primarily affect the recommendations of users similar to those bots.
      2. Only actions taken on posts served in the Home Timeline count as ranking signals. So reactions generated by sharing a link in a group chat do not affect ranking.

  • The same comment block was also inserted in home-mixer/scorers/ranking_scorer.rs:415-446, and a paragraph with the same content was inserted in the README #scoring-and-ranking section.

    • By placing the same statement in three places, X made sure readers are not misled whether they read the code or the documents.

What we learnedC. A path that picks cold start candidates with Thompson sampling appeared, but it is off by default

  • The cold start slot selector was updated verified — home-mixer/scorers/author_cold_start.rs:151-190. Now the way of choosing "which candidate fills the slot" from the cold start candidate set splits into two branches: greedy max-score and Beta reward Thompson sampling.

    • The changed file is author_cold_start.rs.
    • Thompson sampling draws one sample per candidate from its Bayesian posterior and selects by that value; it is a standard bandit technique that induces exploration probabilistically.

  • Six parameters were newly added verified — home-mixer/params/param.rs:687-724.

    • EnableColdStartThompsonSampling = false: the default is off. Actual production still runs greedy.
    • ColdStartBetaAlpha0 = 0.75: the α of the Beta(α₀, β₀) prior; it counts as the prior observation of likes.
    • ColdStartBetaBeta0 = 49.25: β₀; it counts as the prior observation of non-likes. Since α₀ + β₀ = 50 is the effective sample size of the prior, it roughly means the prior knowledge "0.75 likes out of 50 impressions".
    • ColdStartTsTopK = 5: take the top K by Beta sampling, then break ties with the actual score.
    • ColdStartImpressionScale = 1.0: the scale multiplied into view_count.
    • ColdStartTrackedIds = "": a comma-separated list of account and post IDs that specifies the targets for which serving statistics are instrumented.

  • The sampling rule is written in the same file verified.

    • For each candidate i, one sample is drawn from the posterior Beta(α₀ + likes, β₀ + max(views − likes, 0)). The top K are chosen by that value, and within them the candidate with the highest original score is selected.

  • The fact that the default is off matters. As of this release, the cold start applied to real users is still max-score greedy.

    • Thompson sampling is only wired into the A/B infrastructure, and whether it is actually adopted will be decided by upcoming A/B results.

  • If a specific account or post ID is registered in ColdStartTrackedIds, a counter tracks how many times that account appeared from which source in the cold start pipeline. It is a per-item observation hook that lets a specific account be observed directly in A/B experiments.

    • The counter name is home_mixer.cold_start_tracked_ids_total{id, source}.
    • For example, if one politician's account is registered, one can count how many times that account's posts were shown through which cold start path.
    • The existence of this instrumentation hook points the same way as Gen4's under-the-hood transparency approach, which opened account-level label lookup. However, this is X-internal instrumentation, not material released externally.

What we learnedD. Three bool inputs of the ranking model receive real values for the first time

  • The input features of Phoenix (the Transformer ranking model of X For You) were populated for the first time. This input field had been classified as a "dead field" in the canon and remained on the caveat list.
    • Through early Gen4, the field observed in code was bool_features: vec![false; ...].
    • This "dead field" bool_features was entirely filled with vec![false; ...] from Gen3 through early Gen4, so it had no effect as an input.
  • In this commit (Gen4+1), three of them were populated for the first time verified — phoenix/crates/common/xai-recsys/src/util.rs:456-540, 728-900, phoenix/crates/common/xai-recsys/src/model_config.rs:40.
    • The newly populated ones are IS_STALE_POST14D and IS_AUTHOR_FOLLOWED/FOLLOWING_BY_VIEWER_SEQ, three bool sequences in all. They indicate whether a post is stale at 14 days, and the two follow directions between author and viewer.
    • The core of the code diff is two places where vec![false; candidate_seq_len * n_post_bool] was replaced with candidate_bool_features. It applies to both the candidate sequence and the history sequence.
bool feature description
IS_STALE_POST14D When enable_stale_post = true and now - creation_ts > STALE_POST_14D_TTL_SEC, it fills the fav/reply/retweet/quote/view counts with 0 and sets this bool to true. It ignores all engagement signals of posts older than 14 days and only tells the ranker the fact that the post is "stale".
IS_AUTHOR_FOLLOWED_BY_VIEWER_SEQ Indicates whether the viewer follows this candidate's author. It is attached to the candidate sequence and the history sequence respectively.
IS_AUTHOR_FOLLOWING_VIEWER_SEQ Indicates whether the candidate's author follows the viewer; it is an input that detects bidirectional relationships.
  • Two signals that handle stale posts are inserted as a pair verified.

    • If stale, the counts are set to 0 and the bool is raised; if not stale, the actual counts are put in.

    • The ranker can explicitly learn a candidate with "count=0 + is_stale=true" and one with "count=0 + is_stale=false" as different cases.

  • It is especially interesting that the stale post signal is paired with count zeroing. It attaches an explicit label to tell the ranker "this count is low not because the post is unpopular but because it is old and its exposure has stopped".
    • This pairing is a design that lets the ranker work around, through training, the snowball problem (a self-reinforcing loop in which a low count on an old post leads to a low ranking, and that ranking in turn leads to a low count) that the canon has observed through Gen3.
  • It appears to be a design that lets the ranker work around, through training, the problem the canon has observed since Gen3: "a low count on an old post leads to a low ranking, and that ranking in turn leads to a low count, a self-reinforcing loop" inferred. X did not document the purpose of this design directly, but the structure pairing count zeroing with a bool set strongly suggests that direction.
  • The is_mutual_follow boost (reply +15) quoted in Gen4 was a condition hardcoded in the scorer. It also matters that the model now receives follow directions as separate input bools and can pick up a similar pattern through training.
    • The shift from hardcoded boosts to learned signals matches the overall direction seen in the move from Gen3 to Gen4: the weight moves from manual gating to model training.

2DrEM, a noise-robust ensemble ranking paper, is confirmed as Kuaishou's — Kuaishou

Source DrEM: Dual-Side Robust Ensemble Ranking from Noisy User Preference Predictions in Video Recommendation — arXiv:2608.12778 — arXiv, submitted 2026-08-13, paper. It has eight authors (Canwei Huang, Tiantian He, Xiaoxiao Xu, Jun Zhang, Ziran Deng, Weike Pan, Chunjie Chen, Kaiqiao Zhan).

Background Yesterday I registered this paper in radar.md with its affiliation unconfirmed, noting only a statistical likelihood of a Kuaishou link at the inferred grade. Today I opened the arXiv HTML version and checked the author affiliations: five authors use a Kuaishou email domain, which confirms this as a production paper from that company. The paper addresses how to correct noise in upstream model predictions at the ensemble ranking stage, on both the label side and the input side.

What we learnedA. DrEM is Kuaishou's second production paper this month

  • The HTML version confirms that this paper is a collaboration between Kuaishou Technology Beijing and Shenzhen University.
    • Kaiqiao Zhan, Xiaoxiao Xu, Tiantian He, Jun Zhang, and Chunjie Chen use a Kuaishou email domain.
    • Weike Pan, Canwei Huang, and Ziran Deng are affiliated with Shenzhen University.
  • Kuaishou researchers already published two papers this month (HD-Rec 2026-08-11 radar.md, PushDualGen 2026-08-12). This paper is the third.
  • Of these, PushDualGen is the one that states a production deployment, while HD-Rec reports only public benchmark results verified — arXiv 2608.06997.
    • The HD-Rec abstract's experiments cover only "three public cross-domain recommendation benchmarks", and it has no deployment or A/B statement.
  • The three papers share one trait: they all belong to different algorithm families. They address SID cross-domain, push notifications combining SID and CoT, and noise robustness of ensemble ranking, respectively.
    • In effect, this confirms that the company has the resources for several teams and several research lines to publish production SOTA papers at the same time.

What we learnedB. DrEM corrects noise in upstream model predictions on both the label side and the input side

  • The paper addresses a problem specific to the ensemble ranking stage. In the multi-stage pipeline of industrial video recommendation, it assumes that a downstream ensemble ranker uses the predictions of the upstream multi-task ranker both as input features and as the source of proxy preference labels.
    • Here the predicted probabilities that multiple tasks output, such as pctr, pvtr, pcmtr, and pftr, are collectively called pxtr.
  • Because pxtr is the output of an upstream model, it inevitably contains noise. This noise acts in two ways.
    • It flips the proxy preference labels (supervision-side noise).
    • It flows into the feature-side input and shakes the ranking score (feature-side noise).
  • Existing ensemble ranking methods treated pxtr as a reliable signal and ignored the noise. DrEM corrects this noise on both sides at the same time.
    • On the label side, it estimates the probability that the true preference of each pair was flipped (pairwise flip probability, shortened below to flip probability) and introduces a risk-denoising robust loss that corrects the empirical risk with that probability. It proves theoretically that this loss is superior to the basic pairwise loss even when the flip probability estimate has errors (Theorem 1).
    • On the input side, it samples perturbations from the prediction noise distribution of pxtr and trains the output to stay stable under perturbation with a preference-preserving ranking consistency regularizer.
  • The key point is that both corrections are derived from a shared noise model. Because the correction targets of supervision and features are aligned to the same noise source, parameters can be shared to perform synchronized corrections.

What we learnedC. In the production A/B, the gains on sparse behaviors were larger than on dense behaviors

  • The experiment used two groups, with DrEM attached to the production backbones EMER and EASQ respectively; each group was randomly assigned 5.1% of the main traffic at the user level for 7 days verified — HTML version section 5.4 (RQ3).

    "To answer RQ3 and validate real-world performance, we conduct online A/B tests on the industrial short-video platform. We set up two parallel experiment groups to verify the generalization of our DrEM on both representative backbones, applying our DrEM on top of production-grade EMER and EASQ backbone. The experiment runs for 7 days with 5.1% of the main traffic randomly split at the user level via hash-based assignment to each group." — arXiv 2608.12778, section 5.4

The main A/B results are in the following table (section 5.4, Table 2, all metrics p < 0.005) verified.

Metric EMER w/ DrEM EASQ w/ DrEM
Comment +1.388% +0.178%
Follow +1.197% +0.460%
Video View +0.691% +0.117%
Forward +0.683% +0.181%
Like +0.625% +0.048%
Long View +0.401% +0.043%
App Stay Time +0.116% +0.124%
LT7 +0.017% +0.020%
  • Summarizing what the authors observe in the same section, the gain on sparse behaviors is larger than on dense behaviors. The improvements of +1.20% for follow and +1.39% for comment are far larger than +0.69% for view and +0.40% for long view.
  • This is consistent with the theory. The pxtr of sparse tasks (pcmtr, pftr) has high prediction variance, so the flip probability is also high, and the robust correction has correspondingly more room to improve.
  • The heatmap stratified by flip probability in section 5.5 (RQ4) shows the same conclusion. In the low flip-probability range, the improvement for dense tasks (pctr, pvtr) is zero or slightly negative, while in the high range the gain rises sharply to positive values.
  • The authors also explain why EASQ's gain is smaller than EMER's. EASQ already partially mitigates supervision-side noise with its own questionnaire-signal alignment, so there is less room for DrEM's supervision correction to improve.
    • In other words, this can be understood hierarchically: supervision correction yields much larger gains, and on a backbone that already handles that part, only the feature-side correction remains.

Why it matters This paper is the closest to the canon among the three papers Kuaishou published this month. Other services face the same noise problem. X's 26-head weighted sum, Meta's multi-objective ranking, and Netflix's multi-task FM (recommendation foundation model) all have a structure in which upstream pxtr serves as both the input and the label for downstream scorers.

However, the literature does not confirm whether the specific problem DrEM addresses, pxtr noise at the ensemble ranking stage, exists as a separate component at X, Meta, and Netflix, or is mitigated in another way.
