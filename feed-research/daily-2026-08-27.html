    1-1. abuse-enforcement-service/service-lib/src/generic_actions.rs (663줄 신규) — 스코어러가 직접 액션을 요청하는 일반 패스스루

    AES 배경 abuse-enforcement-service/ (AES)는 4세대 첫 공개 때 통째로 드러난 서브레포로, 모델 스코어(BDSM 봇 헤드, LLM slop 라벨, PandaReports 등)를 받아 실제 계정 조치(label / bounce_captcha / bounce_arkose / spam_liveness_check / suspend)로 매핑하는 규칙 엔진이다. 종전의 AES 규칙은 abuse-enforcement-service/service-lib/rules/enforcement_user.yaml과 enforcement_post.yaml에 정적으로 인코딩되어 있었다. 어떤 라벨이 붙으면 어떤 액션을 취하라는 매핑을 CEL 표현식으로 명시하는 방식이며, 예를 들면 다음과 같다.

    - id: anchor_campaign_suspend_cse
  when: '"anchor_campaign_suspend_cse" in score.labels'
  then: { kind: act_suspend_user, perm: true, policy: "Cse" }

    이 방식에는 새 스코어러를 추가할 때마다 AES YAML을 편집해야 한다는 한계가 있었다. 4세대+8이 이 결합을 끊었다. generic_actions.rs(663줄 신규)와 여기에 대응하는 YAML 규칙 두 개(act_requested_actions와 platform_row_without_requested_actions)가 일반 패스스루를 배선했다. 스코어러가 requested_actions 리스트를 직접 붙여서 보내면, AES는 정해진 allowlist를 통과한 것만 실행한다.

    하드코딩된 kind allowlist: 스코어러가 요청할 수 있는 액션 종류는 코드 상수로 고정되어 있다.

    pub const USER_KINDS: &[&str] = &[
    "suspend",
    "label",
    "bounce_captcha",
    "bounce_arkose",
    "spam_liveness_check",
];
pub const POST_KINDS: &[&str] = &["post_label", "suspend_author"];
pub const MAX_REQUESTED_ACTIONS_PER_MESSAGE: usize = 16;

    즉 user entity에는 5종, post entity에는 2종만 요청할 수 있다. 클라이언트가 임의의 kind 문자열을 만들어 낼 수는 없다. 메시지 하나당 요청 가능한 액션은 16개로 제한된다.

    이중 fail-closed 검증은 action_to_spec(entity_type, action, allowlist)에서 이루어진다.

    1. hardcoded_kinds를 통과해야 한다. 통과하지 못하면 "unknown_kind"이고, 다른 엔티티 타입에 속한 kind라면 "entity_type_mismatch"로 구분한다.
    2. 동적 GenericActionAllowlist.kinds에 해당 kind가 들어 있어야 한다. 없으면 "kind_not_allowlisted"다.
    3. suspend나 suspend_author kind라면 allowlist.suspend_policies에 policy가 들어 있어야 한다. 없으면 "policy_not_allowlisted"다.
    4. label이나 post_label kind라면 (a) action.labels가 비어 있지 않아야 하고("no_labels"), (b) 모든 label이 allowlist.labels에 포함되어야 하며("label_not_allowlisted"), (c) ttl_msec >= 0을 만족해야 한다("invalid_ttl").
    5. 중복을 제거한다. 같은 spec이 이미 리스트에 있으면 "duplicate_action"이다.

    거부된 액션은 그냥 버려지지 않고 관측된다. SkippedRequestedAction { kind, head, reason, count } 구조체로 수집되어 outcome.info["requested_actions_skipped"]에 JSON으로 붙고, 별도 메트릭인 GENERIC_ACTION_TOTAL{entity_type, kind, outcome=resolved|skipped, reason}으로도 집계된다. 즉 요청이 왜 통과하지 못했는지가 그대로 로그에 남는다. 스코어러 팀은 자기 요청이 거부된 이유를 바로 확인할 수 있다.

    YAML 규칙 배선은 enforcement_user.yaml에 들어갔다.

    - id: platform_row_without_requested_actions
  when: '"abuse_platform_requested_actions" in score.labels && size(score.requested_actions) == 0'
  then:
    kind: skip
    reason: platform_row_without_requested_actions

- id: act_requested_actions
  when: "size(score.requested_actions) > 0"
  then:
    kind: act_requested_actions

    두 규칙은 짝을 이룬다. 스코어러가 자기 라벨(abuse_platform_requested_actions)로 일반 액션 파이프라인임을 선언해 놓고도 실제 액션 리스트가 비어 있으면 skip하고, 액션이 하나라도 있으면 act_requested_actions decision을 통해 위의 검증 파이프라인으로 라우팅한다. enforcement_post.yaml에는 대칭되는 규칙 하나만 들어갔고, post 쪽에는 platform_row skip이 없다.

    Decision 확장은 abuse-enforcement-service/service-lib/src/lib.rs(+276/−19)에서 이루어졌고, Decision::ActRequestedActions variant가 새로 생겼다. run_enforcement_inner가 이 variant를 만나면 다음과 같이 처리한다.

    let (decision, mut requested_actions_skipped) = match decision {
    Decision::ActRequestedActions => expand_requested_actions_decision(
        facts.entity_type,
        &facts.score,
        &ctx.dynamic_config.generic_action_allowlist(facts.entity_type),
    ),
    Decision::Skip(reason) => (ExpandedDecision::Skip(reason), None),
    Decision::Act(specs) => (ExpandedDecision::Act(specs), None),
};

    allowlist를 통과한 액션이 하나도 없으면 Skip(REQUESTED_ACTIONS_DENIED)가 되고, 하나라도 있으면 Act(specs)가 된다. 즉 요청이 전부 거부되더라도 outcome이 skip으로 명시되기 때문에, 무엇이 요청됐고 왜 거부됐는지가 outcome.info의 JSON에 남는다.

    dynamic_config에서 generic_action_allowlist로 이어지는 경로도 생겼다. growthbook.rs(+126)에 새 메서드가 추가됐다. GrowthBook은 X의 dynamic config이자 feature-flag 시스템으로 보인다 [추정]. 그렇다면 allowlist, 즉 스코어러가 어떤 kind를 요청할 수 있고 어떤 policy와 label을 쓸 수 있는지는 런타임에 A/B로 게이팅할 수 있다. 새 스코어러를 붙일 때 코드를 배포하지 않고도 GrowthBook 콘솔에서 allowlist 항목을 켜고 끌 수 있다.

    이 구조의 첫 클라이언트로 panda_reports_embedding_v10_rough_spam이 함께 유입됐다. enforcement_user.yaml에 규칙이 새로 추가됐다.

    - id: panda_reports_embedding_v10_rough_spam
  when: '"panda_reports_embedding_v10_rough_spam" in score.labels'
  then: { kind: act_suspend_user, perm: false, policy: "PlatformManipulation" }

    이 규칙 자체는 예전 방식 그대로의 정적 매핑이다. 다만 라벨 이름 자체가 새로운 정보를 담고 있다. panda는 X의 내부 spam 검출 시스템 이름으로 보이고 [추정], reports_embedding_v10은 리포트 embedding을 기반으로 하는 검출기의 10번째 버전이며, rough_spam은 확신도는 낮지만 스팸일 가능성이 높다는 판정이다. 조치는 임시(perm: false) suspend에 PlatformManipulation policy를 붙이는 것이다. 즉 이 검출기는 embedding을 기반으로 하고 버전이 v10까지 올라왔다. 계속 재학습되는 파이프라인이라고 볼 수 있다.

    배경 VMRanker는 home-mixer에서 slate reranker 역할을 하는 원격 gRPC 서비스로, Phoenix가 뽑은 후보 점수 위에서 DPP(Determinantal Point Process) 기반 다양성 재정렬(θ=0.65, K=150)을 수행한다. 지금까지 home-mixer/scorers/vm_ranker.rs는 value model 두 개를 지원했다. 하나는 author_diversity로, MPN 폴드백을 기반으로 저자 다양성을 감쇠시키는 값을 home-mixer가 로컬에서 계산해 rank server에 전달했다. 다른 하나는 default로, rank server가 반환한 점수를 그대로 사용했다. 4세대+3(2026-08-18)의 SID 필드 7개 배선이 이 vm_ranker에 붙은 것이다.

    층위별 의미:

    • 아키텍처 이동: 다양성 계산이 home-mixer(client)에서 VMRanker(server)로 옮겨 갔다. 이전에는 home-mixer가 다양성 요구사항을 담은 head weights를 후보마다 만들어 rank server에 전송했는데, 이제는 rank server가 자체 DPP 로직으로 다양성을 처리하고 home-mixer는 반환된 점수만 소비한다.
    • author_diversity에서 dpp로 바뀐 명칭의 실체는 아직 분명하지 않다. dpp가 정말로 기존 재순위 절의 DPP(θ=0.65, K=150)를 가리키는지, 아니면 rank server 안에서만 쓰는 다른 DPP 인스턴스인지는 이 커밋만으로 확정할 수 없다 [추정]. VMRankerValueModelId 파라미터도 함께 정리된 흔적이 home-mixer/params/param.rs에 남아 있다(+10/−29로 순 감소).
    • AuthorColdStart는 사라진 것이 아니라 자리를 옮겼다. home-mixer/scorers/author_cold_start.rs 파일은 여전히 존재하고 +12/−9로 수정됐다. VMRanker의 후처리에서만 빠졌으므로, RankingScorer나 Phoenix 파이프라인 같은 다른 지점에서는 여전히 적용될 가능성이 있다.
    • 삭제된 effective_head_weights의 도착지: 이 메서드가 계산하던 head weights(favorite·reply·retweet·share·dwell·quoted_vqv 등)를 이제 서버가 자체 로직으로 계산하거나, 아니면 head weights라는 개념 자체가 다른 방식으로 대체된 것으로 보인다. VMRanker가 원래의 phoenix 점수를 그대로 소비하고 자체 DPP만 적용한다고 해석하는 편이 자연스럽다 [추정].

    이 단순화는 4세대의 큰 방향, 즉 home-mixer에서 로컬 계산과 캐시를 걷어내고 서빙 산출을 우선 사용하는 흐름의 연장이다. 4세대+5의 UseServedSlateContext 게이트가 slate context 계산을 로컬에서 Phoenix 서빙으로 옮겼던 것과 짝을 이룬다.

    즉 candidate의 quoted 저자와 retweeted 저자의 user_id 리스트를 모아 SocialGraphClient에 이들 중 누가 뷰어를 블록하고 있는지 물어보고, 그 결과를 후보 필드 두 개에 설정한다.

    1-6. Phoenix copy_port tokio::spawn 하드닝 — rate-limit이 병렬 폴링 없이도 in-flight cap 지키게

    **phoenix/crates/serving/xai-recsys-engine/src/copy_port_client.rs (+155)**의 copy_port는 Phoenix 서빙에서 오브젝트 스토리지(S3/xai-o2)로부터 임베딩 테이블과 체크포인트를 다운로드하는 클라이언트다. 이전 코드는 join_all(futures).await로 여러 다운로드를 병렬로 진행했는데, rate limit 배치 안에서 join_all이 futures를 순차적으로 poll하면 실제 in-flight concurrency가 max_concurrent를 넘을 수 있다는 문제가 있었다.

    수정 내용은 다음과 같다.

    // Before:
let batch_results = join_all(batch).await;

// After:
let batch_results = join_all(batch.into_iter().map(tokio::task::spawn))
    .await
    .into_iter()
    .collect::<Result<Vec<_>, _>>()
    .map_err(|e| CopyPortError::Other(format!("copy_port download task join: {e}")))?;

    각 future를 tokio::task::spawn으로 별도 태스크에 감싸면 런타임 스케줄러가 실제로 병렬 실행하고, rate limit 로직(join_rate_limited)이 다음 배치를 issue할 시점을 in-flight 카운트에 근거해 정확히 결정한다. 회귀 테스트도 2개 새로 추가됐다.

    • rate_limit_caps_in_flight_despite_spawn — 6개 다운로드에 concurrency=2 상한 → peak in-flight이 정확히 2
    • rate_limit_paces_between_spawned_batches — 배치 사이의 페이싱이 유지됨

    의미 4세대+7에서 Phoenix 체크포인트 로더 다중 노드 하드닝이 restore path의 OOM을 잡았다면, 이번 변경은 서빙 시점의 병렬 다운로드 스로틀링 정확성을 잡는 하드닝이다. 두 작업은 짝을 이루며, 4세대+6에서 Muon+GB300 학습이 export에 정식 포함된 이후 이어지는 학습·서빙 양쪽 인프라 성숙 사이클의 연장이다. 이런 stability 픽스가 매일 커밋에 붙는다는 사실 자체가, X가 4세대 오픈소스 릴리스를 검증 가능하고 프로덕션에서 신뢰할 수 있는 상태로 유지하는 데 조직 자원을 계속 투입하고 있다는 증거다.

    2. Tlow — WeChat/Tencent 프로덕션 A/B, flow-based item tokenizer가 RQ-VAE 대안으로 등장 (레이더)

    자료 Tlow: Flow-based Item Tokenizer for Recommendation — arXiv 2608.24176, 2026-08-25 v1, 저자 6명 Nian Li, Chonggang Song, Jingtao Ding, Lingling Yi, Yong Li, Qingmin Liao. China's largest social media platform WeChat의 프로덕션 A/B라고 명시되어 있어 소속을 확인했다(HTML 판 abstract에 명시).

    배경 Semantic ID(SID) 라인의 핵심 컴포넌트인 item tokenizer는 각 아이템의 의미 임베딩을 discrete token ID 시퀀스로 변환하는 모듈이다. 사실상의 표준은 RQ-VAE(Residual-Quantized VAE)로, Google의 2023 TIGER 논문 이후 여러 프로덕션 시스템(Netflix Foundation Model, Kuaishou PushDualGen 등)이 채택했다. 하지만 RQ-VAE에는 알려진 문제가 세 가지 있다. (a) codebook collapse가 일어나서 대부분의 code slot이 죽고 소수만 활용된다. (b) quantization 오류가 residual로 축적되어 deep quantization 층에서 오차가 커진다. (c) 불연속성 때문에 유사한 아이템이 완전히 다른 token 시퀀스로 매핑되어 학습이 어렵다.

    Tlow는 이 문제들을 normalizing flow로 접근한다. Flow-based model은 invertible neural network로 임베딩 공간을 학습 가능한 분포로 변환하고 역변환한다. 저자들은 flow 기반 tokenization이 codebook 활용률과 semantic locality 두 축에서 RQ-VAE보다 낫다고 주장한다.

    새로 알게 된 것

    • 프로덕션 A/B [확인]:

      "The retrieval model based on token IDs improves user CTR by 10.32% globally and by 11.64% for new items." — Tlow abstract, 2026-08-25

      즉 글로벌 CTR이 +10.32%, 신규 아이템 CTR이 +11.64% 올랐다. 신규 아이템에서 개선 폭이 더 크다는 것은 콜드스타트에 특히 강하다는 시사다. semantic tokenization 라인의 핵심 이점, 즉 cold item에 대해서도 유의미한 표현을 확보한다는 점이 프로덕션 지표로 확인됐다.

    • 평가 지면 [확인] — WeChat retrieval model이다. 광고인지 유기 콘텐츠인지, 그리고 Look/Video Channels/Moments 가운데 어느 세부 지면인지는 abstract에 공개되지 않았다.

    • 저자 소속 확인 채널 — Tencent 관련 저자 이름(Chonggang Song)이 있고 WeChat이 China's largest social platform으로 abstract에 명시되어 있으므로, Tencent WeChat rec 그룹으로 확정했다.

    정본 반영 radar.md "이번 달 신규"에 ### Tlow (WeChat/Tencent) — flow-based item tokenizer가 RQ-VAE 대안으로 프로덕션 CTR +10.32% 절 추가 (HEGM보다 위, SID 스레드에 링크).

    의미

    • SID/generative retrieval 스레드의 새 축으로, tokenizer 아키텍처 자체가 프로덕션에서 갈리기 시작했다. 지금까지 SID 라인은 대체로 RQ-VAE와 downstream 모델을 조합하는 방식이었다. Tlow는 tokenizer 층을 flow 기반으로 대체해도 프로덕션에서 유효한 지표 개선이 나온다고 밝힌 첫 진술이다. RQ-VAE의 codebook collapse가 실제 서빙에서 문제였다는 방증이며 [추정], Tencent가 이 문제를 겪고 대안을 내놓은 것으로 해석한다.
    • Tencent WeChat이 오랜만에 내놓은 프로덕션 진술이다. WeChat rec은 최근 몇 년 조용한 편이었다. Tlow가 나오면서 유기 콘텐츠 지면의 실제 아키텍처 진술이 재개되는 신호로 보인다. Weixin Video Channels(WeChat의 짧은 비디오 지면)의 rec 스택 논문이 이어질지 관찰할 가치가 있다.
    • 관전 포인트 — (a) code와 상세한 block-wise flow structure가 후속 자료에서 나올지, (b) Kuaishou나 ByteDance, Xiaohongshu 같은 두 번째 회사가 유사한 tokenizer 대안을 진술하면 topics/ 승격 후보가 된다.

    3. TAGR — 익명 대형 live-stream 광고 플랫폼, revenue +16.1% (레이더)

    자료 TAGR: Temporally Adaptive Generative Recommendation for Industrial Live-Streaming Advertising — arXiv 2608.24034, 2026-08-25 v1, 저자 10명 Wencai Ye, Guangyi Liu, Chaoyi Wang, Wenbin Luo, Shengyu Wang 외. 저자 소속과 플랫폼 이름은 abstract에 명시되지 않았다. abstract에서는 "a large-scale e-commerce live-stream advertising platform"이라고만 언급한다.

    배경 라이브 스트리밍 광고는 콘텐츠와 상품, 유저 피드백이 실시간으로 바뀌기 때문에 recommender에 강한 freshness 요구를 부과한다. 지금까지 generative recommender(SID 기반) 라인은 대부분 static 카탈로그를 가정했는데, 라이브는 스트림이 열리고 닫히는 시간 척도가 분 단위라서 static token vocab의 유효 기간이 짧다.

    새로 알게 된 것

    • 프로덕션 A/B 결과 [확인]:
      • live-room entry rate +8.5%
      • shopping-cart click rate +7.4%
      • revenue +16.1% over production baseline
    • 아키텍처 — Temporally Adaptive Generative Recommendation이다. abstract에서는 "designed for rapidly changing live content, promoted products, and user feedback"라고 표현한다. tokenizer 재학습 주기나 online update처럼 구체적인 시간축 adaptation 메커니즘은 abstract에 나오지 않는다. 본문을 확인해야 하지만 이번 배치에서는 넘어갔다.
    • 플랫폼 미공개 — 저자 이름만으로는 확정할 수 없다. 중국 e-commerce live-stream의 대표 후보로는 Kuaishou(Kwai), Alibaba(Taobao Live), Douyin/ByteDance(Douyin E-commerce), Xiaohongshu가 있는데, 저자 이름은 이 가운데 어느 회사와도 직접 매칭되지 않는다 [추정].

    정본 반영 radar.md "이번 달 신규"에 ### TAGR — 익명 대형 e-commerce live-stream 광고 플랫폼, revenue +16.1% 절 추가.

    의미

    • 라이브 스트리밍 랭킹 스레드에 세 번째 회사가 붙었다. 기존의 Twitch(Amazon) Multi-Objective와 Netflix의 라이브 콜드스타트에 이어, TAGR은 광고 지면이자 중국 e-commerce 라이브라는 세 번째 각도를 더한다.
    • generative recommender가 광고와 라이브처럼 빠르게 변하는 도메인에서도 프로덕션 진술을 쌓고 있다. 이전까지는 static short-video나 e-commerce catalog를 기준으로 한 진술이 많았는데, 이번에는 시간축 adaptation이 필요한 도메인에서 나온 진술이다.
    • 플랫폼을 확인하지 못한 것이 가장 큰 약점이다. v2 이후 소속이 공개되거나 저자 이메일 도메인을 확인할 수 있으면 정본 승격을 다시 검토한다.

    검증에서 뒤집힌 것

    없다. 이번 배치의 신규 자료(X 4세대+8, Tlow, TAGR)는 기존 정본을 뒤집지 않는다. VM Ranker 단순화(4세대+8)는 4세대의 아키텍처 정리 흐름과 맞아떨어지고, Following 블록 확장은 정책 방향을 넓힌 것이며, Brazil 계정 갱신은 기존 컴플라이언스 관행을 유지한 것이다. Tlow와 TAGR은 각각의 관찰 스레드(SID/generative retrieval, live-stream)에 새 데이터 포인트로 붙는다.

    레이더

    • 신규 2건:
      • Tlow (Tencent WeChat, arXiv 2608.24176) — flow-based item tokenizer 프로덕션 CTR +10.32%
      • TAGR (익명 e-commerce live-stream, arXiv 2608.24034) — temporally adaptive generative recommendation revenue +16.1%

    arXiv cs.IR triage 30건 가운데 2건이 통과했다. 통과하지 못한 자료는 대체로 offline 벤치마크 위주였고 industry provenance가 없었다. 그중 주목한 미통과 후보는 4건이다. Native Multimodal for CTR(Alibaba로 추정되나 프로덕션 진술 미확인), RecGPT-Mobile-V2(Alibaba 온디바이스 query prediction, 이전 V1을 정본에서 추적하지 않음), WeMM-Embedding(Tencent WeChat multimodal embedding technical report, retrieval 프로덕션 진술 없음), RetrievalFormer(dual-encoder로 search와 rec을 통합한 index, 프로덕션 규모가 명확하지 않음)이다.
