    배경

    4세대(2026-08-13, 47c1bcd)의 초대형 공개가 파라미터와 안전 파이프라인, labeling 서브레포 15개를 통째로 열었고, 바로 다음 날 나온 4세대+1(2026-08-14, c65aa17)이 가중치 해석 규칙과 브라질 선거 필터, Thompson sampling, Phoenix bool 3종, BDSM enforcement note 생성기 부분 공개까지 다섯 방향으로 확장했다 (상세한 내용은 daily/2026-08-16.md에 정리해 두었다). 그 흐름에서 사흘 뒤에 나온 이 커밋(2026-08-17)은 규모가 훨씬 작은 대신 광고와 성인 컨텐츠 판정 계층에 초점을 명확하게 맞추고 있다. X가 4세대의 공개 리듬을 "대형 공개 → 후속 하루짜리 정리 → 며칠 뒤 계층별 정교화"로 잡아가고 있다고 볼 근거가 하나 더 늘었다 [관찰] 2026-08-19.

    특히 세 방향이 canon에 영향을 준다.

    첫째, 광고 브랜드 안전 판정에 V2 로직이 나란히 추가되었다. 4세대 초까지 canon은 home-mixer/models/brand_safety.rs에 있는 compute_verdict가 MEDIUM_RISK_LABELS(14개)와 LOW_RISK_LABELS(3개)를 순서대로 검사해서 광고를 붙일지 판단한다고 반영해 왔다. 오늘 커밋은 그 함수를 지우지 않은 채 옆에 compute_verdict_v2를 새로 만들고, 라벨 세트를 _V2 버전으로 확장했으며, 특정 V1 라벨을 강제로 걸러내는 strip_v1_grok_written 헬퍼를 도입했다. 이것은 라벨 스키마 마이그레이션을 실제 프로덕션에서 어떻게 다루는지 보여주는 구체적인 사례이고, canon 주의 목록에 있는 "죽은 파일" 판별법과도 이어진다. V1과 V2가 둘 다 살아 있고, worst_verdict가 두 결과를 결합하는지 여부에 따라 광고 인접성 판정이 달라진다.

    둘째, 성인 컨텐츠 판정에 판정 불일치를 대비하는 심판(judge) 계층이 추가되었다. 4세대에서 처음 공개된 grox의 안전 파이프라인은 TaskSafetyPtosSafemodelSexNudity(자체 비전 모델을 사용하는 sex/nudity 판정)와 PtOS(정책을 기준으로 삼는 위반 카테고리 판정)를 병렬로 실행하고, 두 결과가 다를 때는 로그만 남겼다. 오늘 커밋은 이 로직을 두 파일로 분리했다. safemodel은 판정만 담당하고(_compare_outcome을 제거했다), 새로 만든 파일 task_safety_ptos_adult_content_cross_validation.py가 safemodel과 PtOS의 판정이 서로 어긋날 때 Grok 4.5 심판을 호출해서 다시 판단을 받는다. 심판이 "hard가 아니다"라고 답하면 최종 결정은 AdultContentSexualSoft로 강등되고, safemodel이 남긴 positive 표시도 지워진다. 즉 판정 계층이 (a) safemodel, (b) PtOS, (c) Grok 4.5 심판이라는 세 층으로 확장되었다.

    셋째, Phoenix retrieval의 인덱싱 게이트가 사실상 제거되었다. phoenix-rankall-strato에 있는 build1FavIndex는 이름 그대로 "1개 이상 favorite을 받은 포스트를 index에 넣는" 함수였고, buildMMEmbMetadataDump(멀티모달 임베딩 메타데이터를 Kafka로 덤프하는 함수)도 같은 favoriteCount >= 1 게이트를 통과해야 실행되었다. 오늘 커밋은 두 게이트를 모두 제거했다. 그래서 이제 모든 후보가 "1fav" 인덱스와 멀티모달 임베딩 덤프로 흘러들어간다. 다만 "1fav"라는 이름은 그대로 남았고, fav가 0인 상태로 도달한 경우는 1fav_uec_count_race라는 새 카운터로 계측만 한다. 이 변경은 canon이 3세대부터 4세대까지 "인덱스는 인기도 신호를 담는다"고 반영해온 이해와 정면으로 어긋난다. retrieval 후보 풀 자체가 사실상 인덱싱된 포스트 전체 집합으로 커진다는 뜻이다.

    핵심 로직인 strip_v1_grok_written은 다음과 같다 [확인]:

    fn strip_v1_grok_written(labels: &HashMap<SafetyLabelType, SafetyLabel>)
    -> Cow<'_, HashMap<SafetyLabelType, SafetyLabel>>
{
    const V1_DUAL_WRITTEN: &[SafetyLabelType] = &[
        SafetyLabelType::NSFA_HIGH_PRECISION,
        SafetyLabelType::NSFA_LIMITED_INVENTORY,
    ];
    const PROMPT_OWNED_RULES: &[i64] = &[1400, 1410, 1420, 1500, 1510, 1610, 1700];
    let is_v1_grox_written = |label_type: &SafetyLabelType, label: &SafetyLabel| {
        V1_DUAL_WRITTEN.contains(label_type)
            && botmaker_rule_id_from(label)
                .is_some_and(|rule_id| PROMPT_OWNED_RULES.contains(&rule_id))
    };
    if !labels.iter().any(|(t, l)| is_v1_grox_written(t, l)) {
        return Cow::Borrowed(labels);
    }
    Cow::Owned(
        labels.iter()
            .filter(|&(t, l)| !is_v1_grox_written(t, l))
            .map(|(t, l)| (*t, l.clone()))
            .collect(),
    )
}

    즉 V2로 판정할 때 (a) 라벨이 NSFA_HIGH_PRECISION이거나 NSFA_LIMITED_INVENTORY이고 (b) 그 라벨의 botmaker rule id가 PROMPT_OWNED_RULES = [1400, 1410, 1420, 1500, 1510, 1610, 1700]의 7개 가운데 하나이면, V1 프롬프트가 dual-write한 라벨로 판단해서 입력 라벨 집합에서 제거한 다음 나머지 라벨만으로 판정한다. 이 처리는 V1 프롬프트가 만든 이중 기록(dual write)을 V2 로직이 무시하고 V2 라벨만으로 판단하게 만드는 마이그레이션 장치에 해당한다.

    compute_verdict_v2의 판정 순서는 다음과 같다 [확인]:

    pub(crate) fn compute_verdict_v2(labels: ..., tweet_id: u64) -> BrandSafetyVerdict {
    let labels = strip_v1_grok_written(labels);
    if MEDIUM_RISK_LABELS_V2.iter().any(|l| labels.contains_key(l)) {
        return BrandSafetyVerdict::MediumRisk;
    }
    let scored_by_grok = labels.contains_key(&SafetyLabelType::GROK_SFA_V2)
        || labels.contains_key(&SafetyLabelType::GROK_NSFA_LIMITED_V2);
    if !scored_by_grok {
        return BrandSafetyVerdict::MediumRisk;
    }
    if tweet_id >= PTOS_CUTOFF_TWEET_ID && !labels.contains_key(&SafetyLabelType::PTOS_REVIEWED) {
        return BrandSafetyVerdict::MediumRisk;
    }
    if LOW_RISK_LABELS_V2.iter().any(|l| labels.contains_key(l)) {
        return BrandSafetyVerdict::LowRisk;
    }
    BrandSafetyVerdict::Safe
}

    판정 순서 자체는 V1과 동일하다 (medium 캐스케이드 → Grok 채점 여부 → PTOS 심사 → low → 그 외에는 safe). 달라진 점은 두 가지다. (a) 참조하는 라벨 이름이 GROK_SFA에서 GROK_SFA_V2로, GROK_NSFA_LIMITED에서 GROK_NSFA_LIMITED_V2로 바뀌었다. (b) V1의 이중 기록을 제거하는 전처리가 앞에 들어갔다.

    의미 (라벨 스키마 마이그레이션의 관찰 가능성)

    canon은 3세대부터 4세대까지 광고 브랜드 안전을 "손으로 짠 규칙 캐스케이드"로 반영해 왔는데, 오늘 확인한 내용은 Grok의 안전 라벨 자체가 버전으로 관리되고 있고, 그 마이그레이션이 코드 안에서 dual-write를 감지하는 로직으로 구현되어 있다는 것이다. 이 내용은 canon 주의 목록에 있는 "죽은 파일" 판별법과도 이어진다. V1과 V2가 둘 다 export되기 때문에, 어느 쪽이 실제로 호출되는지는 상위 하이드레이터(ads_brand_safety_vf_hydrator.rs)에서 확인해야 한다. [확인] 오늘 커밋은 그 하이드레이터도 함께 수정했는데(+13/−7), 상위 호출 경로가 V1에서 V2로 전환되는 중이라는 신호로 볼 수 있다.

    특히 PROMPT_OWNED_RULES = [1400, 1410, 1420, 1500, 1510, 1610, 1700]의 rule id 7개는 이름부터 botmaker 프롬프트가 소유한다고 표시되어 있지만, 4세대에서 공개된 botmaker-rules/의 어느 규칙과 정확히 대응하는지는 공개되지 않았다. rule id를 규칙 파일에 연결하는 매핑 문서가 없기 때문이다. 이 매핑을 canon의 심층 분석 필요 목록에 추가한다.

    새로 추가된 파일 task_safety_ptos_adult_content_cross_validation.py(162줄) [확인] — grox/flows/ptos/task_safety_ptos_adult_content_cross_validation.py:

    핵심 흐름은 다음 4단계로 이루어진다.

    1. 판정 비교 — 새 enum CompareOutcome이 BOTH_POSITIVE·BOTH_NEGATIVE·SAFEMODEL_ONLY_POSITIVE·PTOS_ONLY_POSITIVE 4가지를 구분한다. is_disagreement는 SAFEMODEL_ONLY이거나 PTOS_ONLY일 때 true가 된다. 이 로직은 4세대에서 safemodel_sex_nudity.py 안에 있었는데, 오늘 커밋이 그것을 떼어내 새 파일로 옮겼다.
    2. 게이트 — (a) is_deluxe = ctx.payload.task_type == SAFETY_PTOS_DELUXE이므로 deluxe 플로우에서만 동작하고, 일반 플로우는 예전처럼 로그만 남긴다. (b) 이미 NSFW로 플래그된 포스트이면 건너뛰는데, _post_is_already_flagged_nsfw가 StratoSafetyPostAnnotationsResultDirectMh를 조회해서 확인한다.

    의미 (판정 계층의 확장 방향)

    canon은 지금까지 "판정은 단일 (safemodel 또는 PtOS 또는 Grok) → visibility rules → 필터/광고 인접성" 구조로 반영해 왔는데, 오늘 확인한 내용은 판정 자체를 여러 모델의 앙상블로 재구성하는 방향을 보여준다. 세 층이 서로 다른 모델(safemodel은 자체 비전 모델, PtOS는 정책 판정 모델, Grok 4.5는 LLM 심판)로 구성되고, 판정이 어긋나는 상황을 이용해서 최종 판정을 자동으로 조정한다는 점이 특징이며, 4세대의 "labeling 파이프라인 완전 공개"와 방향이 같다. 앞으로 지켜볼 점은 두 가지다. 이 심판 계층이 다른 카테고리(폭력·혐오·스팸)로도 확장되는지, 그리고 Grok 4.5를 사용하는 비용(추론 코스트)을 어느 정도까지 감당할 수 있는지를 확인해야 한다.

    특히 판정이 강등되는 방향(hard → soft)만 있고 격상되는 방향은 없다는 점도 중요한 관찰이다. 즉 이 심판 계층은 과도한 게이팅을 완화하는 방향으로만 작동하도록 설계되었다. 원래 판정이 놓친 hard 케이스를 심판이 잡아내서 격상하는 로직은 이 커밋에 들어 있지 않다. 이 설계는 성인 컨텐츠 게이팅의 정책 방향이 false positive를 줄이는 쪽이지 false negative를 줄이는 쪽이 아니라는 사실을 코드에서 확인할 수 있게 해 준다.

    2. arXiv triage — SDF (Google Discover가 2년 동안 프로덕션에서 운영한 staleness 필터)

    자료 Decomposing Staleness in Recommender Systems: A Dual-Filter Framework for Supersession and Decay — arXiv:2608.15780 — 2026-08-16 제출, 논문, 저자 6명 전원이 Google LLC 소속이다 (HTML 판에서 저자 affiliation 표기를 확인했다: 이메일 도메인이 모두 @google.com이다). CIKM Applied Research Track 2026에 accepted되었다 (DOI 10.1145/3799682.3840082).

    배경

    Google Discover는 Android 홈스크린과 Google 앱에서 제공되는 개인화 피드 지면이며, DAU는 수억 명, MAU는 수십억 명 규모이다 [확인] (논문 abstract). canon은 지금까지 Google Discover를 추적 서비스로 등록하지 않았는데, Google이 Discover의 알고리즘과 랭킹, retrieval 계층을 통째로 공개한 적이 없었기 때문이다. 이 논문은 그 지면의 staleness 필터만 다루므로 전면적인 아키텍처 공개가 아니라 단일 컴포넌트 공개에 그치지만, 프로덕션에 2년 동안 배포했고 유저 피드백 지표가 54.9% 개선되었다는 실제 A/B 결과 진술이 있어서 레이더 수용 기준(플랫폼 기업 저자, 프로덕션 배포, 대규모 스케일)을 충족한다.

    이 논문이 정의한 문제는 콘텐츠 피드에서 "이 후보가 낡았다"고 판정하는 서로 다른 두 메커니즘을 분리하고, 각각을 독립된 모델로 예측하는 것이다.

    • Supersession (초월/대체) — 새 아이템이 도착해서 이전 아이템의 정보 가치가 무효화되는 경우이다. 예를 들어 스포츠 선수의 팀 이적 소식이 발표되면 그 이전의 이적 협상 기사들이 자동으로 낡는다. 판정 근거는 시간 자체가 아니라 후속 아이템이 존재하는지 여부이다.
    • Relevance decay (관련성 감쇠) — 후속 아이템이 없어도 아이템 자체의 정보 가치가 시간에 따라 자연히 줄어드는 경우이다. 예를 들어 "오늘 밤 유성우" 안내는 그날 저녁에는 유용하지만 다음날부터는 쓸모가 없다. 판정 근거는 시간에 따른 곡선이다.

    기존의 관행(age cutoff, engagement heuristic)은 이 두 메커니즘을 구분하지 못한다. 그래서 (a) age cutoff는 관련성 감쇠를 크게 과대평가하거나 과소평가하고, (b) engagement heuristic은 lagging signal이기 때문에 낡은 컨텐츠가 이미 노출된 뒤에야 반응한다.

    새로 알게 된 것 — 아키텍처와 프로덕션 결과

    SDF를 구성하는 두 필터는 다음과 같다 [확인] — arXiv 2608.15780v1, 3절 Methodology:

    1. Relational Staleness Filter (supersession) — pairwise classification framework를 사용한다. 후보 아이템 d_t와 그 뒤에 도착한 topic-related 아이템 d'의 쌍을 놓고, 학습된 함수 f(d_t, d')가 "d'가 d_t를 낡게 만드는가"를 이진으로 판정한다. 이 판정 결과들의 disjunction (∃ d' > t: f(d_t, d') = 1)이 supersession indicator가 된다. 훈련 데이터는 규모 때문에 수동 어노테이션이 불가능하므로 LLM 파이프라인으로 합성해서 만들고, 지식 증류(knowledge distillation)를 거친 학생 모델을 서빙에 배포한다.
    2. Predicted Traffic Ratio (PTR) Filter (relevance decay) — 아이템의 멀티모달 콘텐츠(텍스트·이미지·비디오)를 입력으로 받아서 미래의 여러 horizon에서 traffic ratio(정규화된 방문 트래픽)를 예측하는 multi-horizon 회귀 모델이다. 학습 라벨로는 아이템의 lifetime visit traffic, 즉 수명 전체에 걸친 방문량을 사용한다. 서빙 시점의 traffic ratio가 임계값보다 낮으면 decay indicator가 1이 된다.
    3. Composition — 두 필터를 disjunction(OR)으로 결합해서 upstream(ranking 이전의 후보 프루닝 단계)에 배치한다. 즉 supersession과 decay 가운데 하나라도 판정되면 후보에서 제거한다. ranking으로 넘어가는 후보 수가 줄어들기 때문에 downstream serving cost도 함께 감소한다.

    A/B 결과 [확인] — 4.2절 Online A/B Testing:

    • 2년 동안 프로덕션에 배포한(initial → 확장 → 안정화) 결과 user-filed staleness reports가 54.9% 감소했다 (in-product user feedback 기준이며, pre-deployment baseline과 비교한 값이다).
      • supersession filter 단독 기여: 64.0% 감소
      • decay filter 단독 기여: 34.4% 감소
    • engagement neutral 제약 아래에서 튜닝했다. "trivially aggressive cuts would reduce staleness further but shrink candidate set and degrade user engagement, which we explicitly rule out." 즉 무리하게 공격적으로 잘라내면 staleness 지표는 더 좋아지지만 engagement를 떨어뜨리기 때문에 그런 방식은 배제했다는 뜻이다.
    • 각 필터가 개별적으로도 statistically significant negative "engagement lift"를 낸다는 진술이 있다. 즉 후보를 프루닝했는데도 engagement가 개선되었다는 뜻인데, 구체적인 % 수치는 abstract에 나와 있지 않다.
    • online staleness는 A/B arm의 통제군과 처리군에서 매주 샘플링해서 4주 연속으로 관찰했다 (view delta 크기로 가중치를 준다).

    의미 (canon 관점)

    이 논문은 canon의 세 방향에 영향을 줄 가능성이 있다.

    1. X의 stale post 처리와 비교하는 축. 4세대+1에서 관찰한 X의 IS_STALE_POST14D bool feature(daily/2026-08-16.md)는 "14일이 지나면 engagement count를 0으로 stamp하고 bool을 셋한다"는 규칙 기반 처리다. 반면 SDF는 (a) supersession을 학습 모델로 예측하고 (b) decay를 lifetime traffic 회귀로 예측하는, 완전히 학습에 기반한 접근이다. 두 접근은 canon의 관점에서 staleness에 대한 서로 다른 두 정의를 반영한다. X는 노출 감소가 count zero로 이어지는 자기강화 루프를 완화하려고 랭커에게 명시적인 라벨을 주는 쪽이고, Google Discover는 candidate pool에서 아예 제거하는 쪽, 즉 retrieval 이전에 프루닝하는 쪽이다. 두 처리가 놓인 위치가 근본적으로 다르다.
    2. 피드 지면의 staleness를 topic으로 승격할 후보. 현재 canon의 topic 목록에는 staleness가 없다. Netflix Foundation Model이나 Meta ConnectionMind가 stale item을 어떻게 처리하는지는 아직 확인하지 못했다. 두 번째 회사에서 비슷한 진술이 나오면 topics/에 절을 새로 만드는 것을 검토한다.
    3. Google Discover를 추적 서비스로 등록할 것인가? 지금은 등록하지 않는다. 이 논문은 단일 컴포넌트인 staleness 필터만 공개했고, retrieval과 ranking, 다양성을 비롯한 나머지 알고리즘 스택은 여전히 공개되지 않았다. 그 상태에서 정본 파일을 만드는 것은 canon의 "서비스 정본은 압축된 결론"이라는 원칙과 맞지 않는다. 레이더에 올려 두었다가 두 번째 컴포넌트가 공개되면 다시 검토한다.
