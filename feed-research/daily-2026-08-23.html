      다만 광고 매출 예측 헤드를 세분화한다는 새 축이 추가됐다는 점이 4세대~+5와 다르다. 새로 나오는 개념을 몇 가지 정리하면 다음과 같다.

      • MACT (Mobile App Conversion Tracking) — 모바일 앱 광고에서 앱 내 이벤트(인앱 구매·튜토리얼 완료·회원 가입 등)를 광고 노출·클릭에 귀속시키는 계측 프레임워크다. 광고주가 SDK로 앱 내 이벤트를 로그하면 X 광고 시스템이 어떤 노출·클릭이 그 이벤트를 유도했는지 대응시킨다. 기존 X 랭커 proto에는 ADS_ATTRIBUTED_MACT_CLICK_INSTALL 하나만 있었는데(앱 설치가 클릭에 귀속), 이번에 인앱 이벤트 6개에 click·view 각 2종을 곱한 12개로 늘어났다.
      • View-through conversion — 사용자가 광고를 봤지만 클릭하지는 않고, 이후 다른 경로로 컨버전(구매·가입 등)에 이른 경우를 말한다. 클릭 기반 귀속(click-through)과 대비되고, 노출만으로도 광고 효과가 있었다고 인정하는 계측 방식이다. 이번에 X 랭커가 view-through 계열 8개 액션(purchase·add_to_cart·checkout_initiated·sign_up·site_visit·session·landing_page_view·upper_funnel)을 신설했다.
      • Delayed feedback — 광고 conversion은 노출·클릭 시점과 실제 컨버전(예: 회원 가입, 인앱 구매) 시점이 몇 시간에서 며칠까지 벌어진다. 학습 시점에 도착한 라벨이 "아직 안 일어남"인지 "안 일어날 것"인지 구분하기 어려워 손실이 왜곡된다. 랭커 문헌에서는 delayed conversion prediction이 별도의 연구 분야로 자리 잡았다(Chapelle 2014 이후). 이번 커밋에서 X는 각 학습 샘플에 is_delayed_feedback 컬럼을 추가하고, 광고 conversion 헤드는 delayed 샘플만, engagement 헤드는 fresh 샘플만 학습하도록 loss mask를 나눴다.
      • Muon optimizer — Newton-Schulz orthogonalization으로 gradient momentum matrix를 근사 직교화하는 optimizer다. Keller Jordan 2024 원문과 Moonshot Kimi K2 계열의 LLM 학습을 거치며 확산됐다. 4세대+4(aad7179)에서 X Phoenix 랭커의 dense-parameter 기본 optimizer로 도입됐지만, TRAINING.md는 export 파이썬 코드가 여전히 AdamW라고 명시하고 있었다. 이번 커밋에서 문서와 config, reference 학습 스크립트가 flagship과 nano가 Muon으로 학습된다고 명시하는 방향으로 다시 쓰이면서 export와 프로덕션 사이의 간극이 좁혀졌다.
      • NVIDIA GB300 (Grace Blackwell 300) — NVIDIA의 2025~2026년 datacenter GPU이고 Blackwell 세대에 속한다(B200 후속). 각 GB300 노드가 대용량 HBM3e과 CUTLASS/CUTe DSL 기반 attention 커널을 지원한다. X가 처음으로 하드웨어 전용 config(batch size, expert parallelism, remat policy, attention impl)를 코드에 명시적으로 드러냈다.
      • xai-o2 object storage — xAI 내부 스토리지 시스템으로 추정되는 S3 호환 오브젝트 스토리지다. 이번 커밋에서 클라이언트 crate 인터페이스는 공개됐지만 실제 구현은 오픈소스 빌드에서 빠졌다. 프로덕션의 checkpoint와 데이터 저장이 xai-o2로 이어진다고 볼 만한 신호다 [추정]. 오픈소스 빌드에서는 표준 object_store crate로 대체해야 한다.

      loss mask 분기 [확인] — phoenix/xrex/models/recsys_model.py loss() 함수:

      if self.config.split_head_training_by_source and delayed_mask is not None:
    conv_head_split_mask = (
        jnp.zeros(num_actions).at[jnp.array(SOURCE_SPLIT_CONVERSION_HEAD_INDICES)].set(1.0)
    )
    eng_head_mask = 1.0 - conv_head_split_mask
    is_delayed = delayed_mask[:, :, None]
    loss_mask = loss_mask * (1 - is_delayed * eng_head_mask)      # delayed 샘플에서는 engagement head 손실 0
    loss_mask = loss_mask * (1 - (1 - is_delayed) * conv_head_split_mask)  # fresh 샘플에서는 conversion head 손실 0

      즉 각 학습 샘플이 fresh(원본 impression)와 delayed(conversion 도착 후 재관측) 두 상태 중 하나이고:

      • fresh 샘플: engagement 헤드(favorite·reply·click 등)만 학습하고, conversion 헤드는 mask=0으로 둔다
      • delayed 샘플: conversion 헤드(위 20개 신설 + 기존 click-conditioned 액션)만 학습하고, engagement 헤드는 mask=0으로 둔다

      메트릭 슬라이스를 신설했다. fresh(delayed=0), delayed_clicked(delayed=1 & clicked=1), delayed_non_clicked(delayed=1 & clicked=0) 세 슬라이스를 관측할 수 있도록 build_metric_masks에 분기를 추가했다. condition_conversion_on_click이 필수 전제조건(assert)이므로, delayed 샘플이라도 "click 있었나"라는 조건 아래에서 conversion을 예측하는 conditional 학습을 그대로 유지한다.

      의미 delayed feedback modeling은 광고 conversion 예측의 표준 문제인데, X는 이제 (a) 별도 kafka 이벤트로 delayed 재관측분을 흘려보내고 (b) 랭커 학습에서 손실을 분기해 fresh는 engagement로, delayed는 conversion으로 갈라서 학습한다. 이는 duplicate labeling 문제(같은 impression을 fresh와 delayed 두 이벤트로 두 번 로그하는 문제)에 대한 손실 정합성 장치이자, conversion 예측 헤드가 20개로 늘어나는 가운데 각 헤드의 학습 signal이 충분히 갱신되도록 유지하는 인프라 뒷받침이기도 하다.

      **mact_in_app_loss_weight**는 MACT 액션 12개에만 곱하는 loss weight이고 기본값은 1.0이다. config 파라미터로 노출돼 있어서 광고 conversion 헤드 12개의 학습 강도를 조정할 수 있다. stats["mact-in-app-loss-weight"]로 관측한다.

      **train_view_through_heads**는 view-through 헤드 8개를 학습할지 결정하는 게이트다. False로 두면 view-through head의 손실 mask를 0으로 만들어 학습하지 않는다. 즉 view-through 예측은 config에서 opt-in으로 켜야 한다.

      **conversion_keep_mask / conversionKeepMask**는 후보마다 conversion 학습에서 제외할지를 표시하는 마스크다. from_record_batch에서 kafka의 conversionKeepMask 컬럼을 읽고, null인 행은 True로 대체한다(=keep). loss()에서 이 마스크를 target_padding_mask와 AND 연산해 conversion 학습 대상에서 제외한다. 주의할 점: sequence packing에서는 all(True)만 허용하고, 아직 배선되지 않은 경우는 assert로 명시적으로 실패시킨다.

      CLI 도움말이 문제를 명시하고 있다:

      glibc malloc_trim(0) on the coordinator thread after each applied hotswap; returns the cycle's freed pages (glibc slots otherwise ratchet ~196 MiB/cycle). No-op under jemalloc.

      의미 Phoenix 서빙에서 embedding table hotswap(주기적으로 새 임베딩 checkpoint를 프로세스 안에서 교체하는 작업)이 glibc 메모리 할당자 아래에서 사이클마다 약 196MiB씩 RSS를 누수해 왔다는 사실이 처음으로 문서에 드러났다. libc의 malloc_trim(0)을 호출해 해제된 페이지를 OS에 반환한다. 다른 할당자인 jemalloc에서는 의미가 없다. 프로덕션 서빙을 다듬는 작은 패치지만, hotswap이 프로덕션에서 오래 돌아가는 인프라라서 이 패치가 필요할 만큼 부담이 쌓였다는 점을 함께 관찰할 수 있다.
