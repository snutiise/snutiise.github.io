    배경

    이 저장소의 services/x.md는 지난 3개월 동안 "공개 소스 3세대"를 정본으로 유지해 왔다. 세 세대는 2023 Scala 초판, 2025 Scala 리프레시(c54bec0, tweet-mixer 신설), 2026 Rust 재작성(aaa167b·e414c17·0bfc279, 총 216파일)이다. 그리고 정본에서 가장 크게 비어 있던 절이 두 개 있었다.

    첫째는 가중치다. 목적함수의 형태가 가중합이라는 점은 확인됐지만, 실제 값은 세 세대 어디에도 없었다. 2026 Rust에서는 crate::params 모듈 자체가 레포에서 빠져 있어서, FavoriteWeight 같은 심볼이 호출부에만 등장하고 정의는 찾을 수 없었다. 널리 인용되는 "reply 13.5 / good_profile_click 12.0 / report −369" 표는 2023-04-05 스냅샷 하나뿐이고, 그마저도 저자가 직접 "프로덕션과 작은 차이 있을 수 있다"고 단서를 붙여 놓은 문서였다.

    둘째는 안전성 계열, 곧 visibility-filtering과 labeling 파이프라인이다. home-mixer 코드에는 VFFilter·AncillaryVFFilter가 fail-closed로 걸려 있었지만, 그 필터가 참고하는 라벨을 누가 언제 어떻게 붙이는가는 완전한 블랙박스였다. grox/ 서브레포는 주석 파이프라인 골격만 부분 공개된 상태였고, 그 밖의 계정 레벨 판단, PageRank, 인위적 행동 탐지, NSFW 미디어 분류, 규칙 엔진, 집행 서비스는 언급조차 없었다.

    이번 릴리스가 두 절을 통째로 뒤집었다. 새 README는 **"Adds key configuration parameters (including weights used to blend predicted action values into a score for a post)"**로 시작하고, 그에 맞춰 home-mixer/params/param.rs 1084줄이 새로 추가됐다. 이어지는 "Adds code for systems that impact whether a post is filtered from the For You feed" 항목과 함께 서브시스템 15개 이상이 신설됐다. Phoenix에는 학습 코드와 synthetic 데이터 생성기, QUICKSTART까지 추가되어 end-to-end로 실행할 수 있게 됐고, 새 SimClusters 서브레포가 home-mixer의 OON retrieval 소스로 연결됐다.

    새 README가 커밋 메시지에서 스스로 평가하듯이, 이 릴리스의 성격은 이제 "로직의 형태를 보여주는 것"에서 "값과 규칙을 검증 가능한 형태로 제시하는 것"으로 넘어왔다. 여기에 짝을 이루어 x.com/i/under_the_hood라는 계정 단위 라벨 투명성 도구가 파일럿으로 공개됐다. 새 README의 주장에 따르면, 유저는 자기 계정과 포스트에 붙은 visibility 라벨을 조회할 수 있고, 그 라벨을 이 레포의 코드와 대조해 왜 그런 취급을 받았는지 확인할 수 있도록 설계됐다.

    새로 알게 된 것: 가중치 밖 상수

    정본이 오랫동안 "네 값 전부 비공개"라고 기록해 왔던 OON 배수와 다양성, VMRanker 상수가 전부 공개됐다.

    • OonWeightFactor = 0.75 [확인]: OON 포스트에 곱하는 감쇠 계수이며, 2023-04-05 스냅샷의 out_of_network_scale_factor 0.75와 일치한다
    • TopicOonWeightFactor = 0.5 [확인]: 토픽 요청일 때에는 더 엄격하게 적용한다
    • NewUserAgeThresholdSecs = 0 [확인]: 신규 유저 라우팅 임계가 0초라는 것은 사실상 이 코드 경로가 비활성 상태로 미러링돼 있다는 뜻이다 [추정]
    • AuthorDiversityDecay = 0.5, AuthorDiversityFloor = 0.25, EnableAuthorDiversity = true [확인]: 같은 작성자의 2번째 포스트에는 (1−0.25)·0.5¹+0.25=0.625 배가 곱해지고, k번째 포스트에는 (1−0.25)·0.5ᵏ+0.25 배가 곱해진다
    • VMRankerDppTheta = 0.65, VMRankerDppMaxSelectedRank = 150, EnableVMRanker = true, VMRankerValueModelId = "dpp", VMRankerClusterId = "Experiment3", VMRankerEnableFallback = false [확인]: 정본이 남긴 열린 질문 "VMRanker/DPP가 켜져 있는가" 에 대한 직접적인 답이다. 켜져 있고, DPP를 사용하며, 폴백은 없다. 따라서 실패했을 때 fail-open으로 조용히 건너뛴다는 canon의 관찰이 그대로 유효하다
    • PhoenixMaxResults = 1000, ThunderMaxResults = 1200, TweetMixerMaxResults = 800, EnableTweetMixerSource = false, EnableSimclustersSource = true, EnablePhoenixSource = true [확인]: 레거시 tweet-mixer는 기본 off로 미러링됐고, SimClusters가 그 자리를 대체한다
    • ShadowTrafficDefaultPercent = 0.3 [확인]: 새 Phoenix 클러스터에는 shadow 트래픽 30%가 기본으로 흐른다
    • ColdStartImpressionThreshold = 1000 [확인]: canon이 "신규 아이템에 아무 장치 없다"고 기록했던 지점인데, 실제로는 임프레션 임계로 정의되어 있다. 임프레션이 1000회 미만이면 "새 작성자·포스트"로 분류하고, 아래의 PostUnexploredWeight로 부스트한다

    새로 알게 된 것: 파이프라인 구조

    정본은 오랫동안 "SimClusters, TwHIN, UTEG/GraphJet, FRS, Earlybird, Lists, Communities — 이 이름들은 home-mixer/ 어디에도 안 나온다"고 기록해 왔다. 이 가운데 SimClusters가 뒤집혔다. 새 README의 서술은 다음과 같다.

    즉 후보 소스가 Thunder(인네트워크) + Phoenix retrieval + SimClusters + (기본 off로 설정된 레거시 tweet-mixer) 로 재편됐다. SimClusters 서브레포가 새로 생겼고, simclusters/의 코어 알고리즘(SVD 기반 sparse 저차원 임베딩, 2020 KDD)이 여기 들어와 있다는 뜻이다. 세부 내용은 simclusters/ 전체를 심층 분석해야 확인할 수 있다.

    새로 추가된 필터는 3개이고, 여기에 정본이 놓쳤던 필터를 하나 더 적는다.

    • OONRetweetReplyFilter: 팔로우하지 않는 계정의 리트윗과 답글, 그리고 부모 포스트가 없는 답글을 걸러낸다 (기존 RetweetDeduplicationFilter와는 별개다)

    • NewUserMinEngagementFilter: 신규 유저에게 노출되는 OON 포스트 가운데 참여 임계에 미달하는 것을 제거한다. 관련 param은 NewUserMinEngagementThreshold, NewUserMinEngagementFilterMetric, NewUserMinEngagementFilterUseRatio, NewUserMinEngagementFilterMaxAccountAgeSecs, NewUserMinEngagementFilterMaxResurrectionAgeSecs이다

    정본이 canon 주의 목록 #2에서 이미 관찰했던 "인네트워크와 OON에 다른 안전 레벨"의 실체가 여기에 있다. 팔로잉 유저에게는 28개 규칙만 적용되고, OON 추천에는 54개 규칙이 적용된다. 평가는 첫 번째 드롭 판정에서 종료되며(short-circuit), OON 전용 규칙군은 캐치업 드롭만 내릴 수 있고 인터스티셜이나 알로우 판정은 없다(canon 주의 목록 #2와 일치한다).

    canon 주의 목록 #1(fail-closed)의 실체를 확인했다. visibility-filtering/rules/registry.rs의 정책 반환값은 Verdict 구조체인데, README는 interstitial을 UI 처리로 넘기고 drop이 실제 필터링에 해당한다고 명시한다. [확인] README.md #labeling-path:

    "interstitial ──► the post stays in the feed; nothing in this repository draws the interstitial"

    새로 알게 된 것: labeling 파이프라인

    새 README는 이 과정을 4단계 "Labeling Path"로 정리한다. 단계는 Content Understanding → Labeling Rules → Storage → Visibility Filtering 순서다. 각 서브시스템의 역할이 처음으로 공식 문서화됐다 [확인].

    • grox/: nearline 콘텐츠 분류기다. 정본에는 이미 부분적으로 반영돼 있다
    • media-model-proxy/: 이미지·비디오 모델(NSFW, 폭력/고어, 혐오 심볼, 주제 분류, 알려진 미디어 매칭)을 서빙하는 프록시다
    • clip/: CLIP 이미지·텍스트 임베딩 모델을 학습한다 (미디어 분류기의 입력이 된다)
    • adult-content/: 성인 미디어 분류기를 학습하고 캘리브레이션한다
    • pnsfwmedia/: CLIP 임베딩과 계정 스코어를 결합한 성인 미디어 판별기다
    • agatha/: 오프라인 배치다. 다른 계정이 이 계정의 포스트에 어떻게 반응했는가를 기준으로 라벨을 붙인다(블록·리포트·스팸 리포트 대비 favorite 비율을 쓴다)
    • bdsm/: 계정의 시계열 행동 시퀀스에서 inauthentic/abusive 신호를 추출한다 (Rust + proto + training + tests 서브디렉토리로 구성된다)
    • user-cred-v2/: 팔로우와 엔게이지먼트 엣지 위에서 PageRank를 돌려 계정 신뢰도 스코어를 만든다
    • scarecrow/: 이벤트 반응형 규칙 러너다. botmaker/를 규칙 엔진으로 임베드한다
    • botmaker/: 규칙 DSL과 컴파일러, 런타임을 담는다
    • botmaker-rules/: scarecrow가 로드하는 실제 규칙이다 (일부는 게이밍 방지를 위해 공개하지 않았다)
    • abuse-enforcement-service/: 모델 스코어를 근거로 계정 조치(라벨링·챌린지·서스펜션)를 결정한다
    • safety-label-user-agg/: 계정이 소유한 포스트가 받은 라벨을 계정 레벨로 집계한다

    이 15개 가운데 grox를 뺀 나머지 서브시스템은 오늘까지 canon에 한 줄도 반영되지 않았다.

    새로 알게 된 것: Phoenix가 실행 가능해졌다

    새 README의 서술은 다음과 같다.

    "Elsewhere, code may not necessarily include build- or deployment-related files or generally self-explanatory infrastructure imports (e.g. xai_service_runner or xai_kafka). ... phoenix/ ships a Cargo workspace, a pyproject.toml, a quickstart and synthetic data generation, so a small model can be trained and served end-to-end." — README.md #deployment-related-code

    정본이 "소스 읽는 법 — 주의 목록" #1에서 관찰했던 "레포 전체가 빌드되지 않는다"는 진술이 부분적으로 해소됐다. Phoenix만은 학습과 서빙까지 end-to-end로 실행할 수 있는 형태로 배포됐다. 나머지 크레이트에는 여전히 crate::params·crate::util·crate::clients·xai_service_runner·xai_kafka 같은 미공개 의존이 남아 있다. [확인] 새 커밋에 추가된 Cargo.toml은 여러 개이며 phoenix 서브트리에 몰려 있다.

    Phoenix retrieval을 위한 새 인덱스 서비스도 공개됐다 [확인] (출처는 README.md #retrieval-index):

    • phoenix-rankall/: Phoenix retrieval이 조회하는 포스트 인덱스를 유지한다. 이벤트가 도착할 때마다 갱신된다
    • phoenix-rankall-strato/: 어떤 인덱스에 포스트가 속하는지 결정하는 이벤트 층이다. visibility-filtering을 먼저 참조한다

    즉 인덱싱 파이프라인이 랭킹 쪽 visibility 규칙과 이미 sync되어 있어서, 포스트가 인덱스에 들어가기 전에 visibility 판단이 먼저 붙는다. 이것은 정본이 전혀 파악하지 못했던 아키텍처 사실이다.

    ⚠ 이 진술을 다룰 때 반드시 함께 밝혀야 할 caveat 다섯 가지

    1. 가중치는 크론이 매일 밀어 넣는 미러이므로 시차가 있다. 헤더에 적힌 sync 시각 이후에 프로덕션에서 일어난 변경은 아직 반영되지 않았을 수 있다. [확인]
    2. 가중치의 부호와 크기를 해석할 때에는 propensity를 함께 고려해야 한다. 파일에 달린 주석이 "값 = 가치 × 1/propensity"라고 명시한다. 즉 리포트 −234와 favorite 0.5의 절대값 비율(468배)이 곧바로 "리포트가 favorite보다 468배 중요하다"는 뜻은 아니다.
    3. 미러링 범위는 home-mixer 안의 param으로 한정된다. VMRanker 원격 서비스의 내부 상수, phoenix 학습 hyperparameter, botmaker 규칙 상수, crate::util 안의 상수(score normalizer, vqv weight 임계 등)는 여전히 레포 밖에 있다. [확인]
    4. Phoenix 학습 코드는 "학습이 가능한" 것이지 "프로덕션과 같은" 것이 아니다. README가 *"a small model can be trained and served end-to-end"*라고 명시해 규모가 다르다는 점을 분명히 한다. 실제 프로덕션 checkpoint와 데이터, infra는 공개되지 않았다.
    5. 일부 botmaker rules는 게이밍 방지를 위해 공개되지 않았다. README가 이를 명시한다. 즉 visibility-filtering이 참조하는 라벨 가운데 일부는 규칙이 공개되지 않은 상태다. [확인]

    • 2026-07-10에 A/B를 시작했다: BidirectionalFollowReplyWeightBoost 값을 5/10/15/20 중에서 무작위로 배정했고, 대다수 유저에게는 0을 적용했다
    • 2026-07-13에 초기 광범위 롤아웃을 진행하면서 20으로 확대했다
    • 2026-07-24에는 X에서 받은 유저 피드백(월드컵이 진행 중인데 관련 포스트가 부족하다는 지적)을 반영해 20에서 15로 낮췄다

    문서가 그대로 인용하는 요약은 다음과 같다.

    "In plain language, the bidirectional follow boost boosts original posts from people you mutually follow by increasing the weight on the predicted probability that you'll reply to a post from one of those authors who you mutually follow." — docs/BIDIRECTIONAL_BOOST_CHANGE.md

    코드에서는 다음과 같이 대응한다.

    • home-mixer/candidate_hydrators/bidirectional_follow_hydrator.rs (신규): SocialGraphClient로 상호팔로우 여부를 조회해 PostCandidate.is_mutual_follow_author에 설정한다
    • home-mixer/models/candidate.rs: 필드 하나를 추가했다
    • home-mixer/scorers/ranking_scorer.rs: bidirectional_boost_eligible(c)를 in_reply_to_tweet_id.is_none() && retweeted_tweet_id.is_none() && is_mutual_follow_author == Some(true)로 정의하고, 조건을 만족하면 reply와 dwell 가중치에 boost를 더한다
    • 조건은 순수 원본에만 적용되고, 답글과 리트윗은 제외되며, 상호팔로우가 아니면 pass-through로 통과시킨다

    즉 원본 포스트에 한해서만 부스트가 붙고, 답글과 리트윗은 대상이 아니다. 이 규칙은 canon에 없던 매우 구체적인 로직이다. [확인]

    의미

    ⚠ 주장 대량 변경. 오늘 이전까지 X 정본에서 가장 크게 비어 있던 절 두 개(가중치 값과 labeling 파이프라인)가 하루에 동시에 해소됐다. 이 저장소의 성격상 이 정도 규모의 canon 재작성은 드문 일이다. 정본 x.md에서 300줄이 넘는 분량이 오늘 바뀌거나 새로 쓰였다.

    첫 번째 의미는 연구 방향의 재정렬이다. 지난 3개월 동안 x.md의 열린 질문들이 다른 서비스(Meta·Netflix)를 관측하는 방향을 이끌어 왔다. "X 광고 스택은 어디까지 공개됐나", "SimClusters의 실 부활 여부", "VMRanker DPP의 배포 상태" 같은 질문이 topics/ 노트 여러 개의 방향을 정했다. 오늘 이 질문들이 답을 얻었으므로, 이 저장소는 이제 "X가 공개한 값이 왜 이런가 / 다른 회사의 대응 지점은 무엇인가" 라는 다음 단계의 질문으로 옮겨간다. 예를 들어 X의 report 가중치 −234와 Netflix GenRec의 catalog softmax는 완전히 다른 손실 함수의 두 극단이고, 이 두 숫자가 정본에 나란히 놓여 있다는 사실 자체가 다음 topics 확장의 기준점이 된다.

    두 번째 의미는 투명성 아키텍처의 산업 표준화가 시작된다는 신호다. docs/BIDIRECTIONAL_BOOST_CHANGE.md가 보여 주는 문서화 방식, 곧 A/B 시작에서 결과 관찰과 파라미터 조정까지를 3주 안에 코드 diff로 공개하는 방식은 다른 회사(Meta·Netflix·YouTube 어느 곳)에서도 지금까지 사례가 없었다. X가 이것을 "example algorithm diff"라고 부르며 앞으로도 반복하겠다고 예고했다면, 비교 가능한 프로덕션 diff 시계열이 처음으로 존재하게 되는 셈이다. 그렇다면 이 저장소가 앞으로 X 커밋 로그를 매일 추적하는 작업의 가치도 상당히 커진다. 다음 커밋에서 어떤 param이 어떻게 바뀌는지가 곧 A/B 결과의 지연 지표가 되기 때문이다.

    세 번째 의미는 정본 주의 목록의 일부를 다시 조정해야 한다는 점이다. "소스 읽는 법 — 주의 목록"의 주의 항목 #1(레포가 빌드되지 않는다) 가운데 Phoenix 부분은 해소됐지만, 나머지는 부분적으로만 해소됐다(crate::params의 이전 판이 지금은 이 파일로 채워졌으나, crate::util·crate::clients는 여전히 미공개다). 주의 항목 #2(README가 지목한 스코어러 3개가 죽은 파일이다)는 아직 검증이 필요한데, 새 릴리스에서 정리됐을 수 있다. 주의 항목 #6(has_cached_posts 비중)은 미해소 상태다. canon 주의 목록은 다음 배치에서 파일별로 재검증할 예정이다 (심층 분석 필요).

    2. arXiv cs.IR triage — 관찰 1건, 정본 반영 0건

    자료 arXiv API cs.IR 최근 30건 (2026-08-12~13)

    배경 매일 배치의 규칙은 다음과 같다. arXiv cs.IR 신규 30건을 제목과 초록으로 훑은 뒤, 프로덕션 저자, A/B 주장, 메커니즘 신규성, 스케일 결과 가운데 하나라도 걸리는 것만 원문을 확인한다. 오늘은 30건 중 대부분이 RAG/QA/text-to-SQL/멀티모달 벤치마크 같은 학술 증분이거나 도메인이 한정된 연구(음악·POI·의료 등)였다. 통과 후보 3건의 원문을 확인했다.

    새로 알게 된 것

    • STAR (2608.12986): "Structured Tokenization and Target-Aware Interest Representation for PCVR Prediction". 초록에서 스스로 "KDD Cup 2026 Tencent UniRec Challenge를 위한 프레임워크"라고 규정한다. 프로덕션 배포 진술은 없다. 탈락: 대회용 프레임워크는 프로덕션 진술이 아니다
    • HCGRec (2608.11980): "Hint-Conditioned Generative Recommendation with Semantic IDs". 저자 소속이 공개돼 있지 않고(arXiv 페이지에 affiliation 없음), CIKM 2026 accepted로 표기돼 있으며, GitHub 링크가 있다. 프로덕션 배포 진술은 없다. 탈락: SID 계열의 학술 증분이다
    • DrEM (2608.12778): "Dual-Side Robust Ensemble Ranking from Noisy User Preference Predictions in Video Recommendation". 저자 소속은 공개돼 있지 않으나, 초록에서 *"large-scale online A/B tests"*로 실제 배포를 주장한다. 저자 이름(Xiaoxiao Xu, Kaiqiao Zhan 등)이 Kuaishou 계열과 통계적으로 일치할 가능성이 있다 [추정]. 관찰 통과: radar.md의 "이번 달 신규"에 3~4줄 포인터를 추가했다(심층 분석은 하지 않았다). 회사 확정과 프로덕션 지면 확정은 다음 배치에서 크로스체크한다
