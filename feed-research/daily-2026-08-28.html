    1-A. Phoenix 체크포인트 저장·복원 스택 재정리

    phoenix/xrex/utils/checkpointing.py(+215/−6)와 phoenix/python/training/xai-checkpointing/xai_checkpointing/load.py(+311/−88)이 저장·복원 양방향에서 RSS(resident set size, 호스트 메모리 실 점유량) 상한을 명시적으로 도입했다. 4세대+7 (2026-08-24)의 restore-side 하드닝에 이어지는 변경이다. 그때는 복원에만 concurrent_gb throttle과 node-lock을 적용했는데, 이번에는 저장에도 같은 원리를 적용했고 복원에는 streamed 변형이 하나 더 붙었다.

    저장 측에 ThrottledD2HArrayHandler를 신설했다 [확인]. 위치는 phoenix/xrex/utils/checkpointing.py:88-181이다.

    • Orbax의 ocp.type_handlers.ArrayHandler를 상속해서 serialize(values, infos, args)를 오버라이드한다. 텐서 리스트를 순회하면서 각 tensor의 addressable_nbytes(현재 프로세스가 담당하는 shard의 실 바이트)를 누적하다가 concurrent_bytes 한도를 넘으면 배치를 flush한다. 배치마다 super().serialize()를 호출하고 future.result()로 D2H와 write가 끝나기를 기다린 뒤에 다음 배치로 넘어간다. 즉 텐서를 한 번에 모두 stage해서 pinned-host 메모리를 한꺼번에 소모하는 대신, 한 배치의 D2H와 저장이 끝나야 다음 배치를 stage한다.
    • 압축 여부에 따라 ThrottledD2HArrayHandler(compressed)와 ThrottledNoCompressionArrayHandler(non-compressed)로 다중 상속을 나눈다. 크기는 save_checkpoint(..., save_concurrent_gb=<N>) 인자로 지정한다. 지정하지 않으면 이전과 동일한 stock Orbax handler(전량 stage)를 그대로 쓰므로 하위 호환이 유지된다.
    • 노드 레벨의 flock도 있다. XAI_SAVE_NODE_SERIALIZE=1 env가 켜지면 /dev/shm/xai_save_node_lock(없으면 /tmp/...)에 fcntl.LOCK_EX를 걸어 같은 노드의 여러 프로세스가 동시에 저장하지 못하게 막는다. restore 측과 동일한 패턴이다(XAI_RESTORE_NODE_SERIALIZE).
    • 로그에는 배치별 leaves count와 GiB를 남기고, max_leaf가 예산을 넘으면 명시적으로 경고한다("that leaf still D2Hs in one shot"). 스로틀 크기가 텐서보다 작을 때 튜닝할 여지가 있다는 것을 사용자에게 알리는 장치다.
    • 의미: Muon+GB300 세대에서 여러 워커가 동시에 checkpoint를 저장할 때 wait_until_finished 바깥의 D2H 스테이지가 host OOM을 일으키는 현상이 관찰됐을 것이다 [추정]. restore 측에 4세대+7을 도입한 논리와 완전히 대칭이다. 4세대+6이 flagship Muon 학습을 export에 정식으로 포함한 뒤, 큰 모델을 저장하기에는 오래된 stock Orbax 설정("write-limiter default 96GB, D2H 전량")이 실제로 부족하다는 것을 측정으로 확인한 결과라고 해석할 수 있다.

    복원 측에 load_checkpoint_streamed를 신설했다 [확인]. 위치는 phoenix/python/training/xai-checkpointing/xai_checkpointing/load.py:365-528이다.

    • 기존 load_checkpoint는 처음에 host_state(모든 텐서의 pinned-host 사본)를 만들어 놓고 배치별로 read into shards 하는 방식이었다. streamed 버전은 device_state를 유지하고, 배치마다 그 배치의 텐서만 pinned-host로 stage → 파일 read → device로 device_put → device_state 갱신 → 배치 pinned-host 해제한다. 즉 어느 시점에서든 pinned-host 사용량의 상한은 현재 배치의 크기와 같다.
    • auto-window: window_gb=None(기본값)이면 _auto_window_bytes = min(max(max_leaf, total/16), 32GB)로 정해진다. 즉 window는 항상 max_leaf보다 크고, 전체를 최소 16개 배치로 나누되 32GB를 넘지 않는다. 사용자가 값을 따로 정하지 않아도 합리적인 window가 자동으로 선택된다.
    • on_replaced 콜백: 배치가 완료되어 device_state의 참조가 새 array로 교체되면 old와 new의 페어 리스트를 콜백에 넘긴다. 호출자는 old array를 즉시 delete하거나 다른 자료구조에서 링크를 교체하는 데 이 목록을 쓴다. 콜백을 지정하지 않으면 전체 목록을 반환한다.
    • copy_aliased_arrays: jax tree에서 같은 array 객체를 두 번 참조하는 aliased 케이스에서, 두 번째 참조부터는 may_alias=False device_put으로 실제 사본을 만든다. streamed load가 배치 단위로 새 array를 교체할 때 aliased 참조가 원본을 놓치지 않도록 미리 처리해 두는 헬퍼다.
    • plan.sort(key=lambda item: item[3], reverse=True)로 큰 텐서부터 처리해서 window packing 효율을 확보한다(max_leaf 이상인 텐서는 어차피 그 텐서 하나로 배치가 차므로 앞쪽에 모아 둔다).

    load_checkpoint 자체도 리팩터링됐다. 헬퍼 함수 5개(_build_read_plan, _pack_read_batches, _convert_domains, _open_tensor, _drain_read_futures)를 추출해 인라인 로직을 정리했고(streamed 버전이 이 헬퍼들을 재사용한다), 예외 로깅은 rank_logger로 통일했다. 별도의 logger = logging.getLogger("checkpointing") 인스턴스는 제거되고 rank_logger 단일 채널로 수렴했다.

    Trainer.warm_start_staging_spec 훅이 새로 생겼다(phoenix/xrex/train/trainer.py:1160-1165). checkpoint에서 params만 복원하고 opt_state는 재초기화하려는 경우에 pinned-host에도 opt_state 사본을 만들지 않는다. 이전에는 restore용 staging sharding으로 device_put할 때 전체 state 구조가 pinned-host로 올라갔는데, 이제는 warm_purge(self.state)로 opt_state를 미리 잘라내고 pinned-host에 stage한 뒤 로드된 부분만 다시 device_put하며 원래 opt_state 필드는 그대로 유지한다. RecsysTrainer.warm_start_staging_spec은 서브클래스에서 이를 오버라이드해 keep_emb_opt_state=True 옵션을 지원한다. 의미: warm start restore가 훨씬 가벼워졌다. flagship Muon 학습이 pretrained params에서 출발하고 optimizer는 새로 시작하는 흐름이 표준으로 자리 잡았다는 방증이다 [추정].

    **admission.reset_estimates와 request_metrics.reset_admission_estimates**가 추가됐다. Phoenix 서빙의 admission controller가 유지하는 service_time과 pipeline_time EWMA를 zero로 리셋할 수 있고, 대응하는 Prometheus gauge도 0으로 내려간다. 회귀 테스트도 두 개 붙었다(reset_estimates_clears_s_and_p, reset_admission_estimates_clears_gauges_and_p). 왜 필요한지는 diff에 단서가 없지만, hot-swap이나 트래픽 프로파일이 급변한 뒤에 EWMA를 즉시 초기화하려는 용도로 보인다 [추정]. 4세대+6의 _glibc_malloc_trim() swap 후처리와 방향이 같다.

    copy_port_client의 로깅도 정리됐다. dense weights load와 emb_table load의 완료 로그에 총 바이트, 경과 시간, GB/s를 함께 적는다(divide-by-zero 가드도 들어 있다). "downloading dense weights prefix=... futures=..." 시작 로그는 삭제됐는데, 완료 로그가 이제 요약 정보를 담고 있어서 시작 로그가 필요 없어졌기 때문이다.

    1-B. trainer_recsys의 valid_step 게이팅 통일

    phoenix/xrex/train/trainer_recsys.py(+29/−19)의 두 학습 루프(dense sync와 async_no_deferred)에서 param update 조건이 통일됐다 [확인]. 위치는 phoenix/xrex/train/trainer_recsys.py:1331-1400이다.

    이전 순서:

    1. valid_step = is_valid_step(gradients)로 dense grad-norm을 검사한다
    2. dense params를 업데이트한다: jnp.where(valid_step, updated, original)
    3. segment_sum 이후 is_valid_step(emb_gradients)로 emb grad-norm을 검사한다
    4. emb table을 업데이트한다: sparse_update(..., valid_step=emb_valid_step)
    5. metric에 valid_step = valid_step & emb_valid_step을 기록한다

    변경 후:

    1. dense grad-norm을 검사해 valid_step을 얻는다
    2. 먼저 segment_sum과 emb grad-norm 검사를 수행해 emb_valid_step을 얻는다
    3. keep_step = valid_step & emb_valid_step을 계산한다
    4. dense params를 업데이트한다: jnp.where(keep_step, updated, original)
    5. emb table을 업데이트한다: sparse_update(..., valid_step=keep_step)
    6. metric에 valid_step = keep_step을 기록한다

    즉 dense와 embedding 어느 한쪽이라도 grad-norm 검사가 실패하면 양쪽 다 원본으로 유지된다. 이전에는 dense가 통과하고 emb만 실패하면 dense params는 새 값으로 갱신되고 emb만 롤백되는 비대칭 상태가 몇 스텝 동안 이어질 수 있었다. 이제는 파라미터와 embedding table이 lock-step으로 움직인다.

    async 경로(update_async_deferred)도 같은 방식으로 통일됐다. pending=jnp.asarray(True)가 pending=keep_step으로 바뀌면서, 비동기 emb gradient update가 이번 스텝의 게이트 결과를 반영해 다음 스텝에 실제로 반영될지가 결정된다. 그리고 _create_async_emb_executables에 있던 assert self.grad_norm_keep_threshold is None이 제거됐다. 이전에는 async deferred 경로가 grad-norm 게이팅과 호환되지 않는다고 전제했는데, 이제는 async에서도 그 threshold를 실제로 사용한다.

    의미 Muon+GB300 세대에서 dense grad와 embedding grad가 서로 다른 스케일로 튀는 현상이 관찰됐을 것이다 [추정]. lock-step 게이팅으로 이 divergence가 남기는 영향을 처음부터 차단했다. 재현 가능한 학습을 위한 정합성 조정이다.

    Manhattan write monotone-only [확인]. 위치는 grox/flows/reply_spam/task_write.py:113-138이고 +22줄이다.

    의미 답글의 첫 판정이 낮게 나오면 그 답글은 계속 낮은 스코어를 유지한다. 새 판정이 관대해져도 서빙 스코어는 갱신되지 않는다. 반대로 첫 판정이 높게(관대하게) 나온 답글은 이후 판정이 엄격해지면 낮아진다. 이는 답글 스팸 판정의 monotone 안전 방향, 곧 한번 스팸으로 잡히면 계속 스팸으로 취급하고 정상에서 스팸으로 가는 재분류만 허용하는 방향과 맞아떨어진다. 답글 랭킹 스코어가 시간축에서 진동하는 것을 없애서, UI와 A/B에서 같은 답글의 랭킹이 오르내리지 않도록 만든다. [추정] 답글 스팸과 랭킹 관측에서 label flapping이 실제로 관측됐을 것이다.

    2. AMBER: Meta AI, "Event Tokenization"으로 이벤트를 단일 LLM 토큰으로 압축 (레이더)

    자료 AMBER: An Event is Worth One Token — arXiv 2608.25546: 2026-08-26 제출이고, 저자 15명이 전원 "AI at Meta"로 표기돼 있다(HTML v1에서 확인했다). 소속 표기는 ∗Core contributors, †Correspondence, AI at Meta다.

    배경 LLM 기반 추천은 "유저 상호작용 시퀀스"를 토큰으로 재표현해 autoregressive 예측을 수행한다. 그런데 종전 방식(text, semantic ID, categorical feature 몇 개)은 각 position에 담기는 정보가 얕아서 query context가 약해지고, 이것이 다음 position의 context로 다시 들어가면서 성능 저하가 시퀀스 길이에 따라 누적되는 문제가 있었다.

    새로 알게 된 것

    • Event Tokenization은 상호작용 이벤트 하나의 "temporal snapshot"(유저, 아이템, 컨텍스트, outcome 신호 전부)을 하나의 compact Event Token으로 압축한다 [확인]
    • 이 Event Token이 LLM의 새로운 입력 유형으로 자리 잡았다. 산업 규모의 오프라인 랭킹·retrieval 벤치마크에서 "compute-quality Pareto frontier"를 개선했다 [확인]
    • Event Token은 non-LLM 랭커에도 feature로 이식할 수 있고(transferability), 통계적으로 유의한 개선을 보였다 [확인]
    • Facebook surface에서 하루 수십억 이벤트의 인코딩을 서빙한다 [확인] HTML에 "supporting online encoding for billions of events per day"라고 적혀 있다

    왜 주목 LLM-native 랭킹 스레드에 네 번째 프로덕션 진술이 추가된다. Netflix GenRec(scoring), Meta ConnectionMind(graph reasoning), Taobao MetaStrategy(offline policy compiler)에 이어 Meta AMBER는 input tokenization 각도에서 접근한다. 서빙 경로에 LLM을 두는 대신 offline이나 nearline 인코더로 접근하면서도 이후 사용처는 넓게 열어 두는 방향인데, Facebook surface에서 online encoding으로 서빙되고 non-LLM 랭커에도 이식된다는 점이 특이하다. Meta의 ConnectionMind(그래프 경로 추론기)와 함께 보면, Meta 안에서도 LLM 기반 recsys 접근이 최소 두 축으로 갈라졌다는 신호다.

    정본 반영 ../radar.md 이번 달 신규 절에 AMBER 엔트리를 추가했다.

    의미 GenRec 스레드가 채점 함수(Netflix) → 그래프 경로 추론기(Meta) → 오프라인 정책 컴파일러(Alibaba) → 입력 인코더(Meta) 네 갈래로 나뉘면서, 서빙 위치와 역할과 계산 예산이 서로 다른 방향으로 다양해졌다. "LLM을 어디에 배치하는가"라는 아키텍처 스펙트럼이 넓어지는 흐름을 확인할 수 있다. 다만 온라인 A/B 수치는 abstract에도 HTML에도 명시돼 있지 않다. Facebook 프로덕션 배포는 확인되지만 랭킹 metric의 lift는 공개되지 않았다.

    3. TransRetrieval: Alibaba Alimama, Transformer scaling law를 광고 retrieval에 적용 (레이더)

    자료 TransRetrieval: Scaling Up Transformer-Based Retrieval for Industrial Recommendation — arXiv 2608.25528: 2026-08-26 제출이다. 저자 10명 가운데 Alibaba(Taobao & Tmall Group Beijing) 소속이 6명(Yunfei Liu, Bin Liu, Ziru Xu, Han Zhu, Jian Xu, Bo Zheng으로, Alimama 광고 라인의 시니어 저자들이다)이고, Renmin University 소속이 4명(Zhifei Zheng, Qiren Zhu, Hanbing Liu, Qi Qi)이다. affiliation은 HTML v1에서 확인했다.

    배경 추천 시스템의 retrieval에 LLM 스케일링 법칙을 적용하려는 시도는 여러 회사에서 있었지만(HSTU, Wukong, LLaTTE), feature heterogeneity 때문에 Transformer layer를 단순하게 쌓기만 하면 diminishing return이 나타난다. 서로 다른 field가 서로 다른 스케일의 token norm을 만들기 때문에, attention이 norm이 큰 feature에 지배되어 signal이 고르게 섞이지 않는다.

    새로 알게 된 것

    • Weighted average aggregation은 heterogeneous field들의 token-norm divergence를 억제해 Transformer를 스케일링할 수 있게 만드는 aggregator다 [확인]
    • Target token compression으로 candidate 하나당 계산량을 85% 절감한다 [확인]
    • Position-style domain embedding은 cross-domain 데이터를 최소한의 오버헤드로 통합한다 [확인]
    • Alibaba 디스플레이 광고 플랫폼에서 한 달간 프로덕션 A/B를 진행했다 [확인]:

    "lifts platform revenue by 2.53% under the same end-to-end latency constraint as the production baseline" — TransRetrieval HTML, 2026-08-26

    • 정확한 수치는 다음과 같다. revenue +2.53% (95% CI [2.22%, 2.70%], p<0.0001), RPM +1.28% (CI [1.14%, 1.56%], p<0.0001)이고, 4 도메인 분산은 Domain A +1.72%, B +2.51%, C +5.39%, D +0.87%다. P99 지연은 ~40ms로 유지된다 [확인].

    왜 주목 스케일링 법칙 스레드에 Alibaba와 Alimama의 첫 진술이 추가된다. 이전에는 Meta HSTU·Wukong·LLaTTE와 Netflix FM으로 회사가 2개였는데, 이제 세 번째 회사(Alibaba 광고 라인)가 들어왔다. 특히 retrieval 스택에 스케일링을 적용했다는 진술이라는 점이 특이한데, 대부분의 회사는 rank 스택에서 시작했기 때문이다. LLaTTE("semantic feature 없으면 스케일링 안 됨")와 HSTU("scaling만으로 됨")의 논쟁에 대해 TransRetrieval은 "field heterogeneity를 명시적으로 다루면 scaling 가능"이라는 세 번째 답을 내놓는다. 그리고 revenue +2.53%가 동일한 지연 조건에서 나왔다는 점에서 강한 프로덕션 진술이다.

    4. SWIM: Kuaishou 메인 피드 재순위 evaluator (레이더)

    자료 SWIM: Step-Wise Integrated Measure for Session-supervised List Evaluation in Generative Re-ranking — arXiv 2608.25104: 2026-08-25 제출이다. 저자는 9명으로, Kuaishou Technology(Beijing) 6명(Chenghao Zhang, Chao Feng, Xunyong Yang, Xiang Li, Yongqi Liu, Kaiqiao Zhan)에 USTC 2명(Yuanhao Pu, Defu Lian)과 Kun Gai(Unaffiliated)가 함께한다. affiliation은 HTML v1에서 확인했다.

    배경 오늘날의 산업 추천 시스템은 재순위(re-ranking) 단계에서 Generator-Evaluator (G-E) 아키텍처를 널리 채택하고 있다. Generator가 후보 리스트를 여러 개 만들면 Evaluator가 그 리스트들을 채점해 가장 좋은 리스트를 고르는 구조다. Kuaishou 같은 short-video 앱에서는 유저가 한 세션 안에서 여러 번 요청을 던지며 상호작용을 이어 가는데, 종전 Evaluator는 리스트 하나에 대한 단일 요청 metric(예: expected watch time)만 최적화해서 세션 전체의 관점을 놓친다.

    새로 알게 된 것

    • SWIM은 유저 행동을 finite-horizon prefix session-level survival process로 모델링한다 [확인]
    • 현재 리스트가 세션 목표에 얼마나 기여하는지를 (a) recursive survival distribution과 (b) reached-position conditional rewards로 factorize한다 [확인]
    • Kuaishou 메인 피드의 재순위에 프로덕션 배포됐다 [확인]:

    "Kuaishou short-video application (>400M DAU, >2 hours average daily engagement) ... 7 days, 5% traffic allocation" — SWIM HTML, 2026-08-25

    • 정확한 수치: App stay time +0.351% (95% CI [0.27%, 0.42%]), 7-day retention +0.048% (CI [0.01%, 0.09%])다 [확인]
    • 배포 방식은 이전 evaluator인 CAVE를 SWIM으로 교체하는 것이고, upstream의 retrieval과 generator는 그대로 유지한다.

    왜 주목 Kuaishou가 이번 달에만 내놓은 네 번째 프로덕션 추천 논문이다(HD-Rec, PushDualGen, DrEM에 이어진다). 이번에는 G-E 아키텍처의 evaluator 자체를 세션 단위 survival process로 재설계했는데, SID·CoT 논쟁이나 pxtr noise 논쟁과는 다른 축이다. Kuaishou 인프라 팀이 재순위 evaluator 문헌을 스택 전체에 걸쳐 재검토하고 있다는 신호로 보인다 [추정]. 다만 app stay 개선폭이 +0.351%로, 이번 달의 다른 Kuaishou 진술(예: DrEM App Stay Time +0.116%)에 비하면 큰 편이다. evaluator 수준의 개입이 downstream metric에 미치는 여지를 명시적으로 크게 잡은 셈이다.

    정본 반영 ../radar.md 이번 달 신규 절에 SWIM 엔트리를 추가했다.
