    (10000, 15), (5000, 15), (3000, 15), (2000, 14), (1500, 13), (1000, 13),
    (750, 12), (500, 11), (300, 10), (200, 9), (150, 8), (100, 7),
    (75, 7), (50, 6), (30, 6), (20, 5), (15, 5), (10, 5),

pub(crate) fn holdout_percent(fav_count: Option<i64>) -> u32 {
    let favs = fav_count.unwrap_or(0);
    if favs <= 1 { return 0; }
    for &(k, pct) in Self::STEPS { if favs > k { return pct; } }
    0
}

      fav_count가 10,000을 넘으면 15%, 5,000 초과도 15%, 2,000 초과 14%, 1,000 초과 13%, 750 초과 12%, 500 초과 11%, 100 초과 7%, 20 초과 5%, ..., 2 초과 3%, 1 초과 2%. **fav_count가 1 이하면 0%**로 뷰어 전원이 항상 본다. 홀드아웃 판정은 InventoryHoldoutFilter::is_held_out(post_id, viewer_id, percent)을 재사용하는데, 이는 splitmix64 계열의 이중 mixing 해시로 (post_id, viewer_id) 쌍의 100-modular 버킷을 구해 percent 미만이면 홀드아웃한다. 즉 같은 유저는 같은 포스트를 결정론적으로 홀드아웃하고, 같은 포스트라도 뷰어마다 다른 부분집합만 홀드아웃한다. 기본 param EnableFavHoldout = false. Param 정의는 home-mixer/params/param.rs의 rust_home_mixer_enable_fav_holdout.

      pub enum EvaluationResult { Evaluated(Box<Action>), NotEvaluated, Failed }
pub const MAX_ACTION_BYTES: usize = 64 * 1024;

      decode_action은 64KB payload 제한(TConfiguration의 4개 상한을 모두 64KiB로), Compact Thrift 프로토콜, trailing byte 금지, Action::NotEvaluated는 거부. 즉 응답이 Evaluated(Action)의 Thrift 인코딩이어야 한다. Action은 xai_x_thrift::action의 오랜 규격(변종에 MessageLink·LimitedAction·TweetVisibilityNudgeAction 등 포함). 의미: VF의 응답 인터페이스가 필터링된 사유 코드 열거형뿐 아니라 완전한 Action 오브젝트를 클라이언트에 되돌리는 방향으로 확장되기 시작. 4세대+20이 열어 뒀던 xDS LDS listener 마이그레이션과 짝으로 읽으면, VF가 client → server 단순 필터에서 richer한 정책 판정 서비스로 이동 중.

    첫째, 홈믹서 랭킹이 인기 있는 포스트에 대한 뷰어별 결정론적 홀드아웃이라는 새 축을 얻었다. InventoryHoldoutFilter가 종류(원본·답글·리트윗) 기준 3-tier 홀드아웃이었다면, FavHoldoutFilter는 인기(fav count) 기준 23-tier 계단 홀드아웃이다. 두 필터가 뷰어와 포스트 쌍에 대해 결정론적이지만 서로 독립된 결정을 내리므로, 이제 홈믹서가 아직 스코어링 이전 단계에서 (a) 포스트 종류별로 균일하게, (b) 인기도별로 계단식으로, 두 종류의 counterfactual 홀드아웃 실험을 병렬로 태울 수 있다. 왜 인기순 홀드아웃인가: 10K+ fav 포스트를 15% 홀드아웃해 두면 그 뷰어들이 그 포스트 없이 다음 최선의 후보로 어떻게 반응하는지 관측 가능해진다. 즉 상위 인기 포스트의 마진 기여도(이 포스트가 홈에서 사라졌을 때의 유저 손실)를 실측 실험으로 잡을 수 있는 인프라가 열린다. 4세대+21의 응답 다양성 3단 관측 side effect와 짝지어 보면, X 랭킹 실측 인프라가 집합 단위 counterfactual(다양성) + 포스트 단위 counterfactual(홀드아웃)이라는 두 축으로 확장되고 있다 [추정]. 4세대+21의 다양성 통계 관측이 A/B 실험 없이도 slate 구성을 관측한다면, 홀드아웃 필터는 A/B 실험을 필터 내부에서 자동으로 태우는 형태다.

    둘째, click_dwell 랭킹 항의 정의가 완전히 바뀌었다. 이전 EnableClickDwellLowFavRatePenalty는 fav 비율이 낮은 포스트의 dwell 예측을 (fav/baseline)^alpha로 낮춰 부풀린 dwell만 보고 오판하는 것을 억제하는 heuristic penalty였다. 4세대+22에서 click_dwell 헤드가 sigmoid BCE 이진 분류로 바뀌면서 헤드의 실효 스케일이 60배 축소된 상태였는데, 이번 커밋은 fav-based penalty를 덜어내는 방향으로 정리했다(4개 튜닝 param과 대응 필드가 삭제됐다). 그 자리에 들어온 EnableCdwellOnImpr는 대안 접근이다: click_dwell 예측(클릭 시의 dwell 확률/시간)을 click 확률로 곱해 임프레션 당 기댓값으로 변환한다. 이 재정의는 두 헤드의 신호를 곱해 얻는 값이므로 "dwell을 늘리는 헤드"와 "click을 늘리는 헤드"가 서로 상쇄나 이중 카운트되는 문제를 줄인다. Netflix N-tower·YouTube ranker가 오래전부터 dwell 헤드를 conditional 확률(P(dwell|click))로 학습한 뒤 서빙에서 P(click)과 곱해 unconditional 기댓값을 만드는 관행과 정렬된다. ⚠ 주장 변경: 어제(2026-09-17) 정본이 "click_dwell_time 헤드의 실효 기여는 이전 대비 ~60배 축소 상태"로 기술했는데, ContClickDwellTimeWeight가 조정되지 않은 상태에서 이 헤드가 click_score와의 곱으로 재정의될 경우 실효 스케일은 다시 변한다. 정확히는 (a) EnableCdwellOnImpr=false(default)이면 60배 축소 유지, (b) 켜지면 확률·확률의 곱으로 뜨는데 이는 이전 초 단위 곱(0-60초 × click prob)이 아니라 확률의 곱(0-1 × 0-1)이 된다. Weight 절대치가 유지되면 실효 스케일은 60배 축소가 아니라 훨씬 더 큰 축소로 갈 수 있고, 이 헤드의 랭킹 기여가 사실상 남은 헤드에 흡수되는 방향이 될 수 있다. 실 배포 여부는 다음 커밋의 EnableCdwellOnImpr mirror flip과 ContClickDwellTimeWeight 재조정 여부에서 관측될 것 [추정].

    셋째, cold-start scorer의 Treatment 팔에서 두 게이트가 함께 완화됐다. is_phoenix_moe 요구가 사라진 것은 cold-start 대상이 이제 MoE 라벨 없이도 Treatment 실험에서 활성된다는 뜻이다. 4세대 초기부터 유지돼 온 이 게이트는 Phoenix MoE 헤드가 cold-start 후보에 대해서만 학습에 활용되도록 제한하는 실험 조건이었는데, 실측 결과 이 조건이 필요하지 않았거나 오히려 손실이었다는 판단이 되어야 완화된다 [추정].     UTH 라벨 재현 잡 스택 신설은 X가 발표한 Under-the-Hood 투명성 툴의 감사 라벨 daily 재계산을 위한 인프라다. 이 라인은 랭킹이 아니라 유저 감사 툴 서빙이므로 정본 반영 대상은 아니지만, 저장소 파일 구성상 랭킹 코드와 같은 레포에 병존한다는 사실은 유의미하다: X가 "왜 내 포스트가 이렇게 취급됐나"를 유저가 직접 조회 가능하게 하는 라인을 랭킹·안전과 같은 리포지토리에서 유지한다는 의도가 남아 있다.
