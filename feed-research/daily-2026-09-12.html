1안전 필터가 백엔드를 더 오래 기다리고, 조회 실패에 대비한 저자 캐시를 갖췄다 — X

자료 xai-org/x-algorithm@fee1d0f — 공개 소스코드, 2026-09-10, 파일 33개, +1587/−391. 이 노트들은 4세대 공개 뒤의 X 커밋에 차례로 번호를 붙여 부르며, 이 커밋(2026-09-10, fee1d0f)은 4세대+19다.

배경 X는 2026-08-13 4세대 공개 이래 For You 파이프라인 소스코드를 xai-org/x-algorithm에 매일 두 번 정도 미러링한다. visibility-filtering(VF, 코드는 visibility-filtering/)은 X 홈 타임라인의 안전 필터 gRPC 서비스이고, Rust로 재작성된 3세대 스택이다. 홈믹서(For You 피드를 조립하는 서비스)가 후보 리스트를 만들면, VF는 후보마다 tweet 메타데이터와 저자 라벨을 두 백엔드에서 가져와 채운 뒤 규칙 엔진에 넣는다. 이번 커밋은 VF에 집중한 중형 diff로, 백엔드 조회의 시간 예산과 실패 처리를 고치고 저자 라벨 자료구조를 줄였다.

VF가 백엔드에서 데이터를 가져와 채우는 이 단계를 하이드레이션이라 한다. tweet 메타데이터는 TES(X의 tweet 코어 조회 서비스인 Tweet Entity Service)에서 가져온다. 저자 라벨은 Gizmoduck(user profile 서비스)에서 가져온다. 하이드레이션에는 두 백엔드를 얼마나 기다려 줄지, 실패했을 때 판정을 어디까지 진행할지, 지연이 어디서 소진되는지라는 세 결정이 얽혀 있다. 이번 커밋은 셋을 모두 건드렸다.

변경은 크게 두 축이다.

  • 축 1은 하이드레이션의 시간 예산과 실패 처리다. 기다리는 시간을 늘렸고, 실패해도 캐시로 저자 기준 규칙을 판정할 길을 열었으며, 지연이 어디서 소진되는지 기록하기 시작했다.
  • 축 2는 저자 라벨 감축과 캐시 primitive 준비다. 라벨은 규칙이 쓰는 11종만 남았고, 새 캐시는 아직 쓰이지 않는다.
  • 축 2를 벗어나는 부수 변경도 있다. 추천 모델의 proto 상수와 모델 코드, 광고 로그 필드, 라벨 투명성 툴의 배치 잡, 이미지 빌더가 바뀌었다.

    • visibility-filtering/clock_cache.rs는 신규 파일 446줄이고, visibility-filtering/lib.rs에 pub(crate) mod clock_cache; 한 줄로 등록됐다. 이번 커밋에서 이 파일을 참조하는 코드는 없다.

  • 신규 파일 clock_cache.rs(446줄)로 들어온 32-way × 64-shard 캐시에는 dead_code 애트리뷰트가 붙어, 컴파일러 경고를 눌러 두었다 확인(같은 커밋). 이것으로 보아 아직 소비자가 없고, 다음 커밋에서 어느 hydrator가 clock_cache.rs의 캐시를 소비하는지가 관측 대상이다.

    • 파일 첫머리:

    • 컴파일러에게 "테스트가 아닌 빌드에서는 이 모듈이 죽어 있는 것을 알고 있다, 경고 내지 마라, 사유는 아직 소비자가 붙지 않았기 때문이다"라고 명시한 것이다.

  • 용량 capacity를 인자로 받아 set_count = capacity / WAYS개 set을 만들고 64개 shard로 분산한다 확인(같은 커밋). shard 하나가 여러 set을 가지고, set 하나가 32개 slot(way)을 가진다.

    • Slot에 저장하는 값은 (key: u64, generation: u64, value: Option<V>) 튜플이다.

    • 주요 정의:

  • CLOCK 알고리즘은 다음처럼 돈다 확인(같은 커밋).

    • 삽입(insert(generation, key, value)): 같은 키가 이미 있고 저장된 generation이 더 크면 건너뛴다. 오래된 값이 새 값을 덮어쓰지 못하게 하려는 것이다. 그렇지 않으면 그 자리에 덮어쓰고 Mark::Referenced로 표시한다. 키가 없으면 hand가 회전하면서 Referenced → Cold로 감쇠시키고, Cold나 Empty를 만나면 그 자리에 삽입한다.
    • 조회(get(key)): 같은 키를 찾으면 Mark::Referenced로 승격하고 Lookup::Found(value)를 리턴한다. 없으면 Miss이고, 저장된 값이 None이면 NotFound다.
    • Generation: 요청마다 begin_request() -> u64가 monotonic 값을 부여한다. 나중에 오는 요청이 오래된 캐시 값을 덮어쓸 수 있는지를 이 값으로 판정한다.

  • 이 캐시는 기존 FallbackCache와는 별개의 primitive다 확인(같은 커밋).

    • 기존 FallbackCache는 4세대에서 정본에 반영된 hydration/fallback_cache.rs이고, 뮤텍스 하나로 보호되는 moka::sync::Cache 기반 TinyLFU다.

  • 두 캐시는 잠금 단위, 교체 정책, 슬롯 배치, 값 타입, 동시성에서 다르다 확인(같은 커밋).

축 기존 FallbackCache (moka와 Mutex) 새 ClockCache
잠금 단위 캐시 전체에 Mutex 하나 shard(64)마다 Mutex
교체 정책 TinyLFU (확률적 빈도) CLOCK (Referenced ↔ Cold 감쇠)
슬롯 배치 동적 hash map 고정 32-way set-associative 배열
값 타입 임의 (Clone) Copy 제약 (u64 정도 크기 값에 적합)
동시성 한 mutex에 병목 가능 64-way sharding으로 대부분 non-blocking

Kuaishou의 캐스케이드 추천 논문 한 편을 radar.md의 "이번 달 신규"에 추가했다. 논문이 제안한 UniRec은 캐스케이드 추천의 pre-ranking과 ranking 단계 fusion을 두 stage의 joint learning으로 정렬하는 방법이고, Kuaishou 프로덕션 A/B에서 app usage duration을 +0.616% 높였다 확인 — arXiv 2609.11052, 2026-09-10 제출.

  • 다루는 문제는 산업용 추천의 캐스케이드 stage(pre-ranking, ranking)가 각기 다른 objective·feature space·latency 제약 아래에서 따로 최적화되는 것이다 확인(같은 논문). upstream은 downstream이 선호하는 아이템을 걸러 내고, downstream fusion은 upstream 개선을 상쇄한다.
  • 두 fusion agent가 input embedding을 일부 공유하고 single computation graph에서 함께 학습되어, gradient가 stage 사이를 흐른다 확인(같은 논문).
  • Dual-axis preference alignment는 두 방향으로 작동한다 확인(같은 논문).
    • 세로(vertical): downstream pairwise preference를 upstream fusion score에 전이한다.
    • 가로(horizontal): 이질적 prior signal에 대한 수십 개 pairwise objective를 bidirectional preference evidence로 재편한다.
  • 또 attribute group-relative regularization으로, 제약 없는(unconstrained) end-to-end fusion이 특정 attribute 그룹에 과집중하는 부작용을 억제한다 확인(같은 논문).
  • 21일 프로덕션 A/B에서 앱 사용시간이 +0.616% relative gain을 보였고, Kuaishou 플랫폼에 fully deployed됐다 확인(같은 논문).

  • HYDRATION_TIMEOUT 390 ms가 실제로 어떻게 작동하는지 본다 — 새 filter_tweets_phase_ms{stage="hydration"} 히스토그램과 filter_tweets_deadline_overrun_ms가 프로덕션 대시보드에 나타나면 실제 P50·P99 지연 분포와 overrun 발생률을 알 수 있게 된다. 홈믹서가 VF에 실어 주는 gRPC deadline 값 자체가 코드로 확인되면 좋다. 지금은 grpc-timeout 헤더 파싱 코드만 확인했고, 실제 값은 공개되지 않았다.
  • TREND_PAGE·EXPLORE_SPOTLIGHT 지면이 어디에 연결되는지 본다 — proto 슬롯이 열렸으므로 홈믹서에 이 지면들의 gRPC 엔드포인트나 후보 파이프라인이 다음 커밋에서 등장할 가능성이 있다. xrecsys_search(4세대+4에서 신설된 검색 랭킹 config)와의 관계도 관측 대상이다.
  • IMMERSIVE_LONG_DWELL 이벤트가 어디서 정의되는지 본다 — grox나 홈믹서에서 immersive 지면의 dwell 시간 임계로 이 aggregation을 만드는 코드가 어디에 나타나는지 확인한다. 학습 config에서 이 aggregation을 소비하는지도 본다.
  • UTH 화면에 국가별 takedown 정보가 나타나는지 본다 — x.com/i/under_the_hood에 국가별 필터나 라벨의 국가 표시가 등장하는지 지켜본다. 4세대+12의 NSFW 16개국 코드 명시와 이번 UTH 국가 필드 확장이 유저 화면에서 어떻게 합쳐지는지가 다음에 볼 점이다.
  • Action::Downrank의 실제 사용처를 계속 찾는다 — 4세대+18 커밋이 남긴 열린 질문이고, 이 커밋에도 여전히 등장하지 않는다.
