    축 1은 hydration의 시간 예산과 실패 처리다. 홈믹서가 후보 리스트를 만들면 visibility-filtering(VF)이 후보마다 tweet 메타데이터를 TES(Tweet Entity Service, X의 tweet 코어 조회 서비스)와 저자 라벨을 Gizmoduck(user profile 서비스)에서 하이드레이트한 뒤 rule engine에 태운다. 이 하이드레이션에 (a) 두 백엔드에 얼마나 기다려 줄지, (b) 실패했을 때 판정을 어디까지 진행할지, (c) 지연이 어디서 소진되는지 세 결정이 얽혀 있다. 이번 커밋은 셋 다 건드렸다.

    축 2는 모델링 노브의 라벨 감축과 캐시 primitive 준비다. VF의 AuthorFeatures가 4세대 공개 이래 HashSet<LabelValue>(thrift 정의 라벨 20+ 종을 담는 heap 자료구조)로 저자 라벨을 담아 왔는데, 이번 커밋에서 이걸 11개 explicit variant를 갖는 AuthorLabel enum + 64-bit bitset으로 좁혔다. 규칙에서 실제로 참조하는 라벨은 이 11개뿐이라 정답이지만, thrift에서 오는 다른 라벨은 이제 인풋에서 명시적으로 버려지고 카운터에만 잡힌다. 함께 신규 파일 clock_cache.rs(446줄)로 32-way set-associative × 64-shard CLOCK 캐시 primitive가 들어왔지만, dead_code 애트리뷰트로 컴파일러 경고를 눌러 둔 것으로 보아 아직 소비자가 없다 — 다음 커밋에서 어느 hydrator가 이걸 소비하는지가 관측 대상이다.

    축 2를 벗어나는 부수 변경도 있다: (i) Phoenix proto가 TREND_PAGE·EXPLORE_SPOTLIGHT 두 지면 상수와 IMMERSIVE_LONG_DWELL action aggregation 상수를 신설했고, (ii) two-tower user tower가 padding 위치에 별도 segment ID를 쓰도록 수정됐으며, (iii) Under-The-Hood(X의 라벨 투명성 툴) 데이터 파이프라인에 국가별 계정 takedown 일일 배치 잡이 새로 붙었고, (iv) grox motion-reveal 이미지 빌더(video → 하이라이트 프레임 생성기)에 ECC affine 정합과 Farneback optical flow refinement 두 단계가 추가됐다.

    결과의 의미: TES가 죽었거나 응답이 없어도 이 tweet의 이전 author_id가 캐시에 있으면 author-side rules는 여전히 판정된다. author-side rules는 유저의 계정 상태(suspended/deactivated/protected/erased/offboarded)와 저자 user_labels 11종(아래 C 참조)이다. tweet-side rules(nullcast, community-only, NSFW media, takedown reason, exclusive content, edit control)는 TES core 없이는 판정할 수 없으므로 여전히 skip된다.

    D. gRPC deadline 관측 (filter_tweets_deadline{outcome=within|overrun|absent}) + hydration/post_hydration 두 phase 분해 [확인] — visibility-filtering/filter_tweets.rs (+42), visibility-filtering/filter.rs (+6/−1), visibility-filtering/rules/metrics.rs.

    filter_tweets.rs::FilterTweetsEndpoint::filter_tweets가 요청 metadata의 gRPC 표준 grpc-timeout 헤더를 파싱한다:

    fn parse_grpc_timeout(metadata: &MetadataMap) -> Option<Duration> {
    let raw = metadata.get("grpc-timeout")?.to_str().ok()?;
    let (digits, unit) = raw.split_at(raw.len().checked_sub(1)?);
    if digits.is_empty() || digits.len() > 8 || !digits.bytes().all(|b| b.is_ascii_digit()) {
        return None;
    }
    let value: u64 = digits.parse().ok()?;
    let nanos_per_unit = match unit {
        "H" => 3_600_000_000_000,
        "M" => 60_000_000_000,
        "S" => 1_000_000_000,
        "m" => 1_000_000,
        "u" => 1_000,
        "n" => 1,
        _ => return None,
    };
    Some(Duration::from_nanos(value.checked_mul(nanos_per_unit)?))
}

    즉 gRPC 스펙의 단위 접미사 H/M/S/m/u/n(시·분·초·밀리·마이크로·나노)을 지원하고 digits ≤ 8자리여야 하며 그 밖의 형식은 None.

    성공 응답 시점에 RequestMetricsGuard::record_deadline(grpc_timeout)이 호출된다:

    pub(crate) fn record_deadline(&self, grpc_timeout: Option<Duration>) {
    let Some(deadline) = grpc_timeout else {
        incr(DEADLINE, &[("outcome", "absent")], 1);
        return;
    };
    let elapsed = self.start.elapsed();
    if elapsed <= deadline {
        incr(DEADLINE, &[("outcome", "within")], 1);
        observe_vm(DEADLINE_REMAINING_MS, &[], millis(deadline - elapsed));
    } else {
        incr(DEADLINE, &[("outcome", "overrun")], 1);
        observe_vm(DEADLINE_OVERRUN_MS, &[], millis(elapsed - deadline));
    }
}

    즉 세 카운터 filter_tweets_deadline{outcome=within|overrun|absent}와 두 히스토그램 filter_tweets_deadline_remaining_ms / filter_tweets_deadline_overrun_ms. VF가 호출자(홈믹서)가 준 데드라인 대비 자기 지연이 얼마나 여유가 있었는지·초과했는지·측정 불가였는지를 처음으로 관측한다.

    visibility-filtering/clock_cache.rs 신규 파일 446줄, visibility-filtering/lib.rs에 pub(crate) mod clock_cache; 한 줄 등록. 파일 상단이 이렇게 열린다:

    즉 컴파일러에게 "테스트가 아닌 빌드에서는 이 모듈이 죽어 있는 것을 알고 있다, 경고 내지 마라, 사유는 아직 소비자가 붙지 않았기 때문이다"라고 명시. 이번 커밋에서 이 파일을 참조하는 코드는 없다.

    내용은 다음과 같다.

    const WAYS: usize = 32;
const SHARDS: usize = 64;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub(crate) enum Lookup<V> {
    Miss,      // 키가 이 캐시에 등록조차 안 됨
    NotFound,  // 등록됐지만 값이 None(예: 백엔드가 NotFound를 리턴)
    Found(V),
}

pub(crate) struct ClockCache<V> { /* shards, set_count, next_generation */ }

    용량 capacity를 인자로 받아 set_count = capacity / WAYS개 set을 만들고 64개 shard로 분산. shard 하나가 여러 set을 가지고, set 하나가 32개 slot(way)을 가진다. Slot에 저장하는 값은 (key: u64, generation: u64, value: Option<V>) 튜플.

    CLOCK 알고리즘은 이렇게 돈다:

    • 삽입 (insert(generation, key, value)): 같은 키가 이미 있으면 저장된 generation이 크면 skip(오래된 값이 새 값을 덮어쓰지 못하게), 아니면 그 자리에 덮어쓰고 Mark::Referenced. 없으면 hand가 회전하면서 Referenced → Cold로 감쇠시키고, Cold나 Empty를 만나면 그 자리에 삽입.
    • 조회 (get(key)): 같은 키를 찾으면 Mark::Referenced로 승격하고 Lookup::Found(value) 리턴, 없으면 Miss. 저장된 값이 None이면 NotFound.
    • Generation: 요청마다 begin_request() -> u64가 monotonic 값을 부여한다. 나중에 오는 요청이 오래된 캐시 값을 덮어쓸 수 있는지를 이 값으로 판정.

    기존 FallbackCache(4세대에서 정본화된 hydration/fallback_cache.rs, 뮤텍스 하나로 보호되는 moka::sync::Cache 기반 TinyLFU)와는 별개의 primitive다. 차이의 핵심:

    축 기존 FallbackCache (moka + Mutex) 새 ClockCache
    Lock granularity 캐시 전체 하나의 Mutex shard(64)마다 Mutex
    Eviction TinyLFU (probabilistic frequency) CLOCK (Referenced ↔ Cold 감쇠)
    Slot layout Dynamic hash map Fixed 32-way set-associative 배열
    Value type 임의 (Clone) Copy 제약 (u64 정도 크기 값에 적합)
    Concurrency 한 mutex에 병목 가능 64-way sharding으로 대부분 non-blocking

    즉 write throughput과 lock contention에 훨씬 강한 새 hot-path 캐시로 읽힌다. 다음 커밋에서 어느 hydrator(TES author_id? Gizmoduck AuthorFeatures? SafetyLabel expiring cache?)의 백엔드로 배선되는지가 주요 관측 대상.
