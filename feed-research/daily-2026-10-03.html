    1. 4세대+34 — X가 generative SID retrieval을 home-mixer 후보 소스로 배선 — X

    자료 xai-org/x-algorithm@76843a5 — xai-org, 2026-10-02T02:06:55Z, 코드.

    배경

    X의 추천 스택은 지난 넉 달 동안 Phoenix(2026년 재구축한 GPU 랭킹 스택)를 중심으로 재편돼 왔다. 그 안에서 "retrieval"은 두 가지 축으로 쪼개져 있었다. 하나는 two-tower retrieval — 유저 타워와 아이템 타워의 임베딩 내적으로 ANN 검색을 돌리는 전통적 OON 소스로, 2026-09-30 커밋에서 xrecsys_two_tower.py가 6-preset 카탈로그로 승격되고 SID 6-level + seqpack + Home/Immersive 두 head 공유가 명시된 자리다. 다른 하나는 generative retrieval(SID generation) — RQ-VAE나 비슷한 양자화로 아이템을 다단계 토큰 시퀀스(semantic ID, 줄여서 SID)로 압축한 다음, Transformer가 유저 히스토리를 조건부로 SID 토큰을 생성하는 방식이다. Pinterest TIGER(2024)·Alibaba PailitaoGR(2025)·Kuaishou OneRec(2025)·Tencent BARGE(2026)·ByteDance GEAR(어제 2026-09-30 arXiv) 같은 라인이 이 쪽이다.

    X 쪽은 그동안 SID 토큰을 학습 config의 sid_num_levels로(two-tower 모델이 아이템 타워의 입력 피처로 소비하는 축으로) 노출해 왔지만, SID를 생성해서 그 자체로 candidate을 뽑는 generative retrieval 경로는 공개된 적이 없었다. 2026-09-04(4세대+15)에서 "Phoenix 서빙 엔진에서 SID retrieval 사이드카가 통째 제거"됐다는 기록이 있었는데, 당시 사이드카는 Phoenix 요청 상에서 유저 히스토리의 각 포스트 ID를 SID로 변환해 주는 lookup 역할이었고 그 역할은 요청에 SID를 미리 실어 넣는 형태로 흡수됐다. 즉 그때까지 X의 "SID retrieval"은 아이템 ID → SID 토큰 lookup이라는 좁은 의미였다.

    오늘 공개는 그 자리를 완전히 바꾼다. (a) Phoenix 측에 SID generative retrieval 전용 Transformer 학습 config와 모델·트레이너·인퍼런스 러너가 신설되고, (b) home-mixer가 이 서비스를 호출하는 SidSource 후보 소스를 추가해, (c) 응답 후보에 shared_prefix_depth를 점수로 붙여 ForYouPhoenixRetrievalMoe로 라벨해 흘려 보낸다. 숫자 하나로 요약하면 이 커밋은 +5227/−756, 파일 105개다. 신규 파일 중 SID 관련 코드가 다섯 개 묶음이다.

    새로 알게 된 것 — B. Phoenix에 SID generative retrieval 전용 Transformer 모델

    [확인] — phoenix/xrex/configs/xrecsys_sid_retrieval.py(신규), phoenix/xrex/models/recsys_sid_retrieval_model.py(신규), phoenix/xrex/train/trainer_sid_retrieval.py(신규), phoenix/xrex/inference/sid_retrieval_runner.py(신규).

    학습 config xrecsys_sid_retrieval.py가 모델의 하이퍼파라미터를 전부 공개한다 [확인] — xrecsys_sid_retrieval.py:11-45:

    • SID 설계: sid_num_levels=6 (6-level 계층 SID), sid_codebook_size=256 (각 레벨 256개 코드) → 이론상 $256^6 ≈ 2.8 \times 10^{14}$ 개 SID 공간. sid_embed_dim=1024(= EMB_TABLE_WIDTH), sid_prediction_hidden_dim=512, sid_level_loss_decay=1.0(레벨별 loss 가중치 감쇠 없음, 즉 6개 레벨 전부 동일 가중치). sid_hash_level=True, sid_cross_attn=True.

    • 학습: Adam optimizer(b1=0.95, b2=0.98), weight_decay=1e-3, 상수 learning rate 2e-3, batch size per device = 128, parallel 축은 ep=128, dp=1(128-way expert-parallel, data-parallel 없음), max_steps = (1e11 / 32) − 100 ≈ 3.125B 스텝.
    • 데이터셋: aggregated_kafka 모드, PhoenixDataset에 path="/path/to/offline_kafka_dump"(필러), num_kafka_partitions=1024, include_candidate_post_ids=True, use_post_sid=True, multimodal_embedding_type=None.

    모델 코드는 Haiku transformed 함수로 _embed_sid_token(code, level)을 레벨별 별도 테이블(sid_emb_level_{level} 크기 [256, 128])로 관리하고, 각 레벨 뒤에 sid_emb_proj_{level} 프로젝션을 거쳐 1024-dim으로 올리는 축에 두는 구조로 보인다 [확인] — recsys_sid_retrieval_model.py:72-100. positive action은 SERVER_TWEET_FAV 단 하나 [확인](line 40) — fav 하나로 좁혀진 포지티브다. hard-negative action 7개(CLIENT_TWEET_REPORT, _NOT_INTERESTED_IN, _SEE_FEWER, _UNFOLLOW_AUTHOR, _BLOCK_AUTHOR, _MUTE_AUTHOR, _NOT_RELEVANT)는 negative supervision에 쓰이는 축이다. 서빙 측 beam decoder의 평가 조건은 eval_num_batches=20·eval_beam_width=128·eval_bs_per_device=8.

    인퍼런스 러너 sid_retrieval_runner.py가 beam search 기반 SID 생성과 SidPostIndex/SidBeamResolver로 생성된 SID 접두사를 실제 post_id 집합으로 역해상하는 두 단계를 분리해 담는다 [확인] — sid_retrieval_runner.py:21-80. 러너의 하이퍼파라미터 중 beam_width·decode_levels가 플래그이고, decode_levels < 6이면 접두사 수준에서 생성을 멈춰 접두사 공유 집합을 반환한다(prefix retrieval). 이것이 home-mixer SidSourceMinPrefixDepth=3과 짝을 이룬다 — 서버는 3~6단계까지 생성하되, 3단계에서 매칭된 모든 post는 접두사 깊이 3을 score로 받아 반환될 수 있다. _CorpusView.sentinel_idx·post_ids_with_sentinel·author_ids_with_sentinel 같은 축에서 코퍼스가 사전 빌드된 인덱스(SID → posts) 형태로 로드돼 있다는 걸 보여준다. 즉 서빙 시점의 코퍼스는 "SID 트라이 + leaf에 담긴 post_id 집합"이고, beam search가 트라이 위에서 top-K 경로를 뽑으면 그 경로 아래 posts가 후보가 된다 [추정] — 코드에서 SidBeamResolver의 세부 구조는 다른 파일(xrex/inference/sid_post_index.py)에 있고 이번 커밋 diff에는 안 나왔다.

    이 설계는 공개된 generative retrieval 가족과 자리가 겹친다: Pinterest TIGER(2024)·Alibaba PailitaoGR(2025)·Kuaishou OneRec(2025)·Tencent BARGE(2026)·ByteDance GEAR(2026-09-30)가 그 라인이다. X판의 특수성은 (a) 6-level × 256-codebook이라는 비교적 좁은 공간(TIGER는 4-level × 2k, OneRec는 3-level × 1024)에 (b) 1023토큰 유저 액션 히스토리를 그대로 조건으로 넣고(TIGER는 유저 히스토리 2050), (c) shared_prefix_depth를 상위 랭킹의 스코어로 넘긴다(TIGER는 생성 확률을 쓰는 쪽), (d) 이미 vocab 설계를 two-tower 모델과 공유해 두 retrieval 축이 같은 유저·아이템·작성자 임베딩 공간을 사용한다는 점에 있다. two-tower가 벡터 공간 ANN을 돌리고, SID retrieval이 코드 공간 beam search를 돌리는 duplication이 아니라 상보 구조를 선언한 셈이다.

    새로 알게 된 것 — C. row-sharded embedding CUDA 커널 묶음 신설

    [확인] — phoenix/xrex/cuda/row_emb/ 12-파일 묶음(총 3,180줄 신규): row_emb_api.cc(+766) · row_emb_comm.cc(+1,104) · row_emb_kernel.cu(+629) · row_emb.py(+290) · row_emb_comm.hpp(+256) · comm_utils.cc(+146) · row_emb_kernel.hpp(+135) · row_emb_common.cuh(+82) · cuda_error_utils.hpp(+68) · comm_utils.h(+57) · comm_utils.py(+47) · __init__.py(+2).

    Phoenix의 기존 async_emb 커널이 열(column) 축으로 샤드된 임베딩 테이블을 다룬다면, 새 row_emb는 행(row) 축으로 샤드된 테이블을 다룬다 [확인]. 즉 vocab이 N개면 N / group_size개 row가 각 rank에 올라가는 구조다. 이 설계는 vocab이 수억 규모(아이템 100M · 작성자 30M)로 커지면 임베딩 테이블이 GPU 수십~수백 장에 걸쳐야 하는 자리에서 중요해진다 — 각 토큰 lookup이 자기 소속 rank에만 질의하면 되고, all-to-all은 토큰을 lookup rank로 보내는 축으로 발생한다 [추정].

    Python 바인딩 row_emb.py는 JAX FFI target 6개(xrex_row_emb_lookup_start, _lookup_done, _stage_update, _rowwise_adagrad_update_start, _rowwise_adagrad_lazy_update_start, _rowwise_adagrad_update_done)를 CUDA 플랫폼에 등록하고, RowEmbContextHandle NamedTuple로 (context_id · group_size · flatten_replicas · tokens_per_rank · emb_width · rows_per_rank · recv_capacity · num_devices_per_node · mesh · table_axis · data_axis)를 묶어 shard spec을 캐리한다 [확인] — row_emb.py:30-80, 100-290.

    핵심 설계 결정 3개:

    1. lookup이 두 단계로 쪼개진다 — lookup_start는 token_ids와 로컬 샤드 테이블을 받아 table_out과 lookup_pin(float32 scalar)을 리턴한다. lookup_done은 pin을 받아 embeddings를 리턴한다. 두 FFI 사이에 다른 compute가 돌 수 있는 창이 열리고, all-to-all 통신이 그 창 안에서 compute와 overlap된다 — Pathways/MegaScale 같은 패턴. tokens_per_rank가 tokens_per_batch / group_size로 결정되고, recv_capacity = min(ceil(tokens_per_rank × recv_factor), tokens_per_rank × group_size)로 수신 버퍼 상한이 미리 잡힌다. recv_factor가 작으면 collision 많을 때 drop, 크면 버퍼 낭비.
    2. rowwise Adagrad가 lookup과 같은 2-phase 구조로 fused — rowwise_adagrad_update_start는 테이블 · row_state(각 row의 accumulator) · gate를 받아 업데이트 중인 테이블 자체를 돌려주고(input_output_aliases={0:0, 1:1}로 in-place), rowwise_adagrad_update_done은 완료 신호를 돌려준다. 추가로 rowwise_adagrad_lazy_update_start는 last_step과 step을 받아 접근된 row만 lazy update하는 변종을 제공한다 — sparse embedding 테이블에 흔한 패턴.
    3. gate 축으로 XLA 순서 보장 — 모든 FFI 함수가 gate: jax.Array를 입력으로 받고 float32 scalar를 출력에 섞어 넣는다. XLA가 자유롭게 재배열할 수 없는 side-effect 체인을 명시적으로 만든다. attrs()로 context_id · flatten_replicas 같은 커뮤니케이터 식별자를 FFI attribute로 넘기고, 같은 context_id면 동일한 통신 그룹을 재사용한다.

    유효성 체크 축: vocab_rows % group_size == 0(row shard 균등 분배), tokens_per_batch % group_size == 0(token shard 균등 분배), emb_width % 8 == 0(8의 배수, bf16 tiling 요건으로 보임 [추정]), recv_factor > 0, 그리고 table_axis 축이 반드시 data_axis 축에 포함돼야 한다. 포함되지 않으면 "token shard가 커뮤니케이터 랭크마다 1개가 아니다"는 ValueError를 던진다.

    의미

    세 겹의 사실이 겹친다.

    1. X가 generative SID retrieval을 "별도 microservice + 전용 Transformer 학습·서빙 스택 + home-mixer 후보 소스 배선"의 완결된 세 축으로 공개한 첫 커밋이다. 지금까지 X의 SID는 (a) two-tower 아이템 타워의 입력 피처(2026-09-30 공개된 xrecsys_two_tower.py에 use_post_sid 플래그)로, 또는 (b) phoenix-rankall의 백필 QPS 800k 상한으로(어제 공개된 SID_BACKFILL_QPS_CAP = 800_000) 간접적으로 모습을 비쳤지만, SID를 직접 생성해서 그 결과를 candidate로 리턴하는 라인은 공개되지 않았다. 오늘 공개는 (i) Phoenix 쪽에 전용 Transformer 모델(8-layer, GQA 20:4, 1030-length context, 6-level × 256-codebook)의 config/모델/트레이너/러너 네 파일을 신설하고, (ii) 별도 microservice(xai-recsys-sid-retrieval.prod.fou.twitter.biz)의 gRPC client와 request shape(seed_post_ids, shared_prefix_depth scoring, prefix retrieval 축 min_prefix_depth=3)을 공개하고, (iii) home-mixer SidSource로 PhoenixMOESource와 같은 ServedType으로 라벨된 후보를 흘려 보내는 전체 체인을 한 번에 공개한다. 이 세 축이 각기 별개 커밋으로 흩어졌다면 "준비 중" 신호였겠지만, 한 커밋에 묶여 공개된 사실이 배선 완성에 가깝다는 뜻이다. 다만 EnableSidSource=false 기본 off이므로 실 트래픽 적용은 FeatureSwitches cron에서 ON 되는 날이 관측 지점이다.

    2. two-tower retrieval과 SID generative retrieval이 "서로 대체"가 아니라 "동일 vocab 공간 위의 두 레이어"로 설계됐다. 두 모델이 같은 유저·아이템·작성자 hash vocab(100M · 30M · double hashing scales/biases 똑같음)을 공유한다는 사실이 xrecsys_sid_retrieval.py:30-45와 2026-09-30 공개된 xrecsys_two_tower.py의 수치를 대조하면 드러난다. 이것이 중요한 이유: generative retrieval이 두 가지 비용 축으로 비싼데(① SID 생성 시간 복잡도가 beam_width × decode_levels × 코드북 크기, ② 코퍼스 측 SID 인덱스 유지 비용), two-tower가 ANN이 돌릴 수 있는 broad recall을 먼저 커버한 뒤 SID retrieval이 접두사 공유도 축에서 보강 recall을 담당하는 상보 구조를 선택한 자리로 보인다 [추정]. 같은 vocab이면 양쪽 모델이 공유 임베딩 테이블로 돌 수도 있는데, 지금 공개된 config는 양쪽 모델이 각자 임베딩 테이블을 가진다. 공유 임베딩으로 통합되는지는 다음 커밋에서 관측해야 한다.

    3. row-sharded 임베딩 CUDA 커널 묶음은 Phoenix 임베딩 설계 자체의 2축 확장이다. 3,180줄 짜리 row_emb가 generative retrieval 모델만을 위해 추가된 건 아니지만, 이번 커밋 묶음의 맥락에서 보면 SID generative retrieval이 요구하는 거대 vocab 임베딩(100M · 30M · 6-level × 256 codebook)이 트리거라는 해석이 자연스럽다. async_emb(column-sharded, 기존)와 row_emb(row-sharded, 신규) 두 샤딩 전략을 공유 adapter(recsys_async_emb.py)로 선택하게 함으로써, 모델별로 최적 샤딩을 고를 수 있는 자리를 마련한 셈이다. two-tower는 하나의 유저 타워 / 아이템 타워를 각각 column-shard로 유지해도 되지만, SID generative 모델은 generation 축에서 각 토큰이 자기 vocab 범위만 참조하므로 row-shard가 더 compact한 통신 패턴을 낳는다 [추정].

    LLM_JUDGE_* action의 재귀환은 이와 별개의 흐름이다. 15일 전 vacate됐던 두 action이 번호를 바꿔(107/108 → 108/109) 재등장한 사실은 "LLM judge를 action 축에 담아 학습 target 중 하나로 소비"하려는 방향이 재조정 후 다시 올라왔음을 뜻한다. 번호가 바뀐 이유는 그 사이 107 자리가 CLIENT_TWEET_LIVE_STREAM_REPLY로 영구 점유됐기 때문이고, 108도 함께 비워 재사용하는 쪽을 택했다. 이번 공개가 모델 학습 config나 wire에서의 소비처는 보여주지 않는다 — proto만 자리 선점. 어느 head 가중치에 들어가는지, 어느 config의 target action list에 포함되는지는 다음 창에서 봐야 한다.

    다음에 볼 것

    • EnableSidSource cron flip 시점: FeatureSwitches cron이 언제 이 param을 true로 돌리는지, 그 시점의 SidSourceMaxSeeds·SidSourceMaxResults·SidSourceMinPrefixDepth 값이 config 기본값에서 바뀌는지가 실 트래픽 적용 시점이다. SidSource.retrieved{type=seeds|retrieved|hydrated} 메트릭이 홈믹서 측 관측 지점.
    • LLM_JUDGE_*(108/109) action의 학습 소비처: proto만 선언됐고 학습 config나 target head 쪽에서 소비하는 코드는 아직 안 보임. 다음 커밋에서 xrecsys_search.py 또는 xrecsys_two_tower.py의 target action list에 108/109가 추가되면 그때가 wire 선언에서 학습 소비로 승격되는 시점이다.
    • two-tower와 SID retrieval 임베딩 테이블 공유 여부: 두 모델이 같은 vocab 설계를 쓰지만 현재 임베딩 테이블은 각자 소유. 다음 커밋에서 체크포인트 공유 또는 임베딩 테이블 재사용 축이 생기면 두 retrieval이 공유 임베딩 위의 두 head로 통합되는 신호다.
    • generative retrieval 심층 분석: 모델의 beam decoder 수학(prefix retrieval 멈춤 조건, score aggregation, SID → post 역해상의 corpus view 구조), 학습 loss(positive=FAV 하나로 좁힌 자리의 negative sampling 축, hard negative action 7개의 가중치), training throughput(ep=128 · dp=1 · bs=128 · max_steps=3.1B 조합의 처리량 추정)이 모두 전면 분석 대상. 심층 분석 필요.
    • row_emb vs async_emb 선택 축: 어느 모델이 row-sharded를 쓰고 어느 모델이 column-sharded를 쓰는지, is_row_sharded(context_handle) 분기의 실제 호출처가 어디인지가 다음 창의 관측 지점. 현재 둘 다 adapter 레이어에서 지원되지만 어느 모델이 "실제로" row-sharded를 쓰는지는 model config의 make_context_handle 호출을 따라가야 보임.
