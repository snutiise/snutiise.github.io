1SID를 생성해 후보를 뽑는 retrieval이 For You 후보 소스로 연결됐다 — X

자료 xai-org/x-algorithm@76843a5 — xai-org, 2026-10-02T02:06:55Z, 코드. 이 노트들은 4세대 공개 뒤의 X 커밋에 차례로 번호를 붙여 부르며, 이 커밋은 4세대+34다. 규모는 +5227/−756, 파일 105개다.

배경 X의 추천 스택은 지난 넉 달 동안 Phoenix(2026년 재구축한 GPU 랭킹 스택)를 중심으로 재편돼 왔다. 그 안에서 "retrieval"은 두 갈래로 나뉘어 있었다.

  • 하나는 two-tower retrieval이다. 유저 타워와 아이템 타워의 임베딩 내적으로 ANN 검색을 돌리는 전통적인 OON(out-of-network, 팔로우하지 않은 계정의 포스트) 소스다. 2026-09-30 커밋에서 xrecsys_two_tower.py가 6-preset 카탈로그로 승격됐고, SID 6-level, seqpack, Home/Immersive 두 head 공유가 명시됐다.
  • 다른 하나는 generative retrieval(SID generation)이다. RQ-VAE나 비슷한 양자화로 아이템을 다단계 토큰 시퀀스(semantic ID, 줄여서 SID)로 압축한 다음, Transformer가 유저 히스토리를 조건으로 SID 토큰을 생성하는 방식이다. Pinterest TIGER(2024)·Alibaba PailitaoGR(2025)·Kuaishou OneRec(2025)·Tencent BARGE(2026)·ByteDance GEAR(어제 2026-09-30 arXiv) 같은 라인이 이쪽이다.

X는 그동안 SID 토큰을 학습 config의 sid_num_levels로 노출해 왔다. two-tower 모델이 아이템 타워의 입력 피처로 쓰는 형태였다. SID를 생성해 그 자체로 후보를 뽑는 generative retrieval 경로는 공개된 적이 없었다.

2026-09-04(4세대+15)에는 "Phoenix 서빙 엔진에서 SID retrieval 사이드카가 통째 제거"됐다는 기록이 있다. 당시 사이드카는 Phoenix 요청에서 유저 히스토리의 각 포스트 ID를 SID로 변환해 주는 lookup 역할이었고, 그 역할은 요청에 SID를 미리 실어 넣는 형태로 흡수됐다. 그때까지 X의 "SID retrieval"은 아이템 ID → SID 토큰 lookup이라는 좁은 의미였다.

이번 커밋은 그 좁은 의미를 완전히 바꾼다. 신규 파일 가운데 SID 관련 코드가 다섯 묶음이고, 다음 세 가지가 함께 들어왔다.

  • Phoenix 쪽에 SID generative retrieval 전용 Transformer의 학습 config, 모델, 트레이너, 인퍼런스 러너가 새로 생겼다.
  • home-mixer(For You 피드를 조립하는 서비스)에 이 서비스를 호출하는 SidSource 후보 소스가 추가됐다.
  • 이 소스는 응답 후보에 shared_prefix_depth를 점수로 붙이고, ForYouPhoenixRetrievalMoe로 라벨해 흘려보낸다.

새로 알게 된 것A. home-mixer가 별도 SID retrieval 서비스를 부르는 후보 소스를 갖췄다

  • home-mixer에 새 후보 소스가 생겼고, 이 소스는 별도 서비스로 분리된 generative SID retrieval microservice를 호출한다 확인 — home-mixer/sources/sid_source.rs(신규 +112).
    • 소스 이름은 SidSource다.
    • 호출을 맡는 클라이언트는 home-mixer/clients/sid_retrieval_client.rs(신규 +246)다.
    • 호출 대상 endpoint는 https://xai-recsys-sid-retrieval.prod.fou.twitter.biz:443이다.
  • 요청은 seed 포스트 ID와 결과 상한, 접두사 깊이 범위를 담고, 응답은 후보마다 포스트 ID와 공유 접두사 깊이를 담는다 확인.
    • gRPC 서비스는 SidRetrievalServiceClient다.
    • 요청 타입은 RetrieveRequest { seed_post_ids, max_results, max_per_seed, min_prefix_depth, max_prefix_depth, caller }다.
    • 응답 타입은 RetrieveResponse { candidates: Vec<Candidate> }이고, 각 Candidate에 post_id·shared_prefix_depth가 담긴다.
  • 이 proto 심볼은 레포 밖에서 들어오고, 레포에는 SID lookup proto만 담은 별도 crate가 함께 공개됐다 확인.
    • 심볼은 xai_recsys_sid_retrieval_proto crate가 외부(비공개 혹은 생성물)에서 가져온다.
    • 함께 공개된 별도 crate xai-recsys-sid-proto에는 sid_lookup.proto만 들어 있다.
    • sid_lookup.proto는 post_id → SID 코드 배열 매핑만 다룬다. 2026-09-04에 사라졌던 lookup 사이드카의 복귀다.
      • 정의는 SidLookupService { LookupSids(repeated int64 post_ids) → repeated PostSids { repeated int32 codes } }다.
    • generative retrieval 쪽 proto는 레포에 포함되지 않았다.
  • 이는 레포 안에서 보이는 생산 코드와 그 "generative retrieval" 전용 proto 정의가 분리된 상태라는 뜻이다 추정.
  • SidSource가 켜지는 조건은 네 축의 AND로, 아래가 모두 참이어야 한다 확인 — sid_source.rs:50-60.
    • EnableSidSource param이 켜져 있다(기본 false).
    • 토픽 요청이 아니다.
    • in-network only 요청이 아니다.
    • cached posts가 없다(cold path).
    • has_post_signals(query)가 true다.
    • 마지막 조건은 SimclustersSource와 완전히 같은 함수를 재사용해, 유저의 포지티브 engagement 신호가 있어야 소스가 돌게 한다는 뜻이다.
    • 두 소스가 같은 seed 집합(유저가 fav/retweet/reply 등으로 상호작용한 포스트 ID)에서 분기한다는 설계가 선언돼 있다.
  • 소스는 유저가 반응한 포스트를 seed로 SID 서비스를 부르고, 받은 후보에 기존 Phoenix MoE(mixture-of-experts, 전문가 혼합) 소스와 같은 라벨을 붙인다 확인.
    • 먼저 post_signal_ids(query)에서 유저의 positive engagement 포스트 ID들을 꺼내고, SidSourceMaxSeeds 상한(기본 50)으로 자른다.

    • 응답 Candidate는 각각 PostCandidate로 바뀐다. 이때 served_type = ForYouPhoenixRetrievalMoe로 표시하는데, 기존 PhoenixMOESource와 같은 라벨이다.
    • shared_prefix_depth는 score 필드에 f32로 들어간다.
    • 마지막으로 CoreDataCandidateHydrator로 작성자·생성 시각 등을 채운 뒤, author_id == 0인 후보는 제거한다.
  • 파라미터 다섯 개가 rust_home_mixer_sid_source_* 이름으로 새로 생겼고, 기본값이 공개됐다 확인 — home-mixer/params/param.rs. 이 파일은 프로덕션 feature-switch 기본값의 크론 미러다.

    • SidSourceMaxResults=800
    • SidSourceMaxSeeds=50
    • SidSourceMaxPerSeed=100
    • SidSourceMinPrefixDepth=3

    • seed마다 최대 100개 포스트, 전체 상한은 800개다. 50 × 100 = 5000이 이론적 상한이지만 800으로 다시 조여진다.

    • xDS 빌드가 10초 안에 끝나지 못하거나 bootstrap이 없으면 DNS 경로(RotatingChannel, 60초 간격 refresh)로 폴백한다.

    • 메트릭 SidRetrievalClient.retrieve{result=success|timeout|failure, path=xds|dns}가 호출 결과와 경로를 라벨로 남긴다. 호출 지연은 SidRetrievalClient.retrieve{path} 히스토그램에 담긴다.
    • 서비스 자체의 readiness probe는 port 29180의 GET /readyz다.
    • keep-alive는 30초 간격·10초 데드라인·idle=true로 설정된다.
  • 소스 쪽 메트릭은 seed 수, RPC 응답 수, 하이드레이션 뒤 남은 수의 세 단계를 각각 측정한다 확인.
    • 메트릭은 SidSource.retrieved{type=seeds|retrieved|hydrated}다.
    • seed 수는 RPC에 보낸 양, retrieved 수는 RPC 응답, hydrated 수는 author_id!=0 생존자다.

새로 알게 된 것B. Phoenix에 SID를 생성하는 전용 Transformer 모델의 학습·서빙 코드가 공개됐다

  • Phoenix에 SID generative retrieval 모델의 학습 config, 모델, 트레이너, 인퍼런스 러너 파일이 새로 생겼다 확인 — phoenix/xrex/configs/xrecsys_sid_retrieval.py(신규).
    • 나머지 세 파일도 신규다.
      • phoenix/xrex/models/recsys_sid_retrieval_model.py
      • phoenix/xrex/train/trainer_sid_retrieval.py
      • phoenix/xrex/inference/sid_retrieval_runner.py
  • 학습 config xrecsys_sid_retrieval.py가 모델의 하이퍼파라미터를 전부 공개한다 확인 — xrecsys_sid_retrieval.py:11-45.
    • 입력 시퀀스 길이는 1030이다. 유저 prefix 1토큰, 유저 액션 히스토리 1023토큰, SID 타겟 6토큰을 더한 값이다. 캔디데이트 시퀀스는 64다.
    • SID는 6-level 계층이고, 레벨마다 256개 코드를 쓴다. 이론상 SID 공간은 $256^6 ≈ 2.8 \times 10^{14}$ 개다.
      • sid_num_levels=6, sid_codebook_size=256
      • sid_embed_dim=1024(= EMB_TABLE_WIDTH), sid_prediction_hidden_dim=512
      • sid_level_loss_decay=1.0은 레벨별 loss 가중치 감쇠가 없다는 뜻이다. 즉 6개 레벨 전부 같은 가중치를 받는다.
      • sid_hash_level=True, sid_cross_attn=True
    • Transformer는 8-layer이고, GQA(grouped-query attention)를 5:1 비율로 쓴다.
      • query_heads=20·kv_heads=4, key_size=128, emb_size=2560
      • attn_logit_cap=80.0에 attn_logit_cap_method="soft_sign", rotary, causal
      • widening_factor=2에 gated_mlp=False(일반 MLP), remat WHOLE
    • 입력 vocab 수치는 2026-09-30(4세대+32)에 공개된 two-tower config의 수치와 정확히 일치한다. 두 모델이 동일한 vocab 공간을 공유한다는 뜻이다.
      • 유저 vocab=0, 아이템 raw vocab=0, 아이템 hash vocab=100M, 작성자 vocab=30M, 액션 타입 60개, continuous action 8개다.
      • _round_up(..., 512)로 512의 배수에 패딩한다.
      • user/item/author 각각에 두 쌍의 해시 함수(linear scale × modulus prime)로 double hashing을 한다.
    • 학습은 Adam optimizer와 상수 learning rate를 쓰고, data-parallel 없이 expert-parallel로 나눈다.
      • Adam optimizer(b1=0.95, b2=0.98), weight_decay=1e-3, 상수 learning rate 2e-3
      • batch size per device = 128, parallel 설정은 ep=128, dp=1(128-way expert-parallel, data-parallel 없음)
      • max_steps = (1e11 / 32) − 100 ≈ 3.125B 스텝
    • 데이터셋은 aggregated_kafka 모드이고, 경로는 필러 값이다.
      • PhoenixDataset에 path="/path/to/offline_kafka_dump"(필러), num_kafka_partitions=1024
      • include_candidate_post_ids=True, use_post_sid=True, multimodal_embedding_type=None
    • 체크포인트 설정도 공개됐다.
      • checkpoint_every_n=100·checkpoint_keep_every_nth=1000·checkpoint_keep_last_n=10·verify_checksums=True
      • replica_axis="replica"·checkpoint_chunked=False·checkpoint_compressed=False

    • 러너 파일은 sid_retrieval_runner.py이고, 되돌리는 단계는 SidPostIndex/SidBeamResolver가 맡는다.

    • 이것이 home-mixer SidSourceMinPrefixDepth=3과 짝을 이룬다. 서버는 3~6단계까지 생성하되, 3단계에서 매칭된 모든 post는 접두사 깊이 3을 score로 받아 반환될 수 있다.
    • _CorpusView.sentinel_idx·post_ids_with_sentinel·author_ids_with_sentinel 같은 필드는 코퍼스가 사전 빌드된 인덱스(SID → posts) 형태로 로드돼 있다는 걸 보여 준다.
    • 즉 서빙 시점의 코퍼스는 "SID 트라이 + leaf에 담긴 post_id 집합"이고, beam search가 트라이 위에서 top-K 경로를 뽑으면 그 경로 아래 posts가 후보가 된다 추정. 코드에서 SidBeamResolver의 세부 구조는 다른 파일(xrex/inference/sid_post_index.py)에 있고, 이번 커밋 diff에는 나오지 않았다.

이 설계는 공개된 generative retrieval 계열과 겹친다. Pinterest TIGER(2024)·Alibaba PailitaoGR(2025)·Kuaishou OneRec(2025)·Tencent BARGE(2026)·ByteDance GEAR(2026-09-30)가 그 계열이다. X판은 다음 점이 다르다.

  • 6-level × 256-codebook이라는 비교적 좁은 공간을 쓴다(TIGER는 4-level × ~2k, OneRec는 3-level × 1024).
  • 1023토큰 유저 액션 히스토리를 그대로 조건으로 넣는다(TIGER는 유저 히스토리 20~50).
  • shared_prefix_depth를 상위 랭킹의 스코어로 넘긴다(TIGER는 생성 확률을 쓰는 쪽이다).
  • 이미 vocab 설계를 two-tower 모델과 공유해, 두 retrieval이 같은 유저·아이템·작성자 임베딩 공간을 쓴다.

two-tower는 벡터 공간 ANN을, SID retrieval은 코드 공간 beam search를 돌린다. 둘은 duplication이 아니라 상보 구조로 선언된 셈이다.

  • Phoenix의 기존 async_emb 커널이 column 방향으로 샤드된 임베딩 테이블을 다룬다면, 새 row_emb는 row 방향으로 샤드된 테이블을 다룬다 확인.
    • vocab이 N개면 N / group_size개 row가 각 rank에 올라가는 구조다.
  • 이 설계는 vocab이 수억 규모(아이템 100M · 작성자 30M)로 커져 임베딩 테이블이 GPU 수십~수백 장에 걸쳐야 할 때 중요해진다 추정. 각 토큰 lookup은 자기 소속 rank에만 질의하면 되고, all-to-all은 토큰을 lookup rank로 보낼 때 발생한다 추정.
  • Python 바인딩 row_emb.py는 JAX FFI target 6개를 CUDA 플랫폼에 등록하고, shard spec을 NamedTuple 하나에 묶어 넘긴다 확인 — row_emb.py:30-80, 100-290.
    • FFI target의 이름은 아래와 같다.
      • xrex_row_emb_lookup_start, _lookup_done, _stage_update
      • _rowwise_adagrad_update_start, _rowwise_adagrad_lazy_update_start, _rowwise_adagrad_update_done
    • NamedTuple은 RowEmbContextHandle이고, 아래 값을 묶는다.
      • context_id · group_size · flatten_replicas · tokens_per_rank · emb_width · rows_per_rank
      • recv_capacity · num_devices_per_node · mesh · table_axis · data_axis

핵심 설계 결정은 3개다.

  1. lookup이 두 단계로 나뉜다. 두 FFI 사이에 다른 연산이 돌 수 있는 창이 열리고, all-to-all 통신이 그 창 안에서 연산과 겹친다. Pathways/MegaScale 같은 패턴이다.
    • lookup_start는 token_ids와 로컬 샤드 테이블을 받아 table_out과 lookup_pin(float32 scalar)을 리턴한다. lookup_done은 pin을 받아 embeddings를 리턴한다.
    • tokens_per_rank는 tokens_per_batch / group_size로 정해진다.
    • 수신 버퍼 상한은 recv_capacity = min(ceil(tokens_per_rank × recv_factor), tokens_per_rank × group_size)로 미리 잡힌다. recv_factor가 작으면 collision이 많을 때 drop이 생기고, 크면 버퍼가 낭비된다.
  2. rowwise Adagrad가 lookup과 같은 2-phase 구조로 fused됐다.
    • rowwise_adagrad_update_start는 테이블, row_state(각 row의 accumulator), gate를 받아 업데이트 중인 테이블 자체를 돌려준다. input_output_aliases={0:0, 1:1}로 in-place 갱신한다.
    • rowwise_adagrad_update_done은 완료 신호를 돌려준다.
    • rowwise_adagrad_lazy_update_start는 last_step과 step을 받아 접근된 row만 lazy update하는 변종이다. sparse embedding 테이블에 흔한 패턴이다.
  3. gate 입력으로 XLA 실행 순서를 보장한다.
    • 모든 FFI 함수가 gate: jax.Array를 입력으로 받고 float32 scalar를 출력에 섞어 넣는다. 이렇게 XLA가 자유롭게 재배열할 수 없는 side-effect 체인을 명시적으로 만든다.
    • attrs()로 context_id · flatten_replicas 같은 커뮤니케이터 식별자를 FFI attribute로 넘긴다. 같은 context_id면 같은 통신 그룹을 재사용한다.
  • 유효성 검사는 다음 조건을 확인한다.
    • vocab_rows % group_size == 0(row shard 균등 분배)
    • tokens_per_batch % group_size == 0(token shard 균등 분배)
    • emb_width % 8 == 0(8의 배수). bf16 tiling 요건으로 보인다 추정.
    • recv_factor > 0
    • table_axis 축이 반드시 data_axis 축에 포함돼야 한다. 포함되지 않으면 "token shard가 커뮤니케이터 랭크마다 1개가 아니다"는 ValueError를 던진다.
  • Phoenix의 async embedding 유틸이 두 커널을 모두 받아들이는 adapter 레이어로 재작성됐다 확인. 이제 column과 row 두 샤딩 전략을 동시에 지원한다.
    • 파일은 phoenix/xrex/utils/recsys_async_emb.py(+112/−36)이고, 받아들이는 커널은 async_emb와 row_emb다.
    • is_row_sharded(context_handle) 분기로 row와 column을 가른다. row-sharded면 table_spec을 P(table_axis, None)으로, column-sharded면 P(None, table_axis)로 돌려준다.
  • 이 커널 묶음은 SID retrieval 모델 전용이 아니라 Phoenix 임베딩 테이블 일반 설계의 확장이지만, 이번 커밋에 함께 공개된 맥락에서 보면 row-sharded 임베딩이 필요한 모델(즉 vocab이 매우 큰 모델)의 등장이 트리거로 보인다 추정.
    • two-tower는 column-sharded로도 돌 수 있지만, generative 모델은 lookup 패턴상 row-sharded가 더 자연스럽다. 각 토큰은 자기 vocab 레벨의 특정 range만 참조하기 때문이다.

정본 반영 services/x.md의 공개 소스 4세대 섹션에 "### 4세대+34 (2026-10-02, 76843a5)" 소절을 새로 만들었다. ## 후보 생성 (retrieval) 절의 retrieval 소스 표에는 SidSource 행을 추가하고, "SID generative retrieval microservice. seed post ID → 6-level × 256-codebook SID beam search → shared_prefix_depth score, served_type=ForYouPhoenixRetrievalMoe로 라벨, EnableSidSource=false 기본 off"로 적었다.

의미 SID를 직접 생성해 후보로 돌려주는 경로가 X 코드에서 처음 공개됐다. 다만 기본값이 off이므로, 실 트래픽 적용의 관측 지점은 FeatureSwitches cron에서 켜지는 날이다. 이번 커밋에서는 세 겹의 사실이 겹친다.

  1. X가 generative SID retrieval을 "별도 microservice + 전용 Transformer 학습·서빙 스택 + home-mixer 후보 소스 배선"의 완결된 세 축으로 공개한 첫 커밋이다.
    • 지금까지 X의 SID는 두 곳에서 간접적으로 모습을 비쳤다. 하나는 two-tower 아이템 타워의 입력 피처(2026-09-30 공개된 xrecsys_two_tower.py의 use_post_sid 플래그)다. 다른 하나는 phoenix-rankall의 백필 QPS 800k 상한(어제 공개된 SID_BACKFILL_QPS_CAP = 800_000)이다.
    • SID를 직접 생성해서 그 결과를 candidate로 리턴하는 라인은 공개되지 않았다.
    • 오늘 커밋은 아래 체인 전체를 한 번에 공개한다.
      • Phoenix 쪽에 전용 Transformer 모델(8-layer, GQA 20:4, 1030-length context, 6-level × 256-codebook)의 config/모델/트레이너/러너 네 파일을 신설했다.
      • 별도 microservice xai-recsys-sid-retrieval.prod.fou.twitter.biz의 gRPC client와 request shape(seed_post_ids, shared_prefix_depth scoring, prefix retrieval 조건 min_prefix_depth=3)을 공개했다.
      • home-mixer SidSource로 PhoenixMOESource와 같은 ServedType으로 라벨된 후보를 흘려보낸다.
    • 이 세 부분이 각기 별개 커밋으로 흩어졌다면 "준비 중" 신호였겠지만, 한 커밋에 묶여 공개된 사실은 연결이 완성에 가깝다는 뜻이다.
    • 다만 EnableSidSource=false가 기본(off)이므로, 실 트래픽 적용은 FeatureSwitches cron에서 ON 되는 날이 관측 지점이다.
  2. two-tower retrieval과 SID generative retrieval은 "서로 대체"가 아니라 "동일 vocab 공간 위의 두 레이어"로 설계됐다.
    • 두 모델은 같은 유저·아이템·작성자 hash vocab(100M · 30M · double hashing scales/biases 똑같음)을 공유한다. xrecsys_sid_retrieval.py:30-45와 2026-09-30 공개된 xrecsys_two_tower.py의 수치를 대조하면 드러난다.
    • generative retrieval은 아래 두 가지 비용이 큰데, two-tower가 ANN으로 돌릴 수 있는 broad recall을 먼저 맡고 SID retrieval이 접두사 공유도로 보강 recall을 담당하는 상보 구조를 고른 것으로 보인다 추정.
      • 하나는 SID 생성 시간 복잡도다(beam_width × decode_levels × 코드북 크기).
      • 다른 하나는 코퍼스 쪽 SID 인덱스를 유지하는 비용이다.
    • 같은 vocab이면 양쪽 모델이 공유 임베딩 테이블로 돌 수도 있다. 그러나 지금 공개된 config에서는 양쪽 모델이 각자 임베딩 테이블을 가진다. 공유 임베딩으로 통합되는지는 다음 커밋에서 관측해야 한다.
  3. row-sharded 임베딩 CUDA 커널 묶음은 Phoenix 임베딩 설계 자체의 2축 확장이다.
    • 3,180줄짜리 row_emb가 generative retrieval 모델만을 위해 추가된 것은 아니다. 하지만 이번 커밋 묶음의 맥락에서 보면, SID generative retrieval이 요구하는 거대 vocab 임베딩(100M · 30M · 6-level × 256 codebook)이 트리거라는 해석이 자연스럽다.
    • 공유 adapter recsys_async_emb.py가 기존 column-sharded 커널 async_emb와 신규 row-sharded 커널 row_emb 가운데 하나를 고르게 해, 모델별로 최적 샤딩을 선택할 여지를 마련한 셈이다.
    • two-tower는 유저 타워와 아이템 타워를 각각 column-shard로 유지해도 되지만, SID generative 모델은 generation 단계에서 각 토큰이 자기 vocab 범위만 참조하므로 row-shard가 더 compact한 통신 패턴을 낳는다 추정.

LLM judge action이 돌아온 것은 이와 별개의 흐름이다. 15일 전 vacate됐던 두 action이 번호를 바꿔(107/108 → 108/109) 재등장한 사실은 "LLM judge를 action 축에 담아 학습 target 중 하나로 소비"하려는 방향이 재조정 후 다시 올라왔음을 뜻한다. 번호가 바뀐 이유는 그 사이 107 자리가 CLIENT_TWEET_LIVE_STREAM_REPLY로 영구 점유됐기 때문이고, 108도 함께 비워 재사용하는 쪽을 택했다. 이번 공개는 모델 학습 config나 wire에서의 소비처를 보여 주지 않고, proto만 자리를 먼저 잡았다. 어느 head 가중치에 들어가는지, 어느 config의 target action list에 포함되는지는 다음 창에서 봐야 한다.

다음에 볼 것

  • SID 소스 스위치가 cron에서 언제 켜지는지 본다 — FeatureSwitches cron이 이 스위치를 true로 돌리는 때가 실 트래픽 적용 시점이다. 스위치는 EnableSidSource param이다. 그때 SidSourceMaxSeeds·SidSourceMaxResults·SidSourceMinPrefixDepth 값이 config 기본값에서 바뀌는지도 함께 본다. home-mixer 쪽 관측 지점은 SidSource.retrieved{type=seeds|retrieved|hydrated} 메트릭이다.
  • LLM judge 액션(108/109)을 학습에서 어디에 쓰는지 본다 — proto만 선언됐고, 학습 config나 target head 쪽에서 소비하는 코드는 아직 보이지 않는다. 다음 커밋에서 xrecsys_search.py 또는 xrecsys_two_tower.py의 target action list에 108/109가 추가되면, 그때가 wire 선언에서 학습 소비로 승격되는 시점이다.
  • two-tower와 SID retrieval이 임베딩 테이블을 공유하게 되는지 본다 — 두 모델은 같은 vocab 설계를 쓰지만, 지금은 임베딩 테이블을 각자 가진다. 다음 커밋에서 체크포인트 공유나 임베딩 테이블 재사용이 생기면, 두 retrieval이 공유 임베딩 위의 두 head로 통합되는 신호다.
  • generative retrieval을 깊이 분석한다 — 아래 세 가지가 모두 전면 분석 대상이고, 심층 분석이 필요하다.
    • 모델의 beam decoder 수학: prefix retrieval 멈춤 조건, score aggregation, SID → post 역해상의 corpus view 구조
    • 학습 loss: positive=FAV 하나로 좁힌 상태의 negative sampling, hard negative action 7개의 가중치
    • training throughput: ep=128 · dp=1 · bs=128 · max_steps=3.1B 조합의 처리량 추정
  • 모델마다 row_emb와 async_emb 가운데 어느 쪽을 쓰는지 본다 — 어느 모델이 row-sharded를, 어느 모델이 column-sharded를 쓰는지, is_row_sharded(context_handle) 분기의 실제 호출처가 어디인지가 다음 창의 관측 지점이다. 지금은 둘 다 adapter 레이어에서 지원되지만, 어느 모델이 "실제로" row-sharded를 쓰는지는 model config의 make_context_handle 호출을 따라가야 보인다.
