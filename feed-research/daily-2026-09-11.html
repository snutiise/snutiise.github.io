1노출 판정 필터가 사유 대신 액션 값으로 포스트를 거른다 — X

자료 xai-org/x-algorithm@75d93d9 — 공개 소스코드, 2026-09-09, 파일 28개, +801/−252. 이 노트들은 4세대 공개 뒤의 X 커밋에 차례로 번호를 붙여 부르며, 이 커밋(2026-09-09, 75d93d9)은 4세대+18이다.

배경 X는 For You 파이프라인 소스코드를 xai-org/x-algorithm에 매일 두 번 정도 미러링한다(2026-08-13 4세대 공개 이래). 이번 커밋은 파일 28개짜리 중형이지만 서로 다른 5개 축을 동시에 건드렸다.

  • 노출 판정은 이제 사유가 아니라 액션 값이 결정한다. visibility-filtering(VF)은 포스트마다 '이 뷰어에게 보여도 되는가'를 판정하는 서비스다.
    • VF 클라이언트가 TweetVisibility에 명시적 Action 필드를 추가했고, home-mixer(For You 피드를 조립하는 서비스)의 VFFilter는 이제 FilteredReason이 아니라 Action enum으로 drop/keep을 결정한다.
    • 판정 축이 "reason에서 파생된 action"에서 "action이 결정, reason은 로깅용 annotation"으로 옮겨졌다.
  • 홈 타임라인에 머리 이미지, 본문, 1~2개 CTA(행동 유도) 버튼으로 구성되는 새 광고 포맷이 first-class로 등장했다. 트윗을 감싸는 프로모트 트윗 포맷이 아닌 6번째 변종이다.
    • home-mixer/util/urt/ad_marshaller.rs에 header_image_prompt_ad_info가 있는 광고를 별도 marshaller로 처리하는 분기가 신설됐다.
  • 콘텐츠 분류 쪽에서는 긴 영상의 첫 프레임이 LLM 프롬프트에 따로 들어간다.
    • grox(Grok 기반 nearline 분류기 서브레포) 미디어 로더가 30초+ 영상에 대해 첫 프레임 preview 이미지를 다운로드·리사이즈한다.
    • 이 이미지는 LLM 프롬프트에 [Video Preview Thumbnail] 라벨과 함께 storyboard(균일 샘플링된 프레임을 격자로 붙인 이미지) 앞에 붙는다.
  • 라이브 방송 프레임이 두 안전 파이프라인의 정식 판정 대상이 됐다.
    • BroadcastLoader가 grox에 새로 들어와 라이브 broadcast(X의 라이브 비디오, Periscope 후신)의 프레임을 추출한다.
    • PTOS(정책 기반 위반 카테고리 판정) adult-content leading-frames와 sex/nudity safemodel, 두 안전 파이프라인이 broadcast 프레임을 정식 payload로 인정한다.
  • 등록된 랭킹 훈련 config 두 개 모두에서 멀티모달 post 임베딩이 학습 입력에서 빠졌다.
    • Phoenix(X For You의 랭킹 모델) 문서 phoenix/README.md의 nano 훈련 config 표에서, multimodal post 임베딩이 xrecsys_seqpack에서 v5로 켜져 있다는 줄이 "off (home_direct_packed and xrecsys_seqpack)"로 바뀌었다.
  • 부수적으로 phoenix NUMA pinning이 isolated CPU를 sched_setaffinity 대상에서 빼도록 고쳐졌고, candidate-pipeline의 quiet-spans feature-gated 로그 6곳이 삭제됐다.

새로 알게 된 것A. VF 판정에 명시적 액션 값이 생겼고, 필터는 이 값으로 거를지 정한다

  • VF의 판정 축이 필터링 사유에서 명시적 액션 값으로 리팩터됐다 확인 — visibility-filtering-client/vf_client.rs (+130/−62).
    • 판정 축은 FilteredReason에서 Action으로 옮겨졌다.
    • 함께 바뀐 파일: visibility-filtering-client/models.rs (+7), home-mixer/filters/vf_filter.rs (+27/−69), home-mixer/candidate_hydrators/vf_candidate_hydrator.rs (+159/−23), home-mixer/candidate_hydrators/vf_following_candidate_hydrator.rs (+6/−11), home-mixer/models/candidate.rs (+1).
  • 클라이언트가 돌려주는 판정 결과는 이제 세 값으로 된 튜플이다 확인.
    1. 결정론적 판정 Action(Allow / Interstitial / Avoid / Downrank / Drop / Tombstone / NotEvaluated)
    2. 로깅과 다운스트림용 annotation FilteredReason
    3. 라벨 lookup 결과 SafetyLabelMap
    • TweetVisibility는 기존 reason: Option<FilteredReason>과 safety_labels에 더해 action: Action 필드를 정식 멤버로 갖게 됐다.
    • 새 helper TweetVisibility::to_visibility_reason()이 action과 reason을 조합해 visibility_reason 필드 값을 유도한다.
  • Strato(코드가 데이터를 조회하거나 저장할 때 거치는 X 내부 시스템) 경로에서는 클라이언트가 Strato에서 받은 사유로부터 액션을 계산한다 확인. 규칙은 세 갈래다.

    • Strato의 정의는 services/x.md 용어 표에 있다.

    • StratoVfClient::get_result가 Strato에서 받은 FilteredReason으로부터 action_from_strato_reason을 거쳐 action을 계산한다.

    • Strato가 준 사유가 SafetyResult이면 그 안의 action을 그대로 쓰고, 그 밖의 non-SafetyResult reason(뮤트·차단·null-cast·exclusive 등)은 무조건 Drop으로 만든다.

    • Strato가 NotEvaluated로 리턴하면 client 층에서 Allow로 승격된다. 이는 Strato가 판정 미실행을 fail-open으로 취급하겠다는 뜻이다.

  • gRPC 경로에서는 응답에 담긴 액션을 그대로 쓴다 확인. 새 gRPC 경로에서는 서버가 action을 결정해서 내려주는 것이 표준이다.
    • result_to_visibility가 gRPC 응답의 result.action을 그대로 Action으로 매핑한다.
    • action 필드가 없으면 Action::NotEvaluated가 된다.
  • 필터 층은 이제 후보의 액션 값으로 거를지 정한다 확인. Allow, Interstitial, Avoid, Downrank는 남기고 Drop, Tombstone, NotEvaluated는 거른다.

    • VFFilter::filter가 이제 candidate.visibility_action의 함수다. 판정 함수는 다음과 같다.

    • 이전 버전은 FilteredReason variants를 매칭했다. SafetyResult면 action == Drop일 때만 걸렀고, 나머지 non-SafetyResult reason(뮤트·차단·null-cast·exclusive 등)은 무조건 drop이었다.

    • 새 버전은 판정 축이 명시적이라 훨씬 읽기 좋다.

  • 조상, 인용, 리트윗 원문 포스트를 거를 때도 액션 값을 본다 확인.
    • vf_candidate_hydrator.rs의 should_drop_ancillary가 조상·quoted·retweeted 포스트의 visibility.action을 봐서 drop 여부를 결정한다.
    • 이전 should_drop_reason(reason: &FilteredReason)은 제거되고, filter 층의 should_drop_action을 공유한다.
  • 후보 객체에 액션 필드가 추가됐다 확인.
    • candidate.rs의 PostCandidate가 visibility_action: Option<Action>을 갖게 됐고, 기존 visibility_reason: Option<FilteredReason>은 유지된다.
    • Hydrator update 함수 두 개(VFCandidateHydrator::update·VFFollowingCandidateHydrator::update)가 이 필드도 함께 채운다.
  • 뷰어가 작성자를 차단한 경우를 가리키는 사유 이름이 새로 생겼다 확인.
    • 새 FilteredReason 변종은 FilteredReason::ViewerBlocksAuthor다. 기존에는 AuthorBlockViewer(작성자가 뷰어를 차단)만 있었다. 이제 대칭 방향인 '뷰어가 작성자를 차단'도 정식 reason 이름을 갖는다.
    • vf_pb::FilteredReason::ViewerBlocksAuthor와 proto to/from 매핑도 추가됐다.

새로 알게 된 것B. 홈 타임라인에 트윗을 감싸지 않는 여섯 번째 광고 포맷이 생겼다

  • 홈 타임라인에 새 광고 포맷이 신설됐다 확인 — home-mixer/util/urt/ad_marshaller.rs (+258/−3).
    • 포맷 이름은 header-image-prompt-ad다.
  • 기존 홈 타임라인 광고는 다섯 포맷이었고, 이번 커밋이 여섯 번째를 추가했다 확인.
    1. 프로모트 트윗(promoted-tweet-<post_id>-<impression>)
    2. preroll 비디오 광고
    3. SSP 트윗/RTB Trend Takeover
    4. RTB image ad (rtb-image-ad-<impression>)
    5. Google SDK Native ad(GoogleSDKNativeAd)
    • 여섯 번째의 엔트리 이름은 header-image-prompt-ad-<impression>이다.
  • 광고에 이 포맷의 정보가 있으면 전용 marshaller가 우선 처리한다 확인. 프로모트 트윗과는 상호 배타적으로 분기된다.

    • marshal_ad() 함수 최상단에 이 분기가 있다.

    • 판단 기준은 AdIndexInfo.header_image_prompt_ad_info: Option<HeaderImagePromptAdInfo> 필드가 있느냐다.

  • 입력 정보(HeaderImagePromptAdInfo)는 광고 인덱스 서비스가 채워 넣는 proto message이고, 필드 구성은 marshaller가 소비하는 형태에서 역산할 수 있다 확인.
    • 헤더 이미지: image_url: String, image_width/height
    • 헤더와 본문 문구: header_text: String, body_text: String
    • 주 CTA: button_text: String, landing_url: String
    • 보조 CTA(비어 있으면 표시하지 않음): secondary_button_text: String, secondary_landing_url: String
    • 클릭 후 광고 dismiss 여부: dismiss_on_click: bool
    • 노출 트래킹 콜백: impression_callback_endpoints: Vec<String>
    • 주 CTA 클릭 트래킹 콜백: click_callback_endpoints: Vec<String>
  • 이 광고는 URT(Universal Response Tree, X의 응답 렌더링 스키마)에 트윗이 아니라 Message 타입 아이템으로 실린다 확인. "메시지 프롬프트"라는 별도 타입이다.
    • 엔트리 구조는 TimelineEntryContent::Item(TimelineItem { content: TimelineItemContent::Message(MessagePrompt { content: MessageContent::HeaderImagePrompt(HeaderImagePrompt { .. }), impression_callbacks }) })다.
    • MessageContent::HeaderImagePrompt가 이 광고 전용 컨텐츠 variant다.
  • 프롬프트 컨텐츠(HeaderImagePrompt)에는 이미지, 문구, 버튼 동작이 담긴다 확인.
    • 이미지(image_variants에 URL·width·height가 담긴다): header_image: MessageImage
    • 헤더 문구: header_text: String, header_rich_text: RichText. plain text와 entity 없는 RichText, 두 형태로 함께 담긴다.
    • 본문(있을 때만): body_text: Option<String>, body_rich_text: Option<RichText>
    • 주 버튼(필수): primary_button_action: MessageTextAction
    • 보조 버튼(secondary_button_text가 비어 있지 않을 때만): secondary_button_action: Option<MessageTextAction>
  • 버튼마다 자체 클릭 이벤트 정보와 callback 리스트를 가진다 확인.
    • 버튼 구조(MessageTextAction)는 text: String과 action: MessageAction { dismiss_on_click, url, client_event_info, on_click_callbacks, on_click_reactive_trigger }로 이뤄진다.
    • 각 버튼의 ClientEventInfo에서 action은 "primary_cta" 또는 "secondary_cta"다.
  • 테스트 3개가 이 계약을 고정한다 확인.
    1. header_image_prompt_ad_marshals_to_message_prompt_entry: entry_id 형식("header-image-prompt-ad-fa4ead01"), impression callback, HeaderImagePrompt content variant, 이미지 URL/치수, 텍스트, 주 CTA URL/dismiss/callback을 assert한다.
    2. header_image_prompt_ad_emits_secondary_button_when_set: secondary_button_text = "Learn more"를 세팅하면 secondary_button_action이 존재하고 action이 secondary_cta다.
    3. header_image_prompt_ad_info_absent_stays_a_tweet_item: header_image_prompt_ad_info: None이면 기존 프로모트 트윗 marshaller로 fall-through한다.

의미 (B) X 홈 타임라인이 트윗을 감싸지 않는 광고 포맷을 새로 정식으로 넣었다.

  • RTB image ad도 이미 트윗과 분리된 이미지 광고였지만, header-image-prompt-ad는 헤더 이미지, 본문 텍스트, 최대 2개 CTA 버튼으로 이뤄진 훨씬 풍부한 컴포넌트 구성을 갖는다.
  • URT MessageContent라는 별도 컨텐츠 타입을 쓰는 광고는 이 포맷이 첫 사례다. 클라이언트 렌더링 관점에서는 트윗이 아니라 in-feed announcement/dialog UI로 렌더링될 가능성이 높다 추정.
  • Secondary CTA를 지원하는 광고 포맷도 홈 타임라인에서는 이번이 첫 진입이다.
  • 광고 인덱스 시스템(공개 안 됨)이 이 광고 포맷을 언제 어떤 조건에서 채우는지는 이 커밋에 없다. 광고 블렌더 5종(safe_gap·partition_organic·partition_organic_low_risk·time_gap·multi_risk) 가운데 어느 것에 진입하는지도 없다.

새로 알게 된 것그 밖의 변경

  • NUMA 노드 안의 격리 코어(isolcpus)에 스레드를 스케줄하려던 Phoenix의 이전 버그가 고쳐졌다 확인.
    • 고친 곳은 phoenix/xrex/utils/gpu.py의 NUMA CPU affinity 처리다. 두 헬퍼 _parse_cpulist(text: str) -> set[int]와 schedulable_cpus(*nodes: int) -> set[int]가 신설됐다.
    • schedulable_cpus는 /sys/devices/system/node/nodeN/cpulist에서 노드 N의 CPU 집합을 읽고, /sys/devices/system/cpu/isolated를 빼서 반환한다.
    • pin_process_to_local_numa는 기존 numa.schedule.run_on_nodes(node) → numa.memory.set_membind_nodes(node)를 둘로 나눴다. numa.memory.set_membind_nodes(node)를 먼저, os.sched_setaffinity(0, schedulable_cpus(node))를 둘째로 실행해 예외 처리를 계층화했다.
    • 노드에 isolated가 아닌 CPU가 없으면 warn을 남기고 membind만 유지한다.
    • Phoenix 학습이 실 프로덕션 host에서 격리된 코어 configuration을 만난 결과로 보인다 추정.
  • 후보 파이프라인의 컴포넌트마다 남기던 feature-gated info 로그 6곳이 삭제됐다 확인.
    • candidate-pipeline의 quiet-spans 로그다. filter.rs·hydrator.rs·query_hydrator.rs·scorer.rs·selector.rs·source.rs에서 #[cfg(feature = "quiet-spans")] tracing::info!(...) 블록이 각 1개씩 제거됐다(총 −40줄).
    • 파이프라인 각 컴포넌트 실행마다 남기는 조용한 info-level 로그였다. quiet-spans feature 조건이 상시 활성화된 상태에서 span record와 중복되므로 제거된 것으로 보인다 추정.
    • Error 로그의 문자열 포맷도 error!(component = self.name(), error = %err, "source_failed")에서 error!("{} Failed: {}", self.name(), err)로 되돌아갔다. 구조화 필드가 제거되고 문자열 로그로 회귀했다.
