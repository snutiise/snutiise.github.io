자료 xai-org/x-algorithm@78460ca — xai-org, 2026-10-07T03:05:56Z, 코드. 파일 22개, +775/−681. 직전 커밋은 2026-10-06의 e62790c(4세대+36)다.

배경

X의 For You 피드는 후보 소스 여러 개가 포스트를 모으고, Phoenix(Grok 기반 Transformer 랭커)가 행동 확률을 예측한 뒤 value model이 가중합으로 순서를 정하는 구조다. 후보 소스는 크게 인네트워크(팔로우한 계정의 글, Thunder)와 OON(out-of-network, 팔로우하지 않은 계정의 글, Phoenix retrieval·SimClusters 등)으로 나뉜다. 2026-10-03에 생긴 PopularPostsSource는 유저와 무관하게 모두에게 같은 "최근 인기 포스트 500개" 목록을 OON 후보로 넣는 소스인데, 지금까지는 기본 off였다.

home-mixer/params/param.rs는 X 내부 feature switch 기본값을 매일 미러링한 파일이다. 그래서 이 파일의 값 변경은 프로덕션 기본값이 바뀌었다는 신호로 읽는다. 이번 커밋은 코드 구조보다 이 기본값 두 개가 바뀐 것이 핵심이다.

새로 알게 된 것A. 인기 포스트 소스가 기본 경로에 들어왔다

  • EnablePopularPostsSource가 false에서 true로 바뀌었다 확인 — home-mixer/params/param.rs:944-948. 미러 sync 시각은 2026-10-06T16:00:58Z다.

  • 소스가 켜지는 조건은 세 가지다: 캐시된 포스트를 재사용하는 요청이 아니고, 팔로우 전용(in_network_only) 요청이 아니며, 플래그가 켜져 있어야 한다 확인 — home-mixer/sources/popular_posts_source.rs:27-31. 유저별로 쓰는 정보는 이미 본 포스트 목록(seen_ids)을 빼는 것 하나뿐이다 확인(같은 파일 50행).

  • README에도 처음으로 OON 소스로 등재됐다 확인 — README.md:

    "popular_posts_source adds a shared list of popular recent posts."

    "A shared list of popular recent posts, initially from the most-followed active accounts."

    "initially"라는 단서는 지금은 팔로워 상위 작성자에서만 뽑지만 범위를 넓힐 수 있다는 뜻으로 읽힌다 추정 — 4세대+36의 잡 코드가 작성자 집합을 BigQuery 스냅샷에서 고르는 구조라 교체가 쉽다.

  • 목록을 만드는 방식은 어제와 같다. 최근 7일 활동 작성자 중 팔로워 상위 0.005%의 원본 포스트를 모으고, 24시간 안의 조회수를 반감기 8시간 가정으로 24시간 누적 조회수로 외삽해 상위 500개를 고른다 확인(4세대+36, home-mixer/popular_posts_job.rs).

새로 알게 된 것B. 새-작성자 부스트 0.02 → 0.015

  • 새-작성자 부스트(post_unexplored)는 노출이 1,000회 미만인 작성자의 인네트워크 포스트에 점수를 더해 주는 콜드스타트 장치다. 이 가중치 PostUnexploredWeight가 home-mixer 미러에서 0.02 → 0.015가 됐다 확인 — home-mixer/params/param.rs:384-388.
  • 같은 이름의 파라미터가 별도 서비스 VM-Ranker의 미러(vm-ranker/params.rs:91-95)에도 있는데, 그쪽은 0.02 그대로다 확인.
  • home-mixer는 4세대+28(2026-09-24) 이후 로컬 가중합을 먼저 계산하고 VM-Ranker RPC로 점수를 정제하며, RPC가 실패하면 로컬 점수를 서빙한다 확인(정본 4세대+28 항목). 따라서 0.015는 최소한 RPC 실패 경로의 값이고, 정상 경로의 최종값이 어느 쪽인지는 이 커밋만으로 판단할 수 없다 추정 — 두 미러가 다른 피처 스위치 키를 읽는지 아직 대조하지 않았다.

새로 알게 된 것C. 검색 랭킹 negative 샘플의 피처 교정

Phoenix는 For You뿐 아니라 검색 결과 랭킹도 학습한다. 학습할 때 실제 노출 기록만으로는 "관련 없는 결과"가 부족해서, 배치 안 다른 유저의 데이터를 빌려 가짜 negative를 만든다. 이것을 in-batch negative sampling이라고 부른다.

  • 검색 쿼리가 있는 배치에서는 negative를 두 종류 만든다 확인 — phoenix/xrex/data/recsys/recsys_batch.py apply_negative_sampling: (1) 다른 유저가 본 포스트를 내 쿼리와 짝짓고, (2) 내가 본 포스트를 다른 유저의 쿼리와 짝짓는다. 두 쿼리의 임베딩 코사인 유사도가 0.9 이상이면 비슷한 쿼리로 보고 버린다. negative에는 "읽지 않고 지나감" 라벨(ClientTweetRecapNotDwelled)이 붙는다.
  • 문제는 포스트 피처를 원래 슬롯에서 통째로 복사한다는 점이다. 2026-09-18(4세대+24)에 들어온 렉시컬 매치 피처 두 개, 즉 exactPhraseSeq(쿼리 문구가 포스트에 그대로 있는가)와 matchedWordFractionSeq(쿼리 단어 중 포스트에 나오는 비율)는 원래 쿼리 기준 값인데, 새 쿼리와 짝지은 negative에도 그대로 남아 있었다 확인(복사 코드 1391-1425행).
  • 이번 커밋은 신규 파일 negative_word_match.py(51줄)로 이를 고친다 확인 — 호출부 recsys_batch.py:1476-1488:
    • search_negative_clear_word_match(기본 False)를 켜면 negative 슬롯의 두 피처를 0(값 없음)으로 지운다.
    • 학습 데이터에 새 컬럼 lexicalTextSeq(포스트 본문)·lexicalQuerySeq(쿼리)·lexicalAuthorSeq(작성자)가 있으면, 외부 라이브러리 xai_search_lexical_match로 새로 짝지어진 쿼리 기준 값을 다시 계산한다.
  • 교정 전에는 특히 (2)번 negative가 "쿼리와 문구가 정확히 일치한다"는 피처를 가진 채 비관련 라벨을 받았다. 모델은 렉시컬 매치 피처를 실제보다 덜 믿도록 학습됐을 것이다 추정 — 피처와 라벨이 체계적으로 어긋나는 구조이기 때문이다.

새로 알게 된 것D. 그 밖의 변경

  • Transformer 각 층의 attention 출력과 FFN 출력 크기(제곱 평균)를 손실에 더하는 정규화 옵션 per_layer_l2_weight가 생겼다. 기본값은 0이다 확인 — recsys_model.py:664, 3827-3830. 활성값이 층을 지나며 커지는 것을 억제하려는 장치로 보인다 추정. 손실 입력을 만드는 함수 4개가 하나로 합쳐진 리팩터링도 있었다.
  • VF(visibility filtering, 노출 가능 여부를 판정하는 안전 계층)에서 tweetypie(포스트 저장소)가 "찾을 수 없음"을 돌려준 포스트는 이제 판정 대상이 아니라 실패로 처리된다 확인 — visibility-filtering/evaluate_tweets.rs.

의미

  • 4세대 공개 이후 X의 OON 후보는 모두 유저 임베딩이나 클러스터 같은 개인화 입력에서 나왔다. 이번에 처음으로 모든 유저에게 같은 목록을 주는 소스가 기본 경로에 들어왔다 확인. 다만 후보일 뿐이고, 실제 노출은 Phoenix 랭킹이 결정한다 추정 — 소스는 점수 없이 PostCandidate만 만든다.
  • 같은 날 인기 작성자 쪽 후보는 늘리고 신규 작성자 부스트는 25% 줄였다. 두 변경이 하나의 실험인지는 코드로 확인할 수 없다 추정.
  • 검색 negative 교정은 플래그가 기본 off라 당장은 학습에 영향이 없다 확인. 그러나 4세대+24에서 렉시컬 피처를 추가한 뒤 학습 데이터 쪽 결함이 3주 만에 드러났다는 점은, 검색 랭커가 이 피처를 아직 제대로 쓰지 못했을 수 있음을 뜻한다 추정.
