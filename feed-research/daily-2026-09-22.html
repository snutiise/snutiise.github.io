1Meta의 trillion-doc personalized search — GPU와 CPU 경로가 나눠 서빙한다 — Meta (Facebook Search 인프라)

자료 Hybrid GPU–CPU Retrieval for Personalized Search at Ultra-Large Scale — arXiv 2609.21281, 2026-09-18 v1 제출, KDD 2027 accepted. 저자 21인 전원 Meta Platforms(Menlo Park). HTML 판에서 소속 확인.

배경 Meta의 personalized search는 유저가 남긴 상호작용 이력에 크게 기대는 질의(사람 이름, 그룹, 관심사)와 아이템 커버리지가 넓어야 하는 질의(navigational, 이름이 정확한 것)를 동시에 처리해야 한다. 후자를 넓게 커버하려면 인벤토리 자체를 서빙 인덱스에 크게 담아야 하고, 전자를 잘 처리하려면 두 타워의 dot product를 넘어서 유저와 아이템 사이의 cross-feature interaction을 인퍼런스 경로에 넣어야 한다. 논문은 이 대립을 "personalization–scale paradox"라고 부른다: 전체 서빙 인벤토리를 GPU 메모리에 올리는 건 자원이 부족하고, CPU에서는 interaction-heavy 모델을 지연 예산 안에 넣기 어렵다. 이 조건을 새 모델 클래스가 아니라 동시 서빙(co-serving) 오케스트레이션으로 푸는 것이 이 논문의 주장이다.

Meta search의 인프라 논문은 공개된 것이 많지 않다. 인용 문헌에도 2020년 Embedding-based retrieval in Facebook search(KDD 2020)와 2021년 Que2Search(KDD 2021) 이후 프로덕션 아키텍처 진술이 오래 없었다. 이번 자료가 프로덕션 A/B 수치와 함께 이 갭을 채운다.

새로 알게 된 것

  • source corpus는 multi-trillion 규모이고, 서빙에 실리는 인벤토리는 여기에서 별도로 뽑는다 확인. 4-trillion figure는 "before selection", ANN scan 대상이 아니다. 정책·품질·언어·프레시니스·중복 검사를 통과한 뒤 하드웨어별 selector가 GPU snapshot과 CPU snapshot을 독립으로 만든다.
  • GPU pathway는 billion-scale 인벤토리를 대상으로 two-tower retrieval과 interaction pre-ranking을 한 프로세스에 fuse해 실행한다. 확인
  • CPU pathway는 tens-of-billions 인벤토리(GPU의 대략 20배)를 다루고, dedicated dense embedding index + eager term-at-a-time scoring + bulk scanning + finer clustering을 조합한다. dot product만 쓰고 유저·문서 벡터 사이에 cross feature는 넣지 않는다. 확인
  • 두 경로는 요청마다 하나만 켤 수도, 둘 다 켤 수도, 각각 독립으로 disable할 수도 있다. 후보는 downstream ranker로 넘어가기 전에 top-level aggregator에서 dedupe된다. 확인
  • 서빙 지연에서 GPU pathway가 P50과 P95에서 더 빠르고 P99만 16% 더 느리다 — 인터랙션 pre-ranking을 포함해 224개 후보를 shared ranker에 넣기 때문이지, 순수 kernel 비교가 아니다. dense CPU pathway는 dedupe 후 59개를 넘긴다. 확인
  • full-system A/B에서 legacy CPU-only 대비 model-scored relevance와 substantive engagement가 함께 오른다 확인. 두 pathway를 따로 A/B로 붙였을 때도 각자의 배포 스코프에서 양(+) 값이었다.
  • 지표는 GSRR(Good Search Result Rate) 로, retention-oriented substantive engagement 지표라고 자체 정의한다. 데일리 assigned population은 millions 단위, 계정 단위 랜덤 배정, 대략 반씩 분할.
  • capacity plan 관점에서 CPU pathway가 어떤 참조 dense retrieval 구현 대비 4배 처리량 개선을 낸다 — 다만 이 비교는 shared ranking·네트워킹·GPU pathway를 제외한 vector op 한정. 확인

"We present a hybrid GPU–CPU co-serving system that resolves the paradox through orchestration rather than a new model class. A high-depth GPU pathway fuses retrieval and interaction pre-ranking over a curated online pool on the order of a billion documents, while a high-breadth CPU pathway searches an independently selected online inventory roughly twenty times larger with lightweight personalized scoring." — arXiv 2609.21281, 2026-09-18

"The system is deployed in production. A full-system A/B test against the legacy CPU-only configuration improves model-scored relevance and substantive engagement, while separate pathway experiments show positive value at their own deployment scopes." — 같은 자료

정본 반영 없음. Facebook Search는 이 저장소의 canon 서비스가 아니다(services는 Facebook Feed 중심). 논문의 결과는 radar.md "이번 달 신규"에 편입한다. 두 번째 회사(구글, Bing, Yandex)가 depth-breadth heterogeneous co-serving을 프로덕션 A/B 수치와 함께 발표하면 topics/retrieval-heterogeneous-compute.md 승격 후보로 관찰한다.

의미 Meta의 프로덕션 retrieval 인프라를 한 계층 더 아래로 열어 준 첫 진술이다. 지난 5년간 Facebook Search에서 공개된 아키텍처 문헌은 EBR(2020)과 Que2Search(2021) 두 편에 사실상 멈춰 있었다. 이번 자료가 heterogeneous compute 층에서 무엇을 하는지를 보여 준다. 다만 VDD 논문의 문맥과 종합하면 이 "Search"는 순수 웹 검색 관점보다는 Facebook 안에서 검색 → 비디오 소비로 이어지는 통합 검색 지면에 걸쳐 있다(둘 다 GSRR을 쓴다). 우리 저장소가 추적하는 Facebook Feed의 후보 생성과는 아키텍처가 다르지만, 두 지면이 인프라를 상당 부분 공유한다는 정황이다(Xue et al., 2026이 "existing GPU platform"으로 인용된다).

2Video Deep Dive의 model-based retrieval — 37일 캠페인이 밝혀 낸 MBR 파이프라인과 human-gated 자동 실험 프로토콜 EvoPilot — Meta (VDD)

자료 Verify, Don't Trust: Agentic Model Development for Video Discovery Retrieval at Scale — arXiv 2609.21257, 2026-09-18 v1 제출, KDD 2027 accepted. 저자 5인 전원 Meta Platforms(Menlo Park). Hao Fu·Baiting Zhu·Minglei Chen·Yinjie Huang·Shuai Ding — 이 5명 가운데 4명은 자료 1의 저자 21인 명단과 겹친다.

배경 LLM agent가 코드 변경, 실행, 평가까지 도는 autoresearch 루프는 이미 있다. 자기완결 스크립트 안에서 몇 분짜리 iteration을 돌리는 것은 잘 알려져 있고, 이번 자료가 다루는 건 그것이 아니다. 여기 대상은 여러 subsystem을 아우르고 학습·인덱싱·서빙이 시간 단위로 굴러가는 온라인 시스템 위에서, hours-long 실행과 weeks-long 캠페인을 자동화된 에이전트가 돌리려 할 때 발생하는 실패 모드다. 코드 변경이 실제로는 no-op이거나, 데이터 window가 새거나, evaluator 시맨틱이 조용히 바뀌었거나, control과 treatment가 서로 다른 서빙 funnel을 지나가는 상황이 있다. 이런 상황에서도 캠페인 자체는 성공적으로 "끝날" 수 있는데, 결론이 유효하지 않다. EvoPilot 은 이 취약성을 human-gated verification 프로토콜로 막는다는 주장이다. 그리고 그 검증을 실증한 사례가 VDD(Video Deep Dive) MBR 시스템의 37일 캠페인이다.

지면 이름 자체는 이번 자료가 논문 코퍼스에 처음 등장시킨다(원문에서 Facebook·Instagram·Reels 지면 이름은 인용 문헌 안에만 나오고, 본문에서는 "VDD" 로만 부른다). VDD는 "hundreds of millions of users를 서빙하는 온라인 follow-on discovery 지면" 이라고만 설명된다. 유저가 seed 비디오를 열면 그 뒤로 볼 만한 비디오를 검색-랭킹 방식으로 이어 준다.

새로 알게 된 것VDD 시스템 쪽

  • 요청은 세쌍(triple) (s, q, u) 이다: seed video s, 기계가 생성한 pivot query q, user/context profile u 확인.
  • MBR (model-based retrieval) 은 downstream ranker가 아니라 dense candidate generator다. 두 단계로 f(s,q,u,d)를 근사한다: ① 두 타워 dot product 기반 ANN, ② 조건부 non-linear scoring(옵션). 확인
  • request tower Q 는 pivot query + user context + seed video의 request-side feature를 받고, candidate tower D 는 candidate video feature만 받는다. 두 벡터 모두 정규화돼서 dot product와 cosine이 같은 순서를 유도한다. 확인
  • 학습 목적: out-of-session in-batch InfoNCE가 primary 손실이다. batch 내에서 같은 세션 예시는 negative에서 제외된다(공동 참여가 negative로 오염되지 않도록). 확인
  • interaction head G(h_r, h_d, a(d))는 candidate-specific 함수로, click과 engagement-derived auxiliary label에 대한 weighted binary cross-entropy를 낸다. 이 head의 relevance output은 인터페이스 호환성용으로 남아 있지만 VDD 설정에서 학습 가중치가 0이다 확인. 총 손실은 InfoNCE + BCE 가중합.
  • 서빙 인덱스: D 타워를 servable inventory에 적용해 "hundreds of millions of videos" 규모의 ANN 인덱스를 "existing GPU platform (Xue et al., 2026)" 위에서 만들고 매 시간 갱신한다. 가중치 자체는 매 시간 재학습하지 않는다 — 임베딩과 인덱스만 매시간 새로 발행한다. 확인
  • 요청 시 ANN이 affinity a(d) 상위 P개를 뽑는다. candidate-conditioned scoring이 켜져 있으면 P개 각각에 대해 interaction head가 점수를 낸다. 그 뒤 task score 결정론적 가중합으로 top-K를 남긴다. 베이스라인은 P = K = 3000, interaction head disabled (즉 순수 two-tower ANN 결과). 확인
  • MBR 위에는 downstream retrieval funnel과 그 위의 랭커가 있다 — 이번 자료는 그 위 계층을 다루지 않는다.

새로 알게 된 것캠페인 결과와 EvoPilot 쪽

  • 캠페인 대상은 7 direction, 총 37일. VDD MBR 파이프라인 위에서 인터랙션 head, 데이터, 목적함수 등을 흔든다. 확인
  • 인터랙션 head는 원래 수동 실험에서 개선을 확인하지 못해 disabled였다. primitive autoresearch attempt는 이 direction을 다시 시도했다가 인터랙션 head가 offline hit-rate를 22 percentage points 떨어뜨린다고 결론 냈다. 잘못된 결론이었다. 확인
  • EvoPilot이 human-gated verification을 걸어서 이 drop을 추적한 결과, 원인은 인터랙션 head가 아니라 evaluation 코드가 output depth를 3,000이 아니라 600으로 계산하는 사전 결함 이었다 확인. 수정 후 matched comparison에서는 offline metric이 3.20 percentage points 개선 됐다.
  • 7일 랜덤 온라인 실험에서 VDD slice의 GSRR이 relative +0.66% 로 유의미 lift, tens of millions 계정 규모, US·Canada slice에서 계측 확인. 실험 리뷰 이후 인터랙션 head 처리가 VDD MBR의 기본 서빙 구성으로 채택됐고 manuscript cutoff 시점까지 켜져 있다. 확인
  • Post-study replay와 mutation test로 invalid 비교는 걸러 내고 valid 비교는 통과시켰다 — 즉 이번에 붙인 control이 post-hoc 재현에도 견딘다는 검증. durable state로 중단된 round를 회복해서 대략 5 GPU-hour의 아티팩트 재생성 비용을 아낀 것도 별도 실증 결과.

"We formalize a VDD request as a triple (s, q, u): the opened seed video s, the machine-generated pivot query q, and a user/context profile u. From a servable inventory 𝒟, the system must retrieve a short ranked list of videos worth watching next. Retrieval is conditioned jointly on (s, q, u). This differs from intent-driven search, which uses a user query alone, and from next-item recommendation, which uses s and u without a query, search relevance, or a retrieval funnel." — arXiv 2609.21257, 2026-09-18

"Publishing applies D to the servable inventory and builds an ANN index of hundreds of millions of videos on an existing GPU platform (Xue et al., 2026). Candidate embeddings and the index are refreshed hourly, but the neural weights are not retrained every hour." — 같은 자료

"After the experiment review, the interaction-head treatment became the default VDD MBR online configuration and remained enabled at manuscript cutoff." — 같은 자료

정본 반영 없음. VDD 지면 자체가 저장소가 추적하는 canon 서비스 목록(Facebook Feed·Instagram·Threads·Reels·X·Netflix)에 없다. 이 자료는 두 각도에서 라디에 편입한다: ① Meta 프로덕션 retrieval 스택 계층 정보의 한 축(자료 1과 함께), ② 산업계 LLM autoresearch 프로토콜의 첫 프로덕션-깊이 진술.

의미 두 가지 관점이 새롭게 잡힌다. 첫째, Meta 안에서 "search + recommendation" 이 섞인 지면(seed video + pivot query)이 자체 retrieval 스택을 가지고 있다는 것이 프로덕션 세부와 함께 처음 진술됐다. Facebook Feed(친구 그래프 축)나 Instagram Reels(재생 시퀀스 축)와 다른 축의 discovery 지면이다. 둘째, 산업계 LLM 자동 실험이 실제로 프로덕션 파이프라인 위에서 굴러가면 명세만으로는 안 되고 evaluator 코드 결함까지 잡히는 human-gated verification 층이 필요하다는 첫 케이스 스터디다. 이는 radar.md에 관찰 중인 LLM-native 랭킹의 확산 스레드와는 각도가 다르다(모델 아키텍처 안에 LLM을 넣는 것 vs 실험 자동화 위에 LLM을 넣는 것). 후자 각도의 첫 대규모 프로덕션 진술.

3ANGLE (Tencent) — 저자 소속 확인 완료 (Tencent 프로덕션 sponsored search ads)

자료 One-Step Retrieval Framework for Real-Time Sponsored Search Ads Using Hierarchical Text Representations — arXiv 2609.18296. HTML 판에서 저자 8인 전원 Tencent Inc. 이메일 도메인 @tencent.com 확인.

배경 이 자료는 daily/2026-09-20.md 레이더에서 "저자 소속 확인 유보"로 남긴 것이다. 오늘 HTML 판을 열어 소속을 확인했다. 프로덕션 소속이 확인된 만큼 radar.md의 ANGLE 항목에 소속 확인을 반영하고, 상태를 "관찰 (소속 확인 대기)" → "관찰 (Tencent 확인)" 으로 갱신한다.

정본 반영 radar.md — ANGLE 항목의 소속과 상태 라인만 갱신. Tencent WeChat/Weixin 광고와의 관계를 자료에서 명시하지는 않으므로 서비스 정본으로는 승격하지 않는다.

의미 저장소의 관찰 중 스레드 중 하나인 LLM-native 랭킹 흐름에서 Tencent가 sponsored search ads 각도로 붙는다는 근거가 추가된다. Tencent PCG의 TGR(생성 랭킹 5 지면 배포)과는 자리가 다르다 — TGR은 유기 콘텐츠 랭킹, ANGLE은 스폰서 검색 광고 retrieval 통합.

다음에 볼 것

  • Xue et al., 2026 확인 — 두 논문 모두 Meta의 "existing GPU serving platform"을 이 참조로 가리킨다. 원본 문서가 어느 지면·인프라 논문인지 확인해서 저장소의 Meta 인프라 계층 이해를 이어 붙이는 것이 관측 순서 1번.
  • VDD 지면 정체 — Facebook Watch 위인지, Reels 위 seed video 흐름인지, Instagram Explore 파생인지가 원문에서 명시적으로 갈리지 않는다. 후속 자료(공식 블로그, IR 콜, Transparency Center 카드)에서 VDD가 어떤 지면과 매핑되는지가 관측 대상.
  • GSRR 지표의 지면 범위 — 두 논문 모두 GSRR을 쓴다. VDD는 GSRR의 "VDD slice", Hybrid GPU-CPU는 "GSRR" 자체 값을 A/B 결과 metric으로 사용한다. 이 지표가 Meta의 통합 검색 지면 전체를 커버하는 metric인지, 각 지면마다 slice로 갈리는지가 확인 대상.
  • Meta의 personalized search에 대한 후속 진술 — Que2Search(2021) 이후 오랜 갭이 열린 뒤 이번에 두 편이 붙어 나왔다. 이어지는 KDD 2027 accepted 논문 목록에 Meta search 인프라 진술이 더 있는지 확인 대상.
