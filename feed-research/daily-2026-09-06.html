    새로 알게 된 것

    A. Cold-start experiment에 codivert impression 패턴이 배선됐다 — 두 arm이 동일한 experiment bucket impression을 남기게 강제

    Codivert는 X 내부 용어로 보인다 [추정](bucket 관측 시점을 두 arm에서 동일하게 맞춰서 A/B 분석에 편향이 들지 않게 하는 패턴, "co-divert"는 두 arm이 같은 시점에서 각자 분기한다는 의미). 이번 커밋은 이 패턴을 코드로 구체화했다.

    신규 param 두 개 [확인] — home-mixer/scorers/author_cold_start.rs, home-mixer/params/param.rs:

    • rust_home_mixer_phoenix_moe_codivert_viewer_is_control (bool, default false)
    • rust_home_mixer_phoenix_moe_codivert_viewer_is_treatment (bool, default false)

    두 param은 moe_codivert_viewer experiment의 bucket membership으로 흘러 들어온다. YAML rule의 짝은 다음과 같이 대칭적이다:

    - description: "co-divert viewer treatment"
  query: >
    [moe_codivert_viewer bucket_membership treatment]
  values:
    rust_home_mixer_phoenix_moe_codivert_viewer_is_treatment: true
    rust_home_mixer_phoenix_moe_codivert_viewer_is_control: false
    rust_home_mixer_enable_viewer_cold_start_boost: true
- description: "co-divert viewer control"
  query: >
    [moe_codivert_viewer bucket_membership control]
  values:
    rust_home_mixer_phoenix_moe_codivert_viewer_is_treatment: false
    rust_home_mixer_phoenix_moe_codivert_viewer_is_control: true
    rust_home_mixer_enable_viewer_cold_start_boost: false

    — home-mixer/scorers/author_cold_start.rs 테스트 fixture, 2026-09-04

    핵심 배선: AuthorColdStart::apply가 실행 순서를 재정렬 [확인] — home-mixer/scorers/author_cold_start.rs. 이전 판(4세대+3까지)에서는 이렇게 흘렀다:

    1. ColdStartTrackedIds 조회 + record_tracked_ids 호출
    2. EnableViewerColdStart가 false면 여기서 조기 반환
    3. viewer_arm(query) 호출(experiment bucket 실 조회, 이때 첫 impression이 남음)
    4. author_corpus(...) 호출(author bucket 실 조회, 이때 author-side impression이 남음)
    5. cold-start 로직 실행

    문제는 2단계 조기 반환이었다. EnableViewerColdStart=false인 control arm은 3·4단계를 아예 밟지 않는다. 그러면 experiment analysis에서 두 arm의 impression 로그 shape 자체가 달라진다. Treatment는 viewer bucket + author bucket을 모두 관측한 사용자만 세고, control은 관측 자체가 아예 없다. 이렇게 되면 triggered-analysis(파이프라인에 실제로 진입한 사용자만 비교)와 intent-to-treat(할당된 모든 사용자를 비교) 사이의 정의가 어긋나고, 파이프라인 진입 편향이 lift 추정을 오염시킨다.

    이번 커밋의 재정렬은 다음과 같다:

    1. ColdStartParams::read(query)가 모든 param을 한 번에 읽고(이 시점에 viewer_arm도 함께 호출돼 viewer bucket impression이 남음), params.arm으로 저장.
    2. record_tracked_ids(candidates, &params.tracked_ids) 호출.
    3. params.arm이 Control 또는 Treatment이면(즉 어느 arm이든 codivert에 속하면), enabled 여부와 무관하게 author_corpus(...)를 호출해 author-side bucket impression을 남긴다.
    4. 그 다음에 !params.enabled이면 scores 원본을 그대로 반환하는 조기 반환. Impression이 이미 남은 뒤이므로 관측 로그는 두 arm에서 대칭.
    5. cold-start 로직 실행.

    즉 control이든 treatment든 (a) moe_codivert_viewer bucket 관측을 정확히 3회, (b) moe_exp(author 대상) bucket 관측을 정확히 2회 남긴다. 관측 count가 arm과 무관하게 같아야 한다는 대칭성이 assertion으로 잠긴 것.

    의미 — canon 이전 판은 4세대+1(2026-08-14) Thompson sampling 배선과 4세대+3(2026-08-18) count_tracked_ids 단순화까지 알았고, 이 두 흐름은 콜드스타트 로직의 진화였다. 이번 커밋은 처음으로 콜드스타트의 A/B 관측 방법론 자체를 코드로 잠근다. SpyingBucketImpressor라는 테스트 유틸(experiment SDK가 노출한 impression 계측 스파이)의 존재까지 드러난다. X가 A/B 실험에서 bucket 관측 대칭성을 회귀 테스트로 강제한다는 문화 관찰이 canon에 붙는다.

    B. Cold-start Treatment 후보 필터가 Phoenix MoE 후보만 남기도록 좁혀졌다

    [확인] — home-mixer/scorers/author_cold_start.rs:

    fn cold_start_corpus_eligible(arm: ViewerArm, c: &PostCandidate, corpus: AuthorCorpus) -> bool {
    match arm {
        ViewerArm::Holdout => !is_phoenix_moe(c),
        ViewerArm::Control => corpus == AuthorCorpus::Control && !is_phoenix_moe(c),
        ViewerArm::Treatment => corpus == AuthorCorpus::Treatment && is_phoenix_moe(c),
    }
}

    이전 판은 ViewerArm::Treatment 분기가 corpus == AuthorCorpus::Treatment 조건만 확인했다. 이번 커밋에서 && is_phoenix_moe(c)가 추가됐다. Treatment 뷰어의 cold-start 후보는 이제 (a) treatment corpus author의 포스트이면서 (b) served_type == ForYouPhoenixRetrievalMoe인 후보만이다.

    테스트도 이름부터 바뀌었다:

    • 이전: treatment_viewer_keeps_treatment_moe_and_cold_starts_treatment_corpus
    • 이번: treatment_viewer_cold_starts_treatment_moe_only [확인] — home-mixer/scorers/author_cold_start.rs

    즉 treatment corpus author의 포스트라도 Phoenix MoE 소스에서 온 것이 아니면 cold-start boost 대상에서 제외된다. cold_start_candidate(...)가 아니라 moe_candidate(...)로 fixture가 대체된 것도 같은 의미다.

    의미 — Phoenix MoE와 cold-start를 하나의 codivert 실험 안에 묶어 서로 confounded되지 않게 하려는 배선이다. Treatment 뷰어는 (a) MoE 배선을 활성화하고 (b) cold-start도 MoE 후보에만 적용해서, "MoE의 효과"와 "cold-start 부스트의 효과"가 겹치지 않게 격리한다. enable_viewer_cold_start_boost가 treatment에서 true·control에서 false로 YAML에 못 박힌 것도 같은 방향이다. Cold-start는 이제 Phoenix MoE의 실 트래픽 실험 옆칸에 재배치됐다.

    C. Engagement counts hydration이 cold-start 게이팅과 분리됐다

    [확인] — home-mixer/candidate_hydrators/engagement_counts_hydrator.rs:

    • 이전: fn enable(&self, query) -> bool { query.params.get(EnableViewerColdStart) || (!query.has_cached_posts && (query.params.get(EnableEngagementCountsHydration) || query.is_shadow_traffic)) }
    • 이후: fn enable(&self, query) -> bool { query.params.get(EnableEngagementCountsHydration) || query.is_shadow_traffic }

    세 가지 변화가 있다: (a) EnableViewerColdStart 종속 제거, (b) !query.has_cached_posts 게이팅 제거(캐시가 있어도 항상 갱신), (c) 정책 축이 순수 hydration flag + shadow traffic으로 좁혀졌다. Cold-start와 engagement counts hydration은 이제 서로 독립적 정책 축이다.

    의미 — 이전 배선은 "cold-start가 켜지면 반드시 engagement counts를 hydrate한다"는 강결합이었다. Cold-start Thompson sampling이 view_count_on_home·fav_count에 의존하는 4세대+1의 초기 배선 유물로 보인다. 이번 분리로 두 파이프라인의 rollout이 서로 걸림 없이 진행된다. 특히 codivert 대칭성(A절)과 결합하면 "Treatment는 cold-start 켜짐 + engagement counts 켜짐, Control은 cold-start 꺼짐 + engagement counts는 자기 flag대로"라는 명확한 실험 축 분리가 가능해진다.

    D. Phoenix serving 요청 계약에 experiment_overrides map과 SlateContext.exact_k/exact_gap 추가

    [확인] — phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto, phoenix/python/common/xai-proto/proto/recsys.proto:

    **PredictNextActionsRequest.experiment_overrides = 21**은 map<string, string> 타입의 새 필드다. 이전엔 Phoenix 서빙이 서비스 배포 시점의 config·feature switch로 experiment 파라미터를 정해 뒀는데, 이 필드가 붙으면 요청마다 experiment 파라미터를 오버라이드할 수 있다. Home-mixer(요청자)가 자기가 이미 A/B 배정된 결정을 Phoenix에 그대로 전달해 downstream(Phoenix)의 experiment 배정이 upstream(home-mixer)과 일관되게 흐르도록 하는 배선으로 읽힌다 [추정]. Codivert 패턴(A절)이 upstream에서 자리를 잡으면서 downstream까지 동일한 experiment 스코프를 지도록 전달 채널이 필요해진 것.

    **SlateContext.exact_k = 16과 SlateContext.exact_gap = 17**은 새 Option<uint32> 필드다. 이전 SlateContext 필드는:

    • sid_known (필드 6), sid_k_l1/2/3 (7–9), sid_gap_l1/2/3 (10–12) — 4세대+3(2026-08-18) VMRanker에서 SID 배선
    • recon_cos_milli (13) — 4세대+9(2026-08-26)
    • recon_count_above (14), recon_gap_above (15) — 4세대+11 무렵

    exact_k/exact_gap는 이 시리즈의 연장이다. sid_k/sid_gap이 semantic ID 코드북 매치 기반 metric이라면, exact_k/exact_gap는 이름 그대로 정확 일치 기반 metric일 가능성이 높다 [추정]. Slate 안의 후보 사이에서 특정 신호(post_id? 저자? 미디어 hash?)가 정확 일치하는 이웃 후보 수(exact_k)와 정확 일치가 나타나기 시작하는 slot 갭(exact_gap)으로 해석하는 것이 SID 계열 필드와 자연스러운 대응이다. 실제 정의는 미공개(Phoenix 서빙 코드가 이 필드를 채우는 곳은 오픈소스에 없음).

    Home-mixer 쪽에서도 대응 필드가 배선됐다 [확인] — home-mixer/models/candidate.rs. SlateContext struct와 From<xai_recsys_proto::SlateContext> 변환 impl 양쪽에 exact_k: Option<u32>, exact_gap: Option<u32> 두 필드가 추가됐다.

    의미 — Phoenix serving이 slate context에 관측 metric을 계속 추가하는 흐름이 이어진다. SID 계열(4세대+3)에서 시작해 recon 계열(4세대+9~+11)로 확장됐고, 이번엔 exact 계열이 붙었다. 소비 경로(RankingScorer 폴백)는 이미 4세대+5 UseServedSlateContext 게이트에 배선돼 있으니, 새 metric이 붙어도 자동으로 흡수된다. experiment_overrides는 upstream/downstream experiment 스코프 일관성 이슈에 대한 계약적 대응으로, codivert 배선(A절)과 시점이 겹치는 게 우연이 아니다.

    F. CoreFeature.text가 예정된 muted-keyword rule을 위해 dead-code로 보존됐다

    [확인] — visibility-filtering/models/tweet.rs:

    #[derive(Clone, Debug, Default)]
pub struct CoreFeature {
    #[cfg_attr(
        not(test),
        expect(dead_code, reason = "retained for the upcoming muted-keyword rule")
    )]
    pub text: String,
    pub source_tweet_id: Option<u64>,
}

    — visibility-filtering/models/tweet.rs, 2026-09-04

    즉 VF 서비스가 hydration 단계에서 각 tweet의 text를 이미 채우고 있지만 현재 어떤 rule도 그것을 소비하지 않는다. Dead-code 억제 어트리뷰트가 명시적으로 "upcoming muted-keyword rule에 쓰기 위해 남겨 둔다"고 밝힌다. 새 테스트 assemble_hydrates_text_from_core_data가 hydration 경로에서 text가 실제로 채워지는지 회귀로 잠근다.

    4세대+4(2026-08-19, aad7179)에서 신설된 FollowingViewerMutedKeywordFilter는 Following 파이프라인 전용(65줄)이었다. 이번 signal은 VF 서비스 자체에도 muted-keyword rule이 곧 붙는다는 예고다. VF는 For You 파이프라인 전역을 커버하므로, 뷰어의 muted-keyword 리스트가 Following뿐 아니라 추천 전체에서 필터되는 정책 확장 방향이다.

    의미 — Muted keyword 필터가 두 파이프라인에서 별개로 구현되던 것이 통합되거나(Following 필터가 VF 서비스로 이관), 아니면 병렬 두 층 배선으로 남을지가 다음 커밋의 관측 포인트다.
