    이 다섯 축은 서로 독립이지만, 하나의 커밋으로 묶여 올라온 점에서 대략 같은 시기의 프로젝트라는 신호다. 이 절에서는 축마다 무엇이 바뀌었는지와 지금까지의 이해가 어떻게 이동하는지를 순서대로 정리한다.

    A. VMRanker DPP — seed_tweet_id pinned anchor

    vm-ranker/dpp.rs의 rescore 시그니처가 새 seed 인자를 받도록 확장됐다:

    pub fn rescore(
    inputs: &[DppInput],
    seed: Option<&DppInput>,
    config: &DppConfig,
    _viewer_id: u64,
) -> Vec<DppResult> { ... }

    동작은 다음 4단계다. (1) 확장된 kernel 구성: 기존 top-K 후보(m = min(inputs.len(), max_selected_rank))에 seed 하나를 더한 total = m + 1 크기의 kernel을 만든다. seed의 q 값은 임의로 1.0으로 고정한다(score가 없으므로). (2) greedy DPP의 첫 슬롯 pinning: greedy_dpp가 이전엔 kernel diagonal이 가장 큰 인덱스를 시작점으로 선택했는데, 새 인자 pinned_first: Option<usize>가 주어지면 그 인덱스를 강제 첫 선택으로 쓴다. 이 인덱스가 seed의 위치다. (3) 예산 확장: pinned가 있으면 max_items = (k + 1).min(n)으로 늘려서 seed가 top_k를 잡아먹지 않게 한다. (4) 결과에서 seed 필터링: 최종 리턴 전에 dpp_result.selected.iter().filter(|&(ki, _)| ki < m)로 seed 인덱스를 배제한다.

    이 4단계로 나타나는 순 효과는 다음 두 가지 계약이다:

    • seed의 임베딩과 가까운 후보는 kernel의 오프대각 항이 커져 결정성(determinantal) 이득이 감소하고, 결과에서 배제될 확률이 올라간다.
    • seed 자체는 결과에 나타나지 않고 top_k도 소진하지 않는다.

    새 테스트 두 개가 이 계약을 잠근다:

    #[test]
fn seed_suppresses_near_duplicate() {
    let seed = make_input(999, 0.0, &[1.0, 0.0]);
    let inputs = vec![
        make_input(1, 10.0, &[1.0, 0.0]),   // seed와 정확히 같은 방향
        make_input(2, 5.0, &[0.0, 1.0]),    // 직교
    ];
    // seed 없이 rescore하면 ids에 1과 2가 모두 들어감
    // seed와 함께 rescore하면 1은 배제, 2만 살아남고 999도 결과에 없음
}

#[test]
fn seed_does_not_consume_top_k_budget() {
    let seed = make_input(999, 0.0, &[0.0, 0.0, 1.0]);
    let inputs = vec![
        make_input(1, 10.0, &[1.0, 0.0, 0.0]),
        make_input(2, 5.0,  &[0.0, 1.0, 0.0]),
    ];
    let config = DppConfig { top_k: 2, ... };
    let result = rescore(&inputs, Some(&seed), &config, 0);
    assert_eq!(result.len(), 2, "seed must not eat top_k budget");
}

    vm-ranker/scoring/dpp_model.rs의 rank가 이 새 파라미터를 어떻게 채우는지도 정의된다:

    fn build_seed_input(req: &RankRequest, ctx: &DppContext) -> Option<DppInput> {
    if req.seed_tweet_id == 0 { return None; }
    match ctx.store.client.get(req.seed_tweet_id) {
        Some(embedding) => {
            DPP_SEED_CONTEXT.with_label_values(&["pinned"]).inc();
            let norm = l2_norm(&embedding);
            Some(DppInput {
                id: req.seed_tweet_id,
                score: 0.0,
                embedding,
                norm,
                embedding_missing: false,
            })
        }
        None => {
            DPP_SEED_CONTEXT.with_label_values(&["embedding_missing"]).inc();
            None
        }
    }
}

    즉 seed의 임베딩이 서빙 시점 스토어에 없으면 pinning 없이 기존 경로로 흐른다. vm_ranker_dpp_seed_context_total{result="pinned"|"embedding_missing"} 카운터가 hit·miss를 분리 관측한다.

    pinned = pinned_first.filter(|&p| kernel[p * n + p] > EPSILON); — vm-ranker/dpp.rs

    임베딩 norm이 0에 가까워 kernel diagonal이 EPSILON 이하면 pin을 포기하고 기존 greedy 경로로 돌아간다.

    어디에 쓰이는가는 이번 커밋만으로는 확정할 수 없다. seed_tweet_id를 실어 주는 홈믹서 파이프라인은 이번 diff에 없다. 자연스러운 소비처 후보는 (1) permalink 페이지의 related tweets — "이 tweet과 이질적인" 슬레이트, (2) 특정 tweet의 "more like this" 흐름의 대안 컬렉션, (3) 스레드 컨텐츠에서 부모 tweet을 seed로 두고 유사한 리플라이를 억제하는 시나리오 등이다 [추정]. 홈 타임라인의 For You 자체가 이 필드를 채워 주는지는 관측 대상이다 — For You는 이론상 seed가 없는 slate 생성이지만, 최근에 본 tweet을 seed로 실어 반복 노출을 줄이는 확장이 논리적으로 가능하다.

    B. Phoenix 후보 점수 로그 — Thrift와 proto의 병렬 발행

    home-mixer/side_effects/phoenix_experiments_side_effect.rs가 이제 후보 하나마다 두 페이로드를 만들어 tokio::join!으로 두 Kafka publisher에 동시에 쓴다.

    첫 페이로드는 기존 Thrift ScoredCandidate다. 이 스트림은 4세대+3(11a71f8, 2026-08-18)의 v3 스키마 이래로 유지되고 있고, 필드는 prediction_scores: Option<BTreeSet<Box<PredictionScore>>>처럼 정렬된 컬렉션이다. Kafka 토픽 PHOENIX_SCORES_TOPIC, cluster Aiml.

    두 번째 페이로드가 이번 커밋의 신설이다. proto LoggedScoredCandidate:

    두 페이로드는 서로 다른 자료구조로 다시 정렬된다:

    let mut prediction_scores = HashMap::new();
for (cluster_id, result) in &experiment_results {

    insert_cluster_scores(&mut prediction_scores, &cluster_name, &scores);

let thrift_scores: BTreeSet<Box<PredictionScore>> = prediction_scores

    즉 파이프라인이 내부적으로 HashMap<String, f64>를 만들어 놓고, Thrift 페이로드용으로만 BTreeSet으로 정렬해서 wrap하고, proto 페이로드는 HashMap을 그대로 map으로 실어 보낸다.

    의미: prediction_scores의 map 표현은 wire 크기(정렬 인덱스 제거)와 소비 측 조회 비용(BTreeSet 대신 map으로 O(1) 조회) 두 축에서 이득이다. Thrift 스트림을 유지하는 것은 다운스트림 소비자가 즉시 스위치할 수 없기 때문이고 [추정], 두 스트림이 병렬로 유지될 이행기가 얼마나 지속되는지는 이번 커밋에 없다.

    키 명명 규약(phoenix.<cluster_name>.<action_name>)과 스코어 필드 집합(28개 참여 헤드 + pdwell 별칭)은 그대로 유지된다. 테스트도 새 헬퍼 insert_cluster_scores와 build_logged_scored_candidate에 대해 각각 붙었다.

    C. VF 클라이언트 발견 — xDS LDS listener 경유로 이관

    visibility-filtering/server_deps.rs가 이전 코드에서는 이런 모양이었다:

    // 이전 (~fee1d0f)
let tes_client = Arc::new(
    init_client_with_retry("tes", init_deadline, || {
        ProdTESClient::new_with_config(
            None,
            datacenter,
            None,
            tes_client_config(deterministic_aperture),
        )
    }).await
);
// tes_client_config는 TESClientConfig 구조체를 반환:
// aperture_size, deterministic_aperture, lb_policy, readiness_probe_port,
// request_timeout_ms, enable_serve_within 등 필드를 채운다.

    즉 클라이언트 조립에 필요한 파라미터 뭉치가 서비스 crate(xai_core_entities::tweet_entity_service_client::TESClientConfig) 안에 정의된 구조체로 격리되어 있었고, 서비스 이름은 datacenter 문자열로 hostname 템플릿을 채워 만들었다.

    이번 커밋에서는 다음처럼 바뀌었다:

    build_xds_strato가 새 헬퍼로 등장하고, 이 헬퍼가 xai_x_rpc::grpc_client::ChannelBuilder로 gRPC 채널을 조립한다:

    async fn build_xds_strato(
    params: XdsStratoParams,
    deterministic_aperture: bool,
) -> anyhow::Result<StratoGrpc> {
    let mut builder = ChannelBuilder::new(params.name)
        .tls(TlsMode::mtls_from_env()?.with_domain_override(params.tls_domain))
        .request_timeout(STRATO_REQUEST_TIMEOUT)     // = HYDRATION_TIMEOUT (390 ms)
        .connect_timeout(STRATO_CONNECT_TIMEOUT)     // 400 ms
        .xds(StartFrom::Lds(params.xds_listener.to_string()))
        .await?
        .eager_resolution(XDS_EAGER_RESOLUTION_TIMEOUT)  // 5 s
        .aperture(STRATO_APERTURE_SIZE)              // 12
        .readiness_probe(READINESS_PROBE_PORT, "/ready")
        .buffer_max_wait(DEFAULT_BUFFER_MAX_WAIT)
        .total_timeout(DEFAULT_TOTAL_TIMEOUT);
    if deterministic_aperture { builder = builder.deterministic(); }
    let channel = builder.build_load_balanced(params.lb_policy).await?;
    let mut strato = StratoGrpc::from_load_balanced_channel(
        channel, None, Some(params.client_id),
        params.retry_config, params.max_batch_size,
    );
    if params.enable_serve_within {
        strato = strato.with_op_context(xai_strato::strato_proto::OpContext {
            serve_within: Some(xai_strato::strato_proto::ServeWithin {
                duration_microseconds: STRATO_REQUEST_TIMEOUT.as_micros() as i64,
                round_trip_allowance_microseconds: 10_000,
            }),
            ..Default::default()
        });
    }
    Ok(strato)
}

    핵심은 .xds(StartFrom::Lds(params.xds_listener)) 한 줄이다. xDS(x Discovery Service) 프로토콜의 **LDS(Listener Discovery Service)**를 리스너 이름 ("tweet-entity-service.prod.tweet-entity-service:fed-grpc" 등)으로 시작점 삼아 xDS control plane과 talking해 endpoint 리스트를 받는다. Envoy 계열 서비스 메시에서 클라이언트가 컨트롤 플레인에서 대상 endpoint 리스트를 동적으로 받는 표준 방식이다.

    TES 경로에만 붙는 옵션이 두 개 있다: (a) enable_serve_within: true로 서버측에 데드라인 힌트(요청이 서버 큐잉에서 얼마나 오래 대기해도 되는지)를 실어 준다. duration_microseconds는 클라이언트 timeout과 같은 값(HYDRATION_TIMEOUT = 390 ms), round_trip_allowance_microseconds = 10_000(왕복 여유분 10 ms). (b) retry_config: Some(RetryConfig::for_idempotent())로 idempotent 요청에 대해 자동 재시도.

    Gizmoduck 경로는 lb_policy가 least_request()고 위 두 옵션이 모두 꺼져 있다. [확인] — server_deps.rs.

    결과의 의미: (1) 서비스 발견 계층이 hostname 템플릿에서 xDS control plane 경유로 옮겨졌다. (2) TESClientConfig·GizmoduckClientConfig처럼 서비스 crate가 export하던 별도 client-config 구조체가 사라지고, 클라이언트 조립 로직이 VF 서비스 자신의 server_deps.rs로 흡수됐다. (3) L2 cache warmer의 Strato 클라이언트도 이제 deterministic_aperture 플래그를 받는다. (4) TES_READINESS_PROBE_PORT와 GIZMODUCK_READINESS_PROBE_PORT가 둘 다 8081이었으므로 통합 상수 READINESS_PROBE_PORT: u16 = 8081로 합쳐졌다.

    4세대+19의 HYDRATION_TIMEOUT 통일이 여기까지 파급됐다는 관점으로도 읽힌다 — 이번엔 클라이언트 조립 코드에서 timeout 상수가 STRATO_REQUEST_TIMEOUT: Duration = crate::hydration::HYDRATION_TIMEOUT로 참조된다.

    E. VF CompactAuthorFeatures — 8-byte NonZeroU64 packing (미배선)

    4세대+19가 AuthorLabelSet(HashSet<LabelValue>) → AuthorLabelSet(u64)로 라벨 표현을 64-bit bitset으로 줄이면서 AuthorFeatures 전체를 16 바이트 Copy 구조체로 잠갔다. 이번 커밋은 그것을 다시 8 바이트로 줄이는 표현을 준비했다:

    #[allow(dead_code)]
pub(crate) struct CompactAuthorFeatures(NonZeroU64);

const COMPACT_PRESENT_BIT: NonZeroU64 = match NonZeroU64::new(1 << 63) {
    Some(bit) => bit,
    None => unreachable!(),
};
const COMPACT_LABEL_SHIFT: u32 = 8;
const COMPACT_LABEL_MASK: u64 = (1 << (63 - COMPACT_LABEL_SHIFT)) - 1;

    레이아웃은 다음과 같다:

    비트 위치 내용
    63 present 마커 (항상 1)
    0~6 7개 계정 상태 flag (is_suspended, is_deactivated, is_protected, is_nsfw_user, is_nsfw_admin, is_erased, is_offboarded)
    7 미사용
    8~62 55-bit label bitset (실제 사용은 11 bit — 4세대+19의 AuthorLabel 11 variant와 1:1)

    to_compact와 from_compact 라운드트립이 함께 정의되고, 테스트가 flag 조합 128개(1 << 7)와 label 조합 2048개(1 << 11)를 모두 exhaustively 검증한다 — 총 262,144 조합. Option<CompactAuthorFeatures>의 크기도 정확히 8 바이트임을 assert한다(NonZeroU64의 niche 최적화가 None을 all-zero로 표현해 별도 태그가 필요 없다).

    #[allow(dead_code)]가 붙어 있으니 이번 커밋에서 소비자는 없다. 어디에 배선될지의 후보는 (1) 4세대+19에 신설된 clock_cache.rs(32-way × 64-shard CLOCK 캐시)의 값 타입 — 이 캐시는 V: Copy를 요구하고 8-byte 값에 최적화되어 있다 [추정], (2) Gizmoduck 하이드레이터의 hot-path 캐시, (3) AuthorFeatures의 wire 표현 자체 등이다. 다음 커밋에서 어느 소비자로 배선되는지가 관측 대상.

    의미: 4세대+19의 HYDRATION_TIMEOUT 상향(80/100 → 390 ms)이 지연 예산을 늘리는 방향이었다면, 이 축은 캐시 hit rate와 hot-path 자료구조 크기를 줄이는 방향이다. VF 서비스가 실 지연을 낮추기 위한 두 방향 프로젝트가 병행 중이라는 신호로 읽힌다 — timeout을 늘려 부분 판정 성공률을 높이고, 라벨/피처 표현을 좁혀 캐시 밀도를 높인다.

    F. VF worldwide takedown 규칙 세밀화

    visibility-filtering/rules/context.rs가 두 조각을 다듬었다.

    첫 조각: legal_takedown_country가 이제 LegalRequest { country_code: "xy" }를 명시적으로 None으로 리턴한다. 즉 world-wide copyright 코드로 표시된 legal request는 이제 DropLegalTakendownPostRule을 트리거하지 않는다.

    fn legal_takedown_country(reason: &TakedownReason) -> Option<&str> {
    match reason {
        TakedownReason::LegalRequest { country_code }
            if country_code.eq_ignore_ascii_case(WORLDWIDE_COPYRIGHT_COUNTRY_CODE) =>
        {
            None
        }
        TakedownReason::LegalRequest { country_code }
        | TakedownReason::UnspecifiedReason { country_code } => Some(country_code),
        TakedownReason::Dmca => Some(WORLDWIDE_COPYRIGHT_COUNTRY_CODE),
        _ => None,
    }
}

    DMCA는 여전히 "xy"를 리턴하므로 DMCA-기반 world-wide 저작권 takedown은 유지된다. 즉 "xy" 코드는 이제 DMCA reason으로 도착한 경우에만 legal takedown을 트리거하고, LegalRequest로 도착한 경우에는 무시된다.

    둘째 조각: local_laws_takedown_country가 이제 BystanderReport { country_code: "xx" } 또는 "xy"를 None으로 리턴한다:

    fn local_laws_takedown_country(reason: &TakedownReason) -> Option<&str> {
    match reason {
        TakedownReason::BystanderReport { country_code } if !is_worldwide_code(country_code) => {
            Some(country_code)
        }
        _ => None,
    }
}

    즉 bystander 신고 중 world-wide 스코프만 붙은 것은 더 이상 DropLocalLawsTakendownPostRule을 트리거하지 않는다. 국가 코드가 실제로 지정된 bystander 신고만 local laws rule이 소비한다.

    새 테스트 3개(legal_takedown_copyright_code_allows_without_viewer_country, unspecified_takedown_worldwide_drops_without_viewer_country, local_laws_takedown_worldwide_allows_any_viewer)가 이 규칙을 골든 코퍼스에 잠근다.

    의미: 4세대+12(6384ca7, 2026-09-01)에서 국가 스코프 처리를 원본으로 도입한 이후 처음의 실질적 정책 완화다. UnspecifiedReason은 여전히 worldwide여도 drop이 유지되므로, 완화는 두 갈래에만 적용된다:

    • LegalRequest{"xy"} → 이전 drop, 이제 allow. "xy"는 저작권 코드로 예약되어 있으므로, legal 채널로 저작권 관련 요청이 도착해도 실제 판정 근거는 DMCA reason이 별개로 도착할 때에만 성립하도록 정리한 것.
    • BystanderReport{"xx"} 또는 BystanderReport{"xy"} → 이전 drop, 이제 allow. bystander 신고는 국가 코드가 명확해야만 rule에 물린다.

    이 두 완화는 이전 규칙이 world-wide 스코프에 대해 지나치게 광범위했다는 인식이 있었음을 시사한다. 실제로 이 조건들이 프로덕션에서 얼마나 자주 발생했는지, 그리고 어떤 크리에이터가 영향을 받았는지는 이 코드만으로는 알 수 없다.

    phoenix/xrex/data/streaming/kafkaconsumer.py에 새 dataclass가 붙었다:

    @dataclasses.dataclass(frozen=True)
class KafkaAuth:
    mode: str                       # "mtls" or "sasl"
    ca_path: str | None = None
    cert_path: str | None = None
    key_path: str | None = None
    sasl_mechanism: str | None = None
    sasl_username: str | None = None
    sasl_password: str | None = None
    verify_broker: bool = False

    @classmethod
    def mtls(cls, ca_path, cert_path, key_path, verify_broker=False): ...
    @classmethod
    def sasl(cls, mechanism, username, password): ...

    def ssl_context(self) -> ssl.SSLContext: ...
    def consumer_kwargs(self) -> dict[str, Any]: ...

    kafkaloader.py의 auto_detect_auth가 다음 순서로 인증 방식을 정한다:

    1. KAFKA_AUTH env var이 "sasl"이면 강제 SASL(mTLS 인증서 검사 skip).
    2. KAFKA_MTLS_CERTS_DIR(기본 /root/client-certs)에 세 파일(ca-bundle.crt, client.fullchain, client.key)이 모두 있으면 mTLS.
    3. client 인증서와 key만 있고 CA bundle이 없으면 KAFKA_MTLS_PLATFORM_CA_BUNDLE(기본 /etc/ssl/internal-ca/ca-bundle.crt) 또는 시스템 truststore(ssl.get_default_verify_paths().cafile)를 truststore로 삼아 mTLS.
    4. SASL_PLAIN_PASSWORD가 있으면 SASL/SCRAM fallback.
    5. 셋 다 실패면 에러.

    이전 코드는 3개 소비자 경로(discover_partition_count, _consumer_poll_loop, _consume_multi_consumer)에서 각각 ssl.create_default_context() + SASL_SSL protocol을 하드코딩했는데, 이번 커밋이 세 경로 모두 새 auth.consumer_kwargs()로 옮겼다.

    의미: Phoenix 학습 파이프라인이 소비하는 recsys 액션 스트림 Kafka(4세대+3의 v3 스키마 이래로 SASL/SCRAM으로 붙어 왔다)가 mTLS로도 붙을 수 있게 됐다. 클러스터 운영 정책의 이관(비밀번호 관리 인프라 → 인증서 관리 인프라)으로 읽힌다 [추정] — 실제 어느 쪽이 프로덕션에서 채택됐는지는 이 코드만으로는 알 수 없다.
