    A. 랭킹 스코어러 per-head weight perturbation [확인]

    [확인] — home-mixer/scorers/ranking_scorer.rs, home-mixer/params/param.rs.

    신규 param 두 개 — WeightPerturbationSigma(f64, default 0.0)와 WeightPerturbationSalt(String, default ""). 헤더 sync 시각도 2026-09-04T16:22:24Z → 2026-09-08T16:24:06Z로 갱신됐다.

    핵심 배선 — ScoringWeights::from_params(&query.params) 뒤에 .perturbed(query)가 붙었다. perturbed() 자체 로직은:

    pub(crate) fn perturbed(mut self, query: &ScoredPostsQuery) -> Self {
    let sigma = query.params.get(WeightPerturbationSigma);
    if sigma <= 0.0 {
        return self;
    }
    let salt = query.params.get(WeightPerturbationSalt);
    for (head, weight) in self.weights_mut() {
        *weight *= (sigma * perturbation_sign(&salt, query.user_id, head)).exp();
    }
    self.recompute_sums();
    self
}

pub(crate) fn perturbation_sign(salt: &str, user_id: u64, head: &str) -> f64 {
    let digest = md5::compute(format!("{salt}:{user_id}:{head}"));
    if digest[0] & 1 == 1 { 1.0 } else { -1.0 }
}

    흔들리는 헤드 26개 — favorite·reply·retweet·photo_expand·video_open·click·open_link·profile_click·vqv·share·share_via_dm·share_via_copy_link·dwell·quote·quoted_click·quoted_vqv·dwell_time·click_dwell_time·active_secs_5m_residual_norm·follow_author·post_unexplored·not_interested·block_author·mute_author·report·not_dwelled. 즉 4세대 랭커의 core positive 17헤드(engagement)와 negative 5헤드(user feedback), 그리고 continuous 3헤드(dwell·click_dwell·active_secs)가 전부 대상이다. 가중치가 흔들리면 positive_sum·negative_sum·total_sum도 함께 재계산(recompute_sums())돼 downstream 게이팅 로직(예: not_dwelled 페널티의 total_sum 스케일링)이 흔들린 값을 그대로 반영한다.

    동작의 성격. 부호가 md5(salt:user_id:head)에 의존하므로:

    • 같은 salt, 같은 유저 → 같은 부호 (요청 사이에 결정론적).
    • 같은 salt, 같은 유저 → 헤드마다 독립적인 부호 (헤드 26개가 서로 다른 방향으로 흔들림).
    • salt를 바꾸면 유저별 배치가 통째로 뒤바뀜 (재현성 있으면서도 salt cycling으로 exploration 재개 가능).
    • 계수 배율은 exp(sigma × sign) = exp(±sigma)이므로 σ=0.1이면 가중치가 약 ±10.5%, σ=0.3이면 약 ±35% 방향으로 흔들린다. 지수 스케일이므로 곱셈 대칭이 보장되고(σ=0.1의 up과 down이 정확히 곱셈 역수 관계) log-space에서 대칭 분포를 만든다.

    해석 (부분 [확인] + [추정]). 이건 세 가지로 읽힐 수 있다:

    1. 가중치 A/B의 gradient-free 인프라 — 프로덕션 유저 트래픽으로 가중치 조합의 sensitivity를 재는 wobble 실험. WeightPerturbationSalt를 실험 arm마다 다르게 세팅하면 arm별로 독립적인 노이즈 프로필. [확인]이 계약 자체이고 A/B용 사용은 [추정].
    2. On-policy exploration / bootstrap-style bandit — VMRanker 이전 단계에서 스코어 자체를 흔들어 impression 다양화를 강제. Bandit에서 UCB보다 Thompson sampling에 가까운 형태(posterior 대신 fixed noise, 그러나 유저-헤드 조합마다 결정론). [추정].
    3. 모델 편향 감사 / robustness 측정 — 가중치가 흔들려도 모델 점수가 안정적으로 어떤 헤드에 의존하는지 관측하는 도구. [추정].

    전제되는 사실. default가 0.0이므로 프로덕션 기본은 여전히 결정론이다. 이 계약이 옵션으로 존재한다는 것 자체가 신호다: 4세대는 지금까지 EnableViewerColdStart(Thompson)·ValueModelMode(dwell_regret_sigmoid) 같은 개별 게이트로 stochasticity를 도입했는데, 이제 참여 헤드 가중치 전체를 대상으로 하는 통합된 stochastic layer를 붙였다. 4세대+16의 codivert impression 대칭 배선과 결이 같다: A/B 인프라 자체가 4세대에서 계속 두꺼워지고 있다.

    한계. salt 값이 실제로 어떤 experiment framework에서 세팅되는지, σ 실 프로덕션 값이 얼마인지, 어느 지면(For You / Following / RankedFollowing)에 적용되는지, 결과 로깅이 어떤 side_effect로 흘러가는지는 오픈소스에 공개되지 않았다.

    의미. 지금까지 X의 grox multimodal 임베딩은 하나의 v5·하나의 v8.2 벡터 공간을 랭킹·retrieval·search 전반에 재사용했다(2026-09-01 4세대+13에서 관측). 이번 배선은 검색 지면 전용 벡터 공간을 처음으로 분리한 사건이다. 4세대+4(2026-08-19)에서 Phoenix가 xrecsys_search config로 검색 랭킹 지면에 확장된 것과 대응한다: 검색 랭킹 모델과 짝을 이루는 검색 문서 임베딩 파이프라인이 이제 완비된 것이다.

    한계. RECSYS_V8_SEARCH_EMBED·RECSYS_V8_SEARCH_BACKFILL_EMBED 두 endpoint의 실제 모델(dimension, base architecture, training data)은 오픈소스에 없다. 검색 지면에 어떻게 소비되는지(retrieval index 이름, ANN 파라미터)도 미공개. Kafka 토픽 grox-multimodal-embedding-v8-search는 등록됐지만 consumer 쪽 지면 코드는 함께 오지 않았다.

    C. Phoenix wire format에 ContentFeatures 진입 [확인]

    [확인] — phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto, phoenix/python/common/xai-proto/proto/recsys.proto, home-mixer/models/content_features.rs (185줄 신규).

    신규 proto message:

    message TweetInfo {
  // ...
  ScoreInfo scoreInfo = 35;
  ContentFeatures contentFeatures = 36;
  ContentFeatures quotedContentFeatures = 37;
}

message ContentFeatures {
  bool hasVideo = 1;
  uint32 maxVideoDurationMs = 2;
  bool hasPhoto = 3;
  uint32 mediaCount = 4;
  uint32 weightedTextLen = 5;
  uint32 newlineCount = 6;
  bool hasUrl = 7;
}

    7개 시그널의 의미. has_video·has_photo·media_count·max_video_duration_ms는 기존에도 개별 필드로 존재하던 미디어 시그널을 하나의 struct로 묶은 것이지만, 나머지 3개는 새롭게 노출되는 텍스트 특성이다:

    • weighted_text_len — 그냥 문자 길이가 아니라 Twitter 자체 텍스트 길이 계산 규칙을 그대로 따른다:
      • URL은 무조건 23자로 카운트(t.co shortener 정책과 동일).
      • CJK 문자, punctuation, 이모지 modifier(스킨톤 등)는 2자.
      • ASCII·기본 라틴은 1자.
      • ZWJ와 skin-tone modifier(0xFE0E·0xFE0F·0x1F3FB..0x1F3FF·0xE0020..0xE007F)는 0자(base 이모지에 흡수).
      • 미디어 첨부 URL은 external URL이 아니다 — 미디어 attachment가 있으면(attachment_urls=1) 첫 URL은 media URL로 취급하고 external URL count에서 제외한다.
    • newline_count — \n 개수. 게시글 형식(줄바꿈으로 목록 만드는 tweet, 시 형태 등)의 프록시.
    • has_url — external URL이 하나 이상 있는지.

    빌더 (home-mixer/models/content_features.rs). 4세대의 코드 스타일대로 순수 함수 2개(build·build_quoted)만 export한다. TextMetrics::of(text, attachment_urls)가 실제 계산을 담당하고, 회귀 테스트 5개로 Twitter의 text weighting rule을 코드화한다:

    assert_eq!(weighted(""), 0);
assert_eq!(weighted("hello world"), 11);
assert_eq!(weighted("日本語"), 6);  // CJK 3자 × 2
assert_eq!(weighted("see https://t.co/abc123 now"), 3 + 1 + 23 + 1 + 3);  // URL=23
assert_eq!(weighted("ok 👍🏽"), 2 + 1 + 2);  // 스킨톤 modifier는 0
assert_eq!(weighted("日本\u{3000}語"), 4 + 2 + 2);  // ideographic space도 CJK 취급

    의미. 이제까지 Phoenix 랭커가 소비하는 컨텐츠 시그널은 (a) 임베딩 테이블에 lookup되는 hashed feature (b) has_media·has_video·view_count 같은 산발적 boolean·정수였다. 4세대+17에서 텍스트 자체의 구조 시그널이 서빙 wire format의 first-class field로 승격됐다. 특히 weighted_text_len은 트윗 UI의 400자 상한과 직결되는 값이므로 "이 포스트가 얼마나 꽉 차 있나 / URL만 걸고 지나가는 pass-through인가" 를 랭커가 명시적으로 학습할 수 있게 된다.

    한계. 이 시그널이 랭킹 헤드에서 어떻게 소비되는지는 이번 커밋에 없다. phoenix/xrex/models/recsys_model.py에 content_features를 읽는 코드가 아직 없기 때문이다. 즉 wire는 실렸으나 학습 소비는 다음 커밋 관측 대상이다.

    D. PTOS adult-content leading-frames 심층 재스캔 경로 [확인]

    [확인] — grox/flows/ptos/plan_safety_ptos_adult_content_leading_frames.py (56줄 신규), grox/flows/ptos/task_safety_ptos_adult_content_leading_frames_filter.py (81줄 신규), grox/flows/ptos/constants.py (+15).

    진입 필터 (TaskSafetyPtosAdultContentLeadingFramesFilter._eligible_with_post). 6단 게이트를 모두 통과해야 재스캔 대상이 된다:

    1. post.user가 있어야 한다(anonymous·삭제된 유저 제외).
    2. post.get_fav_count() >= deluxe_fav_count_threshold — 4세대+12에서 도입된 deluxe 티어 임계(비용 관리). 인기 포스트만 진입.
    3. post.media 또는 post.quoted_post.media에 30초 이상 영상(ADULT_CONTENT_LEADING_FRAMES_MIN_DURATION_SECONDS = 30.0)이 있어야 한다.
    4. prior PTOS 판정이 존재해야 한다 — StratoSafetyPostAnnotationsResultDirectMh.fetch(post_id)이 non-null. 즉 이미 PTOS 파이프라인을 한 번 통과한 포스트를 대상으로 한다.
    5. prior 판정이 NSFW가 아니어야 한다 — prior.safetyBoolMetadata.isNsfw == True면 이미 처리됐으므로 스킵.
    6. 다음 두 조건 중 하나 — (a) prior 판정에 AdultContent 카테고리 violated policy가 있거나, (b) fav count가 512 이상(ADULT_CONTENT_LEADING_FRAMES_UNCONDITIONAL_FAV)이면 진입.

    크롭 적용. 통과한 영상에는 video.crop_seconds = 10.0(ADULT_CONTENT_LEADING_FRAMES_CROP_SECONDS)이 세팅돼 다운스트림 media hydration이 앞 10초만 잘라서 판정한다. 이후 category detection → policy detection → safemodel sex/nudity 판정 → cross-validation 8단 DAG를 다시 밟는다.

    의미. 이 경로가 왜 필요한가:

    • 30초 넘는 영상은 media hydration 비용(디코딩·프레임 추출·모델 호출)이 크므로 실시간 파이프라인은 미리 정해진 sample 프레임만 뽑아 판정한다. 그런데 회피 유저가 첫 15초 이상을 정상 콘텐츠로 채우고 후반에 성인 콘텐츠를 넣는 패턴을 취하면 실시간 판정이 놓칠 수 있다.
    • 4세대+12에서 도입된 PlanSafetyPtosSpecialVideo는 정적 오버레이(캡션·워터마크로 가려진 콘텐츠)를 다루고, 4세대+17의 이 경로는 **시간축 회피(첫 몇 초를 안전하게 위장)**를 다룬다. 이름은 leading-frames지만 실제로는 "앞 10초를 crop해서 재판정"이므로 성인 콘텐츠가 앞부분에 짧게 나타나는 케이스를 특히 겨냥한 것으로 보인다 [추정].
    • prior AdultContent violated policy가 있는데 isNsfw가 아닌 이유는 4세대+7의 3개 카테고리 cross-validator(ChildSafety·ViolentMedia·IllegalAndRegulatedBehaviors)에서 Grok 4.5 심판이 강등만 허용하기 때문에 primary가 AdultContent라 해도 NSFW 태그로 굳어지지 않을 수 있다. 이 경로는 강등된 판정을 다시 뒤집을 수 있는 두 번째 심판을 제공한다.

    진입 임계 512 fav의 함의. deluxe 임계(deluxe_fav_count_threshold)는 훨씬 높은 값일 가능성이 크므로(4세대+7의 log에서 deluxe = 5,000 이상 추정 [추정]), 512 fav 이상의 prior AdultContent 없는 케이스만 unconditional 진입은 prior 판정이 AdultContent를 잡지 못한 저강도 signal 케이스를 커버하려는 것이다. 512는 트위터 중간 인기 포스트에 해당하는 값이고, 이 규모의 오탐/누락은 유저 반응(신고, 뮤트)이 이미 발생했을 확률이 높다.

    한계. 실제 프로덕션에서 이 경로가 얼마나 활성화되는지, 재판정에서 실제로 뒤집는 비율(precision·recall)이 얼마인지, 어떤 심판 모델을 쓰는지(플랜 DAG를 보면 정규 category/policy/safemodel/cross-validation 모두 재실행)는 미공개. Rate limit(TaskRateLimitSafetyPtosAdultContentLeadingFrames)이 별도로 설정되어 비용 상한이 있다.

    • 오픈소스 사건. 4세대+15(2026-09-06 daily 참조)에서 FA4 forward의 varlen 지원 재작성이 공개됐지만, backward pass 원본은 이번이 처음이다. Backward는 학습을 위해 필수이므로 이전에는 X 내부 저장소에만 있고 오픈소스 미러에서는 forward만 공개된 형태였다. 이제 X 랭커의 학습·서빙 attention 커널이 완전히 오픈소스에 있다.
    • SM90 배선 확정. 4세대+15에서 SAVE_H100_RECSYS = 32 remat 정책이 신설됐을 때 "H100에서도 학습이 돈다는 첫 코드 신호"라고만 관측했다. 이번 커밋에서 SM90(H100)용 forward·backward 두 파일이 명시적으로 존재하므로 H100 학습은 이제 배선이 완결됐다. 4세대+6의 _GB300_OVERRIDES(GB300 = Grace Blackwell 300, SM100 세대)에 대한 SM90/H100 대체 경로가 명확해졌다: X는 GB300과 H100 두 세대 하드웨어에 각각 최적화된 attention 커널을 유지한다.
    • flash-attention 상류 재사용. X는 CuTeDSL을 처음부터 새로 쓰기보다 Dao-AILab 원본을 fork해 수정하는 전략을 택했다. 이는 attention 커널이 LLM 커뮤니티가 검증한 표준화된 인프라이며, X도 그 표준을 벗어나지 않았다는 신호다.

    한계. SM90/SM80 커널의 실제 벤치마크(GB/s·TFLOPS·baseline 대비 speedup)는 오픈소스에 없다. block_sparse_utils.py가 큰 폭으로 재작성됐지만 어떤 sparse pattern이 실제로 사용되는지는 모델 config에 명시되지 않았다.
