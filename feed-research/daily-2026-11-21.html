1Following 탭 광고 문턱이 포스트 묶음 2개로 낮아졌다 — X

자료 xai-org/x-algorithm@ed78e06 — xAI, 2026-11-20, 코드. 이 노트들이 붙인 번호로는 4세대+68이다(4세대+N은 2026-08-13 4세대 공개 뒤의 커밋에 이 노트들이 차례로 붙인 번호다).

배경 X의 Following 탭은 팔로우한 계정의 포스트를 시간 역순으로 보여 주는 피드이고, For You와 별도 광고 블렌더(유기 포스트 사이에 광고 자리를 정하는 코드)를 쓴다. 이 블렌더는 화면에 놓을 포스트가 너무 적으면 광고를 하나도 넣지 않는다. home-mixer(For You와 Following 요청을 조립하는 서비스)의 param.rs는 내부 기능 스위치 기본값을 매일 옮겨 적는 미러다. 이번 커밋은 그 문턱을 낮추고, 기본 off인 랭킹·캐러셀 경로 몇 개를 새로 넣었다.

새로 알게 된 것A. Following 탭은 포스트 묶음이 2개만 있어도 광고를 넣는다

  • Following 탭 광고 블렌더의 최소 포스트 묶음 수가 5에서 2로 바뀌었고, 이 값은 기본값이라 바로 적용된다 확인 — params/param.rs:1080-1085
    • param은 AdsFollowingMinPosts(rust_home_mixer_ads_following_min_posts)이고, 미러 동기화 시각은 2026-11-19T16:00:34Z다.
    • Following 블렌더 선택기가 이 값을 블렌더의 min_posts로 넘긴다(selectors/following_blender_selector.rs:41).
  • 묶음 수가 문턱보다 적으면 광고를 모두 빼고 "포스트가 너무 적음" 사유로 기록한다 확인 — ads/following_ad_blender.rs:142-151
    • 연달아 놓인 포스트가 조상 포스트를 공유하면 같은 대화로 보고 한 묶음으로 센다(같은 파일 72-92행).
    • 사유 코드는 AdDropReason::TooFewPosts다. 광고 간격 계산은 그대로라 묶음 2개짜리 화면에 광고가 몇 개 들어가는지는 간격에 달렸다.

새로 알게 된 것B. Phoenix 랭커가 VMRanker 호출까지 맡는 경로가 생겼다

  • 스위치를 켜면 home-mixer는 Phoenix 예측 요청에 VMRanker 호출 정보를 함께 싣는다 확인 — scorers/phoenix_scorer.rs:120-123, 195-203
    • VMRanker는 Phoenix(Grok 기반 트랜스포머 랭커)의 행동별 확률을 가중합하고 DPP(서로 비슷한 후보가 함께 뽑히지 않게 하는 확률 모델) 슬레이트 재정렬을 하는 서비스다.
    • 실리는 값은 VMRanker 호스트 이름, eta, prior_tau 세 개다. 앞의 것은 VMRankerClusterId에서, 뒤의 둘은 PageDecodeEta(기본 0.0)와 PageDecodePriorTau(기본 0.2)에서 온다.
  • Phoenix 응답에 VMRanker 응답이 들어 있으면 home-mixer의 VMRanker 스코어러는 VMRanker를 따로 부르지 않고 그 응답을 쓴다 확인 — scorers/vm_ranker.rs:171-176
    • 응답이 없거나 오류이거나 디코딩에 실패하면 기존처럼 직접 호출한다. 결과는 VMRanker.ranker_vm_rank 메트릭에 sent·received·used·missing·error로 센다.
  • 스위치 EnableRankerVmRank는 기본 off다 확인 — params/param.rs:345-357
  • Phoenix 서버가 이 요청을 받아 VMRanker를 부르는 코드는 같은 커밋에 없다 확인 — 커밋의 변경 파일 목록에는 proto 정의만 있다.
    • proto에 VmRankSpec(요청)과 VmRankResult(직렬화된 VMRanker 응답과 오류 문자열)가 추가됐다.
    • 디코더 이름이 붙은 두 파라미터를 함께 보내므로, VMRanker 결과를 페이지 디코더의 사전 분포로 쓰려는 준비로 본다 추정. 근거는 prior_tau라는 이름과 Phoenix 쪽에서 호출한다는 점뿐이다.

새로 알게 된 것C. Phoenix MoE retrieval을 영상 캐러셀 전용으로 켤 수 있게 됐다

  • 새 스위치가 켜지고 캐러셀이 켜진 요청에서는 Phoenix MoE retrieval 소스가 메인 피드용 스위치가 꺼져 있어도 돈다 확인 — sources/phoenix_moe_source.rs:28-35
    • Phoenix MoE retrieval은 For You 후보 소스 가운데 하나이고, 메인 피드용 스위치 EnablePhoenixMOESource는 기본 off다.
    • 새 스위치는 EnableVideoCarouselMoeSource(기본 false)다(params/param.rs:1520-1525). 캐러셀 자체(EnableVideoCarousel)도 기본 off다.
  • 이 모드에서 MoE에서만 나온 후보는 메인 피드 상위 선택에서 빠지고, 점수를 지운 채 캐러셀 후보 풀로만 간다 확인 — selectors/top_k_score_selector.rs:15-29
    • 다른 소스에서도 나온 후보는 그대로 메인 피드 경쟁에 남는다(util/video_carousel.rs:26-38).
    • 테스트는 점수 1000인 MoE 후보가 상위 선택에 들지 않고, 메인 피드용 스위치를 켜면 1위가 되는 것을 확인한다(같은 선택기 파일 196-225행).

새로 알게 된 것D. 곱셈형 모드에서 영상 시청 시간은 시간 배수로 옮겨졌다

  • 기본 off인 곱셈형 결합 모드(건너뛰지 않을 정도 × 참여 가치 × 체류 시간 배수로 점수를 내는 방식)에서, 영상 열람 후 시청 시간 두 항이 참여 항에서 빠져 체류 시간 배수에 더해진다 확인 — xai-value-model/scoring.rs:89-114
    • 두 항은 video_continuation과 user_video_continuation이고, 합이 음수면 0으로 자른다.
    • 테스트 기대값은 시간 배수 3.0이 3.015로 바뀐 형태다(가중 0.003 × 열람 확률 0.5 × 10초).
  • 페이지 디코더(랭커 상위 후보로 한 페이지를 슬롯 순서대로 고르는 RL 재순위 모델) 학습 보상에서도 VQV(영상 품질 시청) 항이 같은 방식으로 옮겨졌다 확인 — phoenix/xrex/models/page_rl.py
    • 가산형 모드의 합은 전과 같고, 곱셈형 모드에서만 time = 1 + max(dwell, 0) + max(vqv, 0)이 된다.

새로 알게 된 것그 밖의 변경

  • 유저가 For You 트레이스 표시를 켜고 끄는 Under the Hood(유저가 자기 계정과 피드에 대한 정보를 보는 투명성 화면) 설정 화면이 생겼다 확인 — timeline_trace.tsx
    • 안내 문구는 For You를 새로 고치면 후보를 찾고 거르고 순위를 매긴 코드의 트레이스가 보이고, 단계마다 공개 코드로 연결된다고 쓴다. 화면은 별도 스위치가 켜진 유저에게만 열린다.
  • Phoenix 섀도 트래픽(실서비스 응답에 쓰지 않고 실험 클러스터에 같은 요청을 복제하는 것) 비율에서 Experiment19Fou가 0.3에서 0으로 바뀌었다 확인 — params/param.rs:91-108
  • 어제 켜진 teacher 점수 저장이 두 데이터센터 대신 한 곳의 캐시에만 쓴다 확인 — teacher_score_side_effect.rs:158-169
  • 기능 스위치 타기팅 속성에 뷰어의 팔로워 수가 추가됐다 확인 — models/fs_recipient.rs
  • 광고 구매 가치 기준값에 앱 전환 이벤트 다섯 종(구매, 장바구니, 레벨 달성, 튜토리얼 완료, 가입)이 추가됐다 확인 — purchase_value.rs
    • 같은 커밋에서 Phoenix 모델에 광고 CTR 버킷 임베딩 옵션(기본 차원 0)과 광고 proto의 뷰어별 광고 참여 집계 필드가 생겼다.
  • 후보 파이프라인의 하이드레이터를 별도 작업으로 병렬 실행하는 경로, Grox의 이미 주석된 포스트 건너뛰기, abuse-enforcement-service 정리처럼 정책 변화가 없는 변경이 함께 들어갔다 확인 — 커밋 diff

정본 반영 services/x.md ## 한 줄 요약의 기준 커밋을 ed78e06으로 올렸다. ## 광고 2026-11-05 단락 끝에 Following 탭 최소 포스트 묶음 문장을 추가하고, 그 절의 변경 이력 목록에 한 줄을 더했다. Phoenix 절에는 VMRanker 직접 호출 불릿과 곱셈형 시청 시간 하위 불릿을, 피드 지면 절 캐러셀 항목에는 MoE 소스 하위 불릿을, Under the Hood 절에는 트레이스 설정 하위 불릿을 추가했다. ## 출처 기준 sha 표와 변경 이력 요약표에 한 행씩 추가했다.

의미 이번 커밋에서 기본값으로 실제 동작이 바뀐 것은 Following 탭 광고 문턱 하나다. 팔로우가 적거나 새 포스트가 적은 유저의 Following 화면에도 광고가 붙을 수 있다. VMRanker 호출을 Phoenix 쪽으로 옮기는 경로는 home-mixer와 VMRanker 사이의 왕복 하나를 줄이는 구조 변경이지만, 서버 코드가 없으므로 지연 절감이 목적이라는 판단은 추정으로 둔다.

2광고 랭킹 모델 피처를 LLM 에이전트가 고른다 — Meta

자료 Cost-Aware Agentic Feature Optimization System for Fleet-Scale Ranking Models — Meta, 2026-11-19 v1, 논문.

배경 큰 플랫폼은 랭킹 모델 수십·수백 개를 함께 운영하고, 모델마다 공유 피처 풀 수만 개 가운데 무엇을 쓸지 골라야 한다. 피처를 더하면 정확도는 오르지만 피처 파이프라인 비용과 서빙 처리량(QPS)이 한도를 넘을 수 있다. 이번 논문은 이 선택을 LLM 에이전트와 결정적 실험 도구의 조합으로 자동화한 시스템을 보고한다.

새로 알게 된 것A. 피처 선택을 에이전트에게 맡겨 배포까지 했다

  • 저자 9명 전원이 Meta 소속이고, 대상은 광고 랭킹 모델 무리다 확인 — HTML 판
    • 본문은 시스템을 "Agentic ML Exploration (A-MLE) for Ads Ranking"이라고 부른다.
  • LLM이 교차 피처 후보를 만들고, 여러 중요도 지표 순위를 섞은 뒤, Researcher 에이전트가 비용 한도 안에서 10~25회 비동기 시도로 선택을 조정한다 확인 — arXiv 초록
    • 멀티태스크 모델은 과제별 순위를 Pareto front(어느 한 과제를 나쁘게 하지 않고는 더 좋아질 수 없는 선택들의 집합)로 섞는다.
  • 프로덕션 모델들에서 NE(normalized entropy, 낮을수록 좋은 로그 손실 지표) 평균 0.31% 개선, 배포 뒤 온라인 A/B 주요 지표 +0.20%를 보고한다 확인 — 같은 초록
    • 마지막 정리 단계가 피처 파이프라인 비용을 2.3% 줄였고, 측정 잡음을 넘는 회귀는 없었다고 쓴다.

"The optimized models were launched, and in online A/B tests they improved a primary online metric by 0.20%." — Cost-Aware Agentic Feature Optimization System for Fleet-Scale Ranking Models (논문), 2026-11-19

정본 반영 유기 피드가 아니라 광고 랭킹이라 정본에는 넣지 않고 radar.md "이번 달 신규"에 항목을 추가했다.

의미 Meta가 광고 랭킹 개발 과정 자체에 에이전트를 넣고 있다는 근거가 한 주에 두 건 쌓였다. 2026-11-18 Meta Engineering의 광고 랭킹 AI 에이전트 글과 같은 흐름으로 보지만, 논문이 그 글을 인용하는지는 확인하지 않았으므로 추정으로 둔다.

3CTR 모델 깊이를 키우는 병목을 행동 시퀀스 쪽에서 풀었다 — Alibaba

자료 DNA: Unlocking Depth Scaling in CTR Models — Taobao 검색, 2026-11-19 v1, 논문.

배경 긴 유저 행동 시퀀스는 CTR(클릭률) 예측의 가장 강한 신호이고, 산업 랭커는 cross-attention(요청 표현이 행동 시퀀스를 읽는 attention)으로 이 시퀀스를 선형 비용에 처리한다. 그런데 이 층을 더 쌓아도 성능이 거의 오르지 않는다. 이번 논문은 원인을 "매 층이 같은 시퀀스를 다시 읽는다"는 데서 찾고, 시퀀스도 층마다 갱신되게 하는 구조를 제안한다.

새로 알게 된 것A. 시퀀스를 층마다 갱신하면 깊이가 다시 효과를 낸다

  • Taobao 검색에서 cross-attention 스택을 16층에서 28층으로 늘려도 AUC는 0.02pt만 오른다 확인 — arXiv 초록
  • DNA는 층마다 요청 표현이 시퀀스를 읽은 뒤, 각 행동 토큰이 갱신된 요청 표현을 읽어 자신을 고친다 확인 — 같은 초록
    • 갱신은 요청당 한 번이고 모든 후보가 결과를 공유해, 계산량은 시퀀스 길이에 선형으로 남는다.
  • 같은 연산량에서 AUC가 0.08~0.26pt 높고, DNA-4를 Taobao 검색에 배포해 A/B에서 CTR +0.8%, GMV +0.5%를 얻었다고 쓴다 확인 — 같은 초록

정본 반영 추적 서비스 자료가 아니어서 radar.md "추천 모델 스케일링 법칙" 스레드에 추가 근거로 붙였다.

의미 깊이 축의 스케일링 병목이 모델 쪽이 아니라 key-value 쪽 입력에 있다는 주장이 하나 더해졌다. 지면이 검색이라 피드 랭킹에도 같은 결과가 나오는지는 열려 있다.
