      1. Phoenix가 산출한 slate context를 home-mixer가 소비하기 시작 — X (4세대+5, d0cef2f) — For You

      자료 xai-org/x-algorithm @ d0cef2f — "Open-source X Recommendation Algorithm" — 2026-08-20 20:22 UTC, 공개 소스코드. 파일 14개, +479/−200. 4세대+4(2026-08-19, aad7179, 파일 79 +3.3k/−0.7k)에 비하면 1/7 정도 규모지만, 4세대+4에서 proto와 config로 준비만 해 둔 두 스캐폴딩이 처음으로 실제 파이프라인 배선까지 이어진 커밋이다.

      배경 4세대 이후 X 저장소에는 매일 커밋하는 리듬으로 후속 공개가 이어져 왔다: 8/14 4세대+1(c65aa17) → 8/17 4세대+2(b089ce6) → 8/18 4세대+3(11a71f8) → 8/19 4세대+4(aad7179, 대형). 그 다음으로 8/20에 나온 이번 커밋은 4세대+4의 대형 확장 뒤에 이어진 만큼 규모는 작지만, 4세대+4가 준비한 두 스캐폴딩(Phoenix proto의 SlateContext.sid* 필드 신설, RewardOutputs 신설, xrecsys_search config)이 실제 서빙·랭킹 파이프라인 배선으로 넘어가는 시점이라는 점이 이 커밋의 성격이다. 4세대부터 4세대+4까지의 canon 반영은 "proto와 config가 준비됐다"까지였는데, 지금은 SlateContext가 Phoenix 예측 응답을 통해 home-mixer로 실제 흘러들어가는 배선이 처음으로 코드에서 확인된다.

      이 커밋에서 새로 등장하는 개념은 다음과 같다.

      • AI trend — X의 "Trending" 지면(사람들이 많이 이야기하는 이벤트)에 올라오는 항목이다. 이 커밋 이전에는 tweet에 "AI trend" 라벨을 붙이는 로직이 home-mixer 파이프라인에 없었다. Grok이 트윗을 관찰해 어떤 AI trend에 속하는지 판정하고 그 결과를 Strato에 저장해 두는 upstream 파이프라인이 있었으리라고 보이지만(batch_get_tweet_ai_trend API), 그 파이프라인은 이 저장소 밖에 있다 [추정].
      • served slate context — Phoenix 서빙 응답이 후보마다 재순위에 쓸 재료(pool 랭크, fatigue, pre-diversity score, SID 3계층, SID gap 3계층)를 담아 돌려주는 스키마 필드다. 4세대+4의 proto에는 정의만 되어 있었고, 이 커밋에서 소비 경로가 배선됐다.
      • SlateContext — DPP 재순위 슬레이트에서 각 슬롯이 갖는 컨텍스트 벡터다. k는 슬롯 인덱스, pool_rank는 원 스코어 정렬 순위, pool_rank_gap은 위 슬롯과의 pool rank 차이이고, 여기에 fatigue, pre_diversity_score, sid_known이 더해지며, sid_k_l1/l2/l3은 3계층 SID 각각의 슬롯 인덱스를, sid_gap_l1/l2/l3은 각 계층 SID의 슬롯 간 gap을 담는다. 4세대+3 VMRanker에서 SID 필드 7개가 배선됐을 때와 같은 필드 세트다.

      Top-2 trend 선택 + trend당 후보 1개 랜덤 [확인] — ai_trend_feedback_context_hydrator.rs:24-52:

      const TOP_TREND_COUNT: usize = 2;

fn select_feedback_targets(candidate_trends: &[(usize, i64)]) -> HashMap<usize, i64> {
    let mut frequency: HashMap<i64, usize> = HashMap::new();
    for (_, trend_id) in candidate_trends {
        *frequency.entry(*trend_id).or_default() += 1;
    }
    let mut ranked: Vec<(i64, usize)> = frequency.into_iter().collect();
    ranked.sort_by(|a, b| b.1.cmp(&a.1).then_with(|| a.0.cmp(&b.0)));
    ranked.truncate(TOP_TREND_COUNT);

    let mut rng = rand::rng();
    let mut selected: HashMap<usize, i64> = HashMap::new();
    let mut used_indices = std::collections::HashSet::new();
    for (trend_id, _) in ranked {
        let candidates_for_trend: Vec<usize> = candidate_trends
            .iter()
            .filter(|(idx, id)| !used_indices.contains(idx) && *id == trend_id)
            .map(|(idx, _)| *idx)
            .collect();
        let Some(&idx) = candidates_for_trend.choose(&mut rng) else { continue };
        used_indices.insert(idx);
        selected.insert(idx, trend_id);
    }
    selected
}

      절차는 다음과 같다. (1) 조건을 만족하는 후보마다 Strato batch_get_tweet_ai_trend로 trend_id를 조회한다 → (2) 후보들의 trend_id 빈도 히스토그램을 만든다 → (3) 상위 2개 trend를 고른다(동률이면 trend_id가 작은 쪽이 우선이다) → (4) 각 trend에 대해 후보 1개를 무작위로 선택한다 → (5) Strato batch_get_ai_trend_name로 그 trend의 표시 이름을 조회한다. 결국 한 페이지에 최대 2개의 AI trend 라벨이 붙고, 각 trend마다 후보 하나에만 붙는다. 같은 trend에 속한 여러 후보에 같은 라벨을 반복해서 붙이지 않도록 막는 억제 장치다.

      폴백은 세 갈래다. (1) UseServedSlateContext 게이트가 켜져 있고 Phoenix가 모든 후보에 대해 slate context를 보내왔으면 그 값을 그대로 사용한다. (2) 게이트가 꺼졌거나 데이터가 모자라면서 Redis 워밍 캐시가 히트하면, 이전 요청에 저장해 둔 slate context를 재사용한다. (3) 그 밖의 경우에는 로컬에서 compute_slate_contexts(candidates, weighted_scores)로 계산한다. 이 순서는 두 랭킹 브랜치에 동일하게 적용된다.

      의미 slate context를 계산하는 지점이 home-mixer 로컬에서 Phoenix 서빙으로 옮겨 가는 마이그레이션의 첫 단계다. Phoenix는 예측을 만드는 그 순간에 이미 각 후보의 pool 랭크와 fatigue, pre-diversity, SID 3계층 정보를 알고 있으므로, home-mixer가 다시 계산하는 대신 서빙 응답에 실어 보내면 (a) 랭커의 CPU를 절약할 수 있고, (b) Phoenix가 가진 더 풍부한 컨텍스트(예를 들어 SID 3계층은 Phoenix 없이는 계산할 수 없다)를 랭킹 재순위에 반영할 수 있으며, (c) home-mixer가 후보 배분과 재순위만 담당하는 얇은 층으로 계속 축소되는 방향이다. 4세대+3에서 SID가 VMRanker에 배선된 것과 방향이 같다. SID는 정의상 Phoenix 학습 산출물이라 home-mixer가 로컬에서 계산할 수 없는데, 이 커밋으로 그 문제가 서빙 시점에 해결됐다.

      UseServedSlateContext는 기본값 false로 배선됐다. 게이트만 만들어 두고 실제 롤아웃은 후속 파라미터 변경으로 미뤄 둔 상태다. 관전 포인트: 이 게이트가 true로 승격되는 커밋이 나오는 시점이 곧, Phoenix 서빙의 slate context 산출이 프로덕션 트래픽에 반영되는 시점이다.

      2. Xiaohongshu OneModel — 유기·광고·상점 3개 지면 통합 랭커, 프로덕션 A/B [레이더 승격]

      자료 OneModel: A Unified Foundation for Platform-Scale Multi-Scenario Ranking (arXiv 2608.18606) — 2026-08-19 arXiv 제출 (v2, v1은 초기 제출), 논문. 저자는 14명이고(Yinqi Zhang, Peiyu Hu, Yuntian Tang, Siying Gu, Jiahao Liang, Longxin Kou, Haiqing Hu, Shuman Zhuang 등), 초록에 명시된 배포 서비스는 Xiaohongshu(小红书, 중국 라이프스타일 소셜 플랫폼)이다.

      배경 Xiaohongshu는 canon이 아직 추적하지 않는 서비스지만, 여러 비즈니스 스트림(유기 추천, 광고, 상점 상품)을 하나의 앱에서 통합해 서빙한다는 점이 X와 Meta, Netflix의 서비스별 파편 랭커와 비교하면 이례적이다. 이 논문은 세 개 지면을 하나의 랭커로 통합했다는 프로덕션 배포 진술이고, 다음 세 갈래의 프로덕션 진술군에 새로운 각도를 더한다. (a) Netflix Foundation Model은 단일 FM 위에 서비스별 head를 두었고, (b) Meta GEM은 광고 domain 안에서 IG와 FB를 통합하는 backbone을 만들었으며, (c) Yandex Music Gryphon-v2/Sona는 retrieval과 ranking을 통합했다. OneModel은 그 중 하나의 backbone이 서로 다른 비즈니스 스트림(유기·광고·상점)을 동시에 서빙하는 각도로 넘어간다.

      핵심 주장 (arxiv abstract):

      "Platform-scale recommender systems often span multiple business streams such as organic recommendation, advertising, and merchant services, where user behaviors form a continuous cross-stream trajectory. Maintaining separate ranking systems fragments user representations and increases engineering cost. We propose OneModel, a unified framework for multi-stream final ranking. OneModel maps heterogeneous behaviors into shared event sequences, learns long-context user representations with an action-oriented backbone, and introduces Scenario-aware Information Modulation to balance cross-stream transfer and stream-specific specialization."

      — OneModel (arXiv 2608.18606) abstract (논문)

      핵심 아키텍처 요소:

      • 공유 이벤트 시퀀스 — 유기·광고·상점 세 스트림의 사용자 행동을 하나의 이벤트 시퀀스 스키마로 통합한다
      • action-oriented backbone — long-context user representation을 학습하는 부분이다 (구체적인 아키텍처는 abstract에 나오지 않는다)
      • Scenario-aware Information Modulation — cross-stream transfer(공유)와 stream-specific specialization(전용) 사이의 균형을 스위칭과 게이팅으로 조절한다

      프로덕션 배포를 위한 최적화 요소로는 stratified user representation, multi-objective training, feature decomposition, user feature prefetching, shared user-tower computation, graph-level inference optimization을 든다.
